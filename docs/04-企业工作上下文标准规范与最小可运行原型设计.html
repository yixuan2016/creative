摘要：从架构设计进入工程验证

前三份专题分别回答了工作信息从哪里来、企业需要理解哪些工作上下文、以及如何通过统一数据模型和运行认知引擎实现。本专题进一步定义数据契约、事件目录、接口、状态重建、授权协议和本地原型。

第一阶段最小闭环：权威业务系统事件 + 经授权的协同线索 → 标准事件 → 业务对象关联 → 状态重建 → 任务级上下文包 → Agent 只读辅助 → 人工确认与反馈。

1. 目标、范围与非目标

1.1 工程目标

  • 事件、对象、状态和证据使用明确、可版本化的机器可读契约。
  • 源系统通过适配器映射到统一事件信封，不要求改变源系统模型。
  • 关键状态可解释其权威来源、支持事件、有效时间和不确定性。
  • Agent 通过任务级上下文包获取最小必要信息。
  • 原型可重复运行、自动测试和审计。
  • 试点量化准确性、时效、人工核验成本、业务收益和治理风险。

1.2 第一阶段范围

对象用途权威来源示例
Project项目主对象项目管理系统
Task项目任务项目管理系统
Decision项目决策决策记录或审批系统
Risk项目风险风险台账或责任人确认
Evidence证据引用原始系统、文档或会议记录
ActorRef人员、角色、系统或 Agent组织身份系统或连接器身份

首批事件：project.state_changed、task.created、task.updated、task.completed、decision.proposed、decision.approved、risk.identified、evidence.attached。首轮只实现只读查询和上下文生成。

1.3 非目标

  • 不替代项目管理系统、ERP、CRM、OA 或文档系统。
  • 不建设全企业主数据平台，不一次覆盖所有业务领域。
  • 不把模型置信度当作业务确认，不自动消除高影响冲突。
  • 不默认采集员工音频、屏幕、私人通信或无关信息。
  • 不将个人工作记忆自动转化为企业资产。
  • 不把演示数据当作真实企业运行结论。

2. 工程标准与通用约定

原则工程要求
语义统一字段、事件类型和状态枚举有稳定定义
源系统自治保留源系统 ID、原始状态和记录版本
可追溯事件和状态均可定位来源
时间明确区分发生、观察、记录和业务有效时间
不确定性显式confirmed、observed、inferred、disputed、stale、unknown 分开表达
版本可控Schema、本体、策略和 API 版本化
最小权限按主体、用途、对象、字段、动作和时间校验授权
可纠错通过更正事件和替代关系纠错，不静默覆盖
可重放状态投影可以由事件和规则重建

2.1 命名与时间

  • JSON 字段使用 snake_case；枚举使用小写英文。
  • 事件类型使用稳定领域命名；本专题示例为 task.updated。
  • 时间使用带时区的 RFC 3339 / ISO 8601，内部建议统一 UTC。
  • 金额和数量必须记录 currency 或 unit。
  • 扩展字段放入 extensions，不随意增加顶层字段。
时间字段语义
occurred_at业务事件实际发生时间
observed_at连接器或来源观察到事件的时间
recorded_at统一事件账本接收并记录的时间
valid_from / valid_to状态或关系在业务世界中的有效区间
evaluated_at认知引擎计算当前视图的时间

不得用 recorded_at 代替 occurred_at。源系统没有发生时间时，应记录推定规则和时间质量。

3. 首批数据契约

完整机器可读定义见 JSON Schema 文件，采用 JSON Schema Draft 2020-12。

3.1 ObjectRef：业务对象引用

{
  "object_id": "obj_project_014",
  "object_type": "project",
  "tenant_id": "tenant_demo",
  "source_system": "project-system",
  "source_object_id": "PRJ-2026-014",
  "resolution_status": "confirmed"
}

object_id 是上下文层稳定标识；source_object_id 是源系统主键。候选匹配不得直接成为确定性业务关系。

3.2 WorkEvent：工作事件

{
  "event_id": "evt_project_014_002",
  "tenant_id": "tenant_demo",
  "event_type": "project.state_changed",
  "event_schema_version": "0.1",
  "occurred_at": "2026-11-18T09:30:00+08:00",
  "observed_at": "2026-11-18T09:30:04+08:00",
  "recorded_at": "2026-11-18T09:30:05+08:00",
  "object_refs": ["obj_project_014"],
  "payload": {
    "property": "project.status",
    "old_value": "in_progress",
    "new_value": "blocked"
  },
  "source_ref": {
    "source_system": "project-system",
    "native_record_id": "PRJ-2026-014",
    "record_version": "42"
  },
  "assertion_status": "observed",
  "classification": "internal",
  "purpose_tags": ["project_delivery_context"],
  "ontology_version": "ads-common-0.1/domain-project-0.1",
  "lifecycle_status": "active"
}

3.3 ContextPackage：任务级上下文包

上下文包包含 task_id、requester_ref、purpose、scope、included_refs、unresolved_items、allowed_actions、authorization_refs、policy_version、ontology_version、created_at、expires_at 和 lifecycle_status。生成后不应静默改变内容；更新时生成新版本或新 context_id。

3.4 其他核心实体

StateAssertion 表达对象属性的时间化状态；Relation 表达带类型和来源的业务关系；EvidenceRef 指向支持事实的证据位置；AuthorizationGrant 定义主体、目的、范围、分类、动作和有效期。

4. 事件类型目录与映射规范

事件类型触发时机关键 payload默认可信来源
project.state_changed项目状态变化property、old_value、new_value、reason项目管理系统
task.created新任务创建title、assignee、due_at、parent_project项目管理系统
task.updated任务字段变化changed_fields、old_values、new_values项目管理系统
task.completed任务完成completed_at、acceptance_status、evidence_refs项目系统或验收记录
decision.proposed提出决策建议statement、alternatives、rationale_refs经授权会议或文档
decision.approved正式决策获批decision_ref、approver_ref、effective_at审批系统或授权确认
risk.identified发现风险线索description、impact、likelihood风险台账或候选线索
evidence.attached证据关联对象evidence_ref、target_refs、verification_status原始系统或人工核验
权威来源不是全局固定排名。应按 object_type + property + domain_id 配置。例如 project.status 以项目管理系统为准，会议纪要只能提供线索。

连接器需登记源事件类型、字段映射、时间和时区规则、状态映射、对象 ID 解析、数据分类、purpose_tags、Schema 版本、映射版本和责任人。幂等键建议由 tenant_id、source_system、native_record_id、record_version 和 event_type 组成。

5. 状态重建规则

5.1 建议算法

  1. 识别 object_id 和 property。
  2. 查询该对象属性的权威来源配置。
  3. 过滤未授权、撤回、替代或无效事件。
  4. 按业务有效时间和源系统版本识别顺序。
  5. 存在有效权威来源记录时，以权威记录形成当前值。
  6. 其他来源的不同值保留为 conflict，不覆盖权威值。
  7. 没有权威记录时输出 observed / inferred / unknown，不伪造确定状态。
  8. 检查新鲜度，过期值标记 stale。
  9. 输出 supporting_refs、conflicts、unknowns、authority_source、evaluated_at 和 rule_version。

5.2 冲突输出示例

{
  "object_id": "obj_project_014",
  "property": "project.status",
  "value": "blocked",
  "assertion_status": "confirmed",
  "authority_source": "project-system",
  "supporting_refs": ["evt_project_014_002"],
  "conflicts": [{
    "source_system": "meeting-notes",
    "value": "on_track",
    "assertion_status": "inferred",
    "event_id": "evt_project_014_003"
  }],
  "unknowns": ["客户验收日期尚未确认"],
  "rule_version": "project-state-rules-0.1"
}

业务状态与认知状态分离：权威系统记录的 in_progress 与引擎推断的 at_risk 可以并存，必须呈现各自语义、来源和可信级别。

6. 授权与上下文包生成协议

6.1 授权校验维度

每次生成都校验 subject、on_behalf_of、purpose、tenant_id、object_scope、classification_scope、allowed_actions、valid_from / expires_at 和 policy_version。访问每个对象和字段时仍需校验用途与数据范围。

6.2 上下文生成流程

接收 requester · purpose · task · object_scope
↓
主体身份与有效授权检查
↓
对象 / 字段 / 分类 / 时间范围校验
↓
检索授权事件 · 重建状态 · 识别冲突和未知
↓
最小必要裁剪 · 证据引用 · 来源与可信标注
↓
Context Package · TTL · 审计记录

6.3 失效条件

  • 授权到期或撤回；
  • 数据责任方撤回共享；
  • 关键证据失效；
  • 策略版本变化且要求重算；
  • 超过上下文包 TTL；
  • 源数据更正或删除影响任务结论。

6.4 Agent 动作边界

第一阶段允许 summarize、identify_missing_information、draft_follow_up 和 propose_task_update（只提出建议）。更新项目状态、重新分配任务、批准决策、发送客户承诺和修改合同订单必须经过独立审批和授权执行服务。

7.1 通用约定

  • HTTPS；生产采用组织批准的 OAuth2/OIDC 或等效身份体系。
  • 写请求使用 Idempotency-Key。
  • 响应返回 trace_id、schema_version 和 policy_version。
  • 错误包含 code、message、trace_id 和安全可暴露的 details。
  • 生产环境补充速率限制、超时、重试、熔断和审计。

8. 最小可运行原型设计

8.1 原型验证内容

  1. 接收并校验标准事件；
  2. 使用幂等键避免重复事件；
  3. 根据权威来源规则重建状态；
  4. 保留非权威来源冲突线索；
  5. 根据授权范围生成任务级上下文包。

8.2 组件与生产替换方向

组件本地原型生产方向
Event IngestPython 函数API Gateway + Connector
Event Ledger内存字典 / JSON追加式事件存储
Object RegistryJSON 映射身份解析服务
Authority Registry本地配置领域规则目录
State Engine确定性规则可重放状态投影
Policy Gate简化 grantIAM / ABAC / Policy Engine
Context BuilderJSON 上下文包上下文服务
Audit本地记录集中审计

8.3 本地运行

要求 Python 3.10 或以上版本，不依赖第三方 Python 包。

cd prototype
python ads_context_engine.py
python -m unittest -v

8.4 原型限制

原型不连接真实企业系统，不执行真实写回。它不是生产安全边界；生产环境还需补充身份认证、字段级权限、密钥管理、持久化、并发控制、分布式幂等、加密、备份、监控和渗透测试。

9. 项目交付模拟场景

虚构项目 PRJ-2026-014 在项目系统中的状态为 blocked，原因是前置依赖未完成。会议纪要出现“整体仍可按计划推进”的观点，但未经项目负责人确认。Agent 被要求准备状态评审材料。
  • 权威状态：blocked；
  • 状态来源：project-system；
  • 冲突线索：meeting-notes 提供 on_track；
  • 未知项：客户验收日期尚未确认；
  • 允许动作：summarize、draft_follow_up；
  • 禁止直接执行：update_project_status、send_customer_commitment。

9.1 端到端流程

  1. 项目系统产生状态变化事件；
  2. 经授权会议记录提供推断线索；
  3. 连接器标准化并关联 Project；
  4. 事件账本按幂等键保存；
  5. 状态引擎按权威来源规则计算；
  6. 非权威不同值保留为冲突；
  7. 授权服务校验主体、目的和项目范围；
  8. 生成短时上下文包；
  9. Agent 生成摘要和跟进草稿；
  10. 项目负责人确认后，才进入正式业务更新流程。

13.1 评审前必须明确

  1. 项目系统中哪些字段是正式权威字段？
  2. 哪类会议或协同信息允许进入企业上下文？
  3. 会议推断如何由项目负责人确认或否认？
  4. 员工、客户和第三方信息如何分类、裁剪和授权？
  5. 上下文包过期、撤回和源记录删除如何联动？
  6. Agent 摘要、建议和正式业务动作如何分权？
  7. 试点业务价值由谁确认，基线如何采集？

14. 与 ADS 三级数智底座的关系

层级本专题涉及的责任
个人数智底座保留个人原始工作信息和个人控制权；只按明确授权共享必要记录或引用

本专题成果归属企业数智底座内部能力，不形成新的底座层级。个人工作信息进入企业上下文必须经过授权、目的限定、必要性审查和业务责任人确认。

15. 结论：用一个真实流程证明上下文基础设施的价值

工作感知 → 统一事件 → 业务对象映射 → 状态重建 → 证据与冲突 → 任务级上下文包 → Agent 辅助 → 人工确认 → 反馈改进。

第一阶段只选一个项目交付流程，只接入一个权威业务系统和少量经授权来源，只实现五类核心对象和八类事件；先只读、后建议、再审批写回；先本地原型、后企业试点；先验证准确性和治理，再讨论规模化。

真正需要验证的不是 AI 能否总结更多信息，而是企业能否通过统一上下文让 Agent 在正确权限下更准确地理解正在发生什么，并实实在在降低业务协作与管理成本。
