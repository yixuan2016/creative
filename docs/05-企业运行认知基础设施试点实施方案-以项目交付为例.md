## 摘要：这次试点究竟要证明什么

前四份专题已经完成从工作感知、企业运行认知、统一数据模型到工程原型的连续研究。下一步不能只继续扩展架构图或增加接口，而要在真实业务流程中回答三个问题：

1. **ADS 能否更准确地理解一个项目当前正在发生什么？** 能否关联项目、任务、决策、风险、依赖、交付物和证据，并区分权威事实、协同线索、推断、冲突与未知？
2. **这种理解能否切实帮助团队推进工作？** 能否减少项目状态汇总、跨系统查找、遗漏跟进和重复沟通，让项目负责人更快发现阻塞和下一步行动？
3. **这种能力能否在可控治理下复制？** 能否做到来源可追溯、权限最小化、个人信息有边界、关键动作有人确认，并在第二、第三个项目中以较低成本复用？

本专题建议以“项目交付状态评审与风险跟进”为首个场景。先选择一个数据较完整的项目打通端到端闭环，再扩展到 3—5 个同类项目验证复用性。第一阶段只读，Agent 生成状态摘要、风险提示、待确认事项和跟进草稿，不自动修改项目系统、不替代项目经理作出业务判断。

**试点成功不等于 AI 能写出一份漂亮的项目周报，而是：在可核验的证据和授权范围内，系统能更及时、更准确地呈现项目真实状态，并让团队以更低成本采取正确的下一步行动。**

### 本专题的核心交付物

1. 试点章程：目标、范围、项目选择标准、角色、资源和阶段门。
2. 数据源与字段清单：明确每类数据从哪里来、谁负责、哪些字段权威、允许如何使用。
3. 试点业务流程：从事件接入到上下文生成、Agent 辅助、人工确认和反馈。
4. 指标与验收方案：建立试点前基线、样本、口径、目标和 Go / No-Go 标准。
5. 治理与风险控制：数据最小化、用途限定、权限、保留、撤回、审计和人工责任。
6. 十周实施计划：按工作流分工、里程碑和阶段门组织落地。
7. 试点运行手册与评审清单：便于真实团队执行和复盘。

## 1. 试点定位：从“做一个 Agent”转向“验证一项企业基础能力”

### 1.1 试点要验证的核心假设

| 编号 | 假设 | 可验证问题 | 证据 |
|---|---|---|---|
| H1 | 多源信息可以形成一致的项目上下文 | 同一项目的任务、决策、风险和交付物能否正确关联？ | 对象关联准确率、证据引用完整率 |
| H2 | 权威来源与协同线索可以共同工作但不互相覆盖 | 会议观点与项目系统状态冲突时，能否保留冲突并要求确认？ | 冲突识别与处理测试 |
| H3 | 上下文包能降低 Agent 理解业务所需的重复提示 | Agent 是否能在任务上下文内回答项目状态和下一步问题？ | 任务评测、人工修改率 |
| H4 | 上下文辅助可以减少管理协作成本 | 状态汇总和风险跟进是否更快、更完整？ | 时间基线、遗漏率、返工记录 |
| H5 | 同一标准可在多个项目中复用 | 更换项目后，是否主要通过配置而非重写代码完成接入？ | 第二至第五个项目接入工时、规则复用率 |
| H6 | 治理机制可伴随业务能力运行 | 是否做到授权可检查、证据可追溯、撤回可执行？ | 权限测试、审计记录、撤回演练 |

### 1.2 试点边界

**本次纳入：**
- 项目基本信息、阶段、状态、负责人、里程碑；
- 项目任务、负责人、计划日期、实际状态、依赖；
- 正式决策及其审批或确认记录；
- 风险、问题、阻塞项和升级记录；
- 交付物、验收记录和相关证据引用；
- 经项目负责人批准纳入的会议纪要或项目协同记录；
- Agent 生成的摘要、问题清单、跟进草稿及人工反馈。

**本次不纳入：**
- 全员、全群、全量邮件或个人设备的无差别采集；
- 默认开启持续录音、屏幕监控或键盘行为采集；
- 将员工个人工作记忆自动转成企业资产；
- 自动修改项目状态、任务负责人、交付日期或客户承诺；
- 自动批准决策、合同、费用或验收；
- 以 AI 生成的推断代替项目系统的正式记录；
- 一开始就覆盖全部业务部门和全部项目类型。

### 1.3 试点规模建议

采用“两层样本”而不是一开始铺开：

- **样板项目：1 个。** 选择数据链条相对完整、业务负责人愿意参与、问题具有代表性的项目，先完成端到端技术和流程验证。
- **扩展项目：2—4 个。** 使用相同核心对象、事件和上下文服务，验证跨项目配置复用、异常场景适应和实际收益。
- **参与团队：1 个交付团队。** 覆盖项目经理、交付负责人、技术负责人和关键执行角色。人员参与以业务职责为依据，不以个人监控为目的。

项目数量不是硬性 KPI。若数据质量、授权或业务资源不足，应缩小范围，先把一个项目做实，不以扩大覆盖率掩盖质量问题。

## 2. 选择什么项目：建立可执行的准入标准

### 2.1 项目选择条件

| 维度 | 优先条件 | 不建议进入首批试点的情况 |
|---|---|---|
| 业务代表性 | 有明确交付目标、里程碑、跨角色协作和可观察的风险 | 流程极特殊、无法代表其他项目 |
| 数据可用性 | 项目系统有稳定对象 ID、状态、任务和更新时间 | 主要信息只存在于口头沟通，且无法获得授权 |
| 责任清晰 | 有项目经理和业务数据责任人 | 无人对项目状态或字段质量负责 |
| 参与意愿 | 项目团队愿意参与基线采集和结果评审 | 团队认为试点是个人绩效监控 |
| 风险可控 | 可使用脱敏或内部级数据，客户信息有明确边界 | 涉及高度敏感数据且没有批准的处理机制 |
| 可比较性 | 可找到历史周报、状态评审记录或同类项目基线 | 无法建立任何可比较的基线 |

### 2.2 项目分层选择

建议扩展项目至少覆盖以下差异，但不要把完全不同的业务流程混在同一轮验收中：

- 一个进展正常、数据较完整的项目；
- 一个存在任务依赖或跨部门协同的项目；
- 一个存在风险、变更或阻塞的项目；
- 如果条件允许，再加入一个处于不同交付阶段的项目。

这样可以验证系统是否只适用于“数据整齐、问题简单”的理想项目。

### 2.3 试点启动前必须指定的责任人

- 业务发起人：确认试点目标、投入和业务价值。
- 试点业务负责人：对项目范围、流程和业务验收负责。
- 项目经理：确认项目状态、冲突和实际使用反馈。
- 系统数据责任人：确认字段含义、权威来源和接口可用性。
- ADS 产品 / 架构负责人：负责模型、服务、集成与技术路线。
- 数据治理 / 安全负责人：审批数据分类、用途、权限和留存。
- Agent 负责人：负责任务设计、评测、提示和工具边界。
- 试点评估负责人：维护基线、样本、指标和最终评估，尽量独立于开发实施角色。

一人可以承担多个角色，但业务确认、安全审批和技术实现不应全部由同一人代替。

## 3. 首个业务场景：项目交付状态评审与风险跟进

### 3.1 场景定义

**触发任务：** 项目经理准备周度状态评审，或管理者临时询问某个项目是否按计划推进。

**当前常见工作：**
1. 打开项目管理系统查看项目和任务状态；
2. 搜索钉钉群、会议纪要和邮件，了解最新变化；
3. 查找决策记录、问题单和交付物；
4. 向任务负责人逐一确认状态；
5. 手工整理进展、阻塞、风险和待办；
6. 形成周报或评审材料；
7. 会议后再把结论和行动项分散录入不同系统。

**试点后的目标工作：**
1. 选择项目和评审时间范围；
2. ADS 依据授权检索项目、任务、风险、决策、依赖和证据；
3. 运行认知引擎重建当前状态，标注来源、时间、冲突和未知；
4. Agent 生成状态摘要、关键变化、阻塞链、待确认事项和跟进草稿；
5. 项目经理逐项确认、修正或驳回；
6. 确认结果形成反馈记录；正式业务变更仍由授权人员在原系统完成；
7. 下次评审能够看到变化轨迹和未闭环事项。

### 3.2 目标输出

每次评审生成一个可追溯的项目运行视图：

1. **项目概览：** 项目目标、当前阶段、正式状态、负责人和关键里程碑。
2. **本期变化：** 自上次评审以来发生的状态变化、任务变化和重要决策。
3. **交付进展：** 已完成、进行中、逾期、阻塞的关键任务及其证据。
4. **风险与依赖：** 风险描述、影响对象、依赖关系、责任人、下一步动作。
5. **决策链：** 已提出、待确认、已批准、已撤回的决策及其依据。
6. **未知与冲突：** 缺少确认的信息、来源不一致的信息、过期信息。
7. **行动建议：** 建议跟进对象、建议问题、建议截止时间；未经确认不写回。
8. **来源索引：** 每条重要结论可追溯到源系统记录、文档或已批准的会议记录。

### 3.3 用户故事

| 用户 | 用户故事 | 验收重点 |
|---|---|---|
| 项目经理 | 我希望快速看到项目当前状态和变化，不再手工拼接多个系统 | 状态准确、来源完整、能纠错 |
| 交付负责人 | 我希望看到阻塞任务影响了哪些里程碑 | 依赖链和影响范围可解释 |
| 技术负责人 | 我希望识别技术风险和待决事项 | 风险线索不被误判为正式结论 |
| 管理者 | 我希望跨项目比较风险和进展 | 同口径、不过度汇总、可下钻 |
| 数据责任人 | 我希望知道系统中的数据如何被使用 | 授权范围、审计和用途清晰 |

## 4. 数据接入策略：先接权威数据，再补充协同上下文

### 4.1 数据源分层

| 数据源 | 首批用途 | 权威程度 | 接入方式建议 | 首批边界 |
|---|---|---|---|---|
| 项目管理系统 | 项目、任务、负责人、计划和状态 | 对其正式字段为权威 | 只读 API / Webhook / 定时增量 | 只取试点项目和必要字段 |
| OA / 审批系统 | 正式决策、变更审批、授权记录 | 对审批结果为权威 | 只读 API / 事件订阅 | 只取与试点项目相关的审批 |
| 文档 / 知识系统 | 交付物、方案、验收证据 | 对文档版本和审批状态按系统规则确定 | 元数据 + 受控内容引用 | 优先保存引用，不复制整份文档 |
| 钉钉项目群 / 会议纪要 | 发现变化线索、补充原因和待确认事项 | 默认是线索，不直接作为正式状态 | 经过批准的群、纪要或人工提交 | 不全量抓取个人聊天 |
| 风险 / 缺陷系统 | 风险、问题、严重度、责任人和处置状态 | 对正式风险记录为权威 | API / 事件订阅 | 只取项目关联记录 |
| 个人工作感知来源 | 补充个人任务记忆或遗漏线索 | 未经确认不构成企业事实 | 自愿、明确用途、单独授权后再评估 | 不作为第一阶段必需依赖 |

### 4.2 权威字段矩阵

每个字段都必须有明确的“权威来源”和责任人，不能笼统地说某个系统整体最权威。

| 业务属性 | 首选权威来源（示例） | 协同来源的作用 | 冲突处理 |
|---|---|---|---|
| project.status | 项目管理系统 | 会议纪要可提供变化线索 | 保留正式状态，发起人工确认 |
| task.status | 项目管理系统 / 任务系统 | 负责人反馈可提示滞后 | 不直接覆盖正式状态 |
| task.assignee | 项目管理系统 | 群聊可提示实际执行人变化 | 待正式分配记录确认 |
| milestone.due_at | 已批准计划 / 项目系统 | 会议可提出调整建议 | 未批准前不改变计划基线 |
| decision.status | OA 审批或正式决策记录 | 会议讨论属于 proposed | 只有正式审批或授权确认才标记 approved |
| risk.status | 风险台账 / 缺陷系统 | 会议和个人记录可形成候选风险 | 由风险责任人确认 |
| deliverable.acceptance | 验收系统 / 正式验收记录 | 文档评论只能补充证据 | 不以模型判断替代验收 |

以上为设计示例，正式权威矩阵必须由试点业务和系统责任人逐字段签字确认。

### 4.3 连接器接入顺序

1. 项目管理系统：先建立 Project、Task 和 Milestone 的对象与状态。
2. OA / 审批：补齐正式 Decision 和变更审批。
3. 文档系统：补齐交付物和 EvidenceRef。
4. 风险 / 缺陷系统：补齐 Risk、Issue 和 Dependency。
5. 会议纪要：只在授权和范围明确后接入，作为线索来源。
6. 个人工作感知：第一阶段不作为前置依赖，待治理评审通过后再开展独立小范围验证。

### 4.4 接入技术要求

- 所有连接器使用服务身份和最小权限，不使用个人账号长期授权。
- 每个源系统保留原生记录 ID、版本号、更新时间和来源链接。
- 增量同步要支持重试、幂等、断点续传和失败队列。
- 记录数据延迟、缺失率、映射失败率和连接器健康状态。
- 对源系统限流、权限变化、删除和撤回建立处理机制。
- 不能接 API 的系统可先采用人工导入或受控导出，但要标记数据时间和质量等级。
- 不把原始内容复制到新的存储中作为默认方案；优先使用元数据、受控引用和必要摘要。

## 5. 目标技术架构与数据流

### 5.1 试点架构

```text
项目系统 / OA审批 / 文档系统 / 风险系统 / 授权会议纪要
                         |
                 连接器与访问控制
                         |
             标准事件接入与事件账本
                         |
        对象注册表 + 共同本体 / 项目领域本体
                         |
           权威字段规则 + 状态重建引擎
                         |
       冲突识别 / 证据引用 / 未知项 / 新鲜度
                         |
            授权校验与任务级上下文包
                         |
             项目交付 Agent / API
                         |
       项目经理确认、修正、驳回与跟进草稿
                         |
          反馈事件 / 审计 / 指标与持续评估
```

### 5.2 分层责任

| 能力层 | 试点责任 | 不承担的责任 |
|---|---|---|
| 连接与接入层 | 读取授权数据、增量同步、标准化 | 不决定业务事实 |
| 事件与对象层 | 保存变化、解析对象、关联来源 | 不擅自合并不确定对象 |
| 语义与规则层 | 字段含义、权威来源、状态计算 | 不用大模型自由判断覆盖规则 |
| 认知与上下文层 | 形成项目状态视图、冲突和未知 | 不替代系统记录和业务确认 |
| Agent 应用层 | 解释、摘要、提示、草拟跟进 | 不绕过审批执行正式动作 |
| 治理与评估层 | 授权、审计、质量、指标和撤回 | 不将安全检查留给提示词 |

### 5.4 Agent 输出规则

- 每条重要结论都应引用支持记录或明确标记“暂无证据”。
- 把正式事实、观察、推断、冲突和未知分开展示。
- 不把“可能延期”改写为“已经延期”。
- 不把会议讨论改写为正式决策。
- 不生成没有来源的负责人、日期、客户承诺或验收结论。
- 高影响风险必须列出证据和待确认责任人。
- 输出必须带 context_id、生成时间、规则版本和适用范围。
- 上下文过期或授权撤回后，不得继续使用旧上下文执行新任务。

## 6. 业务闭环：让 Agent 进入工作流程，而不是另建一个聊天窗口

### 6.1 首批三个任务

**任务 A：项目状态评审准备**
- 输入：项目 ID、评审周期。
- 输出：项目概览、本期变化、关键任务、里程碑、风险、决策、未知和证据索引。
- 人工动作：项目经理逐项确认，修正错误并补充缺失信息。
- 价值：减少状态收集和周报整理时间。

**任务 B：阻塞与依赖分析**
- 输入：项目 ID 或某个阻塞任务。
- 输出：阻塞原因、上游依赖、受影响任务和里程碑、责任人、待确认问题。
- 人工动作：交付负责人确认影响链和优先级。
- 价值：更早识别跨角色、跨团队依赖。

**任务 C：会议后行动项整理**
- 输入：经批准的会议纪要或人工确认记录。
- 输出：候选决策、行动项、负责人候选、截止时间候选和关联对象。
- 人工动作：会议主持人或项目经理确认后再进入正式任务系统。
- 价值：降低行动项遗漏和重复录入。

### 6.2 交互入口

优先嵌入团队已经使用的工作入口，例如项目系统页面、企业工作台或经批准的钉钉应用入口。若第一阶段无法嵌入，可使用受控 Web 原型，但必须绑定真实项目对象和权限，不应只展示脱离业务系统的聊天演示。

### 6.3 人工确认闭环

Agent 输出的建议进入四种状态：
- accepted：人工确认，可形成后续正式操作建议；
- corrected：人工修正，保留原建议和修正内容；
- rejected：人工驳回，记录原因；
- deferred：信息不足，等待后续证据。

反馈用于修正规则、映射和提示，不得简单把所有人工修改都当作模型训练数据。涉及个人信息或敏感业务内容的反馈应按原授权和留存规则处理。

## 7. 十周实施计划

### 7.1 阶段安排

| 周期 | 阶段 | 主要工作 | 阶段交付 | 阶段门 |
|---|---|---|---|---|
| 第 1 周 | 立项与场景确认 | 明确业务负责人、试点项目、目标任务、范围和成功标准 | 试点章程、RACI、项目清单 | 业务发起人批准 |
| 第 2 周 | 数据与治理盘点 | 系统字段盘点、权威矩阵、数据分类、授权和接口评估 | 数据源清单、字段映射、治理审批 | 安全与数据责任人批准 |
| 第 3—4 周 | 只读连接与对象映射 | 接入项目系统，建立 Project / Task / Milestone，补充审批与文档元数据 | 连接器、对象映射、事件接入 | 样板项目数据可追溯 |
| 第 5 周 | 状态与上下文 | 权威规则、状态重建、冲突与未知、ContextPackage | 项目状态视图、上下文服务 | 业务抽样核验通过 |
| 第 6 周 | Agent 影子运行 | 生成评审摘要和阻塞分析，不进入正式决策流程 | 评测记录、错误分类 | 关键错误可解释和纠正 |
| 第 7 周 | 人工确认试用 | 项目经理在真实评审前使用，确认、修正、驳回 | 反馈闭环、使用记录 | 用户愿意持续使用 |
| 第 8 周 | 扩展项目验证 | 接入 2—4 个项目，测量配置复用和跨项目差异 | 多项目验证结果 | 无重大治理或质量问题 |
| 第 9 周 | 价值与治理评估 | 对比基线、抽样审计、权限撤回和异常演练 | 指标报告、风险清单 | 评估负责人签字 |
| 第 10 周 | 复盘与决策 | 业务评审、架构复盘、成本收益分析 | 试点总结、Go / No-Go 决策 | 决定扩大、调整或停止 |

### 7.2 里程碑定义

- M1（第 1 周末）：试点章程和责任人确认。
- M2（第 2 周末）：数据源、字段权威矩阵和治理边界批准。
- M3（第 4 周末）：样板项目数据接入和对象关联可用。
- M4（第 5 周末）：状态视图可追溯，冲突与未知能正确展示。
- M5（第 7 周末）：至少一个真实项目评审完成 Agent 人工确认闭环。
- M6（第 8 周末）：第二至第五个项目完成复用性验证。
- M7（第 10 周末）：完成指标报告和下一阶段决策。

### 7.3 阶段暂停条件

出现以下任一情况，先暂停相关数据源或功能，不以赶进度为由绕过：
- 数据用途或授权尚未获批；
- 项目对象无法可靠识别，错误关联会影响业务结论；
- 权威字段责任人未明确；
- 高影响事实频繁错误且无法解释；
- 出现未授权数据暴露或审计缺失；
- Agent 产生未经批准的业务写回或客户承诺；
- 项目团队将试点理解为个人绩效监控，且疑虑未得到解决。

## 9. 指标体系：把“好用”变成可验证结果

### 9.1 指标分层

1. 数据质量：对象关联、事件完整性、状态准确性和数据新鲜度。
2. 认知质量：冲突识别、未知项识别、证据可追溯和风险解释。
3. 使用效果：准备时间、查找时间、人工修改率、任务遗漏和用户采用。
4. 业务价值：风险提前发现、阻塞闭环时间、返工和跨角色沟通成本。
5. 治理安全：越权、敏感信息暴露、审计覆盖、撤回生效和高风险动作控制。
6. 复用能力：新项目接入工时、配置复用比例和领域规则变更成本。

### 9.2 建议指标口径与暂定目标

下表中的目标是**试点建议阈值，不是已经验证的结果或企业现行标准**。第 2 周完成基线和样本评估后，由业务、架构、数据治理和评估负责人共同冻结阈值。

| 指标 | 计算口径 | 暂定目标 | 责任人 |
|---|---|---:|---|
| 关键对象关联准确率 | 抽样中正确关联的对象数 / 已接受关联总数 | ≥98% | 数据工程 + 业务核验 |
| 关键状态准确率 | 与人工裁定一致的状态断言数 / 抽样状态断言数 | ≥95% | 项目经理 |
| 证据可追溯率 | 有有效来源引用的关键结论数 / 全部关键结论数 | ≥95% | Agent 负责人 |
| 数据新鲜度达标率 | 在约定时限内到达的事件数 / 应到达事件数 | ≥95% | 连接器负责人 |
| 冲突显式呈现率 | 被正确标记的冲突数 / 抽样真实冲突数 | ≥95% | 认知引擎负责人 |
| 未知项识别率 | 被正确标记的未知项数 / 抽样未知项数 | ≥90% | Agent + 业务核验 |
| 状态评审准备时间 | 试点后中位耗时相对基线的变化 | 降低 ≥30% | 评估负责人 |
| 人工修改率 | 被修改的关键结论数 / 人工审核的关键结论数 | 观察趋势，稳定后争取 ≤20% | Agent 负责人 |
| 审计覆盖率 | 可关联主体、用途、对象、时间和结果的访问数 / 全部访问数 | 100% | 安全 / 平台 |
| 未授权访问成功次数 | 经确认的越权访问成功事件数 | 0 | 安全负责人 |
| 高风险自动写回次数 | 未经审批发生的高风险写回 | 0 | 平台负责人 |
| 新项目接入复用率 | 可复用标准组件与配置工作量 / 新项目接入总工作量 | 试点后测量，建立基线 | 架构负责人 |

### 9.3 基线采集方法

第 1—2 周采集至少两周的现状基线：
- 选择不少于 3 次项目状态评审或同类管理任务；
- 记录准备人、参与人数、准备时间、信息查找时间和会后修正时间；
- 记录状态遗漏、负责人遗漏、日期错误和重复确认次数；
- 获取历史周报、会议纪要和任务记录作为人工裁定样本；
- 记录现有系统数据更新时间和跨系统查找路径；
- 区分项目复杂度、阶段和团队规模，避免把不同任务简单比较。

如果历史记录不完整，可在试点启动前进行前瞻性计时与抽样，不得用回忆估算代替可靠基线。

### 9.4 样本与评测集

建议在试点期形成：
- 至少 3 个项目的验证样本（如实际条件允许）；
- 至少 100 条关键状态或事件关联抽样记录；
- 至少 30 条任务 / 依赖关系核验样本；
- 一组正式决策与会议线索的区分样本；
- 一组真实冲突、过期、缺失和对象歧义样本；
- 一组权限拒绝、撤回、过期上下文和高风险动作测试样本。

样本量是试点设计建议。若项目事件量不足，应如实报告样本限制，不用合成数据冒充真实业务准确率。合成数据只用于补充边界测试。

### 9.5 业务收益计算

建议至少计算三类收益，不在试点前虚构金额：

**时间收益**

`节省工时 = 基线任务总工时 - 试点后任务总工时`

**质量收益**

`遗漏改善率 = (基线遗漏率 - 试点遗漏率) / 基线遗漏率`

**协同收益**

比较跨角色确认次数、阻塞项发现到责任人确认的时间、会议后行动项录入时间和重复沟通次数。

如需折算经济价值，必须由财务或业务负责人确认工时成本口径、项目样本和可归因比例。不能将所有时间节省直接等同于现金节省。

## 10. 数据治理、安全与员工信任

### 10.1 数据治理原则

- 明确业务目的：每个数据源都要说明为何需要、服务哪个任务。
- 最小必要：只接入试点项目、必要字段和有限时间范围。
- 权威分层：系统正式记录、人工确认、协同线索和模型推断分别标识。
- 责任明确：每类数据有业务责任人和系统责任人。
- 原始数据留在原系统：优先保存引用和必要摘要，避免不必要复制。
- 个人信息保护：个人工作感知不是默认数据源；任何接入需单独评估、授权和审批。
- 可撤回、可纠错：授权撤回、数据更正和删除请求应能影响派生上下文。
- 审计可追溯：记录主体、用途、对象、字段范围、策略版本、访问时间和结果。

### 10.2 个人工作感知的特殊边界

本试点不以录音卡、手机或桌面采集作为必要条件。若未来要评估此类来源，必须先明确：
1. 采集主体和明确业务目的；
2. 参与者知情与自愿机制及适用组织制度；
3. 采集范围、敏感信息过滤和第三方信息处理；
4. 原始音频是否保留、保存多久、谁能访问；
5. 个人记忆与企业共享资产的分界；
6. 纠错、撤回、删除和审计流程；
7. 适用法律、劳动关系和数据保护要求的审查。

任何情况下都不应通过隐蔽录音、无差别聊天抓取或个人绩效监控来获得所谓“更完整的上下文”。

### 10.3 最小权限设计

- 连接器使用服务身份，不共享个人密码。
- Agent 身份与发起请求的员工身份分开记录。
- 上下文包绑定 requester、purpose、scope、classification、allowed_actions 和 TTL。
- 不同角色只看到完成任务所需的字段。
- 敏感字段按字段级策略裁剪，不只依赖对象级授权。
- 授权撤回后，缓存、索引、上下文包和下游工具访问应按策略失效。
- 访问失败时默认拒绝，不以模型推断或人工口头要求绕过策略。

### 10.4 人工责任边界

| 事项 | Agent 可以做 | 必须由人 / 正式系统完成 |
|---|---|---|
| 项目状态摘要 | 汇总并引用证据 | 正式状态确认由项目责任人 / 权威系统决定 |
| 风险识别 | 提出风险候选和影响分析 | 风险定级与接受由风险责任人确认 |
| 决策整理 | 区分 proposed / approved 线索 | 正式批准由授权审批流程完成 |
| 任务建议 | 生成任务草稿和跟进建议 | 正式分配和计划变更由授权人员执行 |
| 客户沟通 | 草拟内部审核材料 | 客户承诺和正式发送由授权人员确认 |
| 交付验收 | 汇总验收证据 | 验收结论由正式验收责任人确认 |

| P-15 | 项目经理修正 Agent 输出 | 保留原建议、修正值、操作者和时间 | 反馈 |
| P-16 | 关键结论无证据 | 明确标记未知或无证据，不生成确定陈述 | 质量 |
| P-17 | 上下文包过期 | 读取或执行时拒绝使用旧包 | 生命周期 |
| P-18 | 跨项目访问 | 仅返回当前授权项目范围 | 多租户 / 范围 |

验收不仅检查“回答是否看起来正确”，还要检查底层引用、权限决策、日志和最终业务系统是否被意外修改。

## 12. 风险登记与应对

| 风险 | 可能影响 | 预防措施 | 触发后的处理 |
|---|---|---|---|
| 源系统字段定义不一致 | 状态误判 | 字段字典和权威矩阵评审 | 暂停相关字段推断，人工核验 |
| 对象映射错误 | 项目 / 任务串线 | 精确 ID 优先、候选审核 | 撤销错误关系并重放 |
| 会议线索被当成事实 | 错误管理结论 | assertion_status 和来源标签 | 更正事件并检查下游输出 |
| 数据更新不及时 | 使用过期状态 | freshness 指标和失效标记 | 标记 stale，提示回源确认 |
| Agent 幻觉或遗漏证据 | 错误建议 | 引用约束、评测集、人工审核 | 停止对应任务模板并修正 |
| 权限配置过宽 | 敏感数据暴露 | 最小权限、字段级授权 | 撤权、调查、审计和事件响应 |
| 员工信任不足 | 使用抵触、参与度低 | 公开目的、范围和反馈机制 | 暂停争议数据源，重新评审 |
| 接口依赖和运维成本高 | 试点延期 | 优先少量只读接口 | 先用受控导入验证价值 |
| 单项目成功但不可复用 | 无法规模化 | 多项目扩展验证 | 缩小适用范围或调整模型 |
| 价值无法归因 | 无法决定是否投资 | 先采基线、设评估负责人 | 延长测量或停止扩展 |

## 13. Go / No-Go：什么时候可以扩大试点

### 13.1 Go 条件

同时满足以下条件，才建议进入下一阶段：
- 关键对象关联、状态准确、证据追溯达到事先冻结的阈值；
- 真实项目团队完成至少一个完整的人工确认闭环；
- 评审准备时间或其他明确业务指标出现可重复改善；
- 没有未解决的重大数据授权和安全问题；
- 权限拒绝、撤回、过期和高风险动作测试通过；
- 第二至第五个项目可以复用主要模型、连接器和规则；
- 业务负责人愿意继续投入并承担结果责任。

### 13.2 No-Go / 暂停条件

- 关键状态准确率低于门槛且无法定位原因；
- 关键结论缺少证据，用户无法核验；
- 权限和撤回机制未通过；
- 试点依赖大量人工补录，无法证明比现状更省事；
- 项目团队不愿持续使用，或试点被感知为监控工具；
- 多项目扩展需要为每个项目重写一套模型和逻辑；
- 无法建立可信基线，因而不能判断业务价值。

### 13.3 结果分类

- **Go：** 进入只读企业服务化和更多项目扩展。
- **Conditional Go：** 保留已验证能力，限定场景，先解决明确缺口。
- **No-Go：** 停止扩展，保留研究结论和可复用代码，重新选择场景或调整假设。

不把“按计划完成开发”当成 Go 的充分条件。

## 14. 试点成功后如何演进为企业能力

### 阶段 A：单团队、多项目

验证同一项目领域本体、事件映射、权威规则和上下文服务能否覆盖多个项目。

### 阶段 B：跨团队、同类交付流程

更换团队和项目负责人，验证规则是否依赖某个核心员工的个人经验；检查新团队是否只需少量配置和业务确认。

### 阶段 C：跨领域复用

将 Project / Task / Decision / Risk / Evidence 等通用概念与领域专属字段分离，验证是否能支持客户服务、产品研发、运营等不同场景。跨领域不能只复制项目模型，必须由领域责任人定义语义和权威来源。

### 阶段 D：企业级运行上下文服务

形成稳定的连接器目录、事件规范、对象注册表、领域本体、策略服务、上下文 API、评测体系和运营机制，成为企业数智底座内部可复用的基础能力。

### 阶段 E：受控 Agent 执行

只有在只读准确性、权限、审计、人工确认和业务收益充分验证后，才逐步引入低风险动作，并按动作等级独立审批。不得从“能生成建议”直接跳到“允许自主执行”。

## 15. 与 ADS 三级数智底座的关系

| 底座层级 | 试点中的作用 | 责任边界 |
|---|---|---|
| 个人数智底座 | 个人可选择沉淀工作记忆，并在明确授权后提供必要线索 | 原始个人工作信息由个人侧控制，不默认共享 |
| 企业数智底座 | 接入企业正式系统，形成标准业务数据、项目运行上下文和企业 Agent 服务 | 企业业务数据、业务规则、访问策略和运行责任由企业承担 |
| 业务领域中心数智底座 | 提供共同语义、领域标准、联邦目录和跨域治理协同 | 不汇聚不必要的个人或企业原始数据 |

本试点建设的是企业数智底座内部的“项目交付运行上下文”能力，不是新建第四级底座，也不是以采集更多员工行为来代替业务系统建设。

## 16. 立项前需要组织确认的十项决策

1. 由哪个业务部门作为试点发起方？
2. 哪一个项目作为端到端样板，另外哪些项目作为扩展样本？
3. 项目管理系统、OA、文档和风险系统分别由谁负责？
4. 哪些字段的权威来源和业务责任人已经明确？
5. 哪些会议纪要或项目协同信息允许接入，范围如何限定？
6. 试点部署在什么环境，哪些数据允许进入该环境？
7. 安全、数据治理和适用制度审批由谁完成？
8. 项目经理愿意投入多少时间参与状态核验和试用？
9. 基线指标和最终验收阈值由谁签字冻结？
10. 试点结束后由谁决定扩大、调整或停止？

## 17. 建议立即启动的两周准备动作

### 第 1 周：把业务场景和责任人定下来
- 召开一次 90 分钟试点启动工作坊；
- 确定业务发起人、试点负责人和项目经理；
- 选出 1 个样板项目和 2—4 个候选扩展项目；
- 画出现状项目评审流程，记录耗时和信息来源；
- 确认首批三个 Agent 任务和明确不做的事情。

### 第 2 周：把数据、权限和验收口径定下来
- 与系统责任人完成字段和接口盘点；
- 逐字段确认权威来源、数据分类和负责人；
- 安全 / 数据治理评审接入范围、用途、保留和撤回；
- 采集基线并冻结首批指标口径；
- 评审试点技术方案、资源和阶段门。

**两周准备结束时，必须有一份经过责任人确认的《试点章程》、一份《数据源与权威字段矩阵》、一份《数据授权与风险评审记录》和一份《基线与验收指标表》。缺少这些，不进入真实数据接入。**

## 结论：用真实业务结果决定是否建设企业运行认知基础设施

ADS-WORK-05 的核心建议是：**以项目交付为切入口，以一个样板项目打通闭环，以多个项目验证复用，以真实指标决定是否扩大。**

企业运行认知基础设施的价值不在于把所有数据集中起来，也不在于让 Agent 代替项目经理，而在于让企业能够在正确权限下，把分散在系统、任务、决策、风险和协同过程中的信息组织成可信的运行上下文。

当 ADS 能够持续回答“项目现在是什么状态、为什么、依据是什么、哪里不确定、下一步谁需要做什么”，并且这种能力在不同项目中可复用、可治理、可衡量时，企业数智底座才真正从数据与知识承载走向企业运行认知。

**最终检验标准不是演示效果，而是：真实项目团队愿不愿意持续使用，业务负责人能不能看到可核验的收益，数据和安全责任人能不能放心让它进入企业工作流程。**
