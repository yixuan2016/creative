摘要：把“理解企业运行”变成可实现的数据与引擎

本文件将 ADS-WORK-01 的多源工作感知与个人—企业资产转化、ADS-WORK-02 的企业工作上下文基础设施，推进为统一数据模型、运行认知引擎、上下文服务平面和治理机制的逻辑架构。

核心判断：统一数据模型不等于统一物理数据库。统一的是语义、标识、事件封装和治理规则；数据仍可分布在个人、企业和领域中心的责任边界内。
  1. 事件、状态、证据和标准业务数据必须分开建模。
  2. 上下文引擎关联并解释权威来源，不替代 ERP、CRM 或项目系统。
  3. 运行认知必须允许已确认、观察、推断、冲突、过期和未知状态存在。
  4. Agent 消费的是有范围、有版本、有授权的任务级上下文包。
  5. 企业工作上下文基础设施属于企业数智底座内部能力，不新增第四级底座。

1. 设计目标、范围与架构约束

1.1 设计目标

  • 从业务系统和经批准的协同来源接入工作事件；
  • 关联客户、项目、产品、订单、流程和任务等业务对象；
  • 保留发生、观察、记录和状态有效时间；
  • 重建多源状态，识别冲突、过期、缺失和未知；
  • 组织决策、任务、依赖、风险和证据关系；
  • 按任务、角色、用途和风险生成 Agent 上下文包；
  • 记录 Agent 使用上下文、工具调用、审批和结果；
  • 在不集中复制全部原始数据的情况下支持跨系统协同。

1.2 不解决的范围

本设计不定义全部业务主数据标准，不替换现有业务系统，不指定单一厂商或数据库，不授权未经批准的员工音频/屏幕持续采集，不将个人记忆自动转为企业资产，也不允许 AI 独立完成高风险审批。

1.3 设计约束

编号约束要求

2. 总体架构：统一模型、上下文引擎与服务平面

2.1 三个核心组成

A

统一数据模型

定义事件、业务对象、关系、状态断言、决策、任务、风险、证据、能力资产、授权和审计的公共语义。

B

运行认知引擎

负责事件接入、身份解析、语义映射、状态重建、关系维护、冲突检测、上下文组装和质量评价。

C

上下文服务平面

通过 API、事件订阅和受控查询，向业务应用及 Agent 提供时间线、状态、上下文包和受控回写。

3. 统一数据模型：核心实体与关系

3.1 四组模型

模型组核心实体作用
事实与来源WorkEvent、SourceRecord、EvidenceRef记录发生了什么、来源和核验方式
业务语义BusinessObject、ObjectAlias、Relation、StateAssertion关联业务对象、身份、关系和状态
运行管理DecisionRecord、TaskRecord、RiskRecord、CapabilityAsset表达决策、执行、风险和可复用能力
使用与治理ContextPackage、AuthorizationGrant、PolicyDecision、AuditRecord控制谁因何种目的使用什么上下文

3.2 统一标识原则

  • 每个上下文实体使用稳定的全局或租户范围 ID。
  • 原系统 ID 保留为外部标识，不覆盖源系统主键。
  • 别名和跨系统映射单独存储，字符串相同不代表同一对象。
  • 合并、拆分和映射纠错保留历史。
  • 跨企业引用使用受控标识或联邦引用。

3.3 核心实体定义

实体核心字段设计要点
WorkEventevent_id、tenant_id、event_type、schema_version、occurred_at、observed_at、recorded_at、actor_ref、object_refs、payload、source_ref、evidence_refs、assertion_status、confidence、classification、authorization_ref、ontology_version、lifecycle_status追加式记录；更正通过新事件表达
BusinessObjectobject_id、tenant_id、object_type、canonical_name、domain_id、authority_refs、owner_ref、classification、lifecycle_status、valid_from/to、ontology_version业务语义锚点，不复制全部源字段

3.4 业务关系模型

建议首批关系包括 belongs_to、depends_on、blocks、serves、owns、decided_by、supported_by、affects。关系类型应登记定义、反向关系、基数约束和是否允许推断。会影响任务执行的关系必须有来源和确认状态。

3.5 状态重建原则

不设一个适用于所有字段的简单来源优先级。应按“对象类型 + 属性 + 业务领域”配置权威来源。会议讨论可以作为变化线索，但不能自动覆盖指定权威系统字段。

业务状态与认知状态分开表达。例如引擎可推断项目 at_risk，但该推断不等同于业务责任人正式确认的项目状态。

4. 统一事件封装与示例

4.1 标准事件信封

信封定义跨系统通用字段，payload 按 event_type 和 schema_version 定义。

{
  "event_id": "evt_01JCTX...",
  "tenant_id": "tenant_acme",
  "event_type": "task.updated",
  "event_schema_version": "1.0",
  "occurred_at": "2026-11-18T09:30:00+08:00",
  "observed_at": "2026-11-18T09:30:04+08:00",
  "recorded_at": "2026-11-18T09:30:05+08:00",
  "actor_ref": {"actor_type": "system", "system_id": "project-system"},
  "object_refs": [
    {"object_type":"project","source_system":"project-system","source_object_id":"PRJ-2026-014"},
    {"object_type":"task","source_system":"project-system","source_object_id":"TASK-328"}
  ],
  "payload": {
    "changed_property":"status",
    "old_value":"in_progress",
    "new_value":"blocked",
    "reason_code":"dependency_pending"
  },
  "source_ref": {"source_system":"project-system","native_record_id":"TASK-328","record_version":"42"},
  "assertion_status":"observed",
  "classification":"internal",
  "purpose_tags":["project_delivery_context"],
  "ontology_version":"ads-common-1.x/domain-project-0.x",
  "lifecycle_status":"active"
}

样例中的租户、系统和业务编号均为虚构值，仅用于说明结构。

4.2 事件处理状态

状态含义
received已接收
validated结构与策略校验通过
normalized时间、标识和字段标准化
resolved对象映射完成
pending_review等待人工确认
accepted进入有效上下文
rejected不满足接收条件
superseded / withdrawn被更正替代 / 已撤回

4.3 重复、乱序与更正

  • 重复事件用幂等键去重，同时保留接收日志。
  • 乱序事件按发生时间和源系统版本判断业务顺序，记录时间保留处理顺序。
  • 迟到事件可触发状态重算，保留重算前后版本。
  • 更正通过 correction_of 或 supersedes 建立关联，不物理覆盖原事件。
  • 撤回时识别依赖它的状态投影、上下文包和能力候选。
  • 冲突并存，不采用“最后写入者获胜”作为通用规则。

5.3 状态重建步骤

  1. 识别对象和属性；
  2. 查询该属性的权威来源配置；
  3. 获取权威系统当前值及版本或更新时间；
  4. 获取相关状态断言和事件；
  5. 检查有效时间、观察时间和新鲜度；
  6. 识别冲突、过期、缺失或未确认信息；
  7. 生成当前状态视图和状态解释；
  8. 保留来源、规则版本和计算时间。

5.4 冲突类型

值冲突、时间冲突、身份冲突、语义冲突、权限冲突和证据冲突。输出应包含冲突类型、来源、时间、权威配置、建议处理人和处理状态。高影响冲突不得仅凭模型打分自动消除。

运行认知引擎输出的是基于当前授权数据和规则形成的可解释认知视图，不是企业全部真实状态的完美复制。信息不足时必须允许输出“未知”。

6. Agent 上下文包标准与使用协议

6.1 生成输入

至少需要 requester、purpose、task、scope、requested_fields、policy_context 和 freshness_requirement。

6.2 上下文包内容

  1. 任务目标和任务标识；
  2. 调用主体、所属组织和用途；
  3. 业务对象及权威来源；
  4. 当前状态、可信级别和更新时间；
  5. 关键事件时间线；
  6. 决策、约束、任务和依赖；
  7. 风险、冲突、未知和过期项；
  8. 证据引用；
  9. 允许动作、审批要求和禁止动作；
  10. 数据、本体、策略和上下文包版本。

6.3 上下文包样例

{
  "context_id": "ctx_01J...",
  "task_id": "task_review_project_014",
  "requester_ref": "agent_project_assistant",
  "purpose": "prepare_project_status_review",
  "scope": {"object_refs":["obj_project_014"]},
  "current_state": {
    "delivery_status": {
      "value":"at_risk",
      "assertion_status":"inferred",
      "source_refs":["project-system","event-ledger"]
    }
  },
  "unknowns":["客户验收日期待确认"],
  "allowed_actions":["summarize","draft_follow_up"],
  "approval_required_for":["update_project_status","send_customer_commitment"],
  "policy_version":"context-policy-0.1",
  "ontology_version":"ads-common-1.x/domain-project-0.x",
  "expires_at":"2026-11-19T10:30:00+08:00",
  "lifecycle_status":"active"
}

样例状态为示意性推断，不代表真实项目结论。

6.4 Agent 使用协议

  • 仅读取 context_id 明确包含且允许使用的内容；
  • 不把上下文包未包含的信息假定为事实；
  • 过期、撤回或策略失效时重新申请；
  • 写操作提交动作意图、目标、预期变更和理由；
  • 高风险操作由有权限人员审批；
  • 区分技术执行成功与业务成功；
  • Agent 建议不能自动升级为正式决策。

7.2 接口通用要求

  • 请求包含认证主体和租户上下文；写操作支持幂等键；
  • 返回 trace_id、schema_version 和策略版本；
  • 错误区分认证失败、授权拒绝、对象不存在、映射歧义、状态冲突、过期和系统错误；
  • 证据定位符不得绕过原始系统权限；
  • 接口向后兼容，支持弃用通知；
  • 不能因接口返回而推断用户拥有源系统未授予的权限。

8. 存储与部署逻辑：统一语义，不强制统一技术

逻辑存储内容设计重点
Event Ledger追加式工作事件不可静默覆盖、支持重放与更正链
Object Registry统一对象 ID、源 ID、别名身份映射、合并拆分历史
Relation Store类型化业务关系有效时间、来源、确认状态
State Projection当前和历史状态视图可重建、带来源和规则版本
Evidence Index证据元数据与受控引用不默认复制原始内容
Capability Registry能力资产、版本和验证适用范围、审批和弃用

8.1 技术选型原则

不预设必须使用图数据库、向量数据库或某种消息中间件。试点规模较小时，可采用可维护的关系型数据库加事件表、搜索索引和对象存储引用。是否引入独立图数据库，应由关系查询规模、复杂度和性能测试决定。

8.2 部署与数据驻留

  • 个人原始工作记录优先留在个人责任边界内；
  • 企业业务数据和上下文主要在企业控制环境处理；
  • 领域中心优先登记目录元数据、语义规范、能力描述、授权和审计信息；
  • 跨域查询使用联邦查询、受控 API 或最小必要上下文包；
  • 敏感数据是否可由云端模型处理，须经数据分类、合同和安全评估；
  • 缓存、索引和派生数据继承来源权限与保留约束。

9. 数据治理、安全与生命周期

9.1 授权不是布尔值

授权至少描述主体、代表关系、数据责任方、数据和字段范围、处理目的、接收方或 Agent、允许动作、生效与到期时间、派生和再共享规则、撤回方式、策略版本及审计引用。

9.2 权限决策维度

每次访问评估：谁访问、代表谁访问、访问什么对象和字段、为了什么目的、执行什么操作、处于什么组织和任务环境、数据分类与授权是否允许。

9.3 生命周期

对象建议生命周期
原始来源captured → retained → restricted / expired → deleted or archived
工作事件received → validated → accepted → superseded / withdrawn → archived
状态断言candidate → confirmed / disputed / stale → superseded
证据registered → verified / disputed → expired / restricted
上下文包requested → built → active → expired / revoked
能力资产candidate → validated → approved → active → deprecated / retired

撤回或删除需识别相关缓存、搜索索引、派生状态、上下文包和能力候选，并按适用政策失效、重算、限制或删除。必要的审计记录应与业务内容分离并限制访问。

9.4 必须具备的治理控制

  • 数据分类和字段级敏感标签；
  • 传输与静态加密、租户隔离和最小权限；
  • 访问、导出、模型调用和写回审计；
  • 上下文包 TTL、撤销和缓存失效；
  • 模型输出标注与人工纠错；
  • 保留、删除、法律保全和备份恢复策略；
  • 第三方信息与个人信息的目的限制及必要审查。

10. 企业与 ADS 三级数智底座的衔接

层级可承载内容不应默认承载
个人数智底座个人工作事件、记忆、证据、任务和授权共享记录企业全部业务上下文和其他人的私人记录
企业数智底座企业事件、对象、状态、决策、任务、风险、证据、标准业务数据和能力资产未经授权的个人完整记忆
业务领域中心数智底座共同本体、标准、联邦目录、能力目录、跨域授权和任务审计元数据默认集中存储所有企业原始业务记录和个人原始数据

10.1 个人到企业的受控晋升

  1. 个人侧识别可共享候选；
  2. 判断权属、参与方和第三方信息；
  3. 明确目的、字段、接收方和期限；
  4. 有权主体授权；
  5. 企业责任人审核业务必要性和质量；
  6. 关联企业对象并完成领域本体映射；
  7. 脱敏或裁剪；
  8. 验证后进入企业责任边界；
  9. ADS 联邦目录登记适当元数据和受控引用；
  10. 授权变化和撤回沿原链路传播。

10.2 企业到领域中心的协同

优先共享本体映射、标准版本、资产元数据、能力描述、受控接口、授权任务状态和必要审计结果。企业明细、原始文件和员工记录不会因进入联邦目录而自动跨域开放。

10.3 与 ADS 三端关系

  • 执行端：读取任务级上下文，发起受控动作并回传结果。
  • 管理端：管理本体、数据责任、授权、连接器、目录、能力版本和策略。
  • 考核端：评价事件质量、上下文完整度、任务效果、Agent 可靠性和治理情况。

11. 试点参考：项目交付上下文闭环

11.1 试点范围

建议选择一个项目交付流程，先接入一个项目/任务权威系统、一类经批准的会议或协同记录、一类项目文档或决策记录。不必一开始接入全部员工通信、屏幕或录音数据。

11.2 首批对象与事件

对象：Project、Task、Decision、Risk、Evidence、ActorRole。

事件：task.created、task.updated、task.completed、decision.proposed、decision.approved、risk.identified、evidence.attached、project.state_changed。

11.3 最小运行闭环

  1. 项目系统产生任务状态变化事件；
  2. 经授权会议记录提供决策和依赖线索；
  3. 事件规范化并关联 Project / Task；
  4. 状态引擎读取权威状态，区分事实与推断；
  5. 关系引擎形成依赖与阻塞候选；
  6. 生成项目周报或风险评审上下文包；
  7. Agent 生成状态摘要、未决事项和跟进草稿；
  8. 项目负责人确认或修订；
  9. 结果写回对应系统或上下文记录；
  10. 以周期、遗漏、返工、核验成本和越权情况评估效果。

11.4 验收指标

类别指标验收方式
接入事件接入成功率与源系统抽样记录对账
语义对象关联准确率业务人员抽样确认
状态权威状态一致率与指定权威字段比较
可信证据可追溯率抽样检查结论能否定位来源
时效状态新鲜度测量源更新到上下文可用延迟
质量冲突识别与误报构造和抽样核验冲突案例
Agent建议有效率 / 人工修改率对照业务负责人审阅结果
业务周期、遗漏、返工与试点前基线或对照流程比较
治理未授权访问与错误写回安全测试与审计记录
成本单流程运行成本统计连接器、模型、存储和人工核验

验收阈值应在试点开始前共同确定，不能在结果出来后调整标准以迎合结论。

风险后果设计控制

事件模型过复杂接入成本高从少量高价值事件开始
对象匹配错误错误关联和推断匹配分级、高影响对象人工确认
状态误判错误业务结论权威字段配置、冲突保留、未知状态

14.1 关键验证问题

  1. 统一事件模型能否覆盖首个流程关键变化且不强迫源系统改造？
  2. 对象身份解析准确率是否足够？
  3. 状态引擎能否解释状态来源、时间和不确定性？
  4. 上下文包是否比直接检索多个系统更准确、更安全、更省时？
  5. 业务人员是否愿意确认和纠正事件与关系？
  6. 能力资产能否在另一个团队独立复用？
  7. 单流程模型、连接器、存储、治理和核验成本是否可接受？

16. 结论与下一步

企业工作上下文基础设施可拆解为三项工程能力：统一数据模型、运行认知引擎和上下文服务平面。

  1. 统一数据模型：先定义事件、对象、关系、状态、决策、任务、证据和上下文包。
  2. 运行认知引擎：再建设事件处理、对象解析、语义映射、状态重建、冲突检测和上下文组装。
  3. 上下文服务平面：最后通过受控 API 向 Agent 和业务应用提供任务级上下文与受控动作接口。
建设顺序坚持“小模型、单流程、权威源、可追溯、先只读、再受控写入”。不要一开始就追求全企业知识图谱、全员持续采集或全自动 Agent。

建议的下一项工程工作

  • Project / Task / Decision / Risk / Evidence 五类对象的 JSON Schema；
  • 8—10 种事件类型的 Schema；
  • 一个权威项目系统字段映射表；
  • 对象身份解析和状态重建规则；
  • Context Package 请求与响应 Schema；
  • 只读 API 原型和可重复验收测试。

最终目标不是再建一个知识库，而是让企业拥有一套可计算、可追溯、可治理的运行上下文基础设施，使企业 Agent 在正确的业务事实、正确的权限和正确的责任边界内开展工作。

B. 建议的第一批验收测试

  1. 同一源事件重复投递只形成一条有效业务事件。
  2. 迟到事件触发状态重算并保留前后版本。
  3. 跨系统对象映射保留所有源 ID。
  4. 模糊匹配不确定时进入待确认，不自动合并。
  5. 权威状态与会议推断冲突时显示冲突，不覆盖权威值。
  6. 超过新鲜度阈值的状态标记过期或待刷新。
  7. 未授权 Agent 无法生成含受限字段的上下文包。
  8. 上下文包撤销后阻断后续读取并使缓存失效。
  9. 高风险写操作未经审批不能执行。
  10. 每次 Agent 输出可追溯实际上下文包、来源和策略版本。
  11. 证据来源失效时触发依赖结论复核。
  12. 个人侧授权撤回后，企业侧按规则限制、删除或重算派生内容。
