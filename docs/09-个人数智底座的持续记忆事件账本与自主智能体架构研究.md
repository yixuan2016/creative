## 摘要：个人数智底座不是一个更大的个人知识库

个人知识库主要解决“资料放在哪里、如何检索”；个人数智底座需要进一步解决：

- AI 是否持续理解一个人的工作、生活、目标、关系和偏好？
- 它能否知道一件事从哪里来、是否被确认、后来有没有变化？
- 它能否记住长期有效的经验，同时识别过期、冲突和错误记忆？
- 它能否理解一个人的目标、承诺、任务和时间安排，并协助推进？
- 它能否在获得明确授权后调用工具，而不是只会给建议？
- 用户能否查看、纠正、撤回、导出和删除自己的信息？
- 个人 Agent 能否与企业 Agent 协作，同时不让企业获得个人完整记忆？

**核心判断：个人数智底座应当采用“事件账本 + 持续记忆 + 个人运行对象 + 任务上下文 + 受约束 Agent”的组合架构。**

事件账本记录发生、观察和确认的过程；持续记忆是从事件中形成、能够被纠正的认知视图；目标、任务和承诺是需要持续推进的运行对象；Context Package 是某次任务的最小必要信息集合；Personal Agent 则在明确的权限和风险边界内提出建议、准备动作或执行动作。

这五者不能合并成一个“AI 记忆库”。

### 本专题形成的成果

1. 个人数智底座七层参考架构。
2. 个人事件账本、持续记忆、个人目标/承诺和 Agent 动作四类核心数据契约。
3. 个人事件到记忆、目标和 Agent 动作的端到端示例。
4. 个人记忆生命周期、冲突处理、纠错、撤回和删除传播机制。
5. Personal Agent L0—L3 风险分级与审批机制。
6. 本地优先、多设备同步、个人—企业协同和隐私治理原则。
7. Python 参考原型、自动化合同测试和试点评估指标。

## 1. 研究目标与边界

### 1.1 研究目标

个人数智底座要让 AI 从“回答当前问题”逐步走向“理解个人上下文并协助推进目标”。

| 能力 | 要回答的问题 | 典型输出 |
|---|---|---|
| 多源感知 | 用户在什么渠道产生了哪些信息？ | 来源记录、采集会话、观察结果 |
| 事件理解 | 发生了什么？何时发生？涉及谁和什么对象？ | 个人事件 |
| 持续记忆 | 哪些信息值得长期保留？可信度如何？ | 记忆条目、事实候选、经验 |
| 个人运行管理 | 用户正在追求什么、承诺了什么、下一步做什么？ | 目标、任务、承诺、例程 |
| 个人认知 | 当前处境、冲突、风险和机会是什么？ | 任务上下文、解释、建议 |
| Agent 执行 | 哪些动作可以自动做，哪些必须询问用户？ | 动作提案、审批、执行结果 |
| 反馈学习 | 执行后发生了什么，哪些记忆需要更新？ | 新事件、纠错、记忆更新 |

### 1.2 非目标

本专题不主张：

- 把个人所有聊天、录音、文件和生活数据无差别汇总。
- 默认全天候录音、隐蔽采集或未经同意的旁观者录音。
- 把模型推断自动写成个人事实或正式承诺。
- 让 Agent 获得不受约束的账户、支付、通信、删除或对外发布权限。
- 让企业因为员工使用个人助理而获得个人完整记忆。
- 在首期就建设复杂的通用知识图谱、全量多模态模型或自主执行平台。
- 把个人数智底座等同于某个聊天产品的 Memory 功能。

**个人数智底座是用户控制的数据、记忆和行动系统；某个 AI 产品的 Memory 只是其中可能的一种记忆能力，不能替代事件账本、个人运行对象和授权执行体系。**

## 2. 核心概念：事件、记忆、意图、上下文和行动

### 2.1 五类对象各司其职

| 对象 | 本质 | 是否可被模型推断 | 是否直接代表事实 |
|---|---|---|---|
| Personal Event | 对发生、观察、表达或状态变化的记录 | 可以形成候选事件 | 不一定，必须有断言状态 |
| Memory Item | 从事件和用户确认中形成的可持续认知 | 可以，但必须标记来源和置信度 | 不一定，可能是候选、过期或争议记忆 |
| Intent Object | 目标、任务、承诺、例程或个人项目 | 可以建议候选 | 正式状态需要用户确认或权威系统同步 |
| Context Package | 为某个任务选出的最小必要信息视图 | 可以自动构建 | 不是新的事实源 |
| Agent Action | Agent 准备或执行的动作 | 可以规划 | 提案不等于批准，执行不等于成功 |

### 2.2 事件账本不是记忆库

事件账本记录“发生了什么、系统观察到了什么、用户确认了什么”。

记忆系统记录“哪些信息对未来理解和行动有帮助”。

例如：

- 事件：用户在会议中说“周五前整理风险清单”。
- 候选记忆：用户可能承担了整理风险清单的承诺。
- 确认记忆：用户确认这是一项自己的承诺。
- 个人运行对象：创建一项有截止时间和下一步行动的 Commitment。
- Agent 动作：建议创建提醒，等待用户批准。
- 执行事件：提醒创建成功后，写入一条新的事件并核验结果。

**原始事件不被记忆摘要替代；记忆不覆盖事件；行动结果重新成为事件。**

### 2.3 事件的四种时间

个人事件至少保留：

- occurred_at：事情发生的时间。
- observed_at：设备或系统感知到事情的时间。
- recorded_at：事件正式写入账本的时间。
- valid_time：某个事实或状态在现实中有效的时间范围。

语音转写可能在会议结束后才完成，补录的事件也可能晚于实际发生时间。不能用写入时间代替发生时间。

### 2.4 断言状态

建议统一使用：

- confirmed：用户或有权来源已确认。
- observed：系统观察到，但尚未确认语义。
- inferred：模型推断，必须显式标注。
- disputed：存在冲突或用户提出异议。
- rejected：用户或责任方明确否定。
- stale：曾经成立，但可能已经过期。
- unknown：当前无法判断。

禁止把模型置信度直接等同于事实可信度。置信度描述模型或规则对抽取结果的估计，确认状态描述责任主体是否确认，两者是不同维度。

## 3. 个人数智底座七层参考架构

### L1：多源感知与采集层

来源包括用户手动输入、日历、任务、文档、邮件、即时沟通、会议、语音设备、手机和电脑等。

设计要求：

- 用户明确启用采集来源和用途。
- 对持续录音、设备采集和连接器同步提供可见状态、暂停和撤销入口。
- 尽可能记录来源 ID、版本、采集时间和授权引用。
- 原始音频、视频和文件存入受控来源存储，不直接塞进事件 payload。
- 先支持可靠的少量来源，不追求首期接入所有应用。

### L2：原始来源与个人事件账本层

分为两个不同存储：

1. **Source Vault**：保存用户授权保留的原始文件、音频、消息或内容快照。
2. **Personal Event Ledger**：保存标准事件、来源引用、时间、主体、对象、断言状态和生命周期。

事件账本建议采用追加式记录。纠错通过新增更正事件表达，不静默改写历史。追加式不意味着永远不能删除：用户删除请求、保留期限和适用规则仍须生效；必要时删除原始内容及派生副本，只保留合规所需的最小删除标记。

### L3：身份、时间与语义解析层

负责：

- 识别用户本人、联系人、角色、组织和 Agent。
- 将不同应用中的同一项目、任务或联系人关联为候选对象。
- 解析时间、时区、周期和相对时间。
- 保留 candidate、unresolved 和 conflict，不因名称相似就合并。
- 将来源术语映射到 ADS-WORK-08 共同本体和个人命名空间。

### L4：持续记忆与知识视图层

将事件转换为不同类型的记忆：

| 记忆类型 | 典型内容 | 生命周期特点 |
|---|---|---|
| Episodic 情景记忆 | 某次会议、一次经历、一个具体事件 | 与时间和来源紧密关联 |
| Semantic 语义记忆 | 人物、项目、概念、稳定事实 | 需要持续核验和冲突处理 |
| Procedural 程序记忆 | 用户如何完成某类工作 | 需要经验验证和版本更新 |
| Preference 偏好记忆 | 用户明确表达的偏好 | 允许用户随时纠正或撤回 |
| Goal / Commitment | 用户目标、承诺和责任 | 与截止时间和进展关联 |
| Relationship 关系记忆 | 人与人、人与项目的关系 | 必须有来源、范围和有效时间 |
| Routine 例程记忆 | 用户反复进行的固定活动 | 不应把偶然行为误判为稳定习惯 |
| Project Context 项目记忆 | 项目背景、关键决策和当前问题 | 需要区分个人视角与企业权威状态 |

记忆是可重建的认知视图，不是不可更改的“模型内心事实”。

### L5：个人运行模型层

持续管理：

- Goals：长期或阶段性目标。
- Commitments：用户对自己或他人的承诺。
- Tasks：可执行的工作单元。
- Projects：个人正在推进的项目。
- Routines：周期性例程。
- Dependencies：目标和任务之间的依赖。
- Next Actions：下一步行动。

意图对象必须区分“用户确认”“权威系统同步”和“模型推断候选”。模型推断的任务不能直接变成已确认承诺。

### L6：个人认知与 Context Plane

围绕某次请求、提醒或目标，生成任务级 Context Package：

- 当前目标和任务。
- 相关事件与记忆。
- 时间线和关键变化。
- 已确认事实与推断。
- 冲突、未知和过期信息。
- 可用工具和禁止动作。
- 授权、有效期和策略版本。

上下文不是“把所有记忆都塞给模型”，而是按目的、时间、对象和权限做最小必要选择。

### L7：Personal Agent 与执行层

Agent 负责理解目标、拆解步骤、准备动作、调用工具和验证结果。

必须具备：

- 明确任务目的和范围。
- 工具能力白名单。
- 禁止动作列表。
- 风险等级和审批要求。
- 幂等键、执行超时和结果验证。
- 失败、部分成功和撤销处理。
- 执行结果写回事件账本。

### 横向治理控制面

贯穿七层：身份、授权、隐私分类、加密、留存、撤回、审计、版本、可观测性、用户控制和数据可携带性。

## 4. 持续记忆的生成与维护机制

### 4.1 从事件到记忆的七步流程

1. **接收**：来源进入 Source Vault 或事件接入层。
2. **解析**：转写、OCR、结构化抽取或人工录入。
3. **候选化**：形成事件候选和记忆候选，标注来源、时间和置信度。
4. **关联**：连接人物、项目、任务、目标和历史事件。
5. **确认**：根据影响程度决定自动接受、用户确认或人工审核。
6. **整合**：形成或更新记忆视图，不覆盖历史来源。
7. **复核**：发现冲突、过期或用户纠错时，更新记忆状态并保留依据。

### 4.2 哪些记忆可以自动形成？

| 类型 | 建议策略 |
|---|---|
| 用户明确录入的事实 | 可直接记录为用户声明，但保留来源和时间 |
| 日历/任务等权威系统状态 | 可同步状态，注明源系统和同步时间 |
| 会议转写中的候选任务 | 先形成候选，确认责任人与期限后再成为正式承诺 |
| 用户反复表达的偏好 | 先形成候选，询问用户是否保存为长期偏好 |
| 模型推断的人际关系或敏感属性 | 不自动固化；默认不生成或必须严格审核 |
| 一次偶然行为 | 不应直接推断为稳定习惯 |
| 个人生活安排 | 仅在个人侧按用户授权管理，默认不向企业投影 |

### 4.3 记忆生命周期

candidate → active → stale / disputed → superseded / withdrawn / expired → archived

- Candidate：模型或规则刚生成，尚未充分确认。
- Active：可在授权范围内被检索使用。
- Stale：可能过期，需要重新核验。
- Disputed：存在冲突或用户提出异议。
- Superseded：被新版本替代，保留必要历史关系。
- Withdrawn：用户撤回，不再进入普通检索。
- Expired：超过有效期。
- Archived：按策略归档，不等于继续参与实时决策。

### 4.4 记忆冲突处理

不要采用“最新一条自动覆盖”或“模型置信度最高者胜出”。

建议流程：

1. 为每条记忆保留来源事件和有效时间。
2. 判断冲突是时间变化、来源差异、身份误配还是模型误判。
3. 若来自权威系统，按对象类型使用权威字段规则。
4. 若是个人偏好或个人判断，以用户确认优先。
5. 无法判断时并列保存并标记 disputed。
6. 只有在用户确认或策略允许时，才建立 supersedes 关系。

### 4.5 记忆衰减与复核

不同记忆不能采用统一的“时间越久越不可信”规则：

- 固定身份信息：低频复核，但允许用户随时更正。
- 项目状态：随项目进展和权威系统变化快速更新。
- 偏好：保留历史版本，观察变化后询问用户。
- 目标和承诺：接近截止时间时提高提醒优先级，完成后转入历史状态。
- 程序性经验：通过重复任务结果和评测验证，不因一次成功就认定有效。

记忆衰减只能影响检索优先级或触发复核，不能无依据地篡改原始事件。

## 5. 个人运行模型：让记忆真正服务于生活和工作

### 5.1 为什么不能只有 Memory Item？

如果系统只保存“用户承诺周五完成风险清单”，但没有截止时间、下一步行动、依赖和完成状态，AI 仍然无法持续协助。

因此需要独立的 Personal Intent Object。

| 类型 | 核心问题 | 必要信息 |
|---|---|---|
| Goal | 希望达到什么状态？ | 目标、衡量方式、期限、进展 |
| Commitment | 向谁承诺了什么？ | 承诺主体、对象、期限、确认依据 |
| Task | 下一步要做什么？ | 动作、负责人、状态、完成条件 |
| Routine | 哪些事情需要周期性发生？ | 周期、触发条件、例外和暂停 |
| Project | 正在持续推进什么？ | 目标、范围、阶段、依赖和成果 |

### 5.2 目标—承诺—任务的关系

- 一个 Goal 可以关联多个 Project。
- 一个 Project 可以拆分多个 Task。
- 一个 Commitment 可以对应一个或多个 Task。
- Task 可以依赖其他 Task。
- 完成事件更新 Task 状态，但不能自动证明整个 Goal 已完成。
- 用户可以暂停、调整或取消目标，不应被 Agent 的旧计划绑架。

### 5.3 个人时间线

个人时间线不只是日历，而是将事件、目标、承诺、任务和结果关联起来：

过去发生了什么 → 现在处于什么状态 → 下一步要做什么 → 未来可能发生什么

它可以支持：

- 每日个人工作与生活回顾。
- 承诺追踪和遗漏提醒。
- 项目与个人目标的关联。
- 时间冲突与资源约束提示。
- 阶段性复盘和经验沉淀。

## 6. Personal Agent：从回答问题走向受约束的行动

### 6.1 Personal Agent 的任务闭环

Trigger / User Request → Task Contract → Context Builder → Planner → Policy Gate → Approval → Tool Execution → Verification → Event Write-back → Memory Refresh

每一步都要能说明：

- 为什么触发？
- 使用了哪些记忆和来源？
- 允许调用什么能力？
- 不能做什么？
- 是否需要用户批准？
- 执行是否真的成功？
- 结果是否需要用户确认？

### 6.2 动作风险等级

| 等级 | 行为 | 默认策略 |
|---|---|---|
| L0 | 只读检索、总结、状态查询 | 在授权范围内可自动进行 |
| L1 | 生成草稿、建议、个人提醒草案 | 自动准备，用户可检查 |
| L2 | 修改个人日历、任务、文件或其他可逆状态 | 执行前要求明确确认 |
| L3 | 对外发送、支付、删除、公开发布、修改权限等高影响动作 | 每次动作明确确认；必要时增加额外验证或双重审批 |

风险分级要根据实际副作用判断，而不是根据工具名称判断。创建一个私人草稿和发送一封对外邮件，不属于同一风险等级。

### 6.3 审批绑定具体动作

用户批准的不是一句模糊的“你帮我处理”，而是一个明确动作计划：

- 目标对象。
- 具体动作和字段。
- 使用的工具。
- 预期副作用。
- 计划版本或哈希。
- 有效期。
- 回滚能力。
- 失败处理。

若计划发生实质变化，应重新请求批准。过期批准不能自动沿用。

### 6.4 Agent 结果必须验证

| 执行状态 | 说明 |
|---|---|
| not_started | 尚未执行 |
| queued / running | 已排队或正在执行 |
| succeeded | 工具报告成功，但仍需核验 |
| failed | 执行失败 |
| partial | 部分成功 |
| cancelled | 用户或策略取消 |

结果核验至少检查目标对象、实际状态和副作用。不能仅凭工具返回“成功”就认定任务完成。

### 6.5 个人 Agent 与企业 Agent

个人 Agent 代表个人利益，企业 Agent 代表企业业务责任。两者不能共享一个无限制的记忆空间。

协作方式：

1. 个人 Agent 理解个人上下文和用户意图。
2. 用户选择一项与企业工作有关的内容。
3. 个人 Agent 形成最小必要的企业协作包。
4. 用户明确授权目标企业、用途、字段和接收者。
5. 企业侧生成独立事件 ID 和业务记录。
6. 企业 Agent 只读取企业侧被授权的上下文。
7. 企业处理结果可以通过明确的业务反馈回到个人侧，但不因此获得个人原始记忆读取权。

这与 ADS-WORK-08 的语义投影原则保持一致。

## 7. 多源感知、设备与多端同步

### 7.1 来源接入优先级

建议首期按“可靠性、使用频率、用户价值、接入成本和隐私风险”排序，而不是追求来源数量。

| 来源 | 首期建议 | 主要价值 |
|---|---|---|
| 用户手动输入与快速记录 | P0 | 最明确的用户意图和纠错入口 |
| 日历与任务 | P0 | 目标、承诺、时间和状态 |
| 文档与笔记 | P1 | 项目背景、经验和知识 |
| 即时沟通与邮件 | P1 | 协作事件和承诺线索 |
| 会议语音与转写 | P1/P2 | 多人讨论、决定候选和行动项 |
| 手机/电脑活动信号 | P2 | 用户授权下补充情境 |
| 专用录音设备 | P2 | 作为可选入口，不成为唯一入口 |

### 7.2 语音采集产品要求

针对录音卡或自研语音终端，不能只解决“能录音”，还要解决：

- 采集状态是否清晰可见。
- 是否可以一键暂停和停止。
- 电量、存储、网络和同步状态是否可知。
- 设备离线时如何缓存和补传。
- 是否支持用户选择录音、转写和删除。
- 多人场景下如何尊重参与者告知和同意要求。
- 原始音频保留多久，何时只保留转写或事件。
- 设备丢失后如何远程撤销访问和保护密钥。
- 用户忘记携带或忘记启动时，是否能通过其他已授权来源补足上下文。

**不能把隐蔽、默认开启的持续录音作为个人数智底座的前提。** 用户控制、透明提示和来源替代能力，比单纯追求录音覆盖率更重要。

### 7.3 本地优先与多端同步

建议采用“本地优先、加密同步、用户可控”的策略：

- 设备本地保存待同步事件和必要缓存。
- 每个用户拥有独立加密边界和密钥管理。
- 多设备同步传输加密数据，并保留版本与冲突记录。
- 云端同步不代表服务端默认可读取全部明文。
- 用户可查看设备列表、撤销设备、暂停同步和导出数据。
- 离线事件补传时保留原始发生时间和真实写入时间。
- 删除请求需要传播到缓存、索引、向量库、摘要和派生记忆。

具体加密算法、密钥托管和端侧模型方案，需要安全架构专项评审后确定。

## 8. 个人数据治理与安全边界

### 8.1 默认个人私有

个人事件、记忆和意图对象默认 personal_only。

个人侧与企业侧分别使用：

- 独立的实例 ID。
- 独立的访问控制和加密密钥。
- 独立的数据生命周期。
- 独立的审计和授权记录。
- 明确的投影或导出流程。

共享共同本体不等于共享个人实例数据。

### 8.2 目的绑定授权

任何跨边界共享都需要明确：

- 谁发起共享？
- 为了什么目的？
- 分享给哪个企业或接收者？
- 哪些对象和字段可以共享？
- 哪些字段必须排除？
- 授权有效期多久？
- 是否允许下游再使用？
- 如何撤回和处理派生数据？

### 8.3 删除、撤回与“不要再记住”

删除不是只从向量库中删一条记录。

建议建立依赖关系：

Source Record → Event → Memory Item → Summary / Index / Context Cache → Agent Output

用户提出撤回或删除时：

1. 停止相关数据新的检索、推断和投影。
2. 找到所有依赖该来源的记忆、摘要、索引和缓存。
3. 按用户请求和适用规则删除、限制或替换相应内容。
4. 防止后续从仍保留的来源自动重新生成已删除记忆。
5. 对确需保留的最小审计标记设定独立保留规则。
6. 向用户说明处理范围和未能删除的例外。

### 8.4 关键威胁与控制

| 风险 | 控制措施 |
|---|---|
| 未授权采集 | 显式启用、可见状态、暂停和撤销 |
| 设备丢失 | 本地加密、密钥隔离、设备撤销 |
| 记忆幻觉 | 来源引用、断言状态、人工确认 |
| 身份误合并 | 候选解析、权威 ID、冲突保留 |
| 企业越权读取 | 个人/企业分区、目的绑定投影 |
| 提示注入或恶意来源内容 | 来源内容视为不可信数据，不执行其中的指令 |
| Agent 越权执行 | 能力白名单、风险分级、审批门禁 |
| 重复执行 | 幂等键、动作计划哈希、执行状态机 |
| 删除后重新生成 | 派生链追踪、抑制标记和删除传播 |
| 多端冲突 | 版本化、冲突并列和用户裁决 |

## 9. 工程组件与数据契约

### 9.1 建议的逻辑组件

| 组件 | 职责 | 首期是否需要独立服务 |
|---|---|---|
| Capture Gateway | 连接器、手动录入、设备接入 | 否，可模块化实现 |
| Source Vault | 原始来源受控存储 | 需要独立安全边界 |
| Personal Event Ledger | 事件追加、去重、查询和纠错 | 逻辑独立，物理可先共库 |
| Identity & Time Resolver | 人物、对象、时间解析 | 否 |
| Memory Compiler | 事件到记忆的抽取、合并和复核 | 否 |
| Personal Memory Store | 记忆条目、状态和来源索引 | 逻辑独立 |
| Intent Manager | 目标、任务、承诺和例程 | 否 |
| Context Builder | 任务级上下文生成 | 可复用 ADS Context 设计 |
| Personal Agent Runtime | 规划、工具调用、审批和反馈 | 与企业 Agent Runtime 共享控制原则，但权限隔离 |
| Policy & Audit | 授权、风险、留存、撤回和审计 | 逻辑上必须独立可验证 |

### 9.2 新增数据契约

| 文件 | 职责 |
|---|---|
| [个人事件账本 Schema](../schemas/ads-personal-event-ledger-v0.1.schema.json) | 个人事件标准信封 |
| [个人记忆 Schema](../schemas/ads-personal-memory-item-v0.1.schema.json) | 记忆条目、来源和生命周期 |
| [个人意图对象 Schema](../schemas/ads-personal-intent-object-v0.1.schema.json) | 目标、任务、承诺、例程和项目 |

这些契约复用 ADS-WORK-08 的本体版本与个人命名空间，复用 ADS-WORK-06 的 Task Envelope 和 ADS-WORK-04 的上下文思想；但个人实例不直接复用企业租户 ID、企业权限或企业记忆存储。

### 9.3 推荐存储分层

首期不需要强制引入图数据库：

- 关系数据库：事件元数据、记忆、目标、承诺、授权和状态。
- 对象存储：用户授权保留的音频、文件和多媒体来源。
- 全文索引：对可检索内容建立受权限过滤的索引。
- 向量索引：作为语义检索辅助，不是事实主存储。
- 事件日志：支持追加、重放、审计和派生视图重建。

无论采用何种存储，原始来源、事件、记忆和任务上下文都应有独立身份和生命周期。

## 10. 最小可运行原型与示例

### 10.1 原型范围

本专题原型验证：

1. 个人事件追加与幂等。
2. 模型派生记忆默认进入候选状态。
3. 只有记忆所有者可以确认、纠正和撤回。
4. 敏感记忆默认不进入普通上下文。
5. 用户请求遗忘来源后，相关派生记忆不再被检索或重新生成。
6. L2/L3 Agent 动作在明确批准前不能标记为执行成功。
7. 执行结果保留核验状态。

原型是内存逻辑验证，不连接真实设备、账户或第三方工具，不构成生产级存储和安全实现。

### 10.2 示例过程

用户手动记录：

> 周五前整理项目风险清单并确认责任人。

系统执行：

1. 记录一条 personal.work.commitment_created 事件。
2. 形成一条来源可追溯的承诺记忆。
3. 由用户确认后建立 Personal Commitment。
4. Agent 建议创建提醒。
5. 动作进入 L2 pending approval。
6. 用户批准后，工具才允许执行。
7. 工具结果经过核验，新增一条执行结果事件。
8. 记忆和承诺状态根据新事件更新。

另一条个人生活安排保持 personal_only，不进入企业上下文。

## 11. 试点设计与评估指标

### 11.1 试点范围

建议选择一个愿意参与、工作节奏明确的个人用户小组，先运行 2—4 周。首期不追求全量采集，优先验证用户是否愿意持续使用、记忆是否可信、提醒是否有帮助。

建议只接入：

- 用户手动记录。
- 日历或个人任务中的一个来源。
- 一个文档/笔记来源。
- 可选的会议转写来源，且必须由用户主动启用。

### 11.2 评估指标

| 维度 | 指标 | 解释 |
|---|---|---|
| 采集质量 | 来源覆盖率 | 用户授权且实际可接入的来源覆盖 |
| 事件质量 | Event Precision / Recall | 按事件类型评估抽取质量 |
| 时间质量 | Temporal Accuracy | 发生、观察、记录和有效时间准确度 |
| 关联质量 | Entity Resolution Accuracy | 人物、项目和对象关联准确度 |
| 记忆质量 | Memory Correctness | 用户抽查记忆是否准确 |
| 记忆时效 | Stale Memory Rate | 过期或失效记忆比例 |
| 检索价值 | Retrieval Utility | 是否真正帮助完成当前任务 |
| 纠错成本 | Correction Burden | 用户纠正和管理记忆的负担 |
| 隐私安全 | Unauthorized Projection | 未授权共享次数，目标为零 |
| Agent 安全 | Approval Bypass | 未审批执行 L2/L3 动作次数，目标为零 |
| 执行质量 | Verified Action Success | 经核验的成功执行比例 |
| 用户信任 | User Trust / Control | 用户是否理解并信任系统控制方式 |

### 11.3 试点验收原则

- 所有保留的记忆都能追溯到来源事件或用户明确声明。
- 所有候选推断都能与已确认内容区分。
- 用户纠错、撤回和删除能够传播到派生视图。
- 个人生活信息不因员工身份自动进入企业。
- L2/L3 动作审批绕过次数为零。
- 用户能够查看、导出和控制个人记忆。
- 不以采集时长或记录数量作为主要成功指标，重点衡量上下文帮助和用户控制感。

## 12. 实施路线

| 阶段 | 建议周期 | 交付内容 | Go / No-Go |
|---|---:|---|---|
| P0 语义与治理冻结 | 1—2 周 | 事件、记忆、意图和权限契约 | 数据边界与用户控制可解释 |
| P1 事件账本 MVP | 2—3 周 | 手动录入、来源引用、时间线和导出 | 事件可追溯、可纠错 |
| P2 记忆引擎 MVP | 2—3 周 | 候选记忆、确认、冲突、过期和撤回 | 记忆正确性可评测 |
| P3 个人运行模型 | 2 周 | 目标、承诺、任务和下一步行动 | 状态与用户确认一致 |
| P4 只读/草稿 Agent | 2 周 | Context Package、任务规划和草稿生成 | 不越权、不误报完成 |
| P5 审批与受控执行 | 2—4 周 | L2/L3 审批、幂等、核验和回写 | 审批门禁和回滚可验证 |
| P6 多端与企业协同 | 另行评审 | 多设备同步、个人到企业投影 | 独立安全与隐私评审通过 |

周期为规划估算，不能替代实际资源和安全评审。

## 13. 建议冻结的架构决策（ADR）

1. 个人数智底座以个人为主体，而不是以员工身份为主体。
2. 个人事件账本、记忆、意图对象和 Context Package 分离。
3. 事件采用追加式纠错，原始来源和历史事件可追溯；删除权仍须落实。
4. 记忆默认从候选开始，模型不能静默把推断升级为事实。
5. 每条长期记忆必须有来源、置信度、有效性和用户控制入口。
6. 目标、承诺和任务是独立运行对象，不是自然语言摘要。
7. 个人数据默认 personal_only，跨边界必须目的绑定和最小必要授权。
8. 个人 Agent 使用能力白名单、风险分级和审批门禁。
9. L2/L3 动作未获得有效审批前禁止执行。
10. Agent 执行结果必须核验并写回事件账本。
11. 多设备同步采用本地优先和加密边界，具体密钥方案专项评审。
12. 个人记忆的删除、撤回和抑制必须覆盖派生记忆、索引、缓存和后续重建。

## 14. 本专题结论

个人数智底座真正的核心，不是“记住更多内容”，而是形成一套用户可理解、可控制、可纠错、可持续运行的个人上下文系统。

- 事件账本解决可追溯。
- 持续记忆解决跨时间理解。
- 目标和承诺解决持续推进。
- Context Package 解决任务所需信息组织。
- Personal Agent 解决受约束的行动。
- 治理控制面解决用户自主权和跨边界安全。

**个人数智底座的价值，不在于让 AI 无所不知，而在于让 AI 在用户允许的范围内，可靠地理解重要上下文，并帮助用户把重要事情持续推进。**

重点研究：

1. 个人助理 OS 的用户入口和核心工作台。
2. 手机、电脑、会议、语音终端和应用连接器如何协同。
3. 主动提醒、每日回顾、目标管理和个人时间线的产品体验。
4. 用户如何查看、确认、纠正和删除 AI 记忆。
5. 本地优先、多端同步和离线采集的产品方案。
6. 个人 Agent 如何从只读、草稿走向经批准的执行。
7. 个人产品与 ADS 企业数智底座如何通过授权投影协同。
