## 摘要：让 AI 理解工作，不是把所有信息放进一个知识库

ADS 前七个专题已经形成一条连续路径：多源工作感知、个人与企业数智资产协同、企业工作上下文、统一数据模型与运行认知引擎、标准契约与原型、Agent 协同执行，以及能力资产化。接下来需要回答一个更基础的问题：

**当个人、企业和不同业务领域都在记录自己的工作时，AI 如何知道这些信息分别意味着什么？同一个任务、事件、决策或对象，在不同系统、不同岗位和不同责任边界下，如何保持语义一致，又不混淆数据权属？**

本专题提出：建设一套分层、可扩展、带治理边界的 ADS 工作本体体系。它不是一张全企业通用的大图，也不是把所有个人生活信息企业化，而是由共同核心本体、个人上下文本体、企业工作本体和业务领域本体构成；通过事件类型、对象类型、关系谓词、时间语义、证据规则和映射规则，将多源信号转化为可理解的工作上下文。

### 核心判断

1. **工作事件是理解真实工作过程的关键观测单元，但不是唯一实体。** 事件需要关联行动主体、业务对象、任务、活动、决策、状态、证据和时间。
2. **个人数智底座需要理解“个人的工作与生活”，而不仅是员工工作记录。** 个人生活事件应是个人上下文本体中的一等对象，默认仅由个人控制；不能因为一个人具有员工身份，就将生活上下文并入企业数据。
3. **个人工作事件与企业工作事件不能简单视为同一条记录。** 同一现实发生可以在个人侧形成完整的个人记忆，在企业侧形成经过授权、最小必要和业务确认的投影记录，两者保留受控的派生关系，而不是复制全部内容。
4. **本体、数据 Schema、知识图谱和事件流各自解决不同问题。** 本体定义概念及关系语义；Schema 约束数据形状；事件流记录发生；图存储只是可选实现方式。
5. **三级数智底座是数据与责任边界，不是三个本体层级。** 个人、企业和业务领域中心可以共享语义定义，但不因此共享全部实例数据。
6. **本体映射必须允许不确定、冲突和未映射。** 不应为了统一而强行合并同名对象、同义词或不兼容的业务状态。
7. **能力资产需要绑定任务家族和领域语义。** ADS-WORK-07 的 Capability Asset 应引用本体版本、任务类型、输入输出概念和适用范围，才能被 Agent 正确发现与调用。

### 本专题要交付的标准

- 五层工作本体逻辑模型；
- 个人工作与生活上下文、企业工作本体、领域本体的分层边界；
- 核心概念、对象、事件类型和关系谓词目录；
- 工作事件与个人事件的时间、来源、状态和证据语义；
- 个人事件向企业业务事件投影的授权规则；
- 本体版本、映射、扩展和冲突治理机制；
- 与 ADS-WORK-04 Work Context Schema、ADS-WORK-06 Task Envelope、ADS-WORK-07 Capability Manifest 的兼容方式；
- 项目交付领域的最小试点和评测方法。

> **一句话定位：个人数智底座理解一个人的工作与生活，企业数智底座理解企业业务如何运行，业务领域中心数智底座维护共同语义与跨域协同规则；ADS 通过本体和事件映射把它们连接起来，但不把它们变成一个无边界的数据池。**

## 1. 为什么需要工作本体

### 1.1 只有数据接入，还不等于 AI 理解了工作

一个员工可能在一天内经历：查看项目任务、参加会议、接收口头交代、分析客户问题、修改文档、等待同事反馈、做出判断、创建行动项、处理个人事务。不同系统分别记录其中一部分：

- 日历记录时间安排；
- 即时通讯记录消息；
- 会议系统记录音频、转写和纪要；
- 项目系统记录任务、负责人和状态；
- 文档系统记录内容与版本；
- 业务系统记录正式客户、订单、产品或项目状态；
- 个人助理记录个人目标、工作线索、回顾和提醒。

如果 AI 只是把这些内容汇总或向量化，它仍然可能不知道：

- 某句话是背景说明、建议、承诺，还是已经批准的决定；
- 一项任务属于哪个项目、由谁负责、是否已经创建到正式系统；
- 两个系统中的“客户 A”是不是同一个业务对象；
- 一次会议中的讨论是否真的改变了业务状态；
- 某个个人提醒是否应该进入企业任务系统；
- 某个生活事件是否与工作无关、必须留在个人边界；
- 一项能力资产适用于什么任务、依赖什么领域语义。

本体的价值，是给这些信息提供共同的概念、关系和约束，让 AI 不只是识别文字，而是能够理解文字所指向的工作世界。

### 1.2 本体不等于知识图谱

| 概念 | 解决的问题 | ADS 中的职责 |
|---|---|---|
| 本体 Ontology | 世界里有哪些概念、概念如何定义、关系有什么含义 | 定义共同语义、领域语义、约束和版本 |
| 数据 Schema | 一条记录有哪些字段、字段类型和必填约束 | 约束 WorkEvent、BusinessObject、ContextPackage 等数据结构 |
| 事件流 Event Stream | 何时发生了什么变化 | 追加记录工作事件，支持顺序、重放和审计 |
| 知识图谱 Knowledge Graph | 如何存储和查询实体及其关系 | 可作为关系密集场景的实现方式之一 |
| 主数据 MDM | 哪个客户、产品、项目是权威对象 | 维护权威身份、主数据与源系统映射 |
| 工作上下文 Context | 对某项任务而言，哪些事实、事件和关系相关 | 按任务和授权组织最小必要信息 |
| 能力资产 Capability Asset | 如何完成一类可重复任务 | 引用本体概念、规则、流程、证据和评测 |

**本体定义语义，Schema 定义结构，事件流记录变化，主数据解决身份，Context 组织任务所需信息。** 这些能力可以互相引用，但不能互相替代。

### 1.3 本专题的核心设计问题

1. 哪些概念应成为个人、企业和业务领域共同理解的核心概念？
2. 工作事件、生活事件、活动、任务、承诺、决策和状态之间如何区分？
3. 个人工作记忆如何映射为企业可用的业务记录？
4. 个人生活上下文如何被个人 AI 理解，同时避免企业越权读取？
5. 不同企业、部门、系统和岗位的概念如何映射，而不强行统一？
6. 本体变化后，历史事件、能力资产和 Agent 如何保持兼容？
7. 如何评估事件抽取、对象关联、关系判断和语义映射的质量？

## 2. ADS 三级数智底座与本体边界

### 2.1 三个责任层次，不是三个数据副本

| 层次 | 本体责任 | 实例数据责任 | 默认访问边界 |
|---|---|---|---|
| 个人数智底座 | 个人上下文本体及个人化语义映射 | 个人工作事件、生活事件、目标、承诺、个人对象和个人记忆 | 个人自主控制；默认个人私有 |
| 企业数智底座 | 企业工作本体、企业对象类型和业务规则 | 企业项目、客户、产品、任务、决策、风险、证据和协同记录 | 企业依照业务目的、制度和授权治理 |
| 业务领域中心数智底座 | ADS 共同核心本体、领域语义标准、映射规范和联邦目录 | 原则上维护语义元数据、目录、版本、映射和跨域任务审计；不默认集中保存企业或个人原始事件 | 按任务、主体、目的和授权进行联邦协同 |

三级底座可以共享**本体定义**，但不意味着共享**本体实例**。例如，所有参与方都可以理解 Project、Task、Decision 的概念，但某个项目的具体任务、客户信息和会议事件仍由相应责任主体管理。

### 2.2 个人数智底座应该覆盖工作与生活

个人数智底座的目标不是建立一个“员工工作档案”，而是帮助个人理解自己的完整上下文。建议将个人上下文本体分为：

- **个人工作上下文**：工作事件、项目参与、会议、任务、承诺、决策、协作关系、工作成果和经验。
- **个人生活上下文**：个人日程、生活安排、个人承诺、家庭事务、出行安排、个人目标和日常活动等。
- **个人学习与成长上下文**：学习活动、技能成长、反思、目标进展和个人知识。
- **个人资源与偏好上下文**：个人可支配时间、工具偏好、工作习惯和可由本人管理的资源信息。

这些是个人 AI 的理解维度，不是企业必须采集的字段清单。具体类别应由用户控制、可关闭、可纠正、可删除或按规则到期。

**关键边界：**
- 个人生活事件默认不进入企业数智底座。
- 个人工作事件也不自动等于企业正式业务事件。
- 个人记录中包含企业信息，不代表个人可以绕过企业数据规则对外共享。
- 企业需要的工作信息，应通过明确业务目的、授权、最小必要投影和业务责任人确认形成企业侧记录。
- 企业不能因为员工使用了个人 AI，就默认获得其完整个人记忆。

## 3. 五层工作本体逻辑模型

建议将工作本体组织为五个逻辑层，治理与权限作为贯穿五层的横向控制面。

~~~mermaid
flowchart TB
  L5["L5 能力与执行层<br/>Capability · Skill · Rule · Workflow · Agent · Action"]
  L4["L4 上下文与决策层<br/>Context · Goal · Constraint · Decision · Risk · Uncertainty"]
  L3["L3 语义对象与状态层<br/>Person · Organization · Project · Customer · Product · State · Relation"]
  L2["L2 事件与活动层<br/>Event · Activity · Task · Commitment · Interaction · Outcome"]
  L1["L1 信号与观察层<br/>Source · Observation · Capture · Document · Message · Audio · System Record"]
  G["横向治理：Identity · Authorization · Provenance · Time · Classification · Policy · Version · Audit"]
  L1 --> L2 --> L3 --> L4 --> L5
  G -.governs.-> L1
  G -.governs.-> L2
  G -.governs.-> L3
  G -.governs.-> L4
  G -.governs.-> L5
~~~

### 3.1 L1：信号与观察层 Signal & Observation

描述系统从何处观察到信息，以及原始材料如何被处理。

核心概念：
- SourceRecord：源记录，如消息、文件、会议、日历、业务系统记录。
- Observation：系统对某个信号的观察结果。
- CaptureSession：采集或连接器运行过程。
- Modality：文本、音频、图像、视频、结构化 API、人工输入等模态。
- ExtractionRun：转写、OCR、实体识别、事件抽取等处理任务。

这一层回答“系统看到了什么、从哪里看到、何时看到、经过什么处理”，不直接回答“业务事实是什么”。

### 3.2 L2：事件与活动层 Event & Activity

描述现实世界发生了什么，以及人或系统正在做什么。

| 概念 | 定义 | 例子 |
|---|---|---|
| Event | 某一时点或时间区间内发生的变化或事实候选 | 项目任务被创建、客户提出问题 |
| Activity | 为实现某个目的而持续进行的一组行动 | 项目评审、问题排查、方案设计 |
| Task | 有预期结果、责任主体和完成条件的工作单元 | 完成风险清单核验 |
| Commitment | 某主体对未来行动或结果作出的承诺 | 某人承诺周五前提交材料 |
| Interaction | 两个或多个主体之间的交互 | 会议、沟通、评审 |
| Outcome | 活动或任务产生的结果 | 报告提交、问题关闭 |
| DecisionEvent | 决策被提出、讨论、确认或撤销的事件 | 项目范围调整获批 |

**重要区别：事件不是任务，任务不是活动，活动也不等于结果。** 一次会议可以包含多个事件、决策候选和行动项；行动项只有在责任、目标和确认条件足够明确时，才成为正式任务。

### 3.3 L3：语义对象与状态层 Semantic Object & State

将事件关联到稳定的对象身份和业务语义。

核心概念：
- Actor：人、角色、Agent 或系统。
- Organization / OrganizationUnit：组织及组织单元。
- BusinessObject：企业业务对象，如项目、客户、产品、订单、合同、流程、工单。
- PersonalObject：个人控制的对象，如个人日程项、个人目标、个人项目引用。
- Relation：对象之间有类型、有方向、有时间范围的关系。
- StateAssertion：某个主体在某个时间对对象状态作出的断言。
- IdentityMapping：不同系统 ID、别名和规范对象之间的映射。

对象身份必须有命名空间和责任边界。同名项目不自动是同一项目；同一个人可能在不同组织中承担不同角色；个人助理中的“项目 A”只有经过对象解析，才能与企业项目主数据建立关系。

### 3.4 L4：上下文与决策层 Context & Decision

将对象、事件、状态、关系和证据组织为可用于特定任务的上下文。

核心概念：
- ContextPackage：围绕任务或对象构建的最小必要上下文包。
- Goal：期望达到的目标。
- Constraint：时间、预算、权限、质量或资源约束。
- DecisionRecord：决策内容、参与主体、依据、备选方案、审批和生效范围。
- Risk / Issue：风险与已发生问题。
- Dependency：任务、对象或资源之间的依赖。
- Uncertainty：未知、冲突、过期或证据不足。
- Exception：偏离标准流程、需要人工处理的情况。

这一层回答“对当前任务而言，哪些事实、变化、约束、证据和未知最重要”。

### 3.5 L5：能力与执行层 Capability & Execution

将经过验证的工作方法连接到 Agent 和执行流程。

核心概念：
- CapabilityAsset：能力资产，引用 ADS-WORK-07 的 Manifest。
- Skill / Rule / Playbook / Workflow：可复用能力组件。
- Agent：在明确角色和权限下执行任务的单元。
- Tool / Action：查询或操作外部系统的接口与动作。
- Approval：对具体动作、对象和参数的审批。
- AgentRun / TaskRun：执行实例和任务运行记录。
- Feedback / Evaluation：人工反馈、结果评测和能力改进依据。

能力资产必须声明依赖的本体版本和任务家族。Agent 不能仅凭“语义相似”就调用一个未经验证或不适用的能力。

### 3.6 横向治理层 Governance

五层均必须携带或引用：
- 身份与主体解析；
- 授权、目的限制和最小权限；
- 来源、证据、转换过程和审计；
- 发生时间、观察时间、记录时间和有效时间；
- 数据分类、保留期限和删除 / 撤回规则；
- 本体、Schema、映射和规则版本；
- 置信度、确认状态、冲突与未知；
- 人工确认、升级和责任归属。

## 4. 核心概念语义：不要把相近的工作概念混为一谈

### 4.1 Event、Activity、Task、Commitment、Decision

| 概念 | 关键问题 | 必须具备的语义 |
|---|---|---|
| Event | 发生了什么？ | 类型、主体、对象、时间、来源、状态 |
| Activity | 一段时间内在做什么？ | 目标、参与者、时间区间、过程和结果 |
| Task | 谁需要完成什么？ | 目标、负责人、期限、状态、完成条件 |
| Commitment | 谁承诺了什么？ | 承诺主体、对象、期限、确认依据、履约状态 |
| Decision | 哪个选择被谁在什么权限下确定？ | 决策主体、选项、依据、约束、审批、生效范围 |

不能从“有人在会议上提到某项工作”直接推断“任务已经创建”；不能从“某人说可以考虑”推断“决策已批准”；不能从“系统检测到延期信号”推断“责任人已经承认延期”。

### 4.2 StateAssertion 与事实来源

状态断言是对某个对象属性的有来源描述，不等于不可质疑的真理。

每个重要状态断言至少要保留：
- 主体对象与属性；
- 值或状态；
- 业务有效时间；
- 系统观察时间和记录时间；
- 来源引用与权威级别；
- 断言状态：confirmed、observed、inferred、disputed、stale、unknown；
- 适用规则版本和必要的人工确认。

冲突来源应并列保留。AI 可以解释冲突、提出待确认问题，但不能通过多数票或模型置信度覆盖权威业务系统。

### 4.3 Evidence 与 Assertion

Evidence 是支持或反驳断言的证据引用，不是断言本身。证据需要来源、定位信息、完整性信息和核验状态。一个文档存在，不代表文档中的每一句话都已核验；一段会议转写存在，也不代表说话人归属和决策状态已经确认。

### 4.4 时间语义

至少区分：

| 时间 | 含义 |
|---|---|
| occurred_at | 事件实际发生时间 |
| observed_at | 系统观察或采集到事件的时间 |
| recorded_at | 事件写入系统的时间 |
| valid_from / valid_to | 状态或关系在业务世界中的有效区间 |
| due_at | 任务或承诺的截止时间 |
| reviewed_at | 人工复核时间 |

例如：项目负责人在周一口头确认变更，周三才录入项目系统。事件发生时间与记录时间必须分开；系统不得将周三错误地当成业务变更实际生效时间。

## 5. 个人工作与生活本体：以个人为主体，而不是以员工为主体

### 5.1 个人上下文本体的建议结构

~~~mermaid
flowchart TB
  P["Personal Context Ontology"]
  P --> W["Personal Work Context"]
  P --> L["Personal Life Context"]
  P --> G["Learning & Growth"]
  P --> R["Personal Resources & Preferences"]
  W --> W1["Work Event / Activity / Task"]
  W --> W2["Meeting / Decision / Commitment"]
  W --> W3["Project Participation / Work Product"]
  L --> L1["Personal Schedule / Commitment"]
  L --> L2["Household / Travel / Daily Activity"]
  L --> L3["Personal Goals / Relationships"]
  G --> G1["Learning Event / Reflection"]
  G --> G2["Skill / Goal Progress"]
  R --> R1["Time / Tools / Preferences"]
  R --> R2["Personal Resource"]
~~~

个人本体不是一次性固定的“人生分类表”。它应支持用户自定义类别、别名、关系和记录策略，并允许某些类别不启用、不采集或不保留。

### 5.2 个人工作事件的典型类型

- 参加会议；
- 接收工作信息；
- 识别任务或待办；
- 提出建议；
- 作出个人判断；
- 形成待确认决策；
- 作出明确承诺；
- 完成任务；
- 交付工作成果；
- 发现问题或风险；
- 复盘和经验总结。

这些事件首先是个人对自己工作过程的理解记录。只有符合企业业务目的、权属和授权要求的部分，才进入企业投影流程。

### 5.3 个人生活事件的典型类型

- 个人日程和时间安排；
- 个人承诺与提醒；
- 日常事务和出行安排；
- 个人目标与活动；
- 学习、反思和成长记录；
- 个人关系和资源安排。

生活事件在个人上下文本体中是正式的一等概念，但**不属于企业工作事件的默认扩展字段**。企业侧不应为了“理解员工”而读取个人生活时间线。若个人选择将某个日程窗口用于工作排期，也只应共享所需的可用时间或约束，不应共享无关生活事件的内容和原因。

### 5.4 个人事件向企业事件的投影，不是原始记录同步

同一现实发生可以形成两个不同的语义记录：

1. **个人侧记录**：保留个人理解所需的完整上下文、个人备注和关联信息。
2. **企业侧投影**：仅保留业务任务需要的字段、企业对象引用、来源与授权凭据。

例如，个人在会议后记录了一条待办。个人侧可以保留会议背景、个人判断和提醒；企业侧只接收经确认的项目行动项、责任人、截止时间和项目引用。个人侧的私人备注和无关生活信息不进入企业记录。

投影必须满足：
- 明确的业务目的和接收责任方；
- 对象、字段、时间范围和使用动作均在授权范围内；
- 最小必要字段，不复制原始音频和完整个人笔记；
- 对模糊任务、责任人、日期和决策状态进行人工确认；
- 企业侧记录具有自己的 ID、生命周期和来源引用；
- 撤回授权后停止未来投影，并按治理规则处理已派生记录；
- 企业侧不能通过投影引用反向读取个人原始记录。

### 5.5 个人生活与工作边界的设计原则

- 个人上下文由个人助理管理，企业系统不直接管理个人完整记忆。
- 用户可以把某项个人信息标记为仅个人可见、可用于指定任务或可提交审核。
- “可用于个人任务”不等于“可用于企业任务”。
- 个人工作记录中的客户、同事、供应商和第三方信息，仍受相应业务和隐私规则约束。
- 对高敏感个人类别采取更严格的默认策略，禁止通过宽泛授权一次性开放。
- 企业工作绩效评价不得默认把个人生活数据作为输入。
- 本体分类不能代替法律依据、劳动制度、合同和组织数据治理审查。

## 6. 企业工作本体与领域本体

### 6.1 企业工作本体的共同对象

企业侧建议至少覆盖：
- Organization、OrganizationUnit、Role、Actor；
- Project、Customer、Product、Contract、Order、Process；
- Task、Milestone、Activity、Commitment；
- Decision、Risk、Issue、Dependency；
- Resource、Evidence、SourceRecord；
- StateAssertion、Relation、ContextPackage；
- CapabilityAsset、AgentRun、Approval。

这些是跨业务流程的语义锚点。每个企业可以增加本企业特有对象，但不能在不声明命名空间的情况下重新定义共同概念。

### 6.2 领域本体负责专业语义

不同领域对相同词语可能有不同定义。项目交付中的“验收”、产品研发中的“发布”、供应链中的“交付”、财务中的“结算”，不应只因中文名称相近就合并。

建议采用：
- ADS Core：跨领域稳定概念，如 Actor、Event、Task、Decision、Evidence、Resource。
- Enterprise Ontology：企业组织结构、企业对象和企业业务规则。
- Domain Ontology：项目交付、客户服务、研发、供应链、财务等专业概念。
- Local Extension：团队或系统的局部术语、字段和映射，不得直接修改上层核心定义。

### 6.3 领域本体扩展规则

1. 新概念必须给出稳定 ID、定义、父类、责任 Owner 和使用范围。
2. 扩展概念使用独立命名空间，如 project_delivery.*、customer_service.*。
3. 不得用同名字段覆盖已有核心字段的含义。
4. 若概念只在本地系统成立，应标记为 local，不宣称是企业或 ADS 共同标准。
5. 领域概念之间的映射必须声明映射类型、转换规则、信息损失和复核责任。
6. 领域规则变化必须触发相关事件 Schema、能力资产和评测集的兼容性检查。

### 6.4 语义映射等级

| 映射状态 | 含义 | 后续处理 |
|---|---|---|
| exact | 语义和约束一致 | 可按契约自动映射 |
| equivalent | 近似等价，但需明确适用条件 | 保留映射说明并进行抽样复核 |
| broader / narrower | 上下位概念关系 | 不得直接无损替换 |
| related | 有关系但不等价 | 只建立关联，不合并 |
| candidate | 候选映射，证据不足 | 人工确认 |
| unresolved | 暂无可靠映射 | 保留源术语和原始值 |
| conflict | 不同领域定义冲突 | 保留冲突并升级治理 |

### 6.5 对象身份解析

同一业务对象可能有多个系统 ID、名称和别名。解析流程应为：

1. 保留源系统、租户、原生对象 ID 和版本；
2. 根据权威映射、类型、组织范围和上下文生成候选；
3. 记录匹配依据、置信度和解析状态；
4. 无法唯一确认时返回候选或 unresolved；
5. 由有权业务人员确认后，建立可追溯的 IdentityMapping；
6. 合并、拆分和纠错均保留历史映射。

**禁止仅凭名称相同、文本相似或模型置信度，将两个客户、项目、人员或产品直接合并。**

## 7. 事件驱动的本体运行机制

### 7.1 从信号到事件，再到业务上下文

~~~mermaid
flowchart LR
  S["多源信号<br/>消息 / 会议 / 文档 / 系统记录"]
  O["Observation<br/>观察与解析"]
  C["Event Candidate<br/>事件候选"]
  R["Identity & Semantic Mapping<br/>对象解析与本体映射"]
  P["Policy & Human Review<br/>授权与人工确认"]
  E["Canonical Event<br/>标准事件"]
  X["State / Relation / Evidence<br/>状态、关系、证据"]
  K["Context Package<br/>任务级上下文"]
  A["Capability / Agent<br/>能力调用与执行"]
  F["Feedback Event<br/>结果反馈"]
  S --> O --> C --> R --> P --> E --> X --> K --> A --> F
  F -.改进事件分类与规则.-> R
  F -.更新能力评测.-> A
~~~

### 7.2 事件抽取的状态不能只用“成功 / 失败”

建议事件处理状态与业务确认状态分离。

**处理状态：**
- received：已接收；
- parsed：已解析；
- mapped：已完成候选语义映射；
- awaiting_review：等待人工确认；
- accepted：通过规则或人工确认；
- rejected：被判定为无效；
- corrected：已被更正；
- superseded：已被新记录替代；
- archived：归档。

**业务断言状态：**
- confirmed：已确认；
- observed：已观察；
- inferred：模型或规则推断；
- disputed：存在争议；
- rejected：被否定；
- stale：已过期；
- unknown：未知。

模型完成抽取，不代表业务事实已经确认；数据通过 Schema 校验，也不代表语义正确。

### 7.3 事件最小语义契约

ADS-WORK-04 已定义 WorkEvent 的基础结构，本专题不另造一套互不兼容的事件信封。建议在现有契约基础上冻结以下语义：

| 字段 / 语义 | 说明 |
|---|---|
| event_id | 标准事件唯一标识 |
| event_type | 命名空间.事件类型，如 project.task_status_changed |
| event_schema_version | 事件数据契约版本 |
| occurred_at | 实际发生时间 |
| observed_at | 系统观察时间 |
| recorded_at | 写入时间 |
| actor_ref | 发起或参与主体 |
| object_refs | 涉及的标准对象引用 |
| payload | 事件特有字段，按 event_type 契约约束 |
| source_ref | 原始来源和记录定位 |
| evidence_refs | 支持事件的证据引用 |
| assertion_status | 业务断言状态 |
| classification | 数据分类 |
| purpose_tags | 处理目的标签 |
| authorization_ref | 授权引用 |
| ontology_version | 使用的本体版本 |
| correction_of | 更正或派生关系 |
| lifecycle_status | 事件生命周期 |

### 7.4 事件类型命名规则

建议采用命名空间加动作语义：
- work.task_created
- work.task_status_changed
- work.commitment_recorded
- work.decision_confirmed
- project.risk_identified
- project.milestone_reached
- customer.feedback_received
- personal.work_context_observed
- personal.life_commitment_created
- learning.session_completed

命名应描述发生的事实，不应把未经验证的判断写进事件名称。例如，project.delivery_failed 表示已确认的失败结果；如果只是 AI 识别到延期信号，应使用 project.delivery_delay_candidate 或 work.risk_signal_observed，并保留 inferred / observed 状态。

### 7.5 事件追加与纠错

事件记录采用追加式原则。原始来源和已接收事件不应被静默覆盖。纠错通过更正事件、撤回事件、supersedes 或 correction_of 关系表达。状态视图可以重建，但历史事件和来源引用应可追溯。

## 8. 个人到企业的语义投影标准

### 8.1 投影不是上传，也不是双向同步

个人到企业的投影，是一次有目的、有范围、有接收者、有字段约束的语义转换。它应生成新的企业侧记录，而不是把个人记录的完整内容复制到企业系统。

建议投影请求至少包含：
- source_event_ref：个人侧受控引用；
- target_tenant_id：目标企业租户；
- target_object_ref：目标企业业务对象；
- purpose：明确的企业业务目的；
- requested_fields：拟共享字段；
- recipient_scope：接收角色或系统；
- allowed_actions：允许的处理动作；
- expires_at：授权有效期；
- consent / authorization reference：授权和审批依据；
- transformation_rule_version：投影规则版本。

### 8.2 投影决策矩阵

| 个人侧内容 | 默认策略 | 企业侧处理 |
|---|---|---|
| 个人生活事件 | personal_only | 不投影 |
| 个人工作线索 | personal_only | 由本人选择是否提交审核 |
| 明确的项目行动项 | review_required | 确认项目、责任人、期限和业务目的后投影 |
| 会议中的候选决策 | review_required | 必须确认是否形成正式决策及审批权限 |
| 企业系统中的正式状态 | enterprise_authoritative | 引用权威系统，不用个人记录覆盖 |
| 个人工作方法与经验 | personal_only / review_required | 抽象、去标识化、授权和独立验证后形成能力候选 |
| 个人生活可用时间窗口 | task_specific | 只共享可用性，不共享无关事件原因 |

### 8.3 投影的七个控制点

1. **Purpose**：目的明确且可审计。
2. **Scope**：目标对象、字段、时间范围和接收者明确。
3. **Authority**：个人授权、企业业务责任和适用规则均满足。
4. **Minimization**：只投影完成目标所需的信息。
5. **Confirmation**：重要任务、决策、责任和状态经过适当确认。
6. **Lineage**：保留派生关系和转换版本，但不暴露个人原始记录。
7. **Revocation**：授权撤回后停止未来使用，并按规则处理已派生数据。

授权不是一个布尔值。对个人数据、企业数据、第三方信息和业务秘密，应分别确定处理依据、权限和留存规则。

### 8.4 撤回与派生数据

撤回授权不应被理解为“所有下游记录自动消失”，也不能被理解为“派生后企业可以无限保留”。系统应区分：
- 原始个人记录；
- 个人侧投影请求和授权记录；
- 企业侧派生业务记录；
- 已被业务流程引用的证据或审计记录；
- 从多个来源抽象出的匿名化或聚合能力资产。

撤回后应停止后续读取和新投影；对已有派生记录，由数据 Owner、隐私责任方和业务责任方按适用制度判断删除、限制、替换、保留审计或重新授权。该规则必须在产品和数据契约中实现，不能只写在说明文档里。

- 依赖的本体版本；
- 任务家族；
- 输入输出 Schema；

- 适用领域与不适用条件；
- 评测集版本；
- 已验证的本体映射范围。

Agent Task Envelope 应继续引用 Context Package 和 Policy 版本，不应把本体定义复制到每次任务里。

## 10. 本体版本、扩展与兼容性治理

### 10.1 命名空间策略

建议采用：
- ads.core.*：ADS 共同核心概念；
- ads.personal.*：个人上下文概念；
- ads.enterprise.*：企业工作概念；
- ads.domain.project_delivery.*：项目交付领域概念；
- ads.domain.customer_service.*：客户服务领域概念；
- ads.local.<tenant>.*：企业或租户本地扩展。

本地扩展可以映射到共同概念，但不能静默覆盖共同概念的定义。

### 10.2 版本策略

| 版本变化 | 允许变化 | 兼容要求 |
|---|---|---|
| Patch | 定义修正、别名补充、文档和非语义性错误修复 | 不改变既有含义 |
| Minor | 新增类、关系、事件类型或可选属性 | 不破坏既有事件解释 |
| Major | 删除、重命名、改变基数或语义定义 | 必须迁移计划、双版本读取和回归评测 |

版本号只是发布标签。任何语义变化都必须记录变更理由、影响对象、Owner、迁移规则和生效时间。

### 10.3 废弃与迁移

- deprecated 概念保留旧 ID 和映射说明；
- 新旧版本在迁移期可并行读取；
- 历史事件不得因为新版本发布而被静默改写；
- 需要重解释历史事件时，生成新的派生视图并保留旧解释；
- 影响 Capability Asset 的变化必须触发依赖扫描和回归测试；
- 领域本体变更必须由领域 Owner 负责，不由平台团队单方面定义业务含义。

### 10.4 不强制技术统一

逻辑语义统一不要求所有系统采用同一种数据库、图数据库或知识表示语言。建议：
- JSON Schema 继续约束当前事件和上下文数据契约；
- JSON / JSON-LD 可用于交换本体元数据和语义引用；
- RDF / OWL / SHACL 可作为后续复杂语义推理、约束验证或联邦互操作的候选技术；
- 关系数据库、事件日志、搜索索引和图数据库按实际查询模式组合；
- 不以“必须上知识图谱”作为本体建设的前提。

## 11. 项目交付领域最小试点

### 11.1 为什么从项目交付开始

项目交付天然包含事件、对象、状态、任务、承诺、决策、风险、依赖、证据和角色，能够检验本体是否真的表达了工作过程，而不只是整理名词。

首期范围：
- 项目、里程碑、任务、交付物、风险、问题、决策和证据；
- 项目经理、任务负责人、交付负责人、客户代表等角色；
- 任务创建、状态变化、依赖阻塞、风险识别、决策确认、交付提交和验收等事件；
- 个人会议记录到企业行动项的受控投影；
- 以项目状态评审和风险初筛作为 Agent 使用场景。

### 11.2 端到端示例

1. 个人助理从用户授权的会议记录中识别一条“需要确认项目风险项责任人”的候选工作事件。
2. 个人侧将其保存为 PersonalWorkEvent，保留个人备注和来源。
3. 系统解析候选项目对象，但若存在多个相似项目，不自动选择。
4. 用户确认项目、责任人和下一步动作，并明确提交企业侧的业务目的。
5. Policy Service 检查授权、目标租户、字段范围、接收者和有效期。
6. 投影服务生成新的企业 WorkEvent，引用企业 Project 对象和授权凭据。
7. 企业侧按业务规则创建候选 Task 或 Action Item；是否写入正式项目系统，仍按 ADS-WORK-06 的动作等级和审批要求执行。
8. 项目 Agent 获取 Context Package，使用 ADS-WORK-07 的项目风险初筛能力。
9. 业务责任人确认结果，形成新的状态、证据或反馈事件。
10. 个人侧和企业侧分别保留各自责任范围内的记录，通过受控派生关系追溯，不共享无关个人信息。

### 11.3 首批事件目录

| 事件类型 | 主要对象 | 默认来源 | 确认要求 |
|---|---|---|---|
| project.task_created | Project / Task | 项目系统或经确认投影 | 正式创建需业务系统确认 |
| project.task_status_changed | Task | 项目系统 | 以权威状态源为准 |
| project.dependency_blocked | Task / Dependency | 项目系统、人工确认 | 关键阻塞需确认 |
| project.risk_signal_observed | Project / Task / Risk | 工作事件、监测规则 | 候选风险不得直接变正式风险 |
| project.risk_confirmed | Project / Risk | 风险责任人 | 责任人确认 |
| project.decision_recorded | Project / Decision | 审批、会议或决策记录 | 需核验权限和决策状态 |
| project.deliverable_submitted | Project / Deliverable | 项目系统或文档系统 | 保留版本和来源 |
| project.acceptance_confirmed | Project / Deliverable | 验收系统或授权责任人 | 必须来自权威验收记录 |
| personal.work_commitment_created | Personal Work Context | 个人助理 | 个人侧确认；企业投影另行授权 |

### 11.4 试点评测指标

| 指标 | 定义 | 目标门槛制定方式 |
|---|---|---|
| Event Precision / Recall | 事件抽取准确率和召回率 | 按事件类型和复杂度分别设基线 |
| Entity Resolution Precision | 对象关联正确率 | 高影响对象设置更严格门槛 |
| Relation Accuracy | 责任、依赖、影响等关系准确率 | 对关键关系人工抽样复核 |
| Temporal Accuracy | 发生、观察、记录和有效时间的正确率 | 单独测试迟到、乱序和补录 |
| Assertion Calibration | confirmed / inferred / disputed 分类质量 | 错把推断标为确认属于关键错误 |
| Projection Leakage | 不应投影的字段进入企业侧的比例 | 关键隐私边界要求零容忍 |
| Authorization False Allow | 无授权却允许投影或访问的次数 | 安全门槛，目标为零 |
| Context Utility | Agent 完成任务所需信息的覆盖程度 | 与任务质量和证据覆盖联合评价 |
| Correction Rate | 人工纠错比例及纠错类型 | 区分抽取、映射、规则和源数据问题 |
| Operational Cost | 单个被接受事件或任务的总成本 | 纳入模型、工具、人工复核和维护成本 |

准确率不能替代治理门槛。即使总体抽取质量较高，只要出现未授权个人生活信息投影或高影响错误对象合并，就应暂停相关能力。

## 12. 研究验证与实施路线

### 阶段 A：语义边界冻结（第 1—2 周）

- 确认个人、企业、业务领域中心的责任边界；
- 冻结五层逻辑模型和核心术语；
- 确认个人工作事件与个人生活事件的分类；
- 确认事件、活动、任务、承诺、决策、状态和证据的定义；
- 选择项目交付作为首个领域。

**阶段门槛：** 领域专家能够用统一术语解释一组真实但已脱敏的工作案例。

### 阶段 B：本体目录与映射（第 3—4 周）

- 建立 Core、Personal、Enterprise、Project Delivery 命名空间；
- 建立首批对象、事件类型和关系谓词目录；
- 建立源系统字段映射和对象身份解析规则；
- 标记 exact、equivalent、related、candidate 和 unresolved；
- 对所有核心概念指定 Owner。

**阶段门槛：** 不同系统中的同类事件可以被映射；语义不确定时能保留未知和冲突。

### 阶段 C：个人事件与企业投影（第 5—6 周）

- 个人侧保存工作与生活事件；
- 生活事件默认个人私有；
- 工作事件支持用户选择提交审核；
- 实现最小字段投影、授权校验、人工确认和撤回处理；
- 验证企业侧不能反向读取个人原始记录。

**阶段门槛：** 投影目的、范围、字段和授权可审计，未授权信息不流入企业侧。

### 阶段 D：项目交付本体接入（第 7—8 周）

- 接入项目、任务、里程碑、风险和决策权威数据；
- 建立项目事件类型和对象映射；
- 形成事件时间线、状态视图和 Context Package；
- 将本体版本绑定到 ADS-WORK-07 Capability Manifest；
- 让项目风险初筛能力在只读场景使用。

**阶段门槛：** Agent 能解释关键结论的来源、对象、时间、状态和未知项。

### 阶段 E：跨团队验证与标准治理（第 9 周起）

- 在第二个团队验证本体可理解性和映射成本；
- 比较不同团队的本地术语和流程差异；
- 记录迁移损失、未映射概念和新增领域扩展；
- 建立本体变更评审、版本兼容和回归测试；
- 再决定是否扩展到客户服务或产品研发领域。

**阶段门槛：** 只有获得跨团队证据的概念和映射规则，才能提升共享等级。

## 13. 关键架构决策建议（ADR）

| ADR | 建议决策 | 原因 |
|---|---|---|
| 01 本体范围 | 共同核心 + 个人 + 企业 + 领域分层 | 避免一个巨型本体吞并所有业务语义 |
| 02 个人模型 | 个人工作与生活都属于个人上下文本体 | 以个人为主体，不把人简化为员工 |
| 03 默认边界 | 个人生活事件默认个人私有 | 防止企业工作感知变成生活监控 |
| 04 事件身份 | 个人事件与企业投影事件分配不同 ID | 保持责任、权限和生命周期独立 |
| 05 语义不确定 | 支持候选、未解析、冲突和未知 | 不强迫错误统一 |
| 06 事件标准 | 复用 ADS-WORK-04 WorkEvent 契约 | 避免重复建设不兼容的事件信封 |
| 07 关系语义 | 关系必须有类型、方向、有效时间和来源 | 避免无语义的“相关”边 |
| 08 本体版本 | 本体、Schema、映射、Policy 分别版本化 | 让语义变化可追踪 |
| 09 投影机制 | 个人到企业采用最小必要、目的绑定的单向投影 | 避免原始记忆直接同步 |
| 10 技术选型 | 先冻结语义与契约，再决定图数据库或 OWL | 不把技术选型误当作本体设计 |
| 11 领域扩展 | 使用命名空间和 Owner 治理 | 兼顾共性与业务专业性 |
| 12 能力依赖 | Capability Manifest 显式引用本体版本 | 保证 Agent 调用的语义前提一致 |

### 13.1 需要正式评审的事项

- ADS 共同核心本体由哪个组织或角色维护？
- 个人本体是否采用完全用户可控的本地优先设计？
- 个人工作事件投影到企业的授权和撤回流程由谁负责？
- 企业主数据系统与 ADS 对象身份解析的权威关系如何定义？
- 领域中心是否仅保存本体、映射和资产元数据，哪些情况下允许保存派生数据？
- 本体变更的兼容窗口和旧版本保留期限如何确定？
- 高敏感个人信息和第三方信息的分类、隔离和处理规则如何冻结？

## 14. 验收清单

### 本体与语义
- [ ] 五层模型定义明确，层间职责不混淆。
- [ ] 个人、企业和业务领域本体的范围清晰。
- [ ] Event、Activity、Task、Commitment、Decision、StateAssertion 和 Evidence 定义可区分。
- [ ] 核心概念有稳定 ID、定义、命名空间和 Owner。
- [ ] 关系具有方向、时间、来源和适用范围。
- [ ] 事件类型目录覆盖首个试点的关键过程。

### 个人与企业边界
- [ ] 个人工作与生活事件都能在个人侧表达。
- [ ] 个人生活事件默认不进入企业侧。
- [ ] 个人工作事件不自动成为企业正式事件。
- [ ] 企业投影有目的、字段、接收者、有效期和授权引用。
- [ ] 企业侧无法通过投影引用读取个人原始记录。
- [ ] 授权撤回和派生记录处理规则可执行。

### 事件与映射
- [ ] 原始来源、发生时间、观察时间和记录时间保留。
- [ ] 对象身份解析支持候选和 unresolved。
- [ ] 映射支持 exact、equivalent、related、candidate、unresolved 和 conflict。
- [ ] 冲突和未知不会被模型自动覆盖。
- [ ] 事件更正和历史版本可追溯。

### 工程与运营
- [ ] Ontology Registry、Schema Registry 和 Mapping Registry 有明确责任人。
- [ ] 本体版本与 WorkEvent、ContextPackage 和 Capability Manifest 兼容。
- [ ] 项目交付试点具有人工标注集和质量评测。
- [ ] 投影泄漏和未授权访问纳入零容忍安全门槛。
- [ ] 本体变更有评审、回归、迁移和退役流程。

## 15. 结论：让个人数智底座理解人，让企业数智底座理解业务

ADS 的长期价值，不只是让 AI 可以检索更多资料、调用更多工具或创建更多 Agent，而是让 AI 能够在正确的责任边界内理解真实世界中的事件、对象、关系、状态、目标和行动。

本专题给出三个层次的答案：

1. **个人层：** 以个人为主体，理解个人工作与生活的连续上下文，形成个人可控制的事件、记忆、目标和资源。
2. **企业层：** 以业务对象和工作事件为核心，理解企业运行状态、任务、决策、风险、证据和协同过程。
3. **业务领域中心层：** 以共同核心本体、领域本体、映射规则、联邦目录和版本治理连接不同企业与领域，不默认集中存储底层原始数据。

三者之间不是原始数据的逐级汇总，而是通过本体、身份映射、授权投影、任务上下文和反馈机制建立受控协同。

**工作事件是观察工作世界的入口；本体是理解工作世界的语义骨架；上下文是面向任务的组织方式；能力资产是可复用的工作方法；Agent 是受约束的执行单元。**

### 下一专题建议：ADS-WORK-09

**《个人数智底座的持续记忆、事件账本与自主智能体架构研究》**

进一步研究：
- 个人工作与生活事件如何形成可持续、可纠错的个人记忆；
- 个人事件账本、时间线、目标和承诺如何关联；
- 本地优先、个人控制和多端同步如何设计；
- 个人助理如何从记忆中形成行动建议，又如何避免把推断当成事实；
- 个人工作信息如何通过授权进入企业协同；
- 个人 Agent 与企业 Agent 如何围绕任务契约协作。

> **最终方向：让每个人拥有真正理解自己的个人数智底座，让每家企业拥有真正理解自身运行的企业数智底座，再通过 ADS 的共同语义和治理机制形成可协同、可演进的数智生态。**
