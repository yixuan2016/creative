Executive Summary

从“理解企业”走向“协调企业智能执行”

当 ADS 能持续回答“发生了什么、当前状态是什么、依据是什么、哪里存在冲突和未知”，下一步就不应只是增加一个聊天机器人，而是建立一套能让多个专业 Agent 在统一上下文和权限治理下完成复杂工作的协同执行体系。

核心定位：ADS 提供企业运行认知；Agent Runtime 组织受约束的智能执行；业务系统仍然是正式业务状态和交易结果的权威载体。

01 · Principles & Boundaries

设计原则：先定义协作边界，再讨论智能程度

原则核心要求
Context First先获取任务所需 Context Package，不任意检索全企业数据
Contract First每次委派有明确目标、范围、输入、输出和验收条件
Least PrivilegeAgent、用户、工具和委派链均按最小权限授权
Separate Cognition & Execution企业业务状态、认知判断和 Agent 执行状态分别建模
Human Accountability高影响业务判断由明确的人类责任人承担
Deterministic Guardrails权限、审批、幂等、状态迁移由确定性服务强制执行
Evidence Before Assertion重要结论必须附证据、来源、时间和不确定性
Bounded Autonomy限制步骤、委派深度、工具次数、时间和成本
Observable by Design运行、委派、工具调用和审批使用统一 Trace
Reusable Capability优先沉淀 Skill、工具、规则、任务模板和评测集

Agent、Skill、Tool、Workflow 不能混用

Agent

任务执行单元

有角色、目标、上下文和能力边界，可进行受约束推理。

Skill / Capability

可复用专业能力

代码、规则或模型封装，如依赖路径分析、证据核验。

Tool

外部接口

查询项目状态、读取风险台账、提交待办草稿。

Workflow

流程定义

明确步骤、条件、审批和异常分支，保证流程可控。

架构建议：确定性规则、计算和系统操作优先做成 Skill / Tool；只有在需要语义理解、非结构化分析或动态任务拆解时才引入 Agent。不要把每个 API 都包装成一个 Agent。
02 · Reference Architecture

四个平面：共享上下文、统一控制、专业执行、横向治理

业务人员 / 业务系统事件 / 定时任务提出目标、触发任务或响应业务变化
↓
ADS 企业运行上下文平面统一数据模型 · 运行认知引擎 · Context Package API
↓
Agent 控制平面Agent Registry · Capability Registry · Orchestrator · Plan Validator · Task Broker
↓
专业 Agent A项目上下文状态变化
专业 Agent B风险分析影响范围
专业 Agent C依赖分析阻塞路径
专业 Agent D决策证据版本核验
↓
Verifier · 结果汇总 · 人工确认结构、证据、冲突、未知和业务约束检查
↓
Tool Gateway → 正式业务系统只读查询 / 草稿 / 审批后的受控动作
横向治理：身份 · 策略 · 审批 · 审计 · Trace · 预算 · Kill Switch

ADS Context Plane

负责企业对象、事件、状态、关系、证据、授权和任务级上下文；不负责 Agent 自主编排。

Agent Control Plane

负责 Agent / Capability 注册、计划校验、委派路由、预算、生命周期和版本管理。

Agent Execution Plane

运行具体 Agent、模型调用、Skill 执行、工具请求和结果校验。

Governance & Observability

负责身份、策略、审批、审计、质量评估、成本管理、异常检测和紧急停止。

核心数据流

  1. 用户或业务事件提出有明确目的的任务。
  2. Orchestrator 识别任务类型，读取任务模板和 Agent Registry。
  3. ADS 按主体、用途、对象、时间和字段范围生成 Context Package。
  4. Plan Validator 检查计划、权限、预算和动作等级。
  5. 专业 Agent 按 Task Envelope 执行，只调用允许的工具。
  6. Verifier 检查结果结构、证据、冲突、未知和业务规则。
  7. 人工确认高影响判断；正式动作由业务系统或受控服务完成。
  8. 执行结果回流 ADS，审计和评测记录完整链路。
03 · Core Components

组件职责：模型提出候选，控制服务执行规则

组件核心职责边界
Agent RegistryAgent 身份、版本、角色、能力、所有者和运行限制不授予任意业务数据访问权
Capability RegistrySkill / Tool 输入输出、风险等级、依赖和版本不替代业务权限策略
Orchestrator规划、拆解、委派、汇总、超时和终止不绕过 Policy 执行高风险动作
Plan Validator校验计划结构、动作等级、预算和权限不依赖模型自我声明安全
Agent Runtime装载任务上下文、模型和能力并运行 Agent不能自行扩大授权
Task Broker任务排队、路由、并发、重试和状态更新不改变任务业务含义
Tool Gateway鉴权、参数校验、限流、幂等、审计和结果封装Agent 不持有系统长期凭证
Policy / Approval策略决策、具体动作审批和审批有效期审批不能扩展为永久授权
Verifier检查 Schema、证据、矛盾、范围和验收标准不为无证据内容背书
Run Ledger / Trace记录运行、任务、委派、工具、审批和结果不保存不必要的隐藏推理链
Orchestrator 可以使用模型提出任务分解建议，但任务创建、委派、授权、预算扣减、状态转换和动作提交必须由可测试的控制逻辑执行。模型输出是候选计划，不是系统命令。

Agent Registry 最小登记项

身份与所有权

agent_id、domain、owner、role_description、lifecycle_status。

能力与数据边界

supported_task_types、allowed_capabilities、denied_capabilities、data_classification_ceiling。

运行约束

max_risk_tier、max_delegation_depth、timeout、max_steps、tool_calls、budget。

版本信息

agent_version、model_profile、prompt_version、runtime_version。

输入输出契约

input_contract、output_contract、evaluation_profile。

停用策略

阻止新任务，并定义运行中任务的完成、迁移或取消方式。

04 · Domain Agent Team

项目交付 Agent 团队：一个协调者，多个专业角色

Coordinator

项目协调 Agent

理解目标、拆解任务、分派专业 Agent、汇总结果和呈现待确认事项。

Specialist

项目上下文 Agent

提取项目状态、里程碑、关键变化和时间线证据。

Specialist

风险分析 Agent

识别候选风险、影响对象、触发条件和证据缺口。

Specialist

依赖分析 Agent

分析任务依赖、阻塞链、里程碑影响和关键路径。

Specialist

决策与证据 Agent

核验决策审批状态、交付物版本和证据引用。

Specialist

行动项草拟 Agent

将已核验问题转成内部行动项草稿，不直接写回。

Quality Gate

Verifier Agent

检查结构、来源、冲突、未知、范围和业务约束。

重要：Agent 数量不是架构目标。若某个子任务可由确定性 Skill 或 Tool 完成，应优先使用能力组件，不必创建一个新 Agent。
05 · Task & Result Contract

以结构化任务契约代替自由对话式委派

每次委派必须说明目标、范围、上下文版本、输入、允许能力、禁止动作、输出要求、预算、截止时间、委派规则和失败策略。Task Envelope 是 Runtime、Task Broker、Policy Service 和审计系统共同执行的控制对象，不只是提示词。

输入契约

目标、对象范围、时间窗口、Context ID、完整性摘要、用途和输入数据。

权限契约

允许能力、禁止动作、风险等级、策略版本、审批引用和委派深度。

输出契约

Schema、必需字段、证据引用、冲突、未知、假设和限制说明。

Task Envelope 示例

{
  "task_id": "task-dependency-014",
  "task_type": "analyze_project_dependencies",
  "requester": {
    "subject_type": "agent",
    "subject_id": "agent-project-coordinator",
    "on_behalf_of": "user-project-manager"
  },
  "recipient": {
    "agent_id": "agent-dependency-analysis",
    "agent_version": "0.1"
  },
  "purpose": "prepare_project_status_review",
  "scope": {
    "object_refs": ["obj-project-014"],
    "time_window": {
      "from": "2026-11-17T00:00:00+08:00",
      "to": "2026-11-20T00:00:00+08:00"
    }
  },
  "context_package_ref": {
    "context_id": "ctx-project-review-014",
    "integrity_hash": "sha256:example-digest"
  },
  "allowed_capabilities": ["context.read", "dependency.graph.read"],
  "prohibited_actions": ["project.write", "task.reassign", "customer.send"],
  "risk_tier": "L0",
  "constraints": {
    "evidence_required": true,
    "max_steps": 8,
    "max_tool_calls": 10,
    "max_delegation_depth": 0

  }
}

完整字段、版本和机器可读约束见配套 JSON Schema。示例中的 ID 和数据均为虚构。

Result Contract 必须包含

  • 任务和 Agent 版本、Run ID、执行状态；
  • 简要结果与结构化发现；
  • 每个关键发现的 EvidenceRef；
  • 冲突、未知、假设和限制；
  • 建议下一步和动作提议（如有）；
  • 耗时、工具调用和成本指标。
Verifier 应拒绝缺少必要证据、超出任务范围、把推断写成正式事实或违反输出 Schema 的结果。
06 · Collaboration Patterns

四种标准协作模式，默认采用混合式编排

A · 串行流水线

前一步是后一步的输入

项目上下文 → 风险识别 → 行动项草稿 → 结果核验。

B · 并行分工与汇总

子任务彼此独立

状态、风险、依赖、决策证据并行分析，最后由 Coordinator 汇总。

C · 监督式委派

复杂目标动态拆解

Coordinator 委派专业 Agent，限制最大深度、并发、预算和截止时间。

D · 事件驱动协作

业务变化触发候选任务

项目状态变化、风险升级或交付物更新触发任务，再经策略和去重检查。

推荐架构：中心化控制 + 专业化执行 + 确定性工具服务。不要把 Agent 自由聊天、无限递归委派作为默认机制。

项目评审的协作时序

项目经理提出评审目标
↓
Coordinator 获取 ADS Context Package
↓
状态 Agent项目状态与变化
风险 Agent风险与影响
依赖 Agent阻塞链与里程碑
证据 Agent决策与证据版本
↓
Verifier 检查证据、冲突、未知和范围
↓
Coordinator 汇总评审材料与行动项草稿
↓
项目经理接受 / 修正 / 驳回
↓
经独立审批的动作由 Tool Gateway 执行并回流结果

并行协作的硬约束

  • 子 Agent 使用同一 Context Package 版本，或明确记录上下文差异。
  • 同一业务对象的关键写入默认串行化。
  • Agent 结果有分歧时保留冲突，不用多数票替代事实核验。
  • 超时可返回 partial，但必须标注缺失子任务。
  • 并行数量受租户、业务域、任务类型和成本预算共同限制。
07 · Runtime Lifecycle

Run、Task、Delegation 分层管理，显式表达执行状态

requested → authorized → planned
↓
running ↔ waiting（等待子任务或工具）
↓
成功completed
部分成功partial
失败failed / retryable
停止cancelled / expired
对象定义
Run一次用户目标或业务事件触发的完整执行实例
TaskRun 中可独立分派、追踪和验收的工作单元
Delegation父任务向子 Agent 的正式委派关系
ToolCall一次工具调用及其策略决策、参数和结果
Approval针对具体动作的审批记录
Artifact报告、草稿、清单、证据索引等可交付结果
关键区分：Run 的 completed 只表示 Agent 任务满足其执行契约，不意味着项目状态、风险、验收或其他业务事实已发生改变。
08 · Tool & Action Governance

所有工具调用经过 Tool Gateway，动作按风险分级

Tool Gateway 的九项职责

  1. 解析 Agent、用户和代表关系；
  2. 检查任务目的、对象、字段和数据分类；
  3. 校验工具是否在 Agent 能力清单中；
  4. 校验参数 Schema、业务规则和速率；
  5. 检查审批要求及审批是否绑定当前动作；
  6. 生成幂等键和审计记录；
  7. 调用下游服务；
  8. 保存执行状态、回执和副作用摘要；
  9. 将结果返回 Agent，并在适用时发布标准事件。

动作风险分级

等级动作示例默认策略
L0只读查询与分析查询项目状态、分析依赖、检索证据授权后自动执行
L1内部草拟与建议周报草稿、待办建议、风险提示自动生成，人工确认后使用
L2可逆的内部业务写入创建内部待办草稿、更新非关键标签逐工具审批、幂等、审计和补偿
L3高影响或外部动作客户承诺、合同变更、费用审批、正式验收授权人员在正式系统完成；Agent 提供材料
第一阶段只开放 L0 / L1。L2 逐个工具、逐个场景评审后才可进入沙箱验证。L3 不因 Agent 任务成功或模型置信度高而自动放行。

审批绑定具体动作

审批至少绑定请求主体、代表关系、动作类型、目标对象、完整参数摘要、payload hash、用途、风险等级、审批人、有效期、策略版本和防重放标识。若对象、参数、金额、接收方或内容变化，原审批失效，必须重新审批。

可靠执行要求

  • 副作用调用必须提供 Idempotency-Key。
  • 关键写入使用版本检查或乐观锁。
  • 网络超时不代表下游没有执行；重试前先查询或依赖下游幂等。
  • 跨系统操作采用 Saga / 补偿，不假设分布式原子事务。
  • 无法安全补偿的动作提升风险等级，要求人工执行。
09 · Context & Memory

Agent 可以拥有任务状态，但不能各自维护企业事实孤岛

记忆类型作用归属与治理
Run Context当前运行临时状态、子任务进度和中间结果随 Run 生命周期归档或清理
Capability Memory经验证的规则、流程、模板和能力经验评审、版本化、指定所有者后进入能力库
Enterprise Runtime Context企业对象、事件、状态、决策、风险、证据和关系由 ADS 与业务系统责任边界管理
企业业务事实回到 ADS 运行认知引擎及权威业务系统。不能因为某个 Agent 在历史对话中“记得”项目状态，就跳过 Context API 查询当前事实。

Context Package 失效条件

  • 上下文包过期；
  • 用户或数据责任方撤回授权；
  • 关键源数据更正或证据失效；
  • 对象范围、数据分类或策略版本变化；
  • 任务从只读分析转为写入建议或实际执行。

只读任务的 Context Package 不能自动复用为写入任务的授权凭据。人工接受、修正、驳回和补充信息应形成结构化 Feedback Event，经审核后才可更新规则、Prompt、Skill 或评测集。

10 · Security & Adversarial Risks

把安全控制放在服务端，不把希望寄托在提示词上

风险表现控制
Prompt Injection文档或网页诱导 Agent 越权检索内容视为不可信数据；工具端强制策略
越权委派子 Agent 获得父任务之外的权限权限取交集；每次委派重新 Policy Check
数据外泄敏感内容流向外部工具分类、脱敏、出口控制和工具白名单
工具滥用错误参数、重复提交或异常频率Schema、限流、幂等、预算
结果串线多项目或多租户上下文混用Tenant / Object Scope 隔离
伪造证据Agent 生成不存在的引用EvidenceRef 必须由系统解析验证
循环委派反复创建子任务最大深度、任务数、循环检测和超时
多 Agent 共识幻觉多个 Agent 重复同一错误检查证据独立性，不以多数票替代核验

紧急停止机制

按范围停止

按租户、业务域、Agent、Tool 或 Run 暂停。

撤销执行权限

停止新任务、取消排队委派、禁用高风险工具。

审计与恢复

失效上下文和授权，导出 Trace，回归测试后审批恢复。

13 · Project Delivery Scenario

项目经理提出一个目标，多个 Agent 共同准备评审材料

“请基于截至今天的授权项目上下文，准备本周项目状态评审材料，重点说明延期风险、关键依赖、待确认决策和建议跟进动作。”
  1. Coordinator 识别任务类型并校验项目经理身份、项目范围和用途。
  2. ADS Context Engine 生成指定项目和时间窗的 Context Package。
  3. Plan Validator 校验 Agent 清单、预算、时间和允许动作。
  4. 状态、风险、依赖、决策证据 Agent 并行分析。
  5. Verifier 检查来源、时效、冲突、未知和任务范围。
  6. Coordinator 汇总评审材料，明确事实、推断、冲突和未知。
  7. Action Drafting Agent 生成内部行动项草稿。
  8. 项目经理接受、修正或驳回；正式写入仍走原系统授权流程。
  9. 若未来开放 L2 动作，必须逐项审批、校验幂等并由 Tool Gateway 执行。
  10. 业务系统回执回流 ADS，Run Ledger 归档完整链路。

最终交付内容

项目与变化

项目概览、正式状态、认知状态、本期变化及来源。

风险与依赖

里程碑影响、阻塞链、责任人和待确认事项。

决策与证据

决策审批状态、交付物版本和证据索引。

行动项草稿

行动内容、负责人候选、期限候选和关联对象。

质量说明

未知、冲突、数据新鲜度和未完成子任务。

人工确认

接受、修正、驳回和后续正式系统操作记录。

业务价值与 ADS-WORK-05 基线对齐，比较评审准备时间、跨系统查找次数、风险发现周期、行动项形成耗时、事实遗漏和人工修改比例。Agent 任务数量不是业务价值。

14 · Cost & Reliability

为每次 Run 设置预算，确保失败可恢复

时间与步骤

最大总耗时、单任务超时、最大 Agent 步骤数。

委派与并发

最大委派深度、子任务数、并发数和重试次数。

模型与成本

模型档位、Token 预算、成本预算和降级策略。

可靠性原则

  • 任务队列支持持久化和状态恢复；
  • 事件和工具调用支持幂等；
  • 外部服务故障时明确返回 partial / unavailable；
  • 重试采用退避并设置上限；
  • 重要操作先查询后执行，避免超时导致重复副作用；
  • 子任务失败不能隐藏在汇总文本中；
  • 按 Agent、Tool、租户和业务域提供熔断和降级。
模型路由与缓存策略

简单分类、格式校验和确定性计算优先使用规则或轻量模型；复杂语义理解和任务规划使用适当能力模型。模型降级不能绕过权限和证据要求。缓存必须检查租户、权限主体、上下文版本、完整性和 TTL；授权撤回、源数据更正和策略升级应触发失效。

15 · Implementation Roadmap

从单 Agent 只读，逐步走向多 Agent 受控协同

P0 · 1—2 周
契约与治理

Registry、Envelope、Result、风险策略和预算

P1 · 3—4 周
单 Agent 只读

一个项目 Agent 消费 Context Package

P2 · 5—6 周
影子协同

Coordinator + 2—4 个专业 Agent

P3 · 7—8 周
人工确认

Verifier、修正反馈和行动项草稿

P4 · 9—10 周
受控动作评估

单个低风险内部动作的沙箱评估

P5 · 后续
扩展复用

多项目、多团队和领域能力目录

P4 不是生产写入许可。任何真实 L2 写入必须单独立项、授权、审批并通过幂等、补偿、审计和安全测试。L3 外部或高影响动作仍由授权人员在正式系统完成。

首批工程最小集

  1. Agent Registry（静态配置起步）；
  2. Task Envelope / Result Contract Schema；
  3. 有限状态机 Orchestrator；
  4. Task Broker（单队列即可起步）；
  5. 复用 ADS Context API 的 Context Adapter；
  6. 只读 Tool Gateway；
  7. Schema + 证据 + 规则 Verifier；
  8. Run Ledger / Trace；
  9. 人工审核入口；
  10. 评测数据集与回归测试。

首期不需要先做 Agent 市场、可视化拖拽编排、无限自我规划或复杂自治系统。

ADR推荐选择原因

18 · Readiness Checklist

立项前、上线前和扩大前的检查清单

立项前
  • 业务目标、首批任务和责任人明确；
  • Agent、Skill、Tool 边界已确认；
  • Context Package 和权限模型可复用；
  • Task Envelope 与 Result Contract 已版本化；
  • Tool Gateway、审批和审计设计通过评审；
  • L0—L3 动作等级和审批规则明确；
  • 预算、委派深度和 Kill Switch 已定义；
  • 真实数据处理范围获得批准。
上线前
  • 单 Agent 和多 Agent 正常 / 异常场景通过；
  • 越权、Prompt Injection 和跨项目隔离测试通过；
  • 上下文过期、撤回和版本变化测试通过；
  • 工具幂等、超时、重试和审批绑定测试通过；
  • Trace、审计、成本限制和 Kill Switch 通过；
  • 业务团队确认人工责任和例外处理方式。
扩大前
  • 多项目任务成功率和证据质量达到冻结阈值；
  • 业务周期或质量指标出现可重复改善；
  • 人工修正率和返工原因可解释；
  • 失败恢复和 Kill Switch 演练完成；
  • Agent / Tool 版本和权限有持续维护人；
  • 其他项目已独立复现收益；
  • 业务、安全和架构负责人共同作出 Go / No-Go 决策。
Conclusion & Next Research

ADS 的价值不只是让 Agent 知道企业发生了什么

更重要的是，让 Agent 在可信上下文和明确边界内，协同推进企业下一步工作。

ADS Context

让 Agent 知道企业正在发生什么，以及信息从哪里来。

ADS Ontology

让 Agent 理解业务对象、关系、事件和规则是什么意思。

ADS Policy

让 Agent 知道什么可以访问、什么可以做、什么必须审批。

Agent Runtime

让多个专业 Agent 按任务契约协同完成工作。

ADS Feedback

让执行结果、人工修正和业务验证回流，形成持续改进。

Enterprise Capability

将经验证的规则、工具和任务经验沉淀为可复用能力资产。
