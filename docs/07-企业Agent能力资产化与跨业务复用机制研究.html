Executive Summary

从“使用 AI”走向“积累企业自己的 AI 能力”

如果每次 Agent 任务都从零开始，如果关键经验只存在于某位员工的记忆、聊天记录或个人 Prompt 中，那么企业即使部署很多 Agent，也未必真正积累了组织能力。

核心定义：Capability Asset 是企业在明确业务目的和治理边界下，对可重复工作能力进行结构化描述、验证、版本化、登记和运营后形成的数字化资产。

01 · Why Capability Assets

知识库保存信息，能力资产沉淀“如何把工作做好”

Knowledge

知识内容

告诉人或 Agent 某个概念、事实、背景和参考资料是什么。

Capability

工作能力

告诉人或 Agent 面对一类任务应检查什么、怎么做、如何判断完成。

能力资产需要回答十个问题

任务与适用

解决什么任务？谁可以使用？需要什么输入和前置条件？何时适用、何时不适用？

方法与证据

按什么方法完成？有哪些规则和判断点？输出需要什么证据？

异常与责任

遇到例外如何处理？何时停止或升级？由谁负责维护和审批？

质量与版本

如何证明有效？适用范围是什么？版本如何更新和回滚？

Prompt 不是能力资产。Prompt 可以是能力实现的一部分，但没有输入输出契约、证据标准、适用边界、评测和责任人的 Prompt，不能单独代表成熟能力。

企业能力容易流失的位置

位置表现后果
个人经验专家知道怎么做，过程没有结构化人员变动后能力难延续
临时对话AI 对话中形成的方法没有版本结果难复现
项目复盘建议没有转成可执行标准相同问题反复发生
个人 Prompt有效提示词散落在个人目录难治理、难复用
工具脚本脚本无人维护，权限不清运行风险和维护断层
02 · ADS Architecture Position

能力资产是连接运行认知与 Agent 执行的中间层

Work Sensing感知工作信号，形成工作事件候选
↓
Work Context + Ontology关联业务对象、事件、任务、决策、证据与语义
↓
Runtime Cognition理解当前状态、来源、冲突和未知，生成 Context Package
↓
Capability Asset经过验证的 Skill · Rule · Playbook · Workflow · Evidence Standard
↓
Agent Runtime按任务契约和策略调用能力，组织执行与协作
↓
Feedback & Evaluation人工确认、业务结果、能力评测、版本更新与回滚
架构约束：能力资产属于企业数智底座的能力资产管理与运营范畴，不新增 ADS 第四级数智底座。个人、企业和业务领域中心仍遵循既有责任边界。
能力回答的问题产物
Work Sensing工作中发生了什么信号？原始信号、工作事件候选
Runtime Cognition企业当前状态是什么？依据和未知在哪里？StateAssertion、ContextPackage
Capability Asset这类任务有哪些经过验证的方法？Skill、Rule、Playbook、Workflow
Agent Runtime当前任务由谁、调用什么能力、如何协同？Run、Task、Delegation、Artifact
Feedback & Evaluation能力是否有效，如何改进？Evaluation Result、Feedback Event

能力资产不是企业事实。当前项目状态仍由权威业务系统和 ADS 运行认知机制负责；能力只提供处理某类任务的方法。

03 · Asset Taxonomy

把不同类型的经验放到正确位置

Skill

专业任务能力

项目风险初筛、证据完整性检查。由代码、规则、模型或混合方式实现。

Playbook

情境处理指南

面对项目延期、客户升级等情境的步骤和分支。

Rule

明确判断约束

例如未审批交付物不得标记为正式验收。

Workflow

多步骤流程

多个角色、条件、审批和异常分支的流程编排。

Template

交付物结构

项目状态评审报告、风险清单或标准输出 Schema。

Tool

系统接口

查询项目任务、读取风险台账或生成内部草稿。

Decision Pattern

决策框架

关键路径风险判断、升级条件和选择依据。

Evidence Standard

证据标准

定义什么来源足以支持某类结论。

Evaluation Set

评测样本

标准案例、标签、人工裁定和评分 Rubric。

Capability Asset 是以上一种或多种组件经过组合、验证和治理后形成的可运营资产包。它不等于单个 Prompt，也不必绑定某个 Agent 或模型。
04 · Experience-to-Asset Pipeline

从个人经验到企业能力，必须经过授权、抽象和验证

STEP 01
识别信号

授权工作事件、任务结果、复盘和反馈

STEP 02
经验候选

目标、输入、步骤、依据、结果、例外

STEP 03
拆分因素

个人偏好、项目特例与通用任务结构

STEP 04
抽象能力

前置条件、规则、证据、输出和停止条件

STEP 05
治理审查

授权、隐私、客户信息、IP 和共享范围

STEP 06
独立验证

原作者之外人员、任务样本和盲评

STEP 07
注册运营

Owner、版本、适用范围和复核日期

能力晋升状态

状态名称允许用途
C0原始信号原有责任边界内处理
C1经验记录个人回顾或指定团队复盘
C2模式候选研究、整理和专家评审
C3能力候选沙箱测试，不作为默认企业能力
C4验证能力受控试点调用
C5运营能力资产在登记范围内正式调用
C6跨域成熟资产按明确适用条件推广
个人经验不等于企业资产。原始材料应尽量保留在原责任边界；能力提炼优先保留方法、判断标准和证据要求，而不是复制客户、项目或个人信息。
个人贡献、授权和派生资产的处理

提交者应能查看提交内容、抽象方式和发布范围。企业应明确业务目的、使用许可、维护责任、署名和撤回规则。撤回原始资料授权时，需评估派生资产是否仍可合理保留；不能假设派生资产自动失去全部权利，也不能假设企业可无限保留。

05 · Capability Manifest

让能力成为机器可读、可调用、可治理的标准资产

身份与责任

capability_id、type、version、domain、owner、steward。

适用范围

applicability、non_applicability、preconditions 和 stop_conditions。

输入与输出

Input Contract、Output Contract、证据要求和 Schema 引用。

执行方法

procedure、rules、decision_points、tools 和异常处理。

治理与来源

provenance、授权、数据分类、共享范围和审查状态。

评测与复用

evaluation_profile、portability_profile 和已验证范围。

  "type": "skill",

  "domain": "project_delivery",
  "task_family": "project_risk_identification",
  "lifecycle_status": "candidate",
  "applicability": [
    "项目状态评审准备",
    "项目周期性风险初筛"
  ],
  "non_applicability": [

    "项目范围和时间窗口明确"
  ],
  "evidence_requirements": [

  }

06 · Capability Registry

企业能力目录不是 Prompt 文件夹，而是能力治理入口

发现与适配

按领域、任务、角色和标签检索；查看适用范围、不适用条件和评测状态。

版本与依赖

锁定 Manifest、规则、Tool、Ontology 和模型依赖版本。

发布与回滚

支持灰度、暂停、回滚、废弃和退役。

使用与价值

查看调用效果、接受率、人工修正、成本和业务结果。

Agent Registry 与 Capability Registry 的区别

维度Agent RegistryCapability Registry
登记对象Agent 执行单元可复用能力资产
核心问题谁来执行任务？可以使用什么经过验证的方法？
主要内容角色、模型、权限、运行限制任务、规则、步骤、证据、输出、边界
关系一个 Agent 可组合多个能力一个能力可被多个 Agent 调用
语义检索只能发现候选资产，不能直接决定资产是否可用。实际调用还必须检查生命周期、版本、适用条件、依赖和 Policy。
07 · Portability Ladder

把“能不能复用”拆解成六级可验证假设

点击下方等级，查看对应的验证范围和证据要求。各等级不是能力价值排名；并非所有能力都需要达到跨领域复用。

P0 · 原作者、原任务类型

验证能力定义是否能在原作者重复执行中稳定复现。它只能提供初步功能证据，不能证明跨人复用。

等级验证问题主要证据
P0能否稳定复现原方法？原作者重复任务与功能评测
P1是否不依赖原作者个人记忆？同岗位不同人员独立测试
P2能否跨团队环境复用？团队迁移测试与适配记录
P3能否跨相邻角色边界使用？交接、责任和权限测试
P4能否跨岗位复用抽象任务能力？任务家族迁移和领域适配证据
P5能否跨业务领域迁移？本体映射、规则差异和领域专家裁定
“在 3 个团队中验证有效”比“全企业通用”更准确。必须记录已验证范围、未验证范围、适配要求和证据样本。

复用的四个前提

任务结构相似

目标、输入、关键步骤和输出相似。

业务语义兼容

对象、状态、规则含义一致或有映射。

责任权限兼容

使用者具备所需岗位权限和责任。

证据环境可得

能获得所需上下文、工具和证据。

能力包三层适配

已验证的核心能力任务步骤 · 判断框架 · 证据标准 · 输出契约
↓
领域适配 A术语与阈值系统字段映射
领域适配 B流程与规则业务对象映射
领域适配 C证据与输出例外条件
领域适配 D责任与权限调用范围
↓
角色 / 权限配置 → Agent 或人员调用 → 结果评测与反馈
08 · Portability Experiment

用对照实验，而不是主观感受，证明能力是否可迁移

Baseline

现有工作方式

人员使用当前流程和现有工具，不调用该能力资产。

Assisted

能力辅助方式

人员或 Agent 使用锁定版本的能力资产。

Reference

专家裁定

领域专家对同类任务给出参考结果，供独立评审。

推荐实验流程

  1. 先冻结任务家族、样本范围、评分标准和关键错误清单。
  2. 按简单、常规、复杂、冲突、缺失和异常情况分层取样。
  3. 招募原作者、同岗位人员、其他团队和相邻岗位人员。
  4. 条件允许时随机分配或采用交叉设计，控制学习效应。
  5. 由独立评审者盲评，尽量不让评审者知道组别。
  6. 比较质量、证据覆盖、耗时、返工、关键错误和总成本。
  7. 记录迁移损失、适配投入和未验证范围。
  8. 由业务 Owner 作出 Go、Conditional Go 或 No-Go。

核心评测指标

指标衡量内容注意事项
Task Quality / Acceptance任务质量和业务接受率由预先定义的 Rubric 和责任人评价
Evidence Coverage关键结论的有效证据覆盖证据必须可解析和可追溯
Critical Error Rate关键错误任务占比低频高影响错误单独审查
Completion Time / Rework完成耗时和返工比例明确是否包含培训和等待
Transfer Gap不同人、团队、岗位相对原作者的效果差距识别对原作者的依赖
Adaptation Effort新团队配置和维护投入判断复用是否经济
Policy Violation权限或治理违规不能被平均质量抵消
Cost per Accepted Task每个被接受任务的总成本包含模型、工具和人工复核
样本量应根据预期效应、任务波动和可接受错误率确定。样本不足时必须标记为探索性结果，不能宣称已经证明普遍复用。

Go / Conditional Go / No-Go

GO

达到发布条件

质量达标、证据完整、无未授权动作、跨人独立完成、收益超过适配维护成本。

CONDITIONAL

限定范围使用

核心有效，但需要团队适配、培训或人工审核，且只在已验证范围内调用。

NO-GO

暂停或重做

关键错误、证据不足、依赖隐性个人信息、权限风险或维护成本过高。

09 · First Capability Pilot

从项目交付中提炼首批能力，不先建设全企业能力市场

能力资产类型任务目标首要验证等级
项目状态归纳Skill + Template从授权上下文形成状态摘要P1
项目风险初筛Skill + Evidence Standard识别候选风险并提供证据P1
任务依赖分析Skill + Rule找出阻塞链和里程碑影响P1
决策证据核验Skill + Evidence Standard核对审批状态、证据版本和缺口P1
会议行动项提取Skill + Template从授权会议上下文形成行动项候选P1
项目状态评审流程Workflow + Playbook编排分析、核验和人工确认P2

首个样板：项目风险初筛

输入

项目 Context Package、范围、时间窗、任务、里程碑、依赖、风险台账和证据。

处理

检查上下文、识别风险信号、关联证据、区分事实/推断/冲突/未知。

输出

候选风险、影响对象、证据引用、未知、限制和人工确认项。

首轮结论边界：“该能力在已测试的项目交付任务范围内有效或无效”，而不是“企业所有项目经理都能使用”。
10 · Agent Runtime Integration

能力调用必须经过 Registry、适用性检查和 Policy

用户目标 / 业务事件
↓
Orchestrator 获取 ADS Context Package
↓
Capability Registry 检索候选能力检查版本、生命周期、适用条件和依赖
↓
Policy Service 校验主体、用途、范围和动作权限
↓
Agent Runtime 按锁定版本和契约执行
↓
Verifier 核验证据与输出 → 人工确认 → 反馈评测

能力选择不是简单的语义相似度匹配

  • 任务类型是否匹配；
  • 上下文和前置条件是否满足；
  • 能力状态、版本和依赖是否有效；
  • 当前主体是否有权限；
  • 是否处于已验证的适用范围；
  • 所需证据和工具是否可用；
  • 当前任务风险等级是否允许。

每次调用至少记录

capability_id、version、manifest_hash、run_id、task_id、agent_id、context_id、ontology_version、policy_version、输入摘要、输出 Artifact 引用、前置条件检查结果、依赖版本、人工接受或修正结果、耗时和成本。

能力包不携带个人或系统凭证；能力被 Agent 调用，不意味着 Agent 获得额外业务权限。能力输出仍是候选结果，不能覆盖权威业务事实。
11 · Lifecycle & Operations

发布不是终点，能力需要持续复核和退役

candidate → in_review → sandbox
↓
validated → published
↓
正常维护版本更新回归评测
质量异常suspended调查与回滚
不再推荐deprecated迁移窗口
停止使用retired保留审计引用

必须触发复核的变化

  • 业务制度、流程、阈值或领域本体变化；
  • Tool / Connector API 变化；
  • 模型或 Prompt 升级导致输出行为变化；
  • 质量、证据覆盖或接受率持续下降；
  • 新团队使用时出现系统性迁移失败；
  • 授权、隐私、知识产权或安全问题；
  • 能力 Owner 离岗且没有继任者。
人工反馈如何进入新版本

先将接受、修正、驳回和例外记录归类，再判断是上下文、能力、规则、工具、权限还是评测问题。由 Owner 评审后生成候选版本，在固定评测集和新增案例上回归，通过必要审批后灰度发布，并保留回滚能力。

运营指标

资产健康

已验证资产占比、无人维护资产、过期和暂停资产比例。

复用效果

跨人 / 团队 / 岗位等级、Transfer Gap、适配投入。

业务价值

被接受调用比例、返工改善、周期改善和单位成果成本。

12 · Operating Model

每项正式能力都要有 Owner 和明确的责任链

角色主要责任
经验贡献者提交有价值的任务经验，确认来源与分享范围
Capability Author将经验抽象为结构化能力候选
Domain Expert核验业务规则、适用条件和专业质量
Capability Owner对定义、版本、质量、维护和退役负责
Data / Privacy Steward审查来源、敏感信息和使用边界
Security / Policy Owner审查调用权限、工具风险和策略要求
Evaluation Owner建立评测集、裁定标准和迁移实验
Agent Platform Owner提供 Registry、Runtime、版本和调用机制
Business Process Owner确认流程责任、业务价值和人工确认节点

建议每周检查新候选资产和失败案例；每月复核高频能力、Owner、质量和成本；每季度检查跨团队证据、版本健康和领域规则变化。

14 · Architecture Decisions

建议形成十项架构决策

ADR推荐选择原因
01 沉淀对象Capability Asset，而非个人记忆副本明确可复用的任务能力
02 能力实现Manifest + Skill / Rule / Playbook 组合包避免 Prompt 单体化
03 资产来源授权经验、业务结果、复盘和验证样本保留来源与权利边界
04 发布条件结构化契约、独立评测和明确 Owner避免未经验证的经验成为标准
05 复用评估P0—P5 分层验证不把跨人和跨域混为一谈
06 能力发现Registry + 适用条件 + Policy语义相似不等于可以调用
07 版本策略锁定版本、依赖和回滚保证运行可复现
08 质量反馈人工审核后进入新版本防止单次反馈污染生产能力
09 组织责任每项正式能力必须有 Owner保证长期维护
10 成熟度评价被接受结果和迁移证据避免数量导向
15 · Readiness Checklist

提炼前、发布前、跨人复用前的检查清单

能力提炼前
  • 业务任务和目标明确；
  • 来源、授权和共享范围确认；
  • 个人、客户、商业秘密和知识产权已识别；
  • 个人偏好、项目特例和通用任务方法已区分；
  • Author、Domain Expert 和 Owner 明确；
  • 预期复用等级与验证范围明确。
发布候选能力前
  • Manifest 通过 Schema 校验；
  • 输入输出契约和证据要求明确；
  • 前置条件、不适用条件和停止条件明确；
  • 工具、规则和上下文依赖已登记；
  • 权限、数据分类和治理审查通过；
  • 评测样本、人工裁定、版本和回滚策略明确。
宣称跨人或跨岗位复用前
  • 原作者之外人员独立完成测试；
  • 没有依赖原作者逐项指导；
  • 有 Baseline 与 Assisted 对照；
  • 样本覆盖不同复杂度和异常情况；
  • 评审尽可能采用盲评；
  • 关键错误、证据覆盖和政策违规单独统计；
  • 迁移损失和适配成本可解释；
  • 已验证范围与未验证范围明确；
  • 业务责任人批准扩大使用范围。
进入长期运营前
  • Registry 和调用记录可用；
  • 每项资产有持续维护 Owner；
  • 版本变更有回归测试；
  • 暂停、回滚和退役机制可用；
  • 人工反馈不会直接修改生产能力；
  • 能力效果和业务结果可以关联。
Conclusion & Next Research

不是堆积更多 Prompt 和 Agent，而是持续积累经过验证、可以复用、可以治理、可以改进的企业工作能力。

把经过验证的工作方法转化为可复用能力。

Agent Runtime

在任务和权限范围内调用能力完成工作。

Feedback & Evaluation

用真实结果验证和改进能力资产。

Enterprise Advantage

将业务经验沉淀为可持续积累的组织能力。
