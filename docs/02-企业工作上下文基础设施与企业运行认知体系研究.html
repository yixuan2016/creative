摘要：企业数智底座下一阶段要补上的能力

企业已经拥有 ERP、CRM、项目管理、财务、人力、即时通讯、文档和各类业务系统。这些系统记录了大量业务对象、流程节点和业务结果，但企业真实运行还包含大量分散在系统之间的活动与上下文：一项任务为何改变、一项决策如何形成、项目为什么延期、风险由谁发现、依赖关系何时变化，以及哪些经验已经被验证为可复用能力。

因此，企业数智底座的下一阶段不应只是继续增加数据接入和知识库容量，而应研究一种新的基础能力：企业工作上下文基础设施（Enterprise Work Context Infrastructure）。它将经过授权的工作事件、业务对象、决策、任务、依赖、风险、证据和能力资产关联起来，形成带有时间、来源、责任、状态和权限边界的企业运行上下文。

核心判断：企业数智底座要从“数据与知识承载”进一步发展为“企业运行上下文承载”。上下文不是原始活动数据的堆积，而是经过来源校验、语义映射、时间关联、权限判断和责任确认后形成的任务相关视图。
  1. 企业运行状态必须区分事实、推断、冲突和未知。
  2. 企业工作感知不是员工监控，不以全员持续采集作为默认前提。
  3. Agent 应获得任务所需的最小上下文，而不是默认读取企业所有数据。
  4. 企业能力复用的核心对象是经过验证的流程、规则、模板和 Skill。

1. 研究背景：从企业信息化到企业运行理解

1.1 传统系统记录了什么，又遗漏了什么

企业系统通常以业务对象和流程事务为中心：CRM 记录客户和商机，ERP 记录订单和资源，项目系统记录任务和里程碑，财务系统记录收入和成本，协同系统记录消息和文件。这些记录重要，但分散在不同系统中，语义、时间粒度、对象 ID、状态定义和权限模型并不一致。

企业实际运行还包含任务变化、决策约束、跨项目问题关联、延期原因、客户反馈复现、经验验证等连接性信息。这些信息可能散落在会议、邮件、即时通讯、文档批注、项目记录和个人工作记忆中。把它们汇总成文档，并不意味着企业已经理解它们之间的关系。

1.2 从“有数据”到“有上下文”

层次企业具备的能力典型问题
数据可见查询业务系统和文件数据在哪里？
信息可检索搜索文档、知识库和记录哪些资料可能相关？
上下文可理解关联对象、事件、任务、决策和状态发生了什么、为什么、现在如何？
运行可协同受控地判断、执行、验证和改进下一步谁做什么，结果如何确认？

本研究聚焦第三层，并研究如何安全地支撑第四层。并非每个场景都需要完全自动执行；高风险动作仍应保留人工审批。

1.3 核心研究问题

  • 如何从分散系统和经授权的工作信息中识别企业相关事件？
  • 如何把事件关联到统一的企业业务对象和领域语义？
  • 如何形成当前状态、历史变化、来源证据和未解决事项？
  • 如何识别信息缺失、事实冲突、状态过期和责任不明确？
  • 如何为不同 Agent 提供任务范围内、权限正确、版本明确的上下文？
  • 如何在不建立员工持续监控体系的前提下，获得足以改善业务的运行理解？

2. 与 ADS 三级数智底座的关系

本研究深化企业数智底座能力，不改变 ADS-12、ADS-19 和总体架构 V1.0-Review 已建立的三级责任边界。

第一级

个人数智底座

个人工作上下文的自主沉淀与管理，包括个人工作事件、个人记忆、任务和经授权的个人资产。

边界：不默认向企业开放个人完整记忆。

第二级

企业数智底座

企业运行上下文的主要承载和治理主体，包括业务对象、工作事件、决策、任务、风险、证据、标准数据和能力资产。

边界：不无差别汇聚员工私人信息或原始录音。

第三级

业务领域中心数智底座

共同语义、联邦目录、跨域协同与治理，包括 ADS 共同本体、资产元数据、能力目录、授权协调和跨域任务。

边界：不替代企业业务责任，不成为企业原始数据总仓。

2.1 企业数智底座的定位深化

企业数智底座是企业自己的业务数据与知识基础设施，并进一步增加运行上下文能力。它包括企业业务系统与业务数据库、企业知识库和标准、企业标准业务数据、企业工作事件与协同记录、企业运行上下文模型和状态视图、企业证据与能力资产，以及 Agent 上下文服务和权限控制。

企业工作上下文基础设施不是一个新的独立数据孤岛，而是企业数智底座内部的一组关键能力。它应连接权威业务系统，避免无意义复制所有原始数据。

2.2 ADS 的作用

ADS 提供共同语义、身份与代表关系、授权协调、联邦资产目录、能力注册发现、跨域任务协同、审计与评价机制。企业仍负责自身业务对象、数据质量、业务规则和专业验收。ADS 可以协调任务和语义，但不能因此自动获得企业数据所有权或替代企业业务负责人验收。

3. 核心概念：什么是企业工作上下文

企业工作上下文，是在特定时间、业务范围和授权目的下，围绕一个任务、业务对象或决策所组织的、可追溯的相关事实、事件、状态、关系、证据、责任和未解决事项的集合。

它至少回答六个问题：发生了什么、涉及什么、为什么发生、现在如何、还缺什么、接下来能做什么。

3.1 企业工作上下文不等于什么

概念区别
企业知识库以文档和知识条目为主；上下文还包含事件时间线、业务对象关系、动态状态和未解决事项。
数据湖 / 数仓擅长存储、整合和分析数据；上下文层进一步组织任务相关语义和状态解释。
企业搜索返回相关内容；上下文需要解释内容与当前任务、对象和状态的关系。
流程挖掘分析事件日志中的流程模式；上下文还需连接非结构化事件、决策依据、责任和实时状态。
知识图谱表达实体和关系；运行上下文还强调时间有效性、来源、状态、授权和任务作用域。
数字孪生可为孪生模型提供事件和业务解释，但不等同于完整数字孪生系统。
Agent Memory面向特定 Agent；企业上下文是由企业责任方治理、可供多个获授权 Agent 使用的资产。

3.2 六类核心上下文

类型关注内容示例
执行上下文任务、负责人、状态、期限、依赖、进展项目交付为什么卡住
决策上下文决策、参与角色、依据、约束、备选方案需求为什么被暂缓
关系上下文客户、项目、产品、团队和资源关系客户问题关联哪些产品版本
风险上下文风险信号、影响范围、责任人、处置状态多个任务依赖同一未确认资源
资源上下文人力、预算、设备、算力、时间和能力关键资源冲突
能力上下文流程、模板、Skill、适用条件和验证结果已验证的问题处理流程

4. 企业运行上下文模型：事件、对象、状态与证据

4.1 五类基础对象

  1. 业务对象：项目、客户、产品、订单、合同、工单、流程、团队和资源。
  2. 工作事件：业务活动、状态变化、会议决策、问题发现、客户反馈、任务分配和结果验收。
  3. 状态：对象在特定时间的状态及其有效区间。
  4. 证据：支持事实或判断的原始记录、系统引用、文件、核验记录或人工确认。
  5. 能力资产：经过验证、版本化、明确适用范围的流程、规则、模板和 Skill。

4.2 关键关系

事件发生于业务对象；事件由角色或系统产生；事件改变对象状态；决策基于证据和约束；任务由责任主体承担并依赖其他任务或资源；风险影响一个或多个对象；能力资产适用于特定流程。关系应有类型、方向、有效时间和来源，不能只建立无语义的“相关”边。

4.3 工作事件关键字段

字段含义
event_id / event_type事件标识与事件类型
occurred_at / observed_at / recorded_at发生、观察和记录时间
actor_ref / object_refs参与角色与业务对象引用
action / change动作或状态变化
source_ref / evidence_refs来源与支持证据
confidence / verification_status置信度与验证状态
authorization_ref授权引用
ontology_version共同本体与领域本体版本
sensitivity / purpose敏感级别和处理目的
lifecycle_status候选、确认、争议、失效或归档状态

4.4 必须保留时间语义

至少区分发生时间、观察时间、记录时间和有效时间。例如负责人周一发生变更，周三才录入系统，应保留“周一生效、周三记录”。时间语义是还原历史、判断信息新鲜度和处理冲突的基础。

4.5 状态认知分级

  • 已确认：由权威业务系统或责任人确认。
  • 观察到：来源中出现，但业务含义待确认。
  • 推断中：AI 根据多条信息推断，尚未确认。
  • 存在冲突：多个可信来源给出不一致状态。
  • 已过期：超过该类信息的有效时间或刷新周期。
  • 未知：证据不足，不能判断。
例如，“会议中有人提到可能延期”不能被自动改写为“项目已延期”。AI 推断不能覆盖业务系统事实。

5. 参考架构：企业工作上下文基础设施

5.1 五个能力层与一个治理平面

  1. 多源业务感知与连接：业务系统、项目系统、CRM/ERP、文档、会议、日历、邮件、协同平台和经授权工作记录。
  2. 事件理解与标准化：事件识别、实体解析、去重、时间归一、来源登记、置信度和人工确认。
  3. 企业语义与对象关联：共同本体、领域本体、跨系统对象身份映射。
  4. 运行上下文与状态引擎：事件时间线、当前状态、决策链、任务依赖、风险关系和证据链。
  5. 上下文服务与 Agent 协同：按任务、角色、用途和风险生成上下文包，供 Agent 查询、分析或申请执行。

横向治理平面包括身份与代表关系、对象级权限、授权和用途限制、来源溯源、质量、本体与模型版本、审计、撤回、纠错、Agent 工具权限、人工审批和回滚。

5.2 上下文包（Context Package）

不建议让 Agent 直接读取整个企业上下文图谱。每次任务应生成范围明确的上下文包，包含任务目标和调用主体、相关业务对象与权威来源、当前状态与更新时间、关键事件时间线、决策约束和依赖、风险冲突与未知项、证据引用、可用动作和审批要求，以及上下文、本体、数据和策略版本。

上下文包遵循最小必要原则，按角色、任务、目的和时间窗口裁剪。信息不足时应请求补充或转人工，而不是自行填补事实。

6. 与现有企业系统的关系：不取代权威系统

6.1 权威数据与上下文视图分离

  • 每类关键业务属性登记权威来源和责任方。
  • 上下文层保留原系统对象 ID、更新时间和来源引用。
  • 多源冲突时展示冲突和来源，不擅自覆盖。
  • 推断字段标注状态、依据和置信度。
  • 需要回写的字段通过受控 API 或业务流程写回权威系统，并保留审批和审计。

6.2 连接策略

连接方式适用场景注意事项
API 查询获取当前权威业务状态控制频率、权限和字段范围
事件订阅 / Webhook感知状态变化处理重复、乱序、丢失和重放
定时同步旧系统不支持事件订阅明确新鲜度和同步窗口
受控引用文件、知识库或原始记录访问时再次校验权限
人工确认录入决策、经验和非结构化事项记录确认人、时间和依据
批量导入历史数据初始化明确来源、质量和时间边界

6.3 防止形成新数据孤岛

采用统一事件模型和语义映射；保留源系统 ID 和原始引用；使用开放、可迁移的数据格式；目录只登记元数据和受控引用；上下文层可替换，不把关键业务流程锁定在单一厂商或模型上。

7. 企业运行认知的关键能力

状态重建

从离散事件和权威系统数据中重建对象当前状态，同时保留变化历史。

依赖与阻塞识别

识别任务、团队和资源依赖，提出共享瓶颈候选并交由业务责任人确认。

决策脉络追溯

关联问题、备选方案、约束、证据、参与角色和后续结果。

风险信号聚合

聚合延期、客户反馈、质量问题和资源冲突，区分确认风险与待核验线索。

信息缺口发现

识别责任人缺失、依据缺失、状态过期、系统冲突和待补证据。

能力沉淀复用

从验证过的实践提取流程、模板、规则和 Skill，记录适用范围和失败边界。

8. Agent 如何使用企业运行上下文

8.1 从问答到任务上下文协同

上下文驱动的 Agent 先识别任务，再获取相关对象、状态、约束、证据和权限，最后决定是回答、建议、请求确认还是执行动作。

8.2 分级自治策略

风险等级行为类型建议控制
低风险搜索、摘要、状态解释、提醒草稿授权范围内可自动完成，保留来源
中风险创建任务草稿、资源协调建议、更新非关键字段预览与人工确认后执行
高风险财务承诺、合同变更、客户正式承诺、人员决策、关键生产操作有权限人员审批，必要时双人复核
禁止或不适用超出授权目的、访问敏感个人信息、规避业务控制阻断并审计

8.3 执行可追溯与反馈闭环

记录调用者、Agent 身份、任务 ID、上下文包 ID、来源与版本、策略版本、工具调用、审批人、执行结果、错误和回滚情况。区分 Agent 建议、人员决定、工具执行结果和业务责任人确认的业务结果。

9. 关键创新点

  1. 企业运行上下文层：在业务系统、知识资产和 Agent 之间建立统一上下文层。
  2. 企业工作事件账本：以可追溯事件作为业务变化的连接单位。
  3. 状态可信度与不确定性治理：区分确认、观察、推断、冲突、过期和未知。
  4. 任务级上下文包：为 Agent 提供最小、受控、可追溯的上下文。
  5. 决策链与依赖图：追溯决策原因，并在条件变化时重新评估。
  6. 企业能力验证式沉淀：把反复实践转化为版本化能力资产。
  7. 运行缺口主动发现：发现状态过期、责任缺失、依赖阻塞和证据不足。

10. 试点建议：从一个可观察的业务闭环开始

10.1 首选试点类型

建议优先考虑“项目交付与跨团队协同”或其他具有明确对象、任务、责任人、状态、依赖和结果的流程。这类流程通常能观察到项目系统、会议、文档和协同平台之间的上下文断点，且业务结果较易定义。最终选择应以数据授权清晰、业务负责人明确、风险可控和能够形成对照组为准。

10.2 最小闭环

  1. 选择一个项目或流程，明确业务负责人和参与角色。
  2. 接入一个权威业务系统和一类经批准的协同信息源。
  3. 建立少量核心业务对象和事件类型，不追求一次性建成全企业本体。
  4. 对事件做来源登记、去重、对象关联和人工确认。
  5. 形成状态、决策、任务、依赖、风险、证据和未知项的上下文视图。
  6. 让 Agent 先执行低风险动作，例如汇总状态、发现缺失信息、生成任务草稿。
  7. 由业务负责人确认结果，并记录修订、拒绝和执行情况。
  8. 与原有流程对照，评估业务价值和治理成本。

10.3 第一阶段排除项

  • 全员、全时段持续采集音频或屏幕；
  • 一次性接入全部企业 SaaS；
  • 直接建设覆盖所有领域的完整企业知识图谱；
  • 允许 Agent 自动进行高风险业务承诺；
  • 把推断状态自动写回权威业务系统；
  • 将工作上下文用于未经批准的个人绩效画像。

11. 验证指标与评估方法

维度指标建议定义
覆盖关键事件覆盖率抽样业务事件中被正确识别和关联的比例
语义对象关联准确率事件与项目、客户、产品、任务等关联正确的比例
时效状态新鲜度上下文状态距权威来源最近更新时间的时间差
可信来源可追溯率关键结论可追溯到来源和证据的比例
可信冲突识别率已知多源冲突中被识别并标注的比例
完整上下文完整度对象、状态、责任、依赖和证据字段完整程度
运营阻塞发现有效率被业务负责人确认有价值的阻塞提示比例
运营信息补全周期从发现信息缺口到责任人补全的时间

业务周期时间、返工率、遗漏率与原流程基线比较业务结果变化
治理越权访问与错误写入必须设置阻断目标的安全指标
成本单流程上下文成本连接器、模型、存储、人工核验和运维综合成本

同时报告收益和成本。不能只报告摘要数量或识别事件数；必须确认业务结果、错误率、人工核验和治理成本。

12. 分阶段建设路线

阶段主要工作阶段门槛
0. 业务边界与上下文建模选流程、权威系统、对象、角色、事件语义、指标和治理规则责任主体和授权清楚
1. 事件接入与对象关联接入必要数据源，建立事件模型、时间语义、来源引用和对象映射关联质量达标、来源可追溯
2. 运行上下文视图建立时间线、状态、决策、依赖、风险和信息缺口视图业务人员认为上下文真实有用
3. 上下文驱动的 Agent建立任务级上下文包，先开放查询、解释、提醒和草稿业务效果优于基线，权限与审计有效
4. 跨流程能力复用抽象能力资产，明确适用条件、版本和失败边界在新团队或项目中验证迁移效果

阶段和周期需根据企业现有系统、数据治理成熟度和业务风险调整，不构成工期承诺。

13. 风险与治理原则

风险典型表现控制原则
监控化用于员工持续监控或未经批准的绩效画像目的限定、最小必要、透明告知和组织制度审查
事实混淆AI 推断被当作业务事实认知状态分级、来源引用和人工确认
语义错误不同系统同名对象被错误合并身份治理、匹配置信度和人工核验
信息过期旧状态被当成当前状态新鲜度策略、有效时间和过期标记
权限扩张Agent 为方便而读取过多数据任务级上下文包、最小权限和工具白名单
错误执行根据不完整上下文执行写操作风险分级、审批、幂等、回滚和审计
组织抵触员工担心信息被用于非预期用途共同设计规则、禁用场景、申诉和纠错
系统耦合上下文层成为新单体平台标准事件模型、开放接口和源系统权威性
过度建设先做全企业知识图谱而无业务结果单流程最小闭环，按价值扩展
四条不可妥协原则：上下文不是事实的替代品；缺失不是否定；可见不等于可用；自动化不等于自治。

14. 与 ADS 既有架构研究的衔接

既有架构主题本研究承接方式
ADS 共同本体与业务领域本体为工作事件、业务对象、任务、决策、证据和能力提供共同语义与专业语义
三级数智底座企业运行上下文由企业数智底座承载；个人数据留在个人责任边界；中心侧通过联邦目录和治理协同
ADS 执行端、管理端、考核端执行端调用受控上下文；管理端治理对象、授权和能力；考核端评价任务质量、风险和改进结果
联邦资产目录登记上下文资产、能力资产和标准数据的元数据、责任方、版本、授权与受控引用
证据与标准数据双轨证据支持核验和追溯；经验证的标准数据供 Agent 运行
混合式部署按数据责任、敏感级别和时效选择本地、企业私有环境或云端协同

本研究不新增第四级数智底座，也不把企业工作上下文基础设施定义为 ADS 之外的另一个中心平台。它是企业数智底座内部的能力体系，并通过 ADS 既有治理机制参与跨层协同。

16. 研究结论：企业数智底座需要具备“理解运行”的能力

企业数智底座的价值不应只用接入多少系统、存储多少文档、建设多少知识库或部署多少 Agent 来衡量。更重要的是，它能否逐步形成对企业运行的可信理解。

  • 知道企业有哪些关键业务对象；
  • 理解对象之间如何关联；
  • 看见业务活动和状态变化；
  • 追溯决策、任务和结果的形成过程；
  • 识别风险、依赖、冲突和信息缺口；
  • 将经过验证的能力交给合适的 Agent 使用；
  • 在授权和责任边界内推动执行、验证和持续改进。
建议的演进方向：从企业数据与知识底座，发展为具备业务语义、工作上下文、运行状态理解和 Agent 协同能力的企业数智基础设施。

近期最值得验证的命题

选择一个项目或业务流程，验证系统能否把分散在业务系统、会议和协同记录中的信息，形成准确的对象关系、事件时间线、当前状态、决策依据、任务依赖和未解决事项；再验证企业 Agent 是否能利用这个上下文减少遗漏、缩短处理周期，并保持可审计、可回滚和权限正确。

如果这个最小闭环成立，企业数智底座就不再只是“存放企业数据和知识的地方”，而开始成为“持续理解企业如何运行、并在授权范围内帮助企业改善运行”的基础设施。
