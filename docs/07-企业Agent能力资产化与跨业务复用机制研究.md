## 摘要：从“使用 AI”走向“积累企业自己的 AI 能力”

企业使用 AI 的方式，正在从单次问答、文档生成和知识检索，逐步发展为 Agent 执行任务、多 Agent 协同和业务流程辅助。但如果每次任务仍然从零开始，如果关键经验只存在于某位员工的记忆、聊天记录或个人提示词中，那么企业即使部署了很多 Agent，也未必真正积累了组织能力。

本专题提出：**企业应建立一套以 Capability Asset（能力资产）为核心的沉淀、验证、发布、调用和反馈机制，把经过授权和验证的工作经验转化为可复用的企业能力。**

这里所说的能力资产，不等于个人记忆、知识文章或 Prompt 的简单集合。它必须具备明确的适用任务、输入条件、执行方法、输出契约、证据要求、适用边界、责任归属、版本记录和评测结果。只有当某项能力经过独立验证，并且在明确的适用范围内持续产生价值，它才可以从经验候选升级为企业可运营的能力资产。

### 核心判断

1. **企业真正需要沉淀的不是员工的全部记忆，而是经过抽象和验证的工作能力。** 原始记录首先属于其原有责任边界；个人经验不能默认成为企业共享资产。
2. **能力资产是连接工作上下文与 Agent 执行的中间层。** ADS 运行认知引擎回答“发生了什么、当前是什么、依据是什么”；能力资产回答“在这类任务中，经过验证的方法是什么”；Agent Runtime 负责在任务条件和权限允许时调用能力。
3. **Skill 不是 Prompt，能力资产也不是知识库文档。** Prompt 可以是能力实现的一部分，但一个可运营的能力资产还必须定义输入输出、前置条件、步骤、规则、证据、异常、风险、责任和评测。
4. **复用不是把一个人的工作方式复制给另一个人。** 应把可迁移的任务结构、判断规则、证据标准、工具操作和异常处理从个人风格中分离出来，再验证其适用范围。
5. **跨人、跨岗位、跨团队和跨领域复用是不同难度的假设。** 必须分层验证，不以一次演示、单个专家认可或单项目成功宣称普遍复用。
6. **能力资产必须明确“不适用条件”。** 不知道何时不应该调用，比只描述如何调用更容易造成企业级风险。
7. **能力资产要有生命周期和责任人。** 发布不是终点；模型、流程、制度、工具、业务对象和外部环境变化，都可能使能力过时。
8. **企业能力资产的价值应以被接受的业务结果衡量。** 不以资产条目数量、Prompt 数量、Agent 数量、调用次数或 Token 消耗作为核心成功指标。

### 本专题要形成的交付物

- 企业能力资产的定义、分类和分层模型；
- 个人经验到企业能力资产的授权与转化流程；
- Capability Manifest（能力资产描述契约）；
- Capability Registry（企业能力资产目录）及版本治理；
- Skill、Rule、Playbook、Workflow、Template、Tool、Evaluation Set 的边界；
- 项目交付首批能力资产样例；
- 跨人、跨团队、跨岗位、跨领域的分层复用验证框架；
- 可执行的对照评测方案、指标和 Go / No-Go 门槛；
- 能力资产的运营、反馈、更新、废弃和责任机制；
- 与 ADS Context、Ontology、Policy、Agent Runtime 的架构关系。

> **一句话定位：把个人和团队的工作经验转化为有来源、有边界、有契约、有评测、有版本、有责任人的企业能力资产，并让 Agent 在合适的任务中安全调用。**

## 1. 为什么企业需要能力资产化

### 1.1 只建设知识库，为什么仍然不够

知识库解决的是信息保存、检索和阅读问题，但很多工作并不是“找到一篇资料”就能完成。真正影响任务质量的往往是：

- 面对不同业务情况，应该先检查什么；
- 哪些信息可以作为证据，哪些只是线索；
- 发现冲突时应该找谁确认；
- 什么时候需要升级给负责人；
- 哪些步骤必须按顺序完成；
- 哪些条件不满足时不能继续；
- 结果达到什么标准才算完成；
- 遇到例外时如何降级或停止。

一份项目复盘文档可能写明“要加强风险管理”，但它不一定告诉 Agent：什么信号构成候选风险、如何评估影响、需要哪些证据、何时升级、谁负责确认，以及哪些风险不能由模型自行定级。

因此，企业需要从“知识内容沉淀”进一步走向“可执行、可验证的能力沉淀”。

### 1.2 只沉淀 Prompt，为什么也不够

Prompt 可能包含专家经验，但它通常缺少：

- 明确的任务边界；
- 可验证的输入和输出 Schema；
- 对上下文版本和数据来源的要求；
- 业务规则与授权边界；
- 不适用条件和异常处理；
- 版本变更和回滚机制；
- 独立评测集与效果证据；
- 能力所有者和维护责任。

一个 Prompt 在作者自己的模型、项目和上下文中有效，并不意味着换一个人、换一个团队或换一个模型仍然有效。

**Prompt 可以是能力实现材料，但不能单独代表能力资产。**

### 1.3 企业能力为什么容易流失

| 流失位置 | 典型表现 | 企业后果 |
|---|---|---|
| 个人经验 | 专家知道怎么做，但过程没有结构化 | 人员变动后能力难以延续 |
| 临时对话 | AI 对话中形成了有价值的方法，但没有版本和责任人 | 结果无法复现 |
| 项目复盘 | 复盘写了问题和建议，没有转成可执行标准 | 相同问题反复发生 |
| 个人 Prompt | 个人反复调试出有效提示词 | 难以治理和跨人使用 |
| 团队流程 | 流程依赖熟练员工的口头解释 | 新人上手慢、团队差异大 |
| 工具脚本 | 脚本和自动化散落在个人目录 | 无人维护、权限和风险不清 |
| Agent 运行 | 一次协同任务成功，但没有留下可复用契约和评测 | 每次任务都重新摸索 |

### 1.4 研究目标

建立一套机制，使企业能够：

1. 在合法、明确和必要的前提下识别有价值的工作经验；
2. 把经验中的任务结构、判断规则、证据要求和异常处理抽象出来；
3. 将个人信息、客户信息和项目特定信息与可复用方法分离；
4. 形成结构化、版本化、可调用的 Capability Asset；
5. 在沙箱和真实但受控的业务任务中验证能力；
6. 分层验证其跨人员、跨团队、跨岗位和跨领域的适用性；
7. 让 Agent Runtime 按任务上下文和策略调用能力；
8. 将使用结果、人工修正和业务反馈回流，持续更新资产。

### 1.5 非目标

本专题不主张：

- 将员工全部聊天、录音、邮件和个人记忆汇总成企业能力库；
- 将个人的工作风格、判断偏好或私人信息复制给其他员工；
- 将所有知识文章自动转换成 Skill；
- 将所有 Prompt 自动发布为企业标准；
- 以一个专家的成功案例证明能力具有普遍适用性；
- 让能力资产绕过业务流程、专业责任或系统权限；
- 用 Agent 调用次数代替能力的业务价值；
- 将个人经验中的第三方商业秘密、客户信息或受限内容直接纳入共享资产。

## 2. ADS 能力资产的概念与架构位置

### 2.1 定义：什么是 Capability Asset

**Capability Asset（能力资产）**是企业在明确业务目的和治理边界下，对可重复工作能力进行结构化描述、验证、版本化、登记和运营后形成的数字化资产。

一个能力资产至少要回答十个问题：

1. 它解决什么任务？
2. 谁可以使用？
3. 需要什么输入和上下文？
4. 需要哪些前置条件？
5. 按什么方法或规则完成？
6. 应产生什么输出？
7. 输出需要什么证据支持？
8. 什么时候适用、什么时候不适用？
9. 出错或遇到例外时如何处理？
10. 如何证明它有效、由谁维护、何时复核？

如果一项内容无法回答其中的关键问题，它可能是知识材料或经验候选，但还不能被视为成熟的企业能力资产。

### 2.2 与 ADS 其他能力的关系

| ADS 能力 | 回答的问题 | 主要产物 |
|---|---|---|
| Work Sensing | 工作中发生了哪些可感知信号？ | 原始信号、工作事件候选 |
| Work Context | 这件事涉及哪些对象、活动和上下文？ | WorkEvent、BusinessObject、EvidenceRef |
| Ontology | 这些对象、关系和概念是什么意思？ | 共同本体、领域本体、语义映射 |
| Runtime Cognition | 企业当前状态是什么，依据和未知在哪里？ | StateAssertion、ContextPackage |
| Capability Asset | 这类任务有哪些经过验证的方法和能力？ | Skill、Rule、Playbook、Workflow、Template |
| Agent Runtime | 当前任务由谁、调用什么能力、如何协同？ | Run、Task、Delegation、Artifact |
| Policy & Governance | 谁能访问、调用、修改或发布？ | 授权、审批、审计、版本责任 |
| Feedback & Evaluation | 能力是否有效，怎样改进？ | Evaluation Result、Feedback Event、版本决策 |

**架构约束：能力资产归属企业数智底座的能力资产管理与运营范畴，不新增 ADS 第四级数智底座。** 个人数智底座、企业数智底座和业务领域中心仍按既有责任边界协同。

### 2.3 能力资产不是企业事实

必须区分：

- **企业事实：** 某项目当前状态、某任务负责人、某决策是否审批，由权威业务系统和 ADS 运行认知机制负责。
- **证据：** 支持事实或判断的记录、文档、事件和确认。
- **能力：** 面对某类任务，经过验证的方法、规则和操作步骤。
- **执行结果：** 某次 Agent 或人员调用能力后产生的结果。
- **评测结论：** 在明确样本、条件和标准下，对能力表现的评价。

能力资产不能把“以前某个项目成功过”变成“现在这个项目一定适用”。调用能力时仍需读取当前 Context Package，核对适用条件。

## 3. 能力资产分类：把不同类型的经验放到正确位置

### 3.1 推荐分类

| 类型 | 定义 | 典型示例 | 主要实现 |
|---|---|---|---|
| Skill | 可重复调用的专业任务能力 | 项目风险初筛、证据完整性检查 | 代码、模型、规则或混合 |
| Playbook | 面向一类业务情境的步骤和处理指南 | 项目延期风险处置手册 | 结构化步骤与分支 |
| Rule | 明确的判断约束或业务规则 | 交付物未审批不得标记为正式验收 | 确定性规则或策略服务 |
| Workflow | 多步骤任务、角色和状态的流程编排 | 周期性项目状态评审 | 工作流引擎 / Orchestrator |
| Template | 具有固定结构的交付物模板 | 项目状态评审报告模板 | 文档 / 结构化 Schema |
| Tool | 与外部系统交互的接口能力 | 查询项目任务、读取风险台账 | API / Connector |
| Decision Pattern | 可复用的决策框架、判断树或分析方法 | 关键路径风险判断框架 | 决策树、规则、模型辅助 |
| Evidence Standard | 某类结论的证据要求 | 延期风险需要计划日期、当前状态和依赖证据 | 证据规则与 Schema |
| Evaluation Set | 用于判断能力表现的标准样本和裁定 | 风险识别历史案例集 | 测试样本、标签和评分标准 |
| Ontology Pattern | 领域概念和关系的可复用语义模式 | 项目—任务—里程碑—风险关系 | 领域本体与映射 |

### 3.2 不要把所有东西都叫 Skill

以下边界应保持清晰：

- Prompt：模型交互指令或任务提示。
- Skill：可以被调用并完成明确任务的能力实现。
- Rule：具有明确适用范围和确定性判定逻辑的规则。
- Playbook：人或 Agent 可遵循的情境化处理方法。
- Workflow：多个步骤、角色、条件和审批组成的流程。
- Tool：访问系统或执行动作的接口。
- Template：输出内容的结构与格式。
- Capability Asset：上述一种或多种组件经过组合、验证和治理后形成的可运营资产包。

### 3.3 能力资产组合包

一个面向 Agent 的能力资产通常不是单个 Prompt，而是一个有依赖关系的组合包：

~~~mermaid
flowchart TB
  A[Capability Package]
  A --> B[Capability Manifest]
  A --> C[Task Contract]
  A --> D[Skill / Playbook]
  A --> E[Rules / Decision Patterns]
  A --> F[Evidence Standard]
  A --> G[Tool References]
  A --> H[Output Template]
  A --> I[Evaluation Set]
  A --> J[Governance & Version]
~~~

Manifest 负责描述整个包；内部组件可以独立版本化，但发布时必须锁定依赖版本，避免“同一个能力版本实际调用了不同规则”。

## 4. 从个人经验到企业能力：授权、抽象与晋升机制

### 4.1 个人经验不等于企业资产

个人数智底座中的工作事件、个人记忆、私人判断和临时记录，应首先服务于个人自身的工作理解和管理。企业侧不能默认读取或自动吸收。

进入企业能力资产化流程前，至少需要确认：

- 是否有明确的企业业务目的；
- 信息来源和采集方式是否符合组织规则；
- 是否包含个人隐私、客户数据、第三方信息或商业秘密；
- 相关人员是否具有提交或授权分享的权利；
- 是否可以去标识化、泛化或仅保留方法；
- 是否需要业务、数据治理、安全或知识产权审核；
- 资产发布后谁有权访问、修改、撤回或停止使用。

### 4.2 能力提炼的七步流程

1. **识别经验信号：** 从已授权的工作事件、任务结果、复盘和人工反馈中发现重复出现的有效做法。
2. **建立经验候选：** 记录任务目标、输入条件、实际步骤、判断依据、结果和例外。
3. **拆分个人与组织因素：** 区分个人偏好、特定项目背景、岗位权限、通用任务结构和可迁移规则。
4. **抽象能力结构：** 提炼前置条件、输入、步骤、决策点、证据、输出、失败处理和不适用条件。
5. **治理审查：** 检查授权、隐私、客户信息、商业秘密、知识产权、数据分类和共享范围。
6. **独立验证：** 在原作者之外的人员和任务样本中进行盲测或对照测试。
7. **注册与运营：** 由能力 Owner 审核发布，登记版本、评测证据、适用范围和复核日期。

### 4.3 能力晋升状态

| 状态 | 名称 | 进入条件 | 允许用途 |
|---|---|---|---|
| C0 | 原始信号 | 工作信息或任务记录出现 | 原有责任边界内处理 |
| C1 | 经验记录 | 来源、任务和结果可描述 | 个人回顾或指定团队复盘 |
| C2 | 模式候选 | 发现重复方法或稳定判断模式 | 研究、整理和专家评审 |
| C3 | 能力候选 | 已形成输入、步骤、输出和边界 | 沙箱测试，不作为企业默认能力 |
| C4 | 验证能力 | 完成基础功能、证据和独立人员测试 | 受控试点调用 |
| C5 | 运营能力资产 | 有 Owner、版本、评测、权限和维护机制 | 在登记范围内正式调用 |
| C6 | 跨域成熟资产 | 在多个团队或领域完成独立复用验证 | 按明确的跨域适用条件推广 |

晋升不是自动流水线。每一级都需要责任人审核；授权撤回、来源权利变化、关键规则失效或重大质量问题可以使资产暂停、降级或退役。

### 4.4 原始材料与可复用能力分离

能力提炼时应尽量保留“方法”，而不是复制原始材料：

| 原始材料中的内容 | 能力化后的处理 |
|---|---|
| 某客户的真实名称和特殊需求 | 去标识化为客户类型或约束类别 |
| 某项目的具体排期和人员 | 抽象为任务依赖和里程碑条件 |
| 专家的个人表达方式 | 不作为必须迁移的能力内容 |
| 专家反复检查的事项 | 转为检查清单或证据规则 |
| 某次临时判断 | 记录为假设，等待更多样本验证 |
| 某项目成功的做法 | 明确适用条件后形成候选 Playbook |
| 真实系统凭证或访问方式 | 不进入能力资产；通过 Tool Gateway 管理 |

### 4.5 个人贡献与组织责任

- 提交者应能查看提交了什么、如何被抽象、发布到什么范围；
- 企业应明确资产的使用目的、访问范围和维护责任；
- 个人贡献不等于个人对企业资产永久拥有控制权，也不意味着企业可无限扩大原始数据用途；
- 资产归属、使用许可、署名、激励和收益分配应由企业制度与适用法律确定；
- 撤回原始资料的授权时，必须评估已发布能力是否仍可合法、合理地保留；不能简单假定派生资产自动失去全部权利，也不能假定可以无限保留。

## 5. Capability Manifest：让能力成为可管理、可调用的标准资产

### 5.1 最小描述结构

每个能力资产至少包含以下信息：

| 分组 | 关键字段 | 目的 |
|---|---|---|
| 身份 | capability_id、name、type、version | 唯一识别与版本管理 |
| 业务定位 | domain、task_family、purpose | 明确解决什么问题 |
| 责任 | owner、steward、approver | 确定维护和发布责任 |
| 适用范围 | applicability、non_applicability、preconditions | 防止错误调用 |
| 输入 | input_contract、context_requirements | 明确需要什么数据 |
| 执行 | procedure、rules、decision_points、tools | 说明如何完成 |
| 输出 | output_contract、evidence_requirements | 明确交付和证据标准 |
| 异常 | exceptions、stop_conditions、escalation | 说明失败和升级方式 |
| 治理 | data_classification、sharing_scope、provenance | 控制数据和共享范围 |
| 依赖 | dependencies、ontology_version、tool_versions | 锁定运行依赖 |
| 评测 | evaluation_profile、evaluation_results | 证明能力质量 |
| 复用 | portability_profile、validated_contexts | 描述已验证的复用范围 |
| 生命周期 | lifecycle_status、review_date、change_log | 持续维护和退役 |

### 5.2 能力资产质量门槛

一项资产在发布前必须通过：

- 任务边界明确；
- 输入和输出可结构化验证；
- 前置条件和不适用条件明确；
- 关键判断有来源或规则依据；
- 证据要求可执行；
- 敏感信息和权利边界完成审查；
- 权限和工具依赖经过校验；
- 至少有一组可重复执行的评测样本；
- 责任人、版本和复核日期明确；
- 有失败、异常和人工升级路径。

### 5.3 能力资产不应隐藏上下文依赖

如果某项能力只有在特定项目、特定客户、特定岗位权限或特定工具版本下有效，必须把这些条件写进 Manifest。

例如，“项目风险初筛”可以是通用任务能力，但具体风险阈值、升级规则和交付物要求可能属于特定业务领域。通用能力应引用领域策略，而不是把某个项目的经验误写成全企业规则。

## 6. Capability Registry：企业能力资产目录

### 6.1 Registry 的作用

Capability Registry 不是一个简单的 Prompt 文件夹，而是企业能力资产的登记、发现、依赖管理、版本控制、发布和状态治理入口。

建议提供以下能力：

- 按业务领域、任务类型、角色和能力标签检索；
- 查询能力的适用范围、不适用条件和评测状态；
- 查看 Owner、版本、依赖和变更记录；
- 检查 Agent 是否具备调用资格；
- 按任务上下文匹配候选能力；
- 对能力版本进行灰度、回滚、暂停和退役；
- 查看调用次数、接受率、人工修正和业务价值；
- 追踪能力的来源、派生关系和贡献记录。

### 6.2 Registry 与 Agent Registry 的区别

| 维度 | Agent Registry | Capability Registry |
|---|---|---|
| 登记对象 | Agent 执行单元 | 可复用能力资产 |
| 核心问题 | 谁来执行任务？ | 执行任务时可以使用什么经过验证的方法？ |
| 主要内容 | 角色、模型、权限、运行限制 | 任务、规则、步骤、证据、输出、边界 |
| 生命周期 | 创建、启用、暂停、退役 | 候选、验证、发布、更新、暂停、退役 |
| 复用方式 | 由 Orchestrator 选择执行者 | 由 Agent / Workflow 调用能力 |
| 评测重点 | 任务执行与协同质量 | 能力本身的正确性、适用性和迁移性 |

一个 Agent 可以组合多个 Capability；一个 Capability 也可以被多个 Agent 调用。**能力资产不应绑定某一个特定 Agent 或某一个模型。**

### 6.3 目录发现与调用流程

1. Orchestrator 根据任务目标和 Context Package 识别任务类型；
2. 查询 Capability Registry，获得候选能力；
3. 检查能力状态、版本、适用条件和依赖；
4. Policy Service 校验调用主体、用途、数据范围和动作权限；
5. 选择能力版本并生成调用记录；
6. Agent Runtime 按能力契约执行；
7. Verifier 检查输出和证据；
8. 记录能力效果、人工反馈和运行成本。

### 6.4 能力版本策略

- Patch：不改变输入输出契约的缺陷修复或实现优化；
- Minor：向后兼容的可选能力、规则或输出扩展；
- Major：输入输出、适用范围、关键判断或风险边界发生不兼容变化。

生产运行应锁定 Capability Version 和依赖版本。不得让一个历史 Run 在无记录的情况下自动切换到新版本。

## 7. 跨人、跨岗位、跨业务复用：把模糊判断变成可验证假设

### 7.1 复用不能只用“能不能迁移”来描述

不同复用场景的差异很大。一个能力在同一专家身上重复有效，不代表新人也能使用；在同岗位不同人员有效，不代表相邻岗位也适用；在同类项目有效，也不代表跨业务领域有效。

因此建议建立六级复用验证阶梯：

| 等级 | 验证范围 | 要回答的问题 | 证据强度 |
|---|---|---|---|
| P0 | 原作者、原任务类型 | 能否稳定复现原方法？ | 初步功能证据 |
| P1 | 同岗位、不同人员 | 是否不依赖原作者个人记忆？ | 基础跨人证据 |
| P2 | 同岗位、不同团队 | 是否能跨团队环境复用？ | 团队迁移证据 |
| P3 | 相邻岗位、相同业务流程 | 是否能跨角色边界使用？ | 跨角色边界证据 |
| P4 | 不同岗位、相同任务家族 | 是否能复用抽象任务能力？ | 任务家族迁移证据 |
| P5 | 不同业务领域 | 是否能跨领域迁移，或需要领域适配？ | 跨域证据 |

这些等级不是能力价值排名。某些能力只需要达到 P1 或 P2 就已经具有很高价值；不能把所有能力都要求做到 P5。

### 7.2 复用的对象应是能力单元，而不是个人

需要区分三个层次：

- **个人方法：** 某个人的习惯、表达、偏好、关系网络和经验判断。
- **任务能力：** 完成某类任务所需的步骤、输入、规则、证据和输出。
- **组织能力：** 经过多人员、多场景验证，并由企业责任方维护的稳定能力。

企业应主要验证第二层能否在适用范围内复用，再决定是否将其提升为第三层。不能为了迁移能力而复制个人记忆或建立对员工的画像。

### 7.3 能力可迁移的四个条件

1. **任务结构相似：** 目标、输入、关键步骤和输出足够相似；
2. **业务语义兼容：** 业务对象、状态、规则和指标含义一致，或存在可验证映射；
3. **责任与权限兼容：** 接收者具有完成任务所需的岗位权限和业务责任；
4. **证据与环境可获得：** 接收者能够获得能力所需的上下文、工具和证据。

如果其中任一条件不满足，就应进行适配、限制使用或拒绝调用，而不是简单复制。

### 7.4 复用适配层

跨人和跨岗位复用时，建议把能力包拆成三层：

- **核心能力层：** 与个人身份无关的任务步骤、判断框架、证据标准和输出契约；
- **领域适配层：** 业务术语、阈值、系统字段、流程和领域规则；
- **角色授权层：** 谁能查看什么、谁能确认什么、谁能执行什么。

这样同一核心能力可以在不同团队中复用，但每个团队仍保留自己的业务规则和权限边界。

~~~mermaid
flowchart TB
  A[已验证的核心能力]
  A --> B[领域适配 A]
  A --> C[领域适配 B]
  A --> D[领域适配 C]
  B --> E[角色 / 权限配置 A]
  C --> F[角色 / 权限配置 B]
  D --> G[角色 / 权限配置 C]
  E --> H[Agent / 人员调用]
  F --> I[Agent / 人员调用]
  G --> J[Agent / 人员调用]
  H --> K[结果评测与反馈]
  I --> K
  J --> K
  K --> L[能力版本决策]
~~~

### 7.5 不同复用等级需要不同证据

- P0：原作者重复执行，证明能力定义至少可以复现。
- P1：不同人员在不依赖原作者临场指导的情况下完成相似任务。
- P2：更换团队后，仍能在团队制度和工具差异可控的情况下达到验收标准。
- P3：相邻岗位使用时，能够明确交接边界和责任，不产生权限越界。
- P4：不同岗位执行同一任务家族时，核心步骤和输出仍然有效，角色适配层能够处理差异。
- P5：不同业务领域中，必须验证概念映射、规则差异和领域专家裁定；若需要大量重写，应视为派生资产，而不是原资产直接复用。

### 7.6 复用不是二元结论

每项能力应记录：

- 已验证等级；
- 已验证的人员、团队、岗位和领域范围；
- 未验证范围；
- 适用条件；
- 需要的适配项；
- 失效条件；
- 证据样本数量和质量；
- 结论的置信边界。

“在 3 个团队中验证有效”比“全公司通用”更准确，也更有管理价值。

## 8. 跨人跨岗位复用的实验设计

### 8.1 实验目标

不是证明 AI 比所有员工都强，而是验证：

**在给定任务家族、上下文、权限和质量标准下，能力资产是否能够帮助不同人员以可接受的质量和成本完成任务，并且不依赖原作者持续指导。**

### 8.2 推荐对照设计

对每一项候选能力，至少设置：

- Baseline：人员使用当前流程和现有工具，不调用该能力资产；
- Assisted：人员或 Agent 使用指定版本的能力资产；
- Reference：由领域专家对同一类任务给出裁定或参考结果；
- Review：由独立评审者盲评，尽可能不让评审者知道样本属于哪组。

条件允许时采用随机分配或交叉设计；如果任务不可重复、学习效应明显或样本量不足，则采用分阶段对照，并明确结果的证据等级。

### 8.3 参与者与样本分层

- 原作者：用于确认能力是否保留原始方法；
- 同岗位不同人员：验证跨人迁移；
- 不同团队同岗位人员：验证团队迁移；
- 相邻岗位人员：验证责任边界和角色适配；
- 不同岗位同任务家族人员：验证任务抽象是否成立；
- 不同领域专家：验证领域迁移和本体适配。

任务样本应覆盖简单、常规、复杂、冲突、缺失和异常场景。不能只挑选能力最容易成功的案例。

### 8.4 控制混杂因素

评测时需要记录或控制：

- 人员经验年限和对任务的熟悉程度；
- 是否接受过能力包培训；
- 项目难度和数据完整度；
- 工具、模型和上下文版本；
- 任务是否具有相似的输入质量；
- 评审者是否知道实验组别；
- 是否存在重复任务导致的学习效应；
- 是否由原作者提供额外帮助；
- 任务耗时是否包含培训和等待时间。

### 8.5 核心指标

| 指标 | 定义 | 说明 |
|---|---|---|
| Task Quality | 任务输出质量评分 | 使用预先定义的评分 Rubric |
| Acceptance Rate | 被业务责任人接受的结果比例 | 不能只看模型自评 |
| Evidence Coverage | 关键结论有有效证据支持的比例 | 适用于需要证据的任务 |
| Critical Error Rate | 关键错误任务数 / 评测任务数 | 对高影响错误单独统计 |
| Completion Time | 从任务开始到可接受结果的耗时 | 需明确是否包含人工等待 |
| Rework Rate | 需要实质性返工的任务比例 | 区分格式修改和内容纠错 |
| Human Correction Rate | 关键内容被人工修改的比例 | 记录修改类型与严重程度 |
| Policy Violation Rate | 越权、违规或不合规调用比例 | 不允许用平均质量抵消 |
| Cost per Accepted Task | 每个被接受任务的总成本 | 包含模型、工具和人工复核 |
| Transfer Gap | 不同人员 / 团队 / 岗位相对原作者的效果差距 | 用于识别迁移损失 |
| Adaptation Effort | 为新团队或岗位所需的配置和维护投入 | 判断复用是否真正经济 |

### 8.6 推荐的统计口径

对于质量评分，可以比较 Assisted 与 Baseline 的差值及其不确定区间；对于关键错误、政策违规等低频高影响指标，应单独做案例审查和压力测试，不能只依赖总体均值。

如果采用交叉实验，应考虑任务顺序、人员学习和残留效应；如果样本不足，应标记为探索性结果，不得宣称已证明跨人或跨岗位普遍有效。

样本量应根据预期效应、任务波动和可接受错误率确定，不在研究前随意指定一个看似精确的统一数字。

### 8.7 Go / No-Go 判断

**Go：**

- 输出满足业务最低质量标准；
- 关键结论证据覆盖达到预先冻结的门槛；
- 没有未授权动作成功；
- 跨人员测试不依赖原作者临场指导；
- 复用收益超过培训、适配、维护和复核成本；
- 不适用条件和失败处理清楚；
- 有明确 Owner 和回滚方案。

**Conditional Go：**

- 核心能力有效，但仅在特定团队、角色或数据条件下成立；
- 需要补充领域适配层或培训；
- 只允许在限定范围和人工审核下使用；
- 需要补充更多独立样本。

**No-Go：**

- 关键结论错误或证据不足；
- 依赖个人隐性信息，无法合理抽象；
- 复用后出现权限、隐私或业务责任问题；
- 适配和维护成本高于重复开发成本；
- 无法明确 Owner、适用范围和失效条件。

## 9. 首批项目交付能力资产组合

建议从 ADS-WORK-05 和 ADS-WORK-06 的项目交付场景中提炼首批能力，不要一开始建设全企业能力市场。

| 能力资产 | 类型 | 任务目标 | 首要验证等级 |
|---|---|---|---|
| 项目状态归纳 | Skill + Template | 从授权上下文形成状态摘要 | P1 |
| 项目风险初筛 | Skill + Evidence Standard | 识别候选风险并给出证据 | P1 |
| 任务依赖分析 | Skill + Rule | 找出阻塞链和里程碑影响 | P1 |
| 决策证据核验 | Skill + Evidence Standard | 核对决策状态、证据版本和缺口 | P1 |
| 会议行动项提取 | Skill + Template | 从授权会议上下文形成行动项候选 | P1 |
| 项目状态评审流程 | Workflow + Playbook | 编排状态、风险、依赖、证据和人工确认 | P2 |
| 项目复盘模式提炼 | Playbook + Evaluation Set | 从已验证复盘中提取可复用改进方法 | P2 |

### 9.1 首个样板：项目风险初筛能力

输入：

- 授权的项目 Context Package；
- 项目范围和时间窗口；
- 任务、里程碑和依赖关系；
- 风险台账和历史事件；
- 已确认的业务规则和证据标准。

处理：

1. 检查上下文完整性、时效和范围；
2. 识别延期、依赖变化、资源缺口和未决事项；
3. 关联相关任务、里程碑、风险和证据；
4. 区分已确认事实、候选风险、推断、冲突和未知；
5. 按证据要求输出候选风险；
6. 将正式风险定级留给有权责任人。

输出：

- 候选风险列表；
- 风险信号和影响对象；
- EvidenceRef；
- 推断依据与不确定性；
- 缺失信息和待确认事项；
- 不适用或无法判断的原因；
- 人工核验记录。

### 9.2 跨人验证方法

- 由一位项目交付专家参与能力提炼；
- 由另一位同岗位人员在不接受原作者逐项指导的情况下使用；
- 再由不同团队的同岗位人员使用同一版本；
- 之后由相邻岗位人员测试角色适配；
- 通过盲评、基线对照和任务难度分层，记录效果差异；
- 只有在明确的项目交付范围内复现结果后，才扩大使用范围。

首轮验证的结论应是“该能力在已测试的项目交付任务范围内有效或无效”，而不是“企业所有项目经理都能使用”。

## 10. 能力资产的 Agent 调用机制

### 10.1 调用链

~~~mermaid
sequenceDiagram
  participant U as 用户 / 业务事件
  participant O as Orchestrator
  participant C as ADS Context
  participant R as Capability Registry
  participant P as Policy Service
  participant A as Agent Runtime
  participant V as Verifier
  participant F as Feedback & Evaluation
  U->>O: 提出任务目标
  O->>C: 获取任务级 Context Package
  C-->>O: 返回上下文、版本、证据和权限信息
  O->>R: 查询适用能力
  R-->>O: 返回候选资产、版本、边界和依赖
  O->>P: 校验调用主体、用途和能力权限
  P-->>O: 允许 / 限制 / 拒绝
  O->>A: 以锁定版本和契约调用能力
  A-->>V: 返回结果、证据和限制
  V-->>O: 通过 / 补充 / 人工复核
  O-->>U: 提交结果或待确认事项
  U->>F: 接受 / 修正 / 驳回
  F->>R: 形成版本评估和改进建议
~~~

### 10.2 能力选择不是简单的语义相似度匹配

Agent 选择能力时至少要综合：

- 任务类型是否匹配；
- 输入和上下文是否满足前置条件；
- 能力是否处于允许调用的生命周期状态；
- 能力版本及依赖是否兼容；
- 当前主体是否有权限；
- 是否处于已验证的适用范围；
- 能力所需证据和工具是否可用；
- 当前任务风险等级是否允许；
- 评测表现和维护状态是否达到要求。

语义检索只能发现候选资产，不能直接决定资产是否可用。

### 10.3 能力调用的运行记录

每次调用至少记录：

- capability_id、version、manifest_hash；
- run_id、task_id、agent_id；
- context_id、ontology_version、policy_version；
- 输入摘要和输出 Artifact 引用；
- 前置条件检查结果；
- 工具和依赖版本；
- 评测状态、人工接受或修正结果；
- 运行耗时、成本和错误码。

敏感输入应按数据分类和最小化原则处理，不应为了追踪而无必要复制完整原始内容。

### 10.4 能力资产不得绕过权限

- 能力包不携带可直接使用的个人或系统凭证；
- 能力被 Agent 调用，不意味着 Agent 获得额外业务权限；
- Rule、Playbook 和 Skill 不能替代 Policy Service；
- 业务规则和权限冲突时，服务端策略优先；
- 能力输出仍是候选结果，业务事实以权威系统和责任人确认结果为准。

## 11. 能力资产的持续运营与生命周期治理

### 11.1 生命周期

~~~mermaid
stateDiagram-v2
  [*] --> candidate
  candidate --> in_review
  in_review --> sandbox
  in_review --> rejected
  sandbox --> validated
  sandbox --> candidate: revise
  validated --> published
  published --> deprecated
  published --> suspended
  suspended --> published: reapproved
  deprecated --> retired
  rejected --> [*]
  retired --> [*]
~~~

### 11.2 何时必须复核或暂停

- 业务制度、流程或关键阈值变化；
- 领域本体或关键字段语义变化；
- Tool / Connector API 变化；
- 模型或 Prompt 升级导致输出行为变化；
- 能力质量、证据覆盖或接受率持续下降；
- 新团队使用时出现系统性迁移失败；
- 发现授权、隐私、知识产权或安全问题；
- 原能力 Owner 离岗且没有继任者；
- 资产依赖的外部服务或数据源停止维护。

### 11.3 反馈如何转化为改进

人工反馈不能直接修改生产能力。建议经过以下步骤：

1. 收集接受、修正、驳回和例外记录；
2. 将反馈归类为上下文问题、能力问题、规则问题、工具问题、权限问题或评测问题；
3. 判断是个例还是重复模式；
4. 由对应 Owner 评审；
5. 生成新版本候选；
6. 在固定评测集和新增案例上回归；
7. 经过必要审批后灰度发布；
8. 观察线上质量和业务价值；
9. 保留回滚能力。

### 11.4 能力资产的运营指标

| 维度 | 指标 | 管理目的 |
|---|---|---|
| 资产质量 | 已验证资产占比 | 避免候选经验充斥目录 |
| 使用效果 | 被业务接受的调用比例 | 衡量真实可用性 |
| 复用效果 | 跨人员 / 团队 / 岗位验证等级 | 描述适用范围 |
| 迁移损失 | Transfer Gap | 识别对原作者的依赖 |
| 维护效率 | 版本更新和复核及时率 | 防止能力过时 |
| 经济价值 | Cost per Accepted Task | 衡量单位业务成果成本 |
| 业务价值 | 周期、质量、返工或闭环改善 | 验证实际收益 |
| 治理质量 | 来源可追溯率、权限违规数 | 确保资产可信和合规 |
| 资产健康 | 过期、暂停、无人维护资产占比 | 清理低质量资产 |

不应以 Capability Registry 中的条目数量作为企业 AI 能力成熟度的主要指标。

## 12. 组织机制：谁负责把经验变成企业能力

| 角色 | 责任 |
|---|---|
| 经验贡献者 | 提交有价值的任务经验和案例，确认来源与分享范围 |
| Capability Author | 将经验抽象为结构化能力候选 |
| Domain Expert | 核验业务规则、适用条件和专业质量 |
| Capability Owner | 对资产定义、版本、质量、维护和退役负责 |
| Data / Privacy Steward | 审查数据来源、敏感信息和使用边界 |
| Security / Policy Owner | 审查调用权限、工具风险和策略要求 |
| Evaluation Owner | 建立评测集、裁定标准和迁移实验 |
| Agent Platform Owner | 提供 Registry、Runtime、版本和调用机制 |
| Business Process Owner | 确认流程责任、业务价值和人工确认节点 |
| Human Approver | 对需要人工确认的业务判断和动作承担责任 |

### 12.1 组织运营节奏

- 每周：检查新候选资产、失败案例和人工修正；
- 每月：复核高频能力、Owner、质量、成本和使用范围；
- 每季度：检查跨团队复用证据、版本健康和领域规则变化；
- 重大制度或系统升级时：触发受影响能力的重新评测；
- 每年或按企业制度：复核资产贡献、许可、保留和退役机制。

### 12.2 激励机制

可以鼓励员工提交可验证的能力经验，但不应简单按提交数量奖励。建议综合考虑：

- 被验证并正式发布；
- 被其他人员实际复用；
- 在复用中产生可量化业务改善；
- 降低重复工作和关键人员依赖；
- 维护质量和持续更新；
- 贡献过程符合数据、隐私和知识产权规则。

## 13. 分阶段实施路线

| 阶段 | 周期建议 | 工作内容 | 阶段产物 | 放行条件 |
|---|---|---|---|---|
| P0：能力定义 | 1—2 周 | 定义分类、Manifest、生命周期和治理边界 | 能力标准 V0.1 | 架构和业务评审 |
| P1：单能力提炼 | 3—4 周 | 从项目交付中选择一个任务提炼能力候选 | 项目风险初筛能力包 | 输入输出和边界明确 |
| P2：原作者验证 | 5 周 | 在原作者和重复任务中测试可复现性 | P0 评测结果 | 基础质量达标 |
| P3：跨人验证 | 6—7 周 | 同岗位不同人员盲测和对照 | P1 评测报告 | 不依赖原作者临场指导 |
| P4：跨团队 / 岗位验证 | 8—10 周 | 在其他团队和相邻岗位进行适配测试 | P2 / P3 证据 | 迁移损失和适配成本可接受 |
| P5：能力目录运营 | 后续 | 建立 Registry、版本、调用、反馈和退役机制 | 企业能力目录 | 有持续 Owner 和运营机制 |
| P6：跨领域扩展 | 后续 | 选择任务结构相似的其他领域验证 | P4 / P5 证据 | 领域映射和差异经过评审 |

周期仅为规划建议，应根据样本可得性、业务节奏和人员投入调整。阶段未达到证据要求时应延长或缩小结论范围，不应为了按期交付而跳过验证。

### 13.1 首期最小工程集

1. Capability Manifest JSON Schema；
2. Capability Registry（可先用版本化目录和元数据表起步）；
3. 项目风险初筛 Capability Package；
4. 输入输出契约和证据要求；
5. 版本锁定与依赖清单；
6. 沙箱调用和权限检查；
7. 跨人复用评测模板；
8. 人工接受、修正、驳回记录；
9. 版本评测与发布审批；
10. 能力调用和业务结果的关联 Trace。

首期不必先建设复杂的能力市场、自动化经验挖掘平台或全企业 Skill 商店。

## 14. 关键架构决策（ADR）

| 编号 | 决策 | 推荐选择 | 原因 |
|---|---|---|---|
| ADR-01 | 企业沉淀对象 | Capability Asset，而非个人记忆副本 | 明确可复用的任务能力 |
| ADR-02 | 能力实现 | Manifest + Skill / Rule / Playbook 等组合包 | 避免 Prompt 单体化 |
| ADR-03 | 资产来源 | 授权经验、业务结果、复盘和验证样本 | 保留来源和权利边界 |
| ADR-04 | 发布条件 | 结构化契约、独立评测和明确 Owner | 避免未经验证的经验成为标准 |
| ADR-05 | 复用评估 | P0—P5 分层验证 | 不把跨人和跨域混为一谈 |
| ADR-06 | 能力发现 | Registry 检索 + 适用条件检查 + Policy | 语义相似不等于可以调用 |
| ADR-07 | 版本策略 | 锁定版本、依赖和回滚 | 保证运行可复现 |
| ADR-08 | 质量反馈 | 人工审核后进入新版本 | 防止单次错误反馈污染能力 |
| ADR-09 | 组织责任 | 每项正式能力必须有 Owner | 保证长期维护 |
| ADR-10 | 成熟度评价 | 以被接受结果和迁移证据为核心 | 避免数量导向 |

以上为建议决策，需由正式架构、业务、安全和数据治理评审确认。

## 15. 关键待决策事项

1. 企业是否已有知识资产、流程资产、自动化脚本或 Skill 的登记目录？
2. Capability Registry 应由 ADS 平台统一提供，还是由领域中心维护并通过联邦目录发现？
3. 个人贡献的能力经验如何确认分享许可、署名、使用范围和撤回规则？
4. 哪些类型的经验可以进入企业资产，哪些只能留在个人或项目责任边界内？
5. 谁担任企业级 Capability Owner，谁担任领域级 Owner？
6. 项目交付首批能力应选择风险初筛、状态归纳还是证据核验？
7. 如何获取不暴露客户和个人信息的跨人评测样本？
8. 业务专家如何建立盲评标准和关键错误清单？
9. 哪些能力只需要在一个岗位内复用，哪些值得投入跨领域验证？
10. 能力的使用、贡献和维护是否需要纳入企业绩效或激励机制？

## 16. 立项与验收清单

### 16.1 能力提炼前

- [ ] 明确能力对应的业务任务和目标；
- [ ] 确认经验来源、授权和共享范围；
- [ ] 识别个人信息、客户信息、商业秘密和知识产权；
- [ ] 区分个人偏好、项目特例和可复用任务方法；
- [ ] 指定 Capability Author、Domain Expert 和 Owner；
- [ ] 明确预期复用等级和验证范围。

### 16.2 发布候选能力前

- [ ] Capability Manifest 通过 Schema 校验；
- [ ] 输入输出契约和证据要求明确；
- [ ] 前置条件、不适用条件和停止条件明确；
- [ ] 工具、规则和上下文依赖已登记；
- [ ] 权限和数据分类检查通过；
- [ ] 评测样本和人工裁定标准准备完成；
- [ ] 版本、Owner、复核日期和回滚策略明确。

### 16.3 宣称跨人或跨岗位复用前

- [ ] 原作者之外的人员独立完成测试；
- [ ] 没有依赖原作者逐项指导；
- [ ] 有 Baseline 与 Assisted 对照；
- [ ] 样本覆盖不同复杂度和异常情况；
- [ ] 评审尽可能采用盲评；
- [ ] 关键错误、证据覆盖和政策违规单独统计；
- [ ] 迁移损失和适配成本可解释；
- [ ] 结论明确标注已验证范围与未验证范围；
- [ ] 业务责任人批准扩大使用范围。

### 16.4 进入长期运营前

- [ ] Registry 和调用记录可用；
- [ ] 每项资产有持续维护 Owner；
- [ ] 版本变更有回归测试；
- [ ] 有暂停、回滚和退役机制；
- [ ] 人工反馈不会直接修改生产能力；
- [ ] 能力效果和业务结果可以关联；
- [ ] 有定期复核和权限清理机制。

## 17. 结论：企业 AI 的长期竞争力，来自可持续积累的能力资产

企业使用 AI 的早期优势可能来自模型、工具和应用，但这些能力容易被外部技术追平。更长期的差异化优势，来自企业是否持续积累了自己的业务上下文、领域语义、经过验证的工作方法、专业规则、证据标准和协同能力。

ADS 的能力资产化方向可以概括为：

- **Work Sensing：** 感知真实工作过程中的信号；
- **Work Context：** 将信号关联到业务对象、事件和任务；
- **Runtime Cognition：** 理解企业当前运行状态和证据；
- **Capability Asset：** 把经过验证的工作方法转化为可复用能力；
- **Agent Runtime：** 在任务和权限范围内调用能力完成工作；
- **Feedback & Evaluation：** 用真实结果验证和改进能力资产。

最终要形成的不是一个堆满 Prompt 的目录，而是一套**有来源、有边界、有契约、有证据、有版本、有责任人、能被 Agent 调用并能被业务验证的企业能力资产体系**。

### 下一专题建议：ADS-WORK-08

**《企业工作本体与事件驱动的个人—企业—领域能力协同标准研究》**

建议重点研究：

1. 工作事件、任务、活动、决策、知识和能力之间的统一语义关系；
2. 个人工作事件与企业业务事件的映射、授权和晋升机制；
3. 能力资产如何绑定任务家族、业务对象和领域本体；
4. 个人数智底座、企业数智底座和业务领域中心如何通过联邦目录协同；
5. 如何让事件、上下文、能力和 Agent 执行形成闭环；
6. 如何定义一套可扩展、可治理、可互操作的工作本体标准。
