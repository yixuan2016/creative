# 个人数智底座知识沉淀体系研究总报告

**版本：V1.0｜日期：2026-11-20｜研究状态：阶段性最终整合稿**

> 研究主线：以个人为主体，以多源感知为入口，以事件为基本记录单元，以本体为语义基础，以持续记忆为认知机制，以受约束的 Agent 为行动接口，构建个人自主控制、跨工具可迁移、可与 ADS 安全协同的个人数智底座。

---

## 摘要

个人数智底座不是传统个人知识库的扩容版，也不是把个人文件、聊天记录、会议录音集中起来的资料仓库。它要解决的是一个更基础的问题：AI 如何持续、可信、可纠错地理解一个人的工作、生活、学习、关系、目标、承诺和行为，并在个人授权范围内帮助其记忆、判断、决策和行动。

本研究将前期分散的 PDKS 标准、个人事件本体、录音与多源采集、持续记忆、个人 Agent、Personal Assistant OS 产品形态以及 ADS 三级数智底座关系统一为一套研究体系。

核心判断如下：

1. **从知识库走向个人上下文基础设施。** 知识库主要管理资料；个人数智底座要理解持续发生的事件、对象、关系、状态、目标和行动。
2. **以事件作为事实记录入口。** 原始信号不直接等于事实，AI 摘要不直接等于记忆，记忆也不覆盖原始事件。事件、记忆、意图和 Agent 动作必须分开建模。
3. **多源采集优先于单一录音设备。** 录音是重要入口，但必须与手机、电脑、会议、日历、邮件、钉钉、文档、任务和业务系统等来源共同构成感知网络。
4. **先形成个人资产，再按规则投影企业。** 个人原始数据默认由个人控制；企业侧只接收经过明确目的、授权、最小必要筛选、业务审核、语义映射和质量验证的内容。
5. **用持续记忆连接过去、现在和未来。** 事件账本负责可追溯，记忆负责跨时间理解，目标/承诺/任务负责持续推进，Context Package 负责任务级信息组织。
6. **以经过验证的能力资产实现跨人复用。** 不要求其他人复制某个人的私人记忆，而是将重复实践抽象为流程、模板、规则和 Skill，再验证其在新执行者和新任务中的有效性。
7. **与 ADS 形成上下行协同。** 个人、企业、业务领域中心三级数智底座不是原始数据逐级集中，而是标准数据在授权条件下向上汇流，经验证的标准、能力和协作经验向下回馈。

本报告属于研究体系的阶段性最终整合稿，不等同于已经完成的生产级产品、安全认证或全量部署规格。当前 PDKS 仍处于 transitional Skill development 的实验预览阶段，真实数据采集、跨平台安装、加密、多设备同步和真实租户连接仍需专项验证。

## 一、研究背景与核心问题

### 1.1 为什么传统知识库不足以成为个人数智底座

传统知识库通常以文档、笔记、网页、文件和问答记录为主要对象，擅长解决资料归档、关键词检索和基于内容的问答。但个人真实生活和工作并不是由静态文档组成的。

一个人每天持续发生：

- 工作活动：会议、沟通、任务、项目推进、问题处理、方案设计、客户协作、决策和交付；
- 生活活动：日程安排、个人事务、出行、家庭安排、个人承诺和日常活动；
- 学习成长：学习、阅读、练习、反思、技能进步和经验积累；
- 关系变化：与同事、客户、合作伙伴、朋友和家庭成员之间的互动；
- 目标与资源变化：阶段目标、时间安排、可用资源、优先级和约束。

这些信息分散在不同应用、设备、人员和时间里。大量重要上下文并不会自然形成一份完整文档，例如：一个决定为什么产生、任务为什么延期、某项承诺由谁确认、一个问题此前如何处理、当前目标受到什么约束。

因此，个人数智底座要解决的不是“把资料放得更整齐”，而是让 AI 能够建立一个有来源、有时间、有对象、有状态、可持续更新的个人上下文模型。

### 1.2 当前信息采集方式存在的缺口

| 现有方式 | 已有价值 | 主要缺口 |
|---|---|---|
| 钉钉、邮件、即时通讯 | 记录部分沟通和协作 | 跨应用分散，非正式上下文和线下活动覆盖不足 |
| 日历和任务系统 | 记录安排、责任和状态 | 通常记录结果或计划，不完整记录形成原因和过程 |
| 文档、笔记和知识库 | 保存知识和正式成果 | 需要用户主动整理，难以自动关联事件与行动 |
| 会议转写和录音卡 | 补充口头讨论和会议内容 | 只覆盖部分场景，存在忘带、忘开、充电、成本、数据孤岛和隐私问题 |
| AI 对话 | 能够即时理解和生成内容 | 对话之间容易断裂，信息不一定进入长期记忆，也缺少可靠来源链 |
| 业务系统 | 保存权威业务对象和状态 | 通常无法完整呈现个人参与过程、临时讨论和隐性经验 |

单一工具无法完整反映一个人的真实活动。录音卡能够补充语音信息，但不能独立解决个人上下文理解问题；知识库能够保存资料，但不能自动理解事情如何发生和变化。

### 1.3 研究要回答的六个问题

1. 如何在用户可控、透明和合规的前提下，采集个人工作与生活中的多源信息？
2. 如何把原始信息转换成有时间、主体、对象、来源和状态的事件？
3. 如何从事件中形成可纠错、可过期、可撤回的长期记忆？
4. 如何将记忆与个人目标、承诺、任务、关系和下一步行动连接起来？
5. 如何把适合组织使用的工作信息，经授权转化为企业标准业务数据和能力资产？
6. 如何让不同 Agent、不同设备和不同知识管理工具共享同一套个人数据标准，避免用户被单一平台锁定？

## 二、总体定位与概念边界

### 2.1 个人数智底座的定义

个人数智底座是以个人为数据主体和控制主体，持续接收个人授权的数据来源，通过事件化、语义化、结构化和治理机制，形成可追溯的个人知识、个人记忆、个人目标与承诺、个人标准数据及数智资产，并为个人 AI 助理和 Agent 提供长期上下文与行动支撑的基础设施。

它至少包括：

- 个人知识库：保存可阅读、可编辑、可迁移的知识内容；
- 个人数据库：保存结构化的事件、对象、关系、状态、记忆、目标、承诺和授权；
- 个人数智库：保存经本体语义映射、标准化并可用于智能体运行的数据；
- 来源与证据库：保存原始来源的受控引用、文件、音频、片段和证据定位；
- 运行时与治理能力：负责采集、解析、记忆、检索、授权、执行、审计和反馈。

### 2.2 PDKS、个人数智底座与 Personal AI Life OS 的关系

| 概念 | 定位 | 主要解决的问题 |
|---|---|---|
| PDKS（Personal Data Knowledge System） | 个人数据与知识表达标准及互操作基础 | 不同工具、Agent 和存储之间如何统一表达、校验和迁移 |
| 个人数智底座 | 个人数据、知识、标准数据和数智资产的承载基础 | 个人数据如何持续沉淀、组织、治理和自主控制 |
| Personal AI Life OS | 个人 AI 助理的运行与协作操作系统 | 如何理解上下文、管理记忆、推进目标并在授权下行动 |
| Personal Assistant OS 产品界面 | 用户使用个人助理的产品入口 | 如何让普通用户自然记录、查看、纠错、确认和使用 |

PDKS 不等于 Personal AI Life OS。PDKS 负责数据语言和互操作，个人数智底座负责资产承载，Personal AI Life OS 负责运行与协作。产品界面则把复杂能力转化为用户可以理解的体验。

### 2.3 必须区分的四类对象

- **来源（Source）**：信息来自哪里，例如录音、会议、文件、日历、消息或业务系统。
- **事件（Event）**：发生了什么，或系统观察到了什么。
- **记忆（Memory）**：哪些信息对未来理解和行动有帮助。
- **意图（Intent）**：个人希望达成什么、承诺了什么、下一步要做什么。

此外，Agent 的动作提案（Action Proposal）是 AI 准备执行的动作，不等同于人的任务或承诺。

核心原则：来源不等于事实，事件不等于记忆，记忆不等于任务，人的任务不等于 Agent 执行授权。

## 三、理论基础：融入《智能的阶梯》的运行思想

个人数智底座不是孤立的知识管理工具，它是个人从使用 AI 工具走向拥有个人智能体、再走向智能生态协同的基础条件。

### 3.1 与第一道阶梯的关系：从工具层到智能体层

《智能的阶梯》将个人 AI 助理的关键能力归纳为执行、记忆、成长三大能力。跨越的标志不是 AI 能够回答更多问题，而是用户交给它目标而不是逐步操作，AI 返回经过执行和验证的结果，用户主要负责验收和确认。

个人数智底座为这三项能力提供持续动力：

- 执行：从个人数智库和任务上下文中获得标准数据、约束和工具信息；
- 记忆：从事件账本中形成可追溯、可纠错、可更新的长期记忆；
- 成长：通过结果复盘、人工判断、验证反馈和本体映射，持续更新记忆、规则和能力。

如果没有个人数智底座，助理容易每次对话都从零开始；如果只有执行而没有记忆和复盘，助理也难以持续提升。

### 3.2 与第二道阶梯的关系：从个人智能体到智能生态系统

个人 AI 助理需要与企业或业务领域的端口 AI 助理协同，承接一个人无法独立完成的业务。

这要求双方具备：

- 统一的语义和对象定义；
- 明确的身份、角色和权限；
- 可传递的任务契约和上下文包；
- 有来源和证据的协作记录；
- 可回传的执行结果与反馈。

PDKS 的跨 Agent 数据表达、ADS 的共同本体和任务协同机制，构成个人智能体参与生态协同的基础。每次协作产生的语义对齐、任务包、证据和结果，都可以在授权条件下沉淀为后续协作可复用的标准数据。

### 3.3 与第三道阶梯的关系：从生态协同到世界模型与业务模拟

个人、企业和业务领域中心三级数智底座形成稳定的标准数据汇流机制后，企业业务过程才能逐步形成可供模型理解、推演和模拟的可信数据基础。

个人数智底座的意义不仅是提高个人效率，也在于持续产生真实活动中的标准数据和证据，为企业业务模型提供更完整的上下文。

但这并不意味着当前 PDKS 已经具备世界模型或业务模拟能力。当前研究重点是先把个人侧事件、记忆、授权和标准数据基础建立起来，为后续阶段创造条件。

### 3.4 双环机制：证据与数智分流

《智能的阶梯》中的双环思想可以转化为个人数智底座的核心运行原则：

- **智能体内环**：任务理解、目标规划、过程执行、结果复盘。它消费经过语义映射和标准化的数智数据。
- **人类外环**：判断、执行、验证。它依据运行过程沉淀的证据，决定继续、调整、停止或提升智能体的责任范围。

两条路径使用同源材料，但不能混为一体：

- 证据交给人判断、审批、验收和追责；
- 标准数据交给智能体检索、运行和改进。

因此，个人数智底座必须同时保留来源证据和可运行的标准数据，不能只保留 AI 摘要。

### 3.5 个人本地闭环

建议将个人数智底座的闭环表达为：

**知识存储 → 调度执行 → 本体映射 → 数智驱动 → 结果与证据回流 → 记忆和能力更新。**

闭环每运行一次，都可能产生新的事件、记忆、标准数据和能力候选。人的确认和验证决定哪些内容能够成为稳定资产，不能由模型自行把推断升级为事实。

## 四、总体架构：从多源信号到个人智能

### 4.1 七层逻辑架构

| 层次 | 名称 | 主要职责 | 主要输出 |
|---|---|---|---|
| L1 | 多源感知与采集层 | 接收用户输入、设备、应用和系统来源 | 原始来源、采集会话 |
| L2 | 来源与事件账本层 | 保存来源引用，解析和记录事件 | Source Record、Observation、Event |
| L3 | 身份、时间与语义层 | 识别人、组织、项目、对象、关系和状态 | Entity、Relation、State Assertion |
| L4 | 持续记忆与知识视图层 | 从事件形成记忆，处理冲突、过期和纠错 | Memory Item、Knowledge Asset |
| L5 | 个人运行模型层 | 管理目标、承诺、任务、例程和项目 | Goal、Commitment、Task、Project |
| L6 | 个人认知与上下文层 | 为当前任务组织最小必要上下文 | Context Package |
| L7 | Personal Agent 与执行层 | 规划、审批、工具调用、执行核验和结果回写 | Action Proposal、Agent Run、Feedback Event |

横向治理控制面贯穿七层，包括身份、授权、隐私分类、数据来源、时间、保留、撤回、审计、本体版本、Schema 版本和用户控制。

### 4.2 数据处理主链路

多源信号 → Observation → Event Candidate → 语义关联 → 用户确认或规则核验 → Event Ledger → Memory / Intent → Context Package → Agent Action → 执行验证 → 新事件与反馈。

该链路有三个关键门槛：

1. 原始信号必须保留来源身份和处理过程，不能只留下模型摘要。
2. 事件和记忆必须区分 observed、inferred、confirmed、disputed 等状态。
3. Agent 的高影响动作必须经过授权和审批，执行结果必须验证后才能回写为成功状态。

### 4.3 事件账本与记忆库不能合并

事件账本记录“发生了什么、系统观察到了什么、用户确认了什么”；记忆系统记录“哪些信息对未来理解和行动有帮助”。

例如，会议中有人说“周五前整理风险清单”：

1. 原始来源：会议音频或转写片段；
2. 事件候选：会议中出现一条风险清单相关的行动表达；
3. 候选记忆：用户可能承担了整理风险清单的承诺；
4. 用户确认：确认责任人、截止时间和承诺归属；
5. Intent Object：创建一项个人承诺或任务；
6. Agent 提案：建议创建提醒；
7. 用户审批：批准具体提醒动作；
8. 执行结果：提醒创建成功并核验；
9. 新事件：记录提醒创建和承诺状态变化。

原始事件不被记忆摘要替代；记忆不覆盖事件；行动结果重新成为事件。

### 4.4 事件时间模型

每条事件应尽可能保留四种时间：

- occurred_at：现实中实际发生的时间；
- observed_at：设备或系统感知到的时间；
- recorded_at：正式写入事件账本的时间；
- valid_time：某个事实或状态在现实中有效的时间范围。

补录、延迟转写和多端同步都可能造成时间差，不能使用写入时间冒充事件发生时间。

## 五、多源采集体系：录音是入口之一，不是全部

### 5.1 目标：覆盖个人工作与生活的多源上下文

长期目标是让个人数智底座能够在用户授权范围内覆盖工作、生活、学习和个人资源等活动。覆盖范围广，不等于一次性默认开启全部采集。每个来源、权限范围、历史导入和后台采集都需要独立授权。

| 来源类别 | 典型来源 | 主要沉淀内容 | 建议优先级 |
|---|---|---|---|
| 用户主动输入 | 文字、语音、图片、快速记录、分享 | 明确意图、事实声明、临时记录 | P0 |
| 日程与任务 | 日历、待办、项目任务、提醒 | 时间、目标、承诺、状态变化 | P0 |
| 文档与知识 | Word、PDF、Markdown、笔记、表格、演示文稿 | 知识资产、项目背景、成果和证据 | P1 |
| 沟通协作 | 钉钉、邮件、即时通讯、评论和审批 | 交互事件、任务线索、决策候选 | P1 |
| 会议与语音 | 会议平台、录音、语音消息、电话记录 | 讨论、决策候选、行动项、问题和风险 | P1/P2 |
| 电脑活动 | 文档编辑、应用事件、用户主动选择的屏幕上下文 | 工作过程、文件变化、任务上下文 | P2 |
| 手机与可穿戴设备 | 快速记录、通知、位置或活动信号（如用户启用） | 个人生活与移动场景上下文 | P2 |
| 业务系统 | CRM、ERP、项目管理、工单、财务和业务应用 | 权威业务对象、状态和正式业务记录 | 按业务试点接入 |
| 其他个人领域 | 个人文件、学习资料、家庭事务和个人资源 | 个人知识、目标、安排和成长 | 用户逐项启用 |

来源优先级是试点建议，不代表所有来源都必须接入。应优先选择使用频率高、数据可靠、价值明确、权限可解释且接入成本可控的来源。

### 5.2 录音采集的定位

录音的核心价值是补充非结构化的口头信息，尤其是临时讨论、会议、现场沟通、口头交代和经验判断。但录音本身不是最终知识资产。

完整语音处理链路应为：

采集会话 → 原始音频 → 分段与转写 → 说话人和时间定位 → 主题与对象识别 → 事件候选 → 证据片段 → 个人确认 → 记忆或意图更新。

每一项事件或记忆都应能定位到原始音频或转写中的具体片段；识别不确定的说话人、任务责任人和时间，应保持候选状态。

### 5.3 录音卡和自研硬件的研究判断

现有录音卡暴露的问题主要包括：

- 生态割裂：录音、转写、摘要没有融入个人知识、钉钉、项目系统和 ADS；
- 使用摩擦：需要携带、充电和手动启动，容易忘记或漏录；
- 采集单一：音频不能完整表达屏幕操作、文档变化和业务状态；
- 成本问题：设备采购、账号、模型、存储和维护成本需要整体评估；
- 治理问题：录音可能涉及个人隐私、第三方信息和商业秘密。

因此，不能先把自研录音卡作为唯一答案。应先建设设备无关的统一感知服务层，再验证是否确实需要自研硬件。

| 终端 | 主要定位 | 建议 |
|---|---|---|
| 手机 | 随身记录、语音、通知和即时确认 | 首期优先验证 |
| 电脑客户端 | 深度工作、文档、会议和任务上下文 | 工作场景主入口 |
| 会议系统 | 会议音频、参会人和日历上下文 | 正式会议场景入口 |
| 现有录音卡 | 免手持的补充采集 | 作为对照和补充入口 |
| 自研语音设备 | 低摩擦、组织适配和设备管理 | 需求验证后再立项 |
| Web 工作台 | 记忆、授权、时间线和复盘管理 | 全局管理入口 |

自研设备应重点验证续航、佩戴舒适度、物理暂停、录制指示、离线缓存、加密、数据导出、连接器能力、设备撤销和全生命周期成本。

### 5.4 采集治理要求

- 用户必须知道当前哪些来源处于启用状态；
- 持续录音或设备采集必须有清晰指示、暂停和停止入口；
- 多人场景应遵循适用的告知和同意要求；
- 每个连接器声明权限范围、来源身份、采集时间、保留规则和撤销机制；
- 设备离线时允许受控缓存，恢复后补传并保留真实发生时间；
- 用户可以选择保留原始音频、只保留转写，或在满足规则后删除原始音频；
- 不以“录得更多”作为产品目标，而以重要上下文是否被准确理解为目标；
- 来源没有覆盖到的活动应标记为“未观察到”，不能推断为“没有发生”。

### 5.5 钉钉 DWS 接入

PDKS 当前研究已将钉钉官方 DWS CLI 作为连接器预览方向。运行时需要官方 DWS CLI、OAuth 登录、租户 CLI 访问能力和有效的 PDKS Consent Grant。

当前公开记录表明：连接器存在预览实现，但真实租户投递验证尚未完成，历史分页与回补也未完成。因此，不能将其表述为已经完成生产级钉钉全量采集。

## 六、知识沉淀标准：什么值得沉淀，如何判断质量

本章是整个研究的核心。沉淀不是“采集到就保存”，而是将信息经过来源识别、语义判断、价值判断、确认和治理后，形成可持续使用的个人资产。

### 6.1 PDKS 九类基础数据对象

当前 PDKS 互操作映射定义了九类基础对象：

| 对象 | 定义 | 典型内容 |
|---|---|---|
| entity | 实体或对象 | 人、组织、项目、产品、工具、地点等 |
| source_asset | 来源资产 | 原始文件、录音、消息、文档、系统记录 |
| evidence_segment | 证据片段 | 音频时间段、文档段落、消息片段、截图区域 |
| event | 事件 | 会议、任务变化、承诺、学习、生活活动 |
| assertion | 断言 | 某人表达的观点、事实主张、假设或问题 |
| knowledge_asset | 知识资产 | 方法、流程、经验、概念、原则、教训和洞察 |
| personal_context | 个人上下文 | 角色、职责、能力、约束、偏好、目标和关系 |
| action | 人的行动意图 | 任务、计划、提醒、承诺 |
| relationship | 关系 | 人与项目、事件与来源、任务与目标等关系 |

这九类对象共同构成 PDKS 的基础表达语言。它们不是九个必须让普通用户手动填写的表单，而是系统自动识别和维护的标准对象。

### 6.2 哪些内容应该沉淀

满足以下任一条件的内容，通常值得进入沉淀流程：

1. 用户明确要求记住、保存或追踪；
2. 对未来工作、生活、学习或决策有持续影响；
3. 形成了明确目标、承诺、任务、决策、风险或结果；
4. 反映了稳定偏好、约束、职责、关系或能力；
5. 是未来可能复用的经验、方法、流程、规则或教训；
6. 对重要事件、业务状态或个人经历具有可追溯的证据价值；
7. 多次出现并可能反映长期模式，但仍需避免仅凭重复次数自动认定为事实。

### 6.3 哪些内容不应自动沉淀为长期记忆

- 无明确价值的一次性闲聊和噪声；
- 已有内容的无意义重复副本；
- 没有来源且无法核验的模型推测；
- 未确认的任务责任、承诺、决策或关系；
- 不必要的第三方隐私和敏感信息；
- 超出授权范围的企业或个人数据；
- 已被用户明确要求不再记住的内容；
- 已过期且没有历史或审计价值的临时状态。

不沉淀为长期记忆，不代表必须立即删除原始来源。原始来源是否保留，必须遵循用户选择、来源规则和保留策略。

### 6.4 知识沉淀的六项质量标准

| 标准 | 核心问题 | 最低要求 |
|---|---|---|
| 真实性与来源 | 这条信息从哪里来？ | 保留来源引用、采集方式和处理记录 |
| 时间准确性 | 什么时候发生、什么时候记录？ | 区分发生、观察、记录和有效时间 |
| 语义清晰性 | 它属于什么类型、涉及什么对象？ | 使用明确事件类型、实体和关系 |
| 确认与可信度 | 是事实、观察、推断还是争议？ | 保留断言状态、置信度和确认人 |
| 持续价值 | 未来是否可能帮助理解、决策或行动？ | 有明确用途、复用价值或证据价值 |
| 权属与治理 | 谁控制、谁能使用、何时到期？ | 明确责任主体、分类、授权、保留和撤回规则 |

以上六项中，来源、时间、语义、状态和治理属于基本门槛；不能因为一条内容看起来有用，就跳过授权或来源核验。

### 6.5 建议的沉淀质量分级

以下是建议用于治理和评测的质量层级，不应被误解为当前 PDKS 已经冻结的官方等级：

| 等级 | 名称 | 说明 | 可执行用途 |
|---|---|---|---|
| Q0 | 原始来源 | 音频、文件、消息、图片和系统记录 | 作为原始材料和证据来源 |
| Q1 | 观察/事件候选 | AI 已识别出可能的事件、实体或关系 | 供用户查看、补充和确认 |
| Q2 | 已确认事件 | 用户或权威系统确认事件关键语义 | 进入个人时间线和后续记忆生成 |
| Q3 | 稳定记忆/知识资产 | 有来源、有价值、有有效期和纠错机制 | 支撑个人检索、理解和任务上下文 |
| Q4 | 可复用能力资产 | 经重复实践、独立验证、版本化和适用范围审查 | 在授权范围内跨人员或跨项目复用 |

Q0 到 Q4 不是所有内容必须逐级晋升的流水线。不同类型数据可以停留在适合自己的层级；例如证据片段不一定需要成为长期记忆，个人生活事件也不需要成为企业能力资产。

### 6.6 记忆类型标准

个人长期记忆建议区分：

- Episodic：情景记忆，某次会议、经历、活动和事件；
- Semantic：语义记忆，稳定事实、人物、项目和概念；
- Procedural：程序记忆，如何完成某类工作的方法；
- Preference：偏好记忆，用户明确表达的偏好；
- Goal：目标记忆，个人希望达到的状态；
- Commitment：承诺记忆，对未来行动或结果的承诺；
- Relationship：关系记忆，人与人、人与项目的关系；
- Routine：例程记忆，反复发生的活动和习惯；
- Project Context：项目上下文，项目背景、关键决策、当前问题和变化。

一次偶然行为不能自动成为稳定习惯；一次会议中的提议不能自动成为正式承诺；模型推断不能自动成为已确认事实。

### 6.7 记忆生命周期

建议采用：

candidate → active → stale / disputed → superseded / withdrawn / expired → archived

- candidate：候选，等待确认；
- active：有效，可在授权范围内检索；
- stale：可能过期，需要复核；
- disputed：存在冲突或用户提出异议；
- superseded：被新版本替代；
- withdrawn：用户撤回，不再参与普通检索；
- expired：超过有效期；
- archived：归档，不再默认参与实时判断。

记忆冲突不能简单采用“最新一条覆盖”或“模型置信度最高者胜出”。应保留冲突来源、有效时间和断言状态；权威系统状态按业务权威规则处理，个人偏好以用户确认优先，无法判断时并列保留并标记争议。

### 6.8 个人知识资产的长期维护

每条长期记忆应具备：

- 稳定 ID；
- 明确的记忆类型；
- 来源事件和证据引用；
- 断言状态与置信度；
- 创建和更新时间；
- 有效时间、复核时间或到期时间；
- 派生过程与模型/规则版本；
- 用户查看、纠错、撤回和删除入口；
- 默认共享范围和授权策略；
- 与被替代记录之间的关系。

记忆是可重建、可纠正的认知视图，不是不可更改的“模型内心事实”。

## 七、个人工作与生活本体标准

### 7.1 本体的作用

本体不是简单分类标签，而是统一描述概念、属性、关系、事件类型、状态和约束的语义体系。它让不同来源中的不同说法能够被理解为同一语义对象，也让 AI 能区分相似但并不等价的概念。

例如：

- “我答应周五给出材料”是个人承诺候选；
- “项目任务已创建”是企业任务状态；
- “会议上讨论过这个方案”不等于“方案已经批准”；
- “我和某个客户沟通过”不等于企业 CRM 中已建立正式客户关系。

### 7.2 个人上下文的四个主要领域

个人本体以个人为主体，而不是以员工身份为主体。

1. **个人工作上下文**：工作事件、会议、项目参与、任务、承诺、决策、协作关系、工作成果和经验。
2. **个人生活上下文**：日程、生活安排、个人承诺、家庭事务、出行、个人目标和日常活动。
3. **个人学习与成长上下文**：学习活动、反思、技能成长、阅读、练习和目标进展。
4. **个人资源与偏好上下文**：个人时间、工具偏好、工作方式、可支配资源和明确表达的偏好。

这四类是个人 AI 的理解维度，不是企业必须采集的字段清单。用户可以关闭某些类别、限制用途、纠正或删除记录。

### 7.3 五层本体逻辑模型

| 逻辑层 | 名称 | 主要概念 |
|---|---|---|
| L1 | 信号与观察层 | SourceRecord、Observation、CaptureSession、ExtractionRun、Audio、Document、Message |
| L2 | 事件与活动层 | Event、Activity、Task、Commitment、Interaction、Decision、Outcome |
| L3 | 语义对象与状态层 | Actor、Person、Organization、Project、Customer、Product、PersonalObject、Relation、StateAssertion |
| L4 | 上下文与决策层 | ContextPackage、Goal、Constraint、DecisionRecord、Risk、Issue、Dependency、Uncertainty |
| L5 | 能力与执行层 | CapabilityAsset、Skill、Rule、Workflow、Agent、Tool、Action、Approval、AgentRun |

身份、授权、来源、时间、分类、策略、版本、审计和人工确认是贯穿五层的横向治理控制面。

### 7.4 ADS 两级本体与个人本体的关系

必须避免把“个人、企业、中心三级数智底座”误认为“三级本体”。

本研究采用以下语义治理关系：

- ADS Core：跨个人、企业和领域稳定共享的基础概念与关系；
- Domain Ontology：业务领域专业概念、规则和术语扩展；
- Personal Namespace / Personal Scope：个人上下文中的工作、生活、学习和个人资源概念，是个人应用范围和命名空间，不新增一个与 ADS Core、Domain Ontology 并列的治理层级；
- Enterprise Namespace：企业业务对象、企业状态和企业规则；
- Local Extension：个人或组织的本地术语和映射，不得静默改变共同核心定义。

因此，ADS 的本体治理仍以“共同本体 + 业务领域本体”为主线；个人工作与生活本体是个人数智底座中的应用语义空间，使用共同核心概念并可进行个人化扩展。

### 7.5 核心概念与语义边界

| 概念 | 定义 | 不能混淆为 |
|---|---|---|
| Event | 某时点或时间区间发生的变化或事实候选 | Task、Memory |
| Activity | 为实现目标而持续进行的一组行动 | 单个 Event |
| Task | 有预期结果、责任主体、状态和完成条件的工作单元 | 会议中的任意一句话 |
| Commitment | 主体对未来行动或结果作出的承诺 | 普通建议或讨论 |
| Decision | 在约束和备选方案下，由有权主体作出的选择 | 未确认的意见 |
| Assertion | 有说话人归属的事实主张、观点或假设 | 已验证事实 |
| Evidence | 支持、限定或反驳某项断言的来源引用 | AI 摘要 |
| Memory | 从事件派生、可纠正的长期认知 | 原始事件 |
| Intent | 个人目标、承诺、任务、例程或项目 | Agent 的执行授权 |
| CapabilityAsset | 经过抽象、验证和版本化的可复用工作能力 | 未验证的个人经验 |

### 7.6 事件类型命名

事件类型应描述发生了什么，采用稳定命名空间，例如：

- personal.work.meeting_attended
- personal.work.commitment_created
- personal.work.context_observed
- personal.life.commitment_created
- personal.life.activity_completed
- personal.learning.session_completed
- personal.reflection.recorded
- work.task_status_changed
- work.decision_confirmed
- project.risk_signal_observed

未经确认的风险信号、任务候选和决策候选应使用候选状态，不能直接命名为已确认的业务结果。

### 7.7 关系与对象身份

关系必须具备谓词、方向、时间、来源、证据和状态。例如：

- involves_actor：事件涉及某主体；
- about_object：事件关于某对象；
- generated_from：事件来自某来源；
- derived_from：事件由另一事件派生；
- supports：证据支持某断言；
- contradicts：断言之间存在冲突；
- assigned_to：任务分配给某主体；
- depends_on：任务依赖另一任务；
- supersedes：新记录替代旧记录；
- authorized_by：处理由某授权凭据允许。

同名不代表同一对象。不能仅凭名称、文本相似或向量相似度自动合并人物、项目、客户和产品；无法唯一确认时必须保留候选或 unresolved 状态。

## 八、数据标准与核心数据契约

### 8.1 个人事件账本标准

每条个人事件建议至少包含：

| 字段 | 说明 |
|---|---|
| event_id | 事件唯一标识 |
| subject_ref | 个人主体引用 |
| event_type | 事件类型 |
| event_schema_version | 事件数据契约版本 |
| occurred_at | 发生时间 |
| observed_at | 观察时间 |
| recorded_at | 记录时间 |
| timezone / valid_time | 时区与有效时间 |
| actor_refs | 相关人员、角色或 Agent |
| object_refs | 相关项目、任务、个人对象或业务对象 |
| payload | 事件类型特有内容 |
| source_refs | 来源记录引用 |
| evidence_refs | 证据引用 |
| assertion_status | confirmed、observed、inferred、disputed、rejected、unknown 等 |
| confidence | 置信度 |
| classification | personal、personal_sensitive、restricted 等分类 |
| purpose_tags | 处理目的 |
| ontology_version | 本体版本 |
| processing_provenance | 解析、抽取、映射和人工修订过程 |
| sharing_policy | 共享范围与策略 |
| retention | 保留策略 |
| correction_of / supersedes | 更正与替代关系 |
| idempotency_key | 幂等标识 |
| lifecycle_status | active、superseded、withdrawn、expired、archived 等 |

### 8.2 记忆条目标准

每条 Memory Item 至少包含：

- memory_id、subject_ref、memory_type；
- claim：记忆内容；
- source_event_refs、evidence_refs；
- assertion_status、confidence、classification；
- valid_time、last_confirmed_at、review_after、expires_at；
- memory_lifecycle；
- derivation：派生过程；
- review_policy：复核策略；
- user_controls：用户控制；
- sharing_policy：共享策略；
- ontology_version。

任何长期记忆都必须能追溯到至少一个来源事件，或明确标记为用户主动声明。推断记忆默认从 candidate 开始。

### 8.3 个人意图对象标准

个人运行模型需要独立管理：

| 类型 | 核心问题 | 关键字段 |
|---|---|---|
| Goal | 希望达到什么状态？ | 目标、衡量方式、期限、进展 |
| Commitment | 向谁承诺了什么？ | 承诺主体、对象、期限、确认依据 |
| Task | 下一步要做什么？ | 动作、负责人、状态、完成条件 |
| Routine | 哪些事情需要周期性发生？ | 周期、触发条件、例外和暂停 |
| Project | 正在持续推进什么？ | 目标、范围、阶段、依赖和成果 |

Intent Object 的状态和确认状态应分开。例如 inferred_candidate 不得直接当作 user_confirmed。

### 8.4 PDKS 到 ADS 的映射原则

当前 PDKS—ADS 映射基线明确了以下规则：

- PDKS event → Personal Event Ledger；
- PDKS action → Personal Intent Object，不直接成为 Agent Action Proposal；
- PDKS personal_context → Memory Item；
- PDKS knowledge_asset → Memory Item，并按内容映射为 episodic、semantic 或 procedural；
- PDKS assertion 保留原始表达和说话人归属，不直接等同于已验证事实；
- PDKS entity 作为本体身份引用，不自动创建或合并主数据；
- PDKS source_asset → SourceRecord 引用；
- PDKS evidence_segment → Evidence 引用；
- PDKS relationship → 本体关系，保留谓词、证据、状态、置信度和有效期。

必须保持以下非等价关系：

1. PDKS Event 不等于 ADS Memory Item；
2. PDKS Action 不等于 ADS Personal Agent Action Proposal；
3. PDKS Assertion 不等于 Verified Fact；
4. Personal WorkEvent 不等于 Enterprise WorkEvent；
5. 共享本体定义不等于共享记录所有权。

### 8.5 版本与兼容性

事件 Schema、本体、事件分类、映射规则、授权策略和能力资产都必须带版本。版本升级应声明兼容性、迁移规则、映射损失和回滚策略。不能通过静默修改字段含义来升级标准。

## 九、个人数据存储与互操作

### 9.1 File-first 与结构化数据库并行

建议采用可读文件优先、结构化数据辅助的存储策略：

| 存储形式 | 主要用途 | 适用工具 |
|---|---|---|
| Markdown + YAML | 可阅读、可编辑的知识和记忆视图 | Obsidian、VS Code、普通 Markdown 编辑器 |
| JSON / JSONL | 事件、来源、证据、关系和标准数据 | PDKS、Agent、脚本和数据处理工具 |
| 附件文件 | 音频、图片、PDF、原始文件和多媒体材料 | 本地文件系统或受控对象存储 |
| SQLite | 可选运行时的本地结构化索引和状态 | PDKS Capture Runtime |
| 全文/向量索引 | 检索辅助 | 受权限过滤的搜索组件 |

Markdown 适合长期可读和人工检查，JSON/JSONL 适合机器互操作，SQLite 适合运行时查询。向量索引只能作为检索辅助，不能取代事实主存储和来源证据。

### 9.2 Obsidian 兼容

个人知识资产应当能够通过普通文件夹访问，Obsidian 作为可选阅读和编辑界面，而不是数据唯一所有者。

建议的目录结构：

- inbox/：新采集、待理解和待确认内容；
- sources/：来源元数据和受控引用；
- events/：标准事件记录；
- memories/：长期记忆和知识视图；
- knowledge/：方法、原则、经验和专题知识；
- goals/：目标、承诺和任务；
- entities/：人物、组织、项目和对象；
- evidence/：证据定位和片段元数据；
- attachments/：音频、图片和原始文件；
- policies/：授权、保留和用户偏好；
- exports/：标准化导出与迁移包。

目录结构属于建议基线，可根据实际实现调整，但不能破坏对象身份、来源引用和标准字段。

### 9.3 可迁移与跨 Agent

个人数据不能依赖某一个模型平台或某一种 Agent 的内部记忆格式。标准资产应能够：

- 以开放文件格式导出；
- 保留原始 ID、来源 ID、时间和本体版本；
- 通过标准 Schema 校验；
- 被不同 Agent 读取和解释；
- 在迁移时保留授权和删除状态；
- 将具体宿主权限与 PDKS 数据标准分离。

MCP、Agent Skills 和连接器是接入与调用方式，不是数据主权和存储本身。Skill 本身不会自动获得文件权限、连接器权限或长期存储能力。

### 9.4 本地优先与安全

个人原始数据默认留在个人控制范围。云端模型可以作为可替换的智能能力，通过受控接口调用；不应要求个人把所有原始数据永久交给单一模型平台。

生产级实现需要加密、密钥管理、备份恢复、设备撤销、数据删除传播、多设备冲突处理和审计。当前 PDKS 预览版本尚未完成静态加密、OS Keychain 集成和完整多设备同步，不能将其描述为已经具备生产级安全能力。

## 十、Skill、Agent 与初始化体验

### 10.1 Skill 的定位

PDKS Skill 负责把数据标准和操作流程转化为 Agent 可执行的工作方法。Skill 不替代底层运行时，也不自动赋予 Agent 主机权限。

建议形成以下能力模块：

1. Setup Skill：环境诊断、安装计划、用户确认、初始化和验证；
2. Capture Skill：接入用户主动输入、文件、会议、语音和连接器；
3. Event Extraction Skill：抽取事件、人物、对象、时间和关系；
4. Knowledge Curation Skill：形成候选知识、分类、校验和版本更新；
5. Memory Management Skill：记忆确认、合并、冲突、过期和撤回；
6. Intent Management Skill：目标、承诺、任务、例程和项目管理；
7. Retrieval Skill：按任务和授权生成上下文；
8. Reflection Skill：结果复盘、经验抽取和能力候选生成；
9. Migration Skill：标准导出、导入和跨 Agent 迁移；
10. Governance Skill：授权、分类、保留、审计和删除传播。

### 10.2 Agent-native 初始化

普通用户不应被要求理解 Node、Python、SQLite、JSON-LD 或本体文件。推荐流程是：

环境诊断 → 生成安装计划 → 展示路径、动作和风险 → 用户确认 → 初始化 → 校验 → 连接来源时再次单独授权。

CLI 仍可保留给开发者和故障排查，但不应成为普通用户的唯一入口。

### 10.3 当前 PDKS 预览状态

截至 2026-11-20，GitHub 项目记录显示：

- 当前 PDKS 版本主线为 0.5.3 preview，阶段为 transitional_skill_development，成熟度为 Experimental / Preview；
- Node-native File-first Vault 初始化路径已经形成预览实现，要求 Node.js 22.12+；初始化 Vault 不要求 Python；
- 可选 Capture Runtime 仍是独立 Python 组件，要求 Python 3.10+；
- 推荐流程为 doctor → plan → 明确批准 → apply → verify；
- 初始化不会自动连接来源、收集数据、导入历史、启动后台服务或开启云同步；
- 本地 Vault 文件当前未实现静态加密，不能用于真实敏感数据；
- 官方 DWS CLI 连接器处于预览状态，真实租户验证和历史回补尚未完成；
- GitHub Mirror Status 记录了 0.5.3.1 完整工程包的本地归档校验，但 GitHub 目录尚未逐文件展开完整源代码树。

0.5.3 验证报告记录 162 项自动化测试中 160 项通过、2 项跳过、0 项失败；但 npm 构建、MCP Inspector、MCP Apps、不同 Agent 宿主兼容、跨平台安装和真实 DWS 租户集成等检查尚未执行。未执行不能表述为通过。

因此，当前成果应定位为“已具备部分可验证的标准、原型和 Agent-native 初始化能力的实验预览”，而不是“已经完成的个人数智底座生产系统”。

## 十一、与 ADS 三级数智底座的关系

### 11.1 三级数智底座定位

| 层级 | 正式名称 | 核心职责 | 数据原则 |
|---|---|---|---|
| 第一级 | 个人数智底座 | 个人 AI 助理的本地闭环，沉淀个人知识、数据库、标准数据和数智资产 | 个人原始数据默认留在个人控制范围 |
| 第二级 | 企业数智底座 | 承载企业业务系统、企业知识、企业数据库、标准业务数据和协同资产，驱动企业端口智能体 | 企业数据由企业业务责任主体管理 |
| 第三级 | 业务领域中心数智底座 | ADS 配套的共同语义、跨域目录、能力目录、协调、调度和治理 | 优先协同语义、元数据、引用和授权结果，不无差别汇聚原始数据 |

术语说明：既有 ADS-12 等材料曾使用“智能生态系统中心数智底座”；当前总体架构研究采用“业务领域中心数智底座”。正式架构文件应统一术语并保留版本变更记录。

### 11.2 个人数智底座与企业数智底座的关系

个人数智底座是个人 AI 助理理解和服务个人的基础。企业数智底座是企业业务运行和企业 Agent 协同的基础。个人工作信息可以成为企业数智资产的一个来源，但不是企业数据的唯一来源，也不能自动转化为企业数据。

企业数智底座还需要融合：

- 企业现有业务系统数据；
- 企业知识库和业务数据库；
- 企业正式协同数据；
- 经领域本体映射、标准化和验证的企业标准业务数据；
- 经验证的能力资产、证据和审计记录。

### 11.3 个人资产向企业资产的受控投影

个人到企业的流程必须独立于普通个人记忆沉淀：

**个人形成 → 候选识别 → 本人授权提交 → 企业审核 → 身份与业务对象映射 → 语义标准化 → 质量验证 → 企业发布 → 生命周期治理。**

授权至少明确：

- 授权主体、被授权主体和代表关系；
- 目标企业、接收责任人和业务目的；
- 数据对象、字段、时间范围和允许动作；
- 有效期、再共享条件和撤回方式；
- 是否允许生成派生数据；
- 保存、删除和审计规则。

投影后生成独立的企业事件 ID 和企业生命周期。企业侧不能通过投影引用反向读取个人原始音频、完整笔记或无关生活信息。

### 11.4 个人生活数据的边界

个人生活事件是个人上下文本体的一等对象，但不是企业工作事件的默认扩展字段。

- 个人生活事件默认 personal_only；
- 企业不能因为员工使用个人 AI，就默认获得其完整个人记忆；
- 若用户愿意为工作排期提供个人可用时间，只共享完成该任务所需的可用性或约束，不共享无关生活事件的内容和原因；
- 个人工作记录中的客户、同事和第三方信息仍受相应业务与隐私规则约束。

### 11.5 ADS 在整体体系中的作用

ADS 不负责把个人原始录音集中到中心仓库。ADS 的核心作用是：

- 管理共同本体和共同语义标准；
- 支持身份、角色、代表关系和授权治理；
- 提供跨域联邦资产目录和能力目录；
- 支持任务契约、Agent 协同和跨域调度；
- 管理证据、审计、责任追溯和版本；
- 将经过验证的标准、能力和协作经验回馈到个人与企业侧。

三级底座是治理和资源组织层级，不是本体层级，也不是简单的原始数据逐级汇总。

## 十二、核心创新价值

### 创新一：从静态知识库转向个人连续上下文

不再只保存文档和摘要，而是持续理解事件、对象、关系、状态、目标和变化，使 AI 能回答“发生了什么、为什么发生、现在处于什么状态、下一步要做什么”。

### 创新二：从单一录音转向多源工作与生活感知

录音、手机、电脑、日历、钉钉、邮件、文档和任务系统统一进入事件理解链路。设备可替换，个人数据标准和记忆资产不随设备迁移而丢失。

### 创新三：以事件账本建立可信记忆

将原始来源、观察、事件、断言、记忆和行动分开建模。每条记忆能够追溯来源、置信度、有效期和确认状态，降低 AI 幻觉沉淀为个人事实的风险。

### 创新四：建立个人数据自主权与企业资产转化机制

个人数据先在个人责任边界内沉淀。企业侧通过目的绑定、最小必要授权、审核、映射和验证获得需要的业务信息，而不是默认读取个人完整记忆。

### 创新五：将个人经验转化为可验证能力资产

不复制个人记忆，而是从多次真实任务中提取方法、流程、模板和 Skill。能力资产经过适用范围、质量、风险和版本验证后，才进入跨人员复用。

### 创新六：将证据与标准数据双轨分流

来源证据服务人类判断、审批和验收；标准数据服务智能体运行和升级。两者同源但用途不同，形成可追溯、可审计的智能闭环。

### 创新七：建立跨 Agent、跨工具和跨存储的个人数据标准

通过 PDKS 标准化表达、开放文件存储、Schema 校验和本体版本治理，降低个人知识和数智资产对单一模型平台、Agent 或软件工具的依赖。

## 十三、验证方法与评价指标

### 13.1 不把跨人复用作为第一阶段唯一验证目标

个人记忆高度依赖个人背景、关系和上下文，要求另一个人直接复用原始个人记忆并不合理。应区分：

1. 个人记忆：服务原本人；
2. 团队协同资产：经确认的项目决策、任务和共享背景；
3. 能力资产：从实践中抽象、验证和版本化的流程、模板、规则和 Skill。

### 13.2 四级验证阶梯

| 级别 | 验证对象 | 核心问题 | 主要证据 |
|---|---|---|---|
| L1 个人有效 | 同一个人 | AI 是否准确理解上下文、减少重复整理和遗漏？ | 记忆正确率、检索成功率、纠错成本、节省时间 |
| L2 团队协同 | 同一项目团队 | 是否减少信息遗漏、重复沟通和任务断点？ | 决策追溯、任务闭环、团队确认 |
| L3 岗位复用 | 同类任务、不同人员 | 经验证的流程或 Skill 是否帮助新执行者？ | 任务质量、耗时、错误率、专家介入量 |
| L4 跨项目复用 | 相似流程、不同项目 | 能力资产是否有稳定适用范围和迁移条件？ | 多项目验证、适配成本、失败边界 |

### 13.3 关键评价指标

| 维度 | 指标 | 说明 |
|---|---|---|
| 采集质量 | Source Coverage | 用户授权来源的实际接入覆盖 |
| 事件质量 | Event Precision / Recall | 事件抽取准确率和召回率 |
| 时间质量 | Temporal Accuracy | 发生、观察、记录和有效时间准确度 |
| 关联质量 | Entity Resolution Accuracy | 人物、项目和对象关联准确率 |
| 记忆质量 | Memory Correctness | 长期记忆事实准确程度 |
| 时效质量 | Stale Memory Rate | 过期或失效记忆比例 |
| 检索价值 | Retrieval Utility | 是否帮助完成真实任务 |
| 用户负担 | Correction Burden | 用户纠正和维护记忆的成本 |
| 资产质量 | Enterprise Acceptance Rate | 企业审核与标准化通过比例 |
| Agent 安全 | Approval Bypass | 未审批执行高风险动作次数，目标为零 |
| 数据治理 | Unauthorized Projection | 未授权投影次数，目标为零 |
| 执行质量 | Verified Action Success | 经核验的执行成功比例 |
| 用户信任 | User Trust / Control | 用户是否理解和掌握数据控制权 |
| 复用能力 | Cross-person Task Quality | 新执行者任务质量和专家介入变化 |
| 经济性 | Total Cost per User / Task | 设备、模型、存储、运维和管理的综合成本 |

采集时长、录音数量、知识条目数量不应成为主要成功指标。真正的价值在于减少遗漏、提高上下文检索和任务推进质量，同时不损害用户控制权。

## 十四、实施路线与阶段门槛

### P0：标准与治理冻结

- 冻结 PDKS 数据对象、事件分类和 Schema 基线；
- 冻结个人工作、生活和学习上下文边界；
- 明确个人默认私有、来源授权、保留、删除和撤回规则；
- 明确本体、Schema、映射和版本管理方式；
- 确认首个试点场景和评估指标。

**进入下一阶段条件：** 数据主体、授权边界和退出机制可解释、可执行。

### P1：个人事件账本 MVP

- 支持手动输入和少量高价值来源；
- 建立 Source Vault 和 Personal Event Ledger；
- 实现来源引用、时间模型、去重、幂等和追加式纠错；
- 提供个人时间线、检索、导出和纠错。

**进入下一阶段条件：** 事件可追溯、可纠错，用户能够理解系统记录了什么。

### P2：持续记忆与个人运行模型

- 建立候选记忆、确认、冲突、过期和撤回机制；
- 建立目标、承诺、任务、例程和项目对象；
- 建立事件到记忆和 Intent 的可追溯关系；
- 提供每日回顾和承诺追踪。

**进入下一阶段条件：** 记忆正确性和用户控制体验达到预设标准。

### P3：Personal Agent 只读与草稿能力

- 按任务生成 Context Package；
- 支持只读查询、摘要、草稿和提醒建议；
- 建立工具能力白名单、动作风险等级和执行状态机；
- 记录 Agent 使用的上下文、来源和策略版本。

**进入下一阶段条件：** Agent 不越权、不把推测当事实、不误报执行完成。

### P4：多源授权采集与多端协同

- 逐步接入文档、日历、任务、沟通和会议来源；
- 验证 DWS 等连接器的真实租户能力；
- 验证离线缓存、补传、撤销和删除传播；
- 建立手机、电脑、Web 和可选语音设备的统一身份与状态。

**进入下一阶段条件：** 来源授权、数据同步和撤回机制通过安全评审。

### P5：个人到企业的授权投影试点

- 选择一个明确业务流程；
- 将个人侧候选工作事件提交企业审核；
- 关联企业项目、任务、客户或产品对象；
- 形成独立企业事件和标准业务数据；
- 由企业 Agent 在授权范围内使用。

**进入下一阶段条件：** 业务对象关联准确、企业审核有效、授权和撤回可验证。

### P6：能力资产化与跨人复用

- 从多个真实任务中提取流程、模板、规则和 Skill 候选；
- 由业务负责人验证适用条件和失败边界；
- 建立版本、评测集、依赖和责任人；
- 在新执行者和新项目中开展对照实验；
- 根据结果决定规模化和硬件自研。

**进入下一阶段条件：** 能力资产在新执行者或新项目中产生可重复的质量或效率收益。

## 十五、风险、约束与未完成事项

### 15.1 主要风险

| 风险 | 控制原则 |
|---|---|
| 个人数智底座被异化为员工监控系统 | 个人主体控制、目的限定、透明采集、禁止默认用于无关绩效画像 |
| 个人和企业数据边界混淆 | 个人默认私有，企业投影独立授权、审核和生命周期 |
| 录音涉及第三方隐私 | 明确告知、适用同意要求、敏感过滤和保留策略 |
| AI 推断变成事实 | 保留断言状态、来源和置信度，重要事项人工确认 |
| 人物和项目误关联 | 候选解析、权威 ID、人工确认和冲突保留 |
| 多端同步导致重复或丢失 | 幂等、版本、冲突处理和审计 |
| 删除后从其他来源重新生成 | 派生链追踪、抑制标记和删除传播 |
| Agent 越权行动 | 能力白名单、风险分级、审批门禁和执行核验 |
| 能力资产跨人复用失败 | 适用范围、独立评测、灰度和回滚 |
| 过早追求全量采集 | 先验证高价值来源，逐源授权和渐进接入 |

## 十七、最终结论

个人数智底座的核心不是让 AI 保存更多内容，而是让 AI 在个人授权和控制范围内，持续、可信地理解个人真实发生的事情，并把这些理解转化为可追溯的记忆、可推进的目标与承诺、可执行的任务，以及在经过验证后可复用的能力资产。

这套体系的最终形态不是一个要求用户每天整理资料的知识库，而是一个在用户正常使用设备和应用的过程中，自然形成个人上下文、帮助个人持续行动的智能基础设施。

其长期价值体现在三个层面：

- **对个人：** 减少信息遗忘和重复整理，让 AI 真正理解个人的工作、生活与成长；
- **对企业：** 在尊重个人数据边界的前提下，获得更完整、更可信、可关联业务对象的工作上下文和标准业务数据；
- **对 ADS 生态：** 让个人智能体能够以标准语义、授权和任务契约接入企业及业务领域智能体，形成标准数据自下而上汇流、验证能力自上而下回馈的数智底座矩阵。

最终研究主线可以浓缩为：

**多源感知真实活动 → 事件账本记录事实线索 → 本体建立统一语义 → 持续记忆理解个人 → 目标与承诺驱动行动 → Agent 在授权下执行 → 结果与证据回流 → 经验沉淀为能力资产 → 经授权与 ADS、企业数智底座协同。**

这就是个人数智底座知识沉淀体系从“资料管理”走向“个人智能基础设施”的核心路径。
