Executive Summary

从“把信息存下来”走向“理解工作世界”

如果个人 AI 只记住对话，企业 AI 只搜索文档，Agent 只调用工具，那么它们仍然缺少一套共同的语义结构：谁在做什么、事情发生在哪里、影响哪个对象、形成了什么状态、依据是什么、谁有权确认。

本体的价值：为个人、企业和业务领域提供共同概念、关系和约束；不意味着把所有实例数据放在同一个地方。

01 · Why Ontology

本体不是知识图谱的别名，也不是再建一个数据库

概念解决的问题ADS 中的职责
Ontology概念是什么、彼此有什么关系？共同语义、领域语义、约束和版本
Schema数据有哪些字段和类型？约束 WorkEvent、BusinessObject 等结构
Event Stream何时发生了什么变化？追加事件、重放和审计
Knowledge Graph如何存储和查询实体关系？可选的关系存储实现
MDM哪个客户、项目或产品是权威对象？主数据身份和源系统映射
Context当前任务需要哪些信息？按任务和授权组织最小必要信息
关键区分：本体定义语义，Schema 定义结构，事件流记录变化，主数据解决身份，Context 组织任务信息。它们互相引用，但不能互相替代。

AI 真正需要理解的工作关系

主体

谁发起、参与、负责或确认？人、角色、Agent 还是系统？

事件

发生了什么？是观察、讨论、承诺、决策还是正式状态变化？

对象

影响哪个项目、客户、产品、任务、交付物或个人目标？

时间

什么时候发生、何时观察、何时记录、何时生效？

依据

来源在哪里？是权威记录、人工确认还是模型推断？

责任

谁有权确认、修改、共享和采取下一步行动？

L2 · 事件与活动层

04 · Semantic Precision

事件、活动、任务、承诺、决策：五个概念必须分开

选择一个概念，查看它的定义、必要语义和常见误判。

Event · 发生了什么？

某个时点或时间区间内发生的变化或可观察事实候选。需要类型、主体、对象、时间、来源和断言状态。常见误判：把讨论内容直接当成已确认决定。

概念必须回答关键字段
Event发生了什么？类型、主体、对象、时间、来源、状态
Activity一段时间内在做什么？目标、参与者、时间区间、过程、结果
Task谁需要完成什么？目标、负责人、期限、状态、完成条件
Commitment谁承诺了什么？承诺主体、对象、期限、确认依据、履约状态
Decision谁在什么权限下确定了哪个选择？选项、依据、约束、审批、生效范围
不能从“有人提到某项工作”推断“任务已经创建”；不能从“可以考虑”推断“决策已批准”；不能从“检测到延期信号”推断“责任人已经承认延期”。

时间语义不能压成一个时间戳

Occurred

事情实际发生的时间。

Observed

系统感知到事情的时间。

Recorded

事件写入系统的时间。

Valid

状态或关系在业务世界中生效的时间。

  • 会议背景与提醒
  • 个人工作目标

ENTERPRISE PROJECTION

企业侧最小必要记录

  • 经确认的项目行动项
  • 责任人和截止时间
  • 企业项目对象引用
  • 授权、来源和转换版本

边界原则：个人生活事件是个人本体的一等对象，但不是企业工作本体的默认字段。企业不应为了“理解员工”而读取个人生活时间线，也不应将个人生活数据默认用于绩效评价。
个人本体是否应该允许用户自定义？

应该。个人生活和工作方式存在差异，个人本体需要支持本地类别、别名、关系和记录策略。ADS Core 只提供稳定语义锚点，不应要求每个人采用完全相同的个人分类表。

06 · Enterprise & Domain Ontology

共同核心保持稳定，业务领域保留专业差异

ADS CORE

共同核心本体

Actor、Event、Task、Decision、Evidence、Resource、Time、Authorization。

ENTERPRISE

企业工作本体

企业组织、项目、客户、产品、流程、任务、风险和业务规则。

DOMAIN

业务领域本体

项目交付、客户服务、研发、供应链、财务等专业概念。

语义映射状态

状态含义处理方式
exact语义和约束一致按契约自动映射
equivalent近似等价但有适用条件保留映射说明和抽样复核
broader / narrower上下位概念关系不得直接无损替换
related相关但不等价建立关联，不合并
candidate / unresolved候选或无法可靠映射保留原值，等待确认
conflict不同领域定义冲突并列保留并升级治理
同名不代表同义。项目交付中的“验收”、研发中的“发布”、供应链中的“交付”不应只因词面相似就合并。领域扩展使用命名空间和 Owner 治理。

身份解析的六步

  1. 保留源系统、租户和原生对象 ID。
  2. 根据类型、权威映射和组织范围生成候选。
  3. 记录匹配依据、置信度和解析状态。
  4. 无法唯一确认时返回 candidate 或 unresolved。
  5. 由有权业务人员确认后建立 IdentityMapping。
  6. 合并、拆分和纠错均保留历史映射。

处理状态与业务断言状态必须分开

PIPELINE STATUS

处理状态

received → parsed → mapped → awaiting_review → accepted / rejected → corrected / superseded → archived

ASSERTION STATUS

业务断言状态

confirmed、observed、inferred、disputed、rejected、stale、unknown

模型完成抽取，不代表业务事实已经确认；数据通过 Schema 校验，也不代表语义正确。重要状态必须保留来源、有效时间和确认责任。

事件追加与纠错

事件采用追加式原则。原始来源和已接收事件不应被静默覆盖。纠错通过更正事件、撤回事件、supersedes 或 correction_of 关系表达；状态视图可以重建，但历史事件和来源引用必须可追溯。

投影决策矩阵

个人侧内容默认策略企业侧处理
个人生活事件personal_only不投影
个人工作线索personal_only由本人选择提交审核
明确项目行动项review_required确认项目、责任人、期限和业务目的后投影
会议中的候选决策review_required确认决策状态和审批权限
企业正式状态enterprise_authoritative引用权威业务系统，不用个人记录覆盖
个人工作方法candidate抽象、去标识化、授权和独立验证后成为能力候选
不可逆的边界错误：未授权个人生活信息进入企业上下文；企业通过派生引用反向读取个人原始记录；把个人 AI 推断直接写成企业正式任务或决策。

撤回不是一句“删除”，需要处理派生链

撤回后停止新的读取、投影和下游调用；对已派生记录，由数据 Owner、隐私责任方和业务责任方按制度判断删除、限制、替换或保留审计。若能力资产由多来源抽象形成，也要重新评估来源授权和可保留性。

09 · Ontology Registry

本体 Registry 管理语义，而不直接承载所有实例数据

Ontology Registry

共同、个人、企业和领域本体的版本与状态。

Vocabulary Service

术语、别名、定义、多语言名称和标签。

Schema Registry

事件、对象、任务和能力资产的数据契约。

Identity Resolution

人、组织、项目、客户和产品的身份解析。

Mapping Service

源字段、事件类型、领域概念和目标语义映射。

Policy Service

主体、目的、范围、分类、动作和授权校验。

Event Gateway

事件接收、Schema 校验、幂等和路由。

Context Builder

面向任务生成最小必要上下文包。

Audit & Evaluation

记录映射、调用、人工修正和评测结果。

首期不必把每个组件拆成微服务。先用模块化单体、关系数据库、事件日志和对象存储实现语义契约；只有在规模和责任边界明确后再拆分。

五种版本必须分开管理

ontology_version、event_schema_version、mapping_version、policy_version 和 source_record_version 各自承担不同职责。能力资产还要绑定其依赖的本体版本和评测集版本。

10 · Versioning & Compatibility

本体变化不能静默改变历史事件的含义

版本变化允许变化兼容要求
Patch定义修正、别名补充、非语义错误修复不改变既有含义
Minor新增类、关系、事件类型或可选属性不破坏既有事件解释
Major删除、重命名、改变基数或语义定义迁移计划、双版本读取和回归评测

命名空间建议

ads.core.*

跨领域稳定概念：Actor、Event、Task、Decision、Evidence。

ads.personal.*

个人工作、生活、学习和资源上下文。

ads.enterprise.*

企业组织、业务对象和工作流程概念。

ads.domain.* / ads.local.*

业务领域与企业本地扩展，必须有 Owner 和映射规则。

逻辑语义统一不要求所有系统采用同一种数据库。JSON Schema 继续约束当前契约；JSON-LD 可用于语义交换；RDF / OWL / SHACL 可作为复杂推理和约束验证的候选技术，而不是首期前置条件。

关键质量指标

Event Precision / Recall

事件抽取准确率和召回率，按事件类型与复杂度分层。

Entity Resolution

对象关联正确率；高影响对象采用更严格门槛。

Relation Accuracy

责任、依赖、影响等关系准确率。

Temporal Accuracy

发生、观察、记录和有效时间的正确率。

Projection Leakage

不应投影字段进入企业侧的比例，关键边界零容忍。

Authorization False Allow

无授权却允许访问或投影的次数，目标为零。

准确率不能抵消治理违规。只要出现未授权生活信息投影或高影响错误对象合并，就应暂停相关链路。

13 · Architecture Decisions

建议冻结的十二项架构决策

ADR建议决策
01共同核心 + 个人 + 企业 + 领域分层，避免单一本体吞并所有业务语义。
02个人本体覆盖工作与生活，个人是主体而不是员工身份。

09个人到企业采用目的绑定、最小必要的单向投影。

14 · Readiness Checklist

  • 个人生活事件默认不进入企业侧。
  • 个人工作事件不自动成为企业正式事件。
  • 企业投影有目的、字段、接收者、有效期和授权引用。
  • 企业侧无法通过投影引用读取个人原始记录。
  • 授权撤回和派生记录处理规则可执行。
事件与映射
  • 来源、发生时间、观察时间和记录时间保留。
  • 对象身份解析支持 candidate 和 unresolved。
  • 映射支持 exact、equivalent、related、candidate、unresolved 和 conflict。
  • 冲突和未知不会被模型自动覆盖。
  • 事件更正和历史版本可追溯。
工程与运营
  • Ontology Registry、Schema Registry 和 Mapping Registry 有明确责任人。
  • 本体版本与 WorkEvent、ContextPackage 和 Capability Manifest 兼容。
  • 项目交付试点有人工标注集和质量评测。
  • 投影泄漏和未授权访问纳入零容忍安全门槛。
  • 本体变更有评审、回归、迁移和退役流程。
Conclusion & Next Research

让个人数智底座理解人，让企业数智底座理解业务

不是把所有人的信息汇总到一个地方，而是让不同责任边界拥有共同语义，并在明确授权下形成协同。
