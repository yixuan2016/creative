## 摘要：从架构设计进入工程验证

前三份专题依次回答了三个问题：

- ADS-WORK-01：工作信息从哪里来，个人工作信息如何在授权和审核后成为企业数智资产？
- ADS-WORK-02：企业需要理解哪些工作上下文，如何形成对企业运行的动态认知？
- ADS-WORK-03：如何通过统一数据模型、运行认知引擎和上下文服务平面实现这种能力？

本文件进入工程验证阶段，定义首批标准数据契约、事件类型、接口约定、状态重建规则、上下文生成协议和最小可运行原型。目标是让开发团队可以基于本文件建立第一版服务，让业务团队可以基于真实项目交付流程验证数据质量、上下文价值和治理边界。

本专题不以“建设一个新的企业知识库”为目标，也不要求第一阶段接入企业所有系统或采集所有员工活动。第一阶段仅验证一条最小闭环：

**权威业务系统事件 + 经授权的协同线索 → 标准事件 → 业务对象关联 → 状态重建 → 任务级上下文包 → Agent 只读辅助 → 人工确认与反馈。**

### 本专题交付物

1. 一套 JSON Schema：定义事件、对象、关系、状态、证据、授权和上下文包等契约。
2. 一份 OpenAPI 草案：定义事件接入、对象解析、状态查询和上下文包服务接口。
3. 一组项目交付模拟数据：覆盖权威系统事件、会议推断、状态冲突和授权范围。
4. 一个 Python 标准库原型：演示事件接入、幂等去重、权威状态重建、冲突保留、上下文包生成和权限拒绝。
5. 一组自动化验收测试：验证关键功能和治理约束。
6. 一份实施与评审清单：明确从本地原型到企业试点的差距。

## 1. 目标、范围与非目标

### 1.1 工程目标

- 让事件、对象、状态和证据使用明确、可版本化的机器可读契约。
- 让不同系统通过适配器映射到统一事件信封，而不要求源系统改变内部数据模型。
- 让每个关键状态都能解释其权威来源、支持事件、有效时间和不确定性。
- 让 Agent 通过任务级上下文包获取最小必要信息，而不是直接获得全企业数据访问权。
- 让原型具备可重复运行、可自动测试、可审计的基本能力。
- 让试点能够量化评估准确性、时效、人工核验成本、业务收益和治理风险。

### 1.2 第一阶段范围

第一阶段选择项目交付场景，只实现以下对象：

| 对象 | 用途 | 权威来源示例 |
|---|---|---|
| Project | 项目主对象 | 项目管理系统 |
| Task | 项目任务 | 项目管理系统 |
| Decision | 项目决策 | 决策记录或审批系统 |
| Risk | 项目风险 | 风险台账或责任人确认 |
| Evidence | 证据引用 | 原始系统、文档或会议记录 |
| ActorRef | 人员、角色、系统或 Agent 引用 | 组织身份系统或连接器身份 |

首批事件类型：

- project.state_changed
- task.created
- task.updated
- task.completed
- decision.proposed
- decision.approved
- risk.identified
- evidence.attached

第一阶段只实现只读查询与上下文生成。Agent 写回、自动审批、自动变更项目状态不在首轮原型范围内。

### 1.3 非目标

- 不替代项目管理系统、ERP、CRM、OA 或文档系统。
- 不建设全企业主数据平台或一次性覆盖所有业务领域。
- 不在原型中实现生产级身份认证、分布式事务、消息队列和高可用。
- 不将模型置信度当作业务确认，不自动消除高影响冲突。
- 不默认采集员工音频、屏幕、私人通信或与业务目的无关的信息。
- 不将个人工作记忆自动转化为企业资产。
- 不把演示数据或原型结果当作真实企业运行结论。

## 2. 工程标准与通用约定

### 2.1 标准化原则

| 原则 | 工程要求 |
|---|---|
| 语义统一 | 字段、事件类型和状态枚举有稳定定义 |
| 源系统自治 | 保留源系统 ID、原始状态和原始记录版本 |
| 可追溯 | 事件和状态均可定位来源 |
| 时间明确 | 区分发生时间、观察时间、记录时间和业务有效时间 |
| 不确定性显式 | confirmed、observed、inferred、disputed、stale、unknown 分开表达 |
| 版本可控 | Schema、本体、策略和 API 都有版本 |
| 最小权限 | 按主体、用途、对象、字段、动作和时间校验授权 |
| 可纠错 | 通过更正事件、替代关系和失效状态纠错，不静默覆盖 |
| 可重放 | 状态投影可以由事件和规则重建 |
| 可迁移 | 优先使用 JSON、JSON Schema、OpenAPI 等开放格式 |

### 2.2 命名约定

- JSON 字段使用 snake_case。
- 事件类型使用稳定的领域命名规则；本专题示例使用 task.updated。
- ID 使用带类型前缀的字符串仅作为可读示例；生产环境需确定 UUID、ULID 或组织统一 ID 规范。
- 枚举值使用小写英文，展示名称可由界面本地化。
- 时间采用 RFC 3339 / ISO 8601，必须包含时区偏移；内部计算建议统一转换为 UTC，展示时按用户或业务所在地转换。
- 金额、数量等有单位的数据不得只保存无单位数字，应同时记录 currency / unit。
- 扩展字段放入明确的 extensions 对象，不随意增加顶层字段。

### 2.3 时间语义

| 字段 | 含义 | 示例 |
|---|---|---|
| occurred_at | 业务事件实际发生时间 | 会议中确认任务延期的时间 |
| observed_at | 连接器或来源观察到该事件的时间 | Webhook 到达时间 |
| recorded_at | 统一事件账本接收并记录的时间 | 平台入库时间 |
| valid_from / valid_to | 状态或关系在业务世界中的有效区间 | 项目状态开始生效时间 |
| evaluated_at | 认知引擎计算当前视图的时间 | 状态投影生成时间 |

不得用 recorded_at 代替 occurred_at，也不得因为某条消息晚到就认定其业务发生时间更晚。

### 2.4 统一事件信封

每个进入统一上下文模型的事件都必须包含 event_id、tenant_id、event_type、event_schema_version、occurred_at、observed_at、recorded_at、object_refs、payload、source_ref、assertion_status、classification、purpose_tags、ontology_version 和 lifecycle_status。actor_ref 可为空，但必须说明来源主体未知。

接入连接器应补齐 observed_at 和 recorded_at；若源系统没有发生时间，应明确记录 occurred_at 的推定规则和时间质量，不可伪装为源系统精确时间。

## 3. 首批数据契约

完整机器可读定义见 schemas/ads-work-context-v0.1.schema.json。该文件使用 JSON Schema Draft 2020-12，并以 $defs 复用公共结构。

### 3.1 ObjectRef：业务对象引用

~~~json
{
  "object_id": "obj_project_014",
  "object_type": "project",
  "tenant_id": "tenant_demo",
  "source_system": "project-system",
  "source_object_id": "PRJ-2026-014",
  "resolution_status": "confirmed"
}
~~~

object_id 是上下文层稳定标识；source_object_id 是源系统主键。两者不得混为一谈。若身份解析只有候选结果，应使用 candidate 状态并进入审核流程，不应创建确定性业务关系。

### 3.2 WorkEvent：工作事件

~~~json
{
  "event_id": "evt_project_014_002",
  "tenant_id": "tenant_demo",
  "event_type": "project.state_changed",
  "event_schema_version": "0.1",
  "occurred_at": "2026-11-18T09:30:00+08:00",
  "observed_at": "2026-11-18T09:30:04+08:00",
  "recorded_at": "2026-11-18T09:30:05+08:00",
  "actor_ref": {"actor_type": "system", "actor_id": "project-system"},
  "object_refs": ["obj_project_014"],
  "payload": {
    "property": "project.status",
    "old_value": "in_progress",
    "new_value": "blocked",
    "reason_code": "dependency_pending"
  },
  "source_ref": {
    "source_system": "project-system",
    "native_record_id": "PRJ-2026-014",
    "record_version": "42"
  },
  "assertion_status": "observed",
  "classification": "internal",
  "purpose_tags": ["project_delivery_context"],
  "ontology_version": "ads-common-0.1/domain-project-0.1",
  "lifecycle_status": "active"
}
~~~

源系统事件的 assertion_status 可以是 observed。状态引擎结合权威来源目录和源记录版本判断该事件是否可作为权威状态依据，不应把模型 confidence 当作唯一判断标准。

### 3.3 StateAssertion：状态断言

状态断言是状态引擎生成或接收的可追溯结果。至少包含对象、属性、值、有效时间、来源、确认状态和计算规则版本。对于当前状态，应同时保留权威来源和非权威来源的冲突项。

### 3.4 Relation：关系

关系必须有 predicate、主体、客体、来源、有效时间和 assertion_status。首批关系为 belongs_to、depends_on、blocks、decided_by、supported_by 和 affects。关系类型应登记定义、反向关系、基数约束和是否允许推断。

### 3.5 ContextPackage：任务级上下文包

~~~json
{
  "context_id": "ctx_project_review_014",
  "task_id": "task_review_project_014",
  "requester_ref": "agent_project_assistant",
  "purpose": "prepare_project_status_review",
  "scope": {
    "object_ids": ["obj_project_014"],
    "time_window": {
      "from": "2026-11-17T00:00:00+08:00",
      "to": "2026-11-20T00:00:00+08:00"
    }
  },
  "included_refs": {
    "object_ids": ["obj_project_014"],
    "event_ids": ["evt_project_014_001", "evt_project_014_002"]
  },
  "unresolved_items": [
    {"type": "state_conflict", "property": "project.status"}
  ],
  "allowed_actions": ["summarize", "draft_follow_up"],
  "authorization_refs": ["grant_project_assistant_demo"],
  "policy_version": "context-policy-0.1",
  "ontology_version": "ads-common-0.1/domain-project-0.1",
  "created_at": "2026-11-19T10:00:00+08:00",
  "expires_at": "2026-11-19T10:30:00+08:00",
  "lifecycle_status": "active"
}
~~~

上下文包应视为有生命周期的交付物。生成后不应静默改变内容；如需更新，应生成新版本或新 context_id，并关联 supersedes。上下文包过期、撤销或授权变化后，读取必须重新校验。

## 4. 事件类型目录与映射规范

### 4.1 首批事件目录

| 事件类型 | 触发时机 | 关键 payload | 默认可信来源 |
|---|---|---|---|
| project.state_changed | 项目状态变化 | property、old_value、new_value、reason | 项目管理系统 |
| task.created | 新任务创建 | title、assignee、due_at、parent_project | 项目管理系统 |
| task.updated | 任务字段变化 | changed_fields、old_values、new_values | 项目管理系统 |
| task.completed | 任务完成 | completed_at、acceptance_status、evidence_refs | 项目管理系统或验收记录 |
| decision.proposed | 提出决策建议 | statement、alternatives、rationale_refs | 会议/文档，经授权 |
| decision.approved | 正式决策获批 | decision_ref、approver_ref、effective_at | 审批系统或授权确认 |
| risk.identified | 发现风险线索 | description、impact、likelihood、affected_refs | 风险台账或候选线索 |
| evidence.attached | 证据关联对象 | evidence_ref、target_refs、verification_status | 原始系统或人工核验 |

### 4.2 来源等级不是全局固定排名

不建立“ERP 永远高于会议、项目系统永远高于邮件”的全局排名。应按 object_type + property + domain_id 配置权威来源。例如：

| 对象属性 | 权威来源示例 | 可作为线索的来源 |
|---|---|---|
| project.status | 项目管理系统 | 会议纪要、邮件、Agent 摘要 |
| task.status | 项目管理系统 | 会议纪要、协同消息 |
| decision.approval_status | 审批系统或正式决议 | 会议讨论、聊天记录 |
| risk.confirmed_status | 风险台账或责任人确认 | AI 风险检测、会议线索 |

### 4.3 事件映射规则

连接器应提供独立映射配置，至少包括 source_system、source_event_type、target_event_type、source_field 到 canonical_field 映射、时间字段和时区规则、源状态映射、对象 ID 解析规则、数据分类、purpose_tags、schema_version、映射规则版本和责任人。

每次映射规则变更都要可追溯。旧事件保留原映射版本，不因规则更新而静默改变历史含义。

### 4.4 幂等与更正

推荐幂等键：

tenant_id + source_system + native_record_id + record_version + event_type

若源系统无 record_version，应由连接器定义稳定的变更指纹，并记录其算法版本。重复事件不得重复产生状态变化或业务副作用。

更正通过 correction_of 或 supersedes 关联原事件；撤回应记录原因、授权依据和影响范围。禁止直接覆盖事件账本中的原始事件。

## 5. 状态重建规则

### 5.1 输入

状态引擎输入包括对象身份与属性、相关工作事件和状态断言、权威来源注册表、领域状态映射、有效时间和新鲜度规则、事件确认状态与证据引用。

### 5.2 建议算法

1. 识别 object_id 和 property。
2. 查询该对象属性对应的权威来源配置。
3. 过滤未授权、已撤回、已被替代或无效的事件。
4. 按业务有效时间和源系统版本识别事件顺序。
5. 若存在有效权威来源记录，以权威记录形成当前值。
6. 将其他来源的不同值保留为 conflict，不覆盖权威值。
7. 若不存在权威来源记录，不得伪造确定状态；可输出 observed / inferred / unknown。
8. 检查新鲜度阈值，过期值标记 stale。
9. 输出 supporting_refs、conflicts、unknowns、authority_source、evaluated_at 和 rule_version。

### 5.3 冲突输出样例

~~~json
{
  "object_id": "obj_project_014",
  "property": "project.status",
  "value": "blocked",
  "assertion_status": "confirmed",
  "authority_source": "project-system",
  "supporting_refs": ["evt_project_014_002"],
  "conflicts": [
    {
      "source_system": "meeting-notes",
      "value": "on_track",
      "assertion_status": "inferred",
      "event_id": "evt_project_014_003"
    }
  ],
  "unknowns": ["客户验收日期尚未确认"],
  "evaluated_at": "2026-11-19T10:00:00+08:00",
  "rule_version": "project-state-rules-0.1"
}
~~~

### 5.4 业务状态与认知状态分离

- 业务状态：权威业务系统或责任人正式确认的状态。
- 认知状态：引擎根据多源信息形成的观察、推断、冲突和风险视图。

例如，项目管理系统仍记录 in_progress，而引擎根据延期事件推断 at_risk。两个值不必互相覆盖，必须分别呈现其语义、来源和可信级别。

## 6. 授权与上下文包生成协议

### 6.1 授权校验维度

每次上下文生成必须校验 subject、on_behalf_of、purpose、tenant_id、object_scope、classification_scope、allowed_actions、valid_from / expires_at 和 policy_version。

授权不应仅由用户登录或 Agent 角色决定。访问每个对象和字段时仍要执行用途与数据范围校验。

### 6.2 上下文生成步骤

1. 接收 requester、purpose、task 和 object_scope。
2. 解析主体身份和代表关系。
3. 查询有效授权和策略版本。
4. 校验对象范围、时间范围和字段范围。
5. 检索可访问事件、状态、关系和证据。
6. 计算当前状态与冲突、未知、过期项。
7. 仅保留任务必需信息。
8. 标注来源、权威性、时间和不确定性。
9. 生成 context_id、expires_at 和 integrity_hash。
10. 写入审计记录。

### 6.3 上下文包失效条件

- 授权到期或撤回；
- 数据责任方撤回共享；
- 关键证据失效；
- 策略版本变化且要求重新计算；
- 超过上下文包 TTL；
- 包含的源数据被更正或删除，且更正影响任务结论。

系统应定义失效传播策略：阻断后续读取、清理缓存、触发重建，并根据合规要求保留最小必要审计记录。

### 6.4 Agent 动作边界

第一阶段只允许 summarize、identify_missing_information、draft_follow_up 和 propose_task_update（只提出建议，不执行写入）。

以下动作必须经过独立审批和授权执行服务：update_project_status、reassign_task、approve_decision、send_customer_commitment、modify_contract_or_order。

## 7. API 规范草案

完整 OpenAPI 文件位于 openapi/ads-work-context-v0.1.yaml。

### 7.1 首批端点

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | /v1/events:ingest | 接入标准工作事件 |
| POST | /v1/objects:resolve | 解析源系统对象 |
| GET | /v1/objects/{object_id}/state | 查询对象状态 |
| GET | /v1/objects/{object_id}/timeline | 查询对象时间线 |
| POST | /v1/context-packages:build | 生成任务级上下文包 |
| GET | /v1/context-packages/{context_id} | 读取上下文包 |
| POST | /v1/context-packages/{context_id}:revoke | 撤销上下文包 |
| POST | /v1/actions:propose | 提交动作建议 |

### 7.2 API 通用约定

- 传输协议使用 HTTPS；生产环境采用组织批准的 OAuth2/OIDC 或等效身份体系。
- 写请求使用 Idempotency-Key。
- 每个响应返回 trace_id、schema_version 和 policy_version（适用时）。
- 分页使用稳定游标，不依赖不稳定的 offset 深分页。
- 错误响应统一包含 code、message、trace_id 和可安全暴露的 details。
- 不能在错误信息中泄露无权访问的对象是否存在。
- 生产环境需定义速率限制、超时、重试、熔断和审计策略。

### 7.3 建议错误码

| HTTP | code | 含义 |
|---|---|---|
| 400 | INVALID_SCHEMA | 请求结构不符合 Schema |
| 401 | UNAUTHENTICATED | 未认证 |
| 403 | POLICY_DENIED | 策略或授权拒绝 |
| 404 | RESOURCE_NOT_FOUND | 资源不存在或不可见 |
| 409 | IDEMPOTENCY_CONFLICT | 幂等键冲突或版本冲突 |
| 409 | ENTITY_RESOLUTION_AMBIGUOUS | 对象解析存在歧义 |
| 409 | STATE_CONFLICT | 状态存在需要处理的冲突 |
| 410 | CONTEXT_EXPIRED | 上下文包已过期或撤销 |
| 422 | SEMANTIC_VALIDATION_FAILED | 语义校验失败 |
| 429 | RATE_LIMITED | 请求频率超限 |
| 500 | INTERNAL_ERROR | 未预期服务错误 |

## 8. 最小可运行原型设计

### 8.1 原型目标

原型应能在开发者本地运行，不依赖企业真实数据，不连接真实业务系统，不执行真实写回。它只验证五个核心环节：

1. 接收并校验标准事件；
2. 使用幂等键避免重复事件；
3. 根据权威来源规则重建状态；
4. 保留非权威来源的冲突线索；
5. 根据授权范围生成任务级上下文包。

### 8.2 原型组件

| 组件 | 原型实现 | 生产替换方向 |
|---|---|---|
| Event Ingest | Python 函数 | API Gateway + Connector |
| Event Ledger | 内存字典 / JSON 文件 | 追加式事件存储 |
| Object Registry | JSON 对象映射 | 主数据引用与身份服务 |
| Authority Registry | 本地配置 | 可治理的领域规则目录 |
| State Engine | 确定性规则 | 可重放状态投影服务 |
| Policy Gate | 简化授权规则 | IAM / ABAC / Policy Engine |
| Context Builder | JSON 上下文包 | 独立上下文服务 |
| Audit | 本地列表 | 集中审计与安全分析 |

### 8.4 本地运行方式

预期演示输出：事件接收结果、重复事件被识别为 duplicate、项目权威状态、非权威会议线索形成的冲突项、生成的 context_id、上下文包含的对象/事件/状态/未知项/允许动作，以及审计记录摘要。

## 9. 项目交付模拟场景

### 9.1 场景描述

虚构项目 PRJ-2026-014 在项目管理系统中的状态为 blocked，原因是一个前置依赖尚未完成。会议纪要中有人提出“项目整体仍可按计划推进”，该信息只是会议线索，尚未经过项目负责人确认。项目 Agent 被要求准备项目状态评审材料。

原型需要正确输出：

- 权威状态：blocked；
- 状态来源：project-system；
- 冲突线索：meeting-notes 提供 on_track；
- 未知项：客户验收日期尚未确认；
- 允许动作：summarize、draft_follow_up；
- 不允许直接执行：update_project_status、send_customer_commitment。

### 9.2 端到端流程

1. 从项目系统接收项目状态变化事件；
2. 从经授权的会议记录接收推断线索；
3. 连接器完成标准化并映射到同一个 Project 对象；
4. 事件账本按幂等键保存；
5. 状态引擎按 project.status → project-system 规则计算；
6. 非权威来源不同值进入 conflict 列表；
7. 授权服务校验 Agent 的主体、目的和项目范围；
8. Context Builder 生成短时上下文包；
9. Agent 只基于上下文包生成摘要和跟进草稿；
10. 项目负责人确认后，才通过后续正式业务流程更新系统。

### 9.3 业务价值假设

本试点需要验证而不是预设以下收益：

- 项目状态汇总时间是否下降；
- 状态核验和追问次数是否下降；
- 决策、任务和依赖遗漏是否减少；
- Agent 生成内容的人工修改比例是否下降；
- 业务人员是否信任来源可追溯的状态解释；
- 单项目上下文维护成本是否可接受。

## 10. 自动化验收测试

| 编号 | 测试场景 | 预期结果 |
|---|---|---|
| T-01 | 合法事件接入 | 返回 accepted 并记录事件 |
| T-02 | 同一事件重复投递 | 返回 duplicate，不重复改变状态 |
| T-03 | 缺少 event_id 或 source_ref | Schema 校验失败 |
| T-04 | 引用不存在的对象 | 进入待解析或拒绝，不建立确定关系 |
| T-05 | 权威来源与非权威来源值冲突 | 权威值保留，冲突显式输出 |
| T-06 | 无权威来源 | 输出 observed / inferred / unknown，不伪造 confirmed |
| T-07 | 事件已撤回 | 不再参与当前状态重建 |
| T-08 | 事件晚到 | 可重算并保留重算版本 |
| T-09 | 请求对象超出授权范围 | 返回 POLICY_DENIED |
| T-10 | 请求目的不匹配 | 返回 POLICY_DENIED |
| T-11 | 上下文包超过 TTL | 后续读取被阻断 |
| T-12 | 受限分类事件 | 不进入未授权上下文包 |
| T-13 | Agent 请求高风险动作 | 只生成建议或要求审批，不直接执行 |
| T-14 | 上下文包撤销 | 后续读取被阻断，缓存失效 |
| T-15 | Agent 输出引用 | 能追溯 context_id、event_id 和 policy_version |

### 10.1 试点指标建议

| 维度 | 指标 | 计算方式 |
|---|---|---|
| 接入质量 | 事件接入成功率 | 成功接入事件 / 应接入事件 |
| 去重质量 | 重复事件抑制率 | 正确识别重复数 / 重复投递数 |
| 对象解析 | 对象关联准确率 | 正确映射数 / 抽样映射数 |
| 状态质量 | 权威状态一致率 | 与权威源一致的状态数 / 抽样状态数 |
| 可追溯性 | 证据引用完整率 | 有有效来源引用的结论数 / 抽样结论数 |
| 时效 | 上下文可用延迟 | 源变更到上下文可查询的时间 |
| Agent 质量 | 人工修改率 | 被修改的输出项 / 审阅输出项 |
| 业务效果 | 汇总耗时变化 | 试点前后同类任务耗时对比 |
| 治理 | 越权成功次数 | 目标值为 0 |
| 成本 | 单任务综合成本 | 模型、存储、连接器和人工核验成本 |

所有指标需要在试点前定义采样方法、统计周期和目标阈值。不能只展示成功案例，应同时保留失败、冲突和人工纠错样本。

## 12. 实施路线与阶段门

### 阶段 1：契约评审

交付：JSON Schema、事件目录、对象目录、权威字段清单、授权模型。

阶段门：业务、数据和安全责任人确认首批定义。

### 阶段 2：本地原型

交付：模拟数据、事件接入、状态重建、上下文生成、自动化测试。

阶段门：T-01 至 T-13 核心测试通过，关键冲突和越权场景符合预期。

### 阶段 3：只读企业试点

交付：一个真实项目系统连接器、受控会议/文档来源、只读 Context API、Agent 摘要能力。

阶段门：权威状态一致率、对象映射准确率和治理指标达到预先约定阈值。

### 阶段 4：人工确认闭环

交付：业务确认界面、纠错事件、审计、质量反馈和上下文撤销机制。

阶段门：人工纠错可追踪，授权撤回和源数据更正能够影响派生上下文。

### 阶段 5：受控动作与第二场景复用

交付：动作提议、审批、受控写回、第二项目或第二团队的复用验证。

阶段门：第二场景独立验证有效，且业务收益大于新增治理与维护成本。

## 13. 架构决策与评审问题

| 编号 | 决策 | 本版建议 | 评审问题 |
|---|---|---|---|
| ADR-01 | Schema 格式 | JSON Schema Draft 2020-12 | 是否有组织级标准格式 |
| ADR-02 | API 描述 | OpenAPI 3.1 | 是否采用统一 API 网关规范 |
| ADR-03 | 事件模式 | 追加式事件 + 更正事件 | 是否需要事件总线与回放 |
| ADR-04 | 对象身份 | 上下文 ID 与源 ID 分离 | 谁负责对象映射确认 |
| ADR-05 | 状态来源 | 按对象属性配置权威来源 | 权威字段责任人是谁 |
| ADR-06 | 上下文包 | 短时、可撤销、不可静默变更 | 默认 TTL 和刷新规则 |
| ADR-07 | Agent 权限 | 第一阶段只读 | 哪些动作需要人工审批 |
| ADR-08 | 数据驻留 | 个人、企业和领域中心边界分离 | 哪些元数据可以跨域共享 |
| ADR-09 | 原型技术 | Python 标准库，便于验证逻辑 | 生产技术栈何时选型 |
| ADR-10 | 试点场景 | 项目交付 | 选择哪个真实项目和业务负责人 |

### 13.1 评审前必须明确的事项

1. 项目系统中哪些字段是正式权威字段？
2. 哪类会议或协同信息允许进入企业上下文？
3. 会议推断如何由项目负责人确认或否认？
4. 员工、客户和第三方信息如何分类、裁剪和授权？
5. 上下文包过期、撤回和源记录删除如何联动？
6. Agent 的摘要、建议和正式业务动作如何分权？
7. 试点业务价值由谁确认，基线如何采集？

## 14. 与 ADS 三级数智底座的关系

本专题的工程成果归属企业数智底座内部能力，不形成新的底座层级。

| 层级 | 本专题涉及的责任 |
|---|---|
| 个人数智底座 | 保留个人原始工作信息和个人控制权；只按明确授权共享必要记录或引用 |
| 企业数智底座 | 建设事件接入、对象映射、状态重建、运行上下文、企业 Agent 上下文服务 |
| 业务领域中心数智底座 | 提供共同语义、标准版本、联邦目录、跨域授权协同和审计规则 |

个人工作信息进入企业上下文必须经过授权、目的限定、必要性审查和业务责任人确认。企业向领域中心共享时优先共享可发现的元数据、标准和能力描述；原始业务记录不因目录登记而自动开放。

## 15. 结论：用一个真实流程证明上下文基础设施的价值

ADS-WORK-04 将研究路线推进到可验证工程层：

**工作感知 → 统一事件 → 业务对象映射 → 状态重建 → 证据与冲突 → 任务级上下文包 → Agent 辅助 → 人工确认 → 反馈改进。**

第一阶段应保持范围克制：

- 只选一个项目交付流程；
- 只接入一个权威业务系统和少量经授权来源；
- 只实现五类核心对象和八类事件；
- 先只读、后建议、再审批写回；
- 先本地原型、后企业试点；
- 先验证准确性和治理，再讨论规模化。

真正需要验证的不是“AI 能否总结更多信息”，而是：

**当企业把工作事件、业务对象、权威状态、决策、任务、风险和证据组织成统一上下文后，Agent 是否能够在正确权限下更准确地理解企业正在发生什么，并实实在在降低业务协作与管理成本。**
