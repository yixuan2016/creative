STANDARD SECTION 01

摘要

个人数智底座不是把个人文件、录音、聊天记录和知识笔记集中到一个更大的知识库，而是建立一套由个人控制、可持续理解、可追溯、可纠正、可迁移，并能在明确授权下与企业数智底座协同的数据与语义基础设施。

本规范建立从多源信号到个人数智资产的统一表达方式，规定数据对象、事件语义、来源证据、知识记忆、个人意图、身份关系、数据质量、存储互操作、授权治理以及 Agent 使用边界。它以 PDKS 作为个人数据表达与互操作标准，以 ADS 共同本体和领域本体作为语义桥梁，以 ADS-WORK-09 的事件账本、持续记忆和个人运行对象作为运行契约，并与 ADS-WORK-10 的多终端感知和个人助理 OS 体验衔接。

本规范的核心原则是：

  1. 先保留来源，再形成认知。 原始来源、证据、事件、断言、记忆和行动对象必须区分，摘要不能替代证据。
  2. 先记录发生，再判断意义。 事件可以是观察或推断候选，不因被记录就自动成为事实。
  3. 记忆是可纠正的派生视图。 记忆必须能够追溯到来源事件，支持确认、纠错、冲突、过期、撤回和删除。
  4. 个人工作与生活共同构成个人上下文。 但个人生活数据默认不进入企业数智底座。
  5. 共享语义不等于共享数据。 个人、企业和领域中心可以使用共同概念，但各自管理其数据实例和责任边界。
  6. 采集、处理、共享和执行均须有边界。 授权应绑定主体、目的、数据范围、接收方、期限和撤回机制。
  7. 标准与实现解耦。 采用开放文件格式和版本化契约，不将数据主权绑定到单一模型、Agent、Skill、厂商或存储产品。
STANDARD SECTION 02

1. 目的、范围与规范性用语

1.1 目的

本规范用于统一个人数智底座中数据如何采集、表达、关联、沉淀、存储、治理和交换，降低不同采集入口、不同 Agent、不同 Skill、不同模型和不同存储系统之间的语义差异。

本规范尤其解决以下问题：

  • 一段录音、一次会议、一条消息或一个文件，如何保留其来源与证据定位；
  • 如何区分观察、事件、断言、事实、知识、记忆、目标、承诺和任务；
  • 如何从多源信号形成可持续使用的个人工作与生活上下文；
  • 如何避免把 AI 推断、会议建议或未确认行动项写成既定事实；
  • 如何让个人数据可以由本人查看、纠正、导出、撤回和删除；
  • 如何在不转移个人数据所有权的前提下，向企业投影经过授权的最小必要业务信息；
  • 如何让不同 Agent 和 Skill 以一致方式读取标准数据、生成候选结果和提交受约束的行动提案。

1.2 适用范围

本规范适用于个人数智底座覆盖的以下领域：

  • 个人工作：会议、沟通、项目参与、任务、承诺、决策、成果、协作关系和工作经验；
  • 个人生活：日程、生活安排、个人承诺、出行、家庭事务、个人目标和日常活动；
  • 学习与成长：学习活动、阅读、练习、反思、技能和成长目标；
  • 个人资源与偏好：时间安排、工具偏好、工作方式、个人资源和用户明确表达的偏好；
  • 多源采集：人工输入、文件、文档、邮件、即时通讯、日历、业务系统、音频、图像、视频、设备和授权连接器；
  • 智能处理：转写、OCR、结构化抽取、事件识别、实体解析、关系抽取、记忆整合、上下文构建和 Agent 辅助执行。

本规范不要求所有用户启用所有数据类别，也不要求默认采集全天候音频、视频、位置或其他高敏感数据。

1.3 不适用范围

本规范不替代：

  • 企业业务系统的权威主数据和业务流程规范；
  • 企业法务、档案、财务、人力资源及行业监管要求；
  • 设备、操作系统、云平台和模型服务商自身的安全规范；
  • 具体 Agent 或 Skill 的产品交互设计；
  • 具体数据库、向量数据库、图数据库或消息队列的技术选型。

1.4 规范性用语

本规范中的“必须”表示符合本规范所需的强制要求；“应”表示推荐要求，除非有明确理由不应偏离；“可以”表示可选实现方式。

本规范中的“事实”仅指已由适当责任主体或权威来源确认的事实记录，不代表系统对现实世界作出绝对真实性保证。模型置信度不能替代责任主体确认。

STANDARD SECTION 07

2. 总体标准框架

2.1 三层标准体系

标准层核心体系主要职责关键产物
数据表达层PDKS定义个人数据对象、记录结构、事件分类、来源证据、知识资产和交换格式Record Schema、Event Taxonomy、Ontology、数据文件
语义互操作层ADS Core + Domain Ontology + Personal / Enterprise Namespace定义概念、对象、事件、关系、状态及个人—企业语义映射共同本体、领域本体、映射规则、身份引用
数智运行层ADS-WORK-09 / ADS-WORK-10定义事件账本、持续记忆、个人意图、上下文、Agent 动作和用户交互Event Ledger、Memory Item、Intent Object、Context Package、Action Proposal

三层之间必须保持职责分离：数据 Schema 不代替本体；本体不代替事件记录；事件账本不代替记忆；记忆不代替目标和任务；Agent 动作提案不等于用户授权。

2.2 五层语义模型

层级名称核心对象主要回答
L1信号与观察层SourceRecord、Observation、CaptureSession、ExtractionRun系统从哪里看到了什么？
L2事件与活动层Event、Activity、Task、Commitment、Interaction、Decision、Outcome发生了什么、正在做什么？
L3语义对象与状态层Actor、Person、Organization、Project、Customer、PersonalObject、Relation、StateAssertion涉及谁、什么对象及其状态？
L4上下文与决策层ContextPackage、Goal、Constraint、DecisionRecord、Risk、Issue、Uncertainty对当前任务而言什么最相关？
L5能力与执行层CapabilityAsset、Skill、Rule、Workflow、Agent、Tool、Action、Approval、AgentRun如何在约束下完成任务？

身份、来源、证据、时间、分类、授权、保留、版本、审计、置信度和人工确认是贯穿五层的横向治理控制面。

2.3 与个人数智底座七层运行架构的关系

五层语义模型用于定义“数据和概念如何表达”；七层运行架构用于定义“系统如何处理和运行”。二者不是互相替代的层级：

  1. 多源感知与采集；
  2. 原始来源与个人事件账本；
  3. 身份、时间与语义解析；
  4. 持续记忆与知识视图；
  5. 个人运行模型；
  6. 个人认知与 Context Plane；
  7. Personal Agent 与受约束执行。

实现时可以合并或拆分软件组件，但不得因此混淆各类数据对象的语义职责。

STANDARD SECTION 11

3. 数据对象标准

3.1 PDKS 九类基础对象

PDKS 的基础表达由九类对象构成。它们是机器处理和互操作的对象模型，不是要求用户手动填写的九张表单。

对象代码对象名称定义典型内容
entity实体具有稳定身份、可被引用的主体或对象人、组织、项目、产品、工具、地点
source_asset来源资产原始信息或外部系统记录的来源载体音频、文件、消息、文档、日历记录
evidence_segment证据片段来源资产中支持、限定或反驳某项表达的可定位片段音频时间段、文档段落、消息片段、截图区域
event事件某个时间点或时间区间发生、被观察或被报告的事情会议、任务变化、承诺、学习活动、生活活动
assertion断言某个主体表达的事实主张、观点、假设、问题或判断“客户认为方案不可行”“可能存在延期风险”
knowledge_asset知识资产具有持续理解或复用价值的知识表达方法、流程、经验、概念、原则、教训、洞察
personal_context个人上下文描述个人角色、职责、能力、约束、偏好、目标和关系的上下文当前职责、工作方式、个人目标、时间约束
action人的行动意图人计划、承诺或需要推进的事项任务、计划、提醒、承诺
relationship关系两个或多个对象之间有类型、有方向的关联人参与项目、事件来源于文件、任务依赖目标

3.2 对象之间的基本关系

  • Source Asset 可以包含多个 Evidence Segment；
  • Event 必须能够引用一个或多个 Source Asset，或明确标记为用户主动声明；
  • Assertion 应保留表达者、表达时间、来源和状态；
  • Knowledge Asset 应引用来源事件或明确标记为用户主动创建；
  • Personal Context 可以由多个事件和知识资产逐步支持；
  • Action 应关联来源事件、目标或用户主动输入；
  • Entity 可以被事件、断言、知识、行动和关系引用；
  • Relationship 必须声明关系谓词、方向、来源或依据、状态及有效时间。

3.3 五类核心运行对象必须区分

对象本质是否允许模型推断是否直接代表事实
Personal Event对发生、观察、表达或状态变化的记录可以形成候选事件不一定，必须带断言状态
Memory Item从事件和用户确认中形成的可持续认知可以，但必须保留来源和置信度不一定，可能候选、过期或争议
Intent Object目标、任务、承诺、例程或个人项目可以建议候选正式状态需用户确认或权威系统同步
Context Package为特定任务组织的最小必要信息视图可以自动构建不是新的事实源
Agent Action ProposalAgent 准备执行的具体动作提案可以规划提案不等于批准，执行不等于成功
STANDARD SECTION 15

4. 事件与时间标准

4.1 事件定义

事件是对现实发生、系统观察、用户表达或状态变化的有来源记录。事件可以是候选，不应因进入账本就自动被解释为已确认事实。

事件必须回答或显式标记以下问题：

  • 发生了什么；
  • 何时发生或何时观察到；
  • 涉及哪些主体和对象；
  • 信息来自哪里；
  • 当前属于观察、推断、确认还是争议；
  • 由谁或哪个系统处理；
  • 该记录适用何种分类、用途和保留策略。

4.2 事件类型命名

事件类型必须采用稳定、可扩展、机器可解析的命名空间。推荐使用小写点分层形式：

  • personal.work.meeting_attended
  • personal.work.commitment_created
  • personal.work.context_observed
  • personal.life.commitment_created
  • personal.life.activity_completed
  • personal.learning.session_completed
  • personal.reflection.recorded
  • work.task_status_changed
  • work.decision_confirmed
  • project.risk_signal_observed

具体事件类型必须遵循对应版本的 Event Taxonomy。映射到 ADS 时，必须保留原始 PDKS taxonomy code 和 taxonomy version，不得只保留转换后的代码。

候选风险必须表达为风险信号或风险候选；讨论中的方案不得直接编码为已批准决策；会议中的行动项不得在责任人和确认状态不清楚时直接成为正式承诺。

4.3 四种时间

事件及记忆应区分以下时间：

字段含义示例
occurred_at事情实际发生的时间会议开始时间
observed_at设备或系统感知到信息的时间录音文件上传时间
recorded_at记录写入账本的时间转写和解析后写入时间
valid_time某事实或状态在现实中成立的有效区间项目负责人任职有效期

发生时间未知时必须允许空缺或 unknown，不得将 recorded_at 自动填充为 occurred_at。所有时间戳必须包含时区或使用明确的 UTC 表达；展示时可按用户时区转换，但原始时间语义必须保留。

4.4 事件状态与断言状态

事件生命周期和断言状态是两个不同维度。

建议的断言状态：

  • observed：系统观察到原始信号，语义尚未确认；
  • inferred：模型或规则推断；
  • confirmed：用户、有权责任人或权威系统已确认；
  • disputed：存在冲突或用户提出异议；
  • rejected：被用户或有权责任主体明确否定；
  • stale：曾经成立，但当前可能过期；
  • unknown：当前无法判断。

事件生命周期可采用：

  • candidate；
  • active；
  • superseded；
  • withdrawn；
  • expired；
  • archived。

系统不得用 lifecycle_status 替代 assertion_status，也不得用置信度替代确认状态。

4.5 事件账本原则

  1. 事件记录原则上追加，不以新摘要覆盖原始事件；
  2. 更正通过 correction_of、supersedes 或等价关系表达；
  3. 重复采集必须支持幂等识别；
  4. 来源无法解析时应保留 unresolved 状态，不得伪造来源；
  5. 事件删除或撤回应传播到依赖的记忆、索引、摘要和缓存；
  6. 事件与记忆之间必须通过稳定引用建立关系。
STANDARD SECTION 21

5. 来源资产与证据标准

5.1 来源资产要求

Source Asset 至少应记录：

  • source_id：稳定来源标识；
  • source_type：文件、录音、消息、邮件、日历、业务系统记录、人工输入等；
  • source_system：来源系统或设备；
  • native_record_id：来源系统原生记录 ID，若存在；
  • capture_mode：manual、connector、voice、device、import 等采集方式；
  • modality：text、audio、image、video、structured_data 等；
  • captured_at：采集时间；
  • observed_at：系统观察时间；
  • owner_or_subject_ref：来源关联主体；
  • original_uri 或 storage_ref：受控存储引用；
  • content_hash：可用时记录完整性校验值；
  • consent_or_authorization_ref：需要授权的采集应保留授权引用；
  • retention_policy_ref：来源保留策略。

来源元数据与来源内容可以分开存储。敏感原始文件不应为了方便而复制到多个无治理的目录。

5.2 证据片段要求

Evidence Segment 必须能够定位回原始来源。根据来源类型，定位信息可以包括：

  • 音频或视频：起止时间、媒体文件引用、说话人候选；
  • 文档：文件引用、页码、段落或文本偏移；
  • 消息：平台、会话 ID、消息 ID、发送者和时间；
  • 图片：文件引用、页面或区域坐标；
  • 结构化系统：系统名、记录 ID、字段路径、版本或快照时间。

证据片段应保留原文或原始内容引用、定位信息、提取方式和必要的置信度。AI 摘要不能作为唯一证据替代原始来源。

5.3 录音与语音采集标准

录音是个人多源感知的重要入口之一，但不是唯一入口，也不得成为个人数智底座的前提条件。

录音采集应满足：

  1. 采集由用户主动启用或通过明确授权的规则触发；
  2. 设备或应用应提供清晰可见的录音状态，支持暂停、停止和撤销；
  3. 不得以隐蔽、欺骗或绕过设备提示的方式进行录音；
  4. 对其他参与者的录音，应遵守适用法律、组织制度和场景要求；
  5. 记录设备、采集会话、开始结束时间、文件标识、时区、采集模式和授权依据；
  6. 转写文本必须关联原始音频及时间片段，不能丢失可追溯性；
  7. 说话人识别应保留不确定性，不得仅凭声音相似自动认定身份；
  8. 会议摘要、决策、承诺和行动项必须区分“原话证据”“模型提取候选”和“人工确认结果”；
  9. 原始音频保留期限、转写保留期限和记忆保留期限应分别治理；
  10. 录音、转写和摘要不得默认向企业、其他 Agent 或第三方共享。

5.4 多源采集的统一入口

来源可以来自钉钉 DWS、日历、邮件、即时通讯、文档、项目系统、浏览器、桌面文件、移动设备、录音设备和人工输入。连接器必须声明数据范围、采集频率、权限、同步状态、撤销方式和失败处理。

接入一个来源不等于授权其全部历史数据；初始化 PDKS 不应自动连接来源、导入历史记录、启动后台采集或启用云同步。

STANDARD SECTION 26

6. 知识沉淀与记忆标准

6.1 沉淀判断

满足以下任一条件的内容可以进入沉淀流程：

  • 用户明确要求记住、保存或追踪；
  • 对未来工作、生活、学习或决策有持续影响；
  • 形成明确目标、承诺、任务、决策、风险或结果；
  • 反映稳定偏好、约束、职责、关系或能力；
  • 具有未来可复用价值的方法、流程、规则、经验或教训；
  • 对重要事件、业务状态或个人经历具有证据价值；
  • 多次出现并可能反映长期模式，但重复本身不能直接证明事实。

6.2 不应自动形成长期记忆的内容

  • 无明确价值的一次性闲聊和噪声；
  • 已有内容的无意义重复副本；
  • 没有来源且无法核验的模型推测；
  • 未确认的任务责任、承诺、决策或关系；
  • 不必要的第三方隐私和敏感信息；
  • 超出授权范围的个人或企业数据；
  • 用户明确要求不再记住的内容；
  • 已过期且无历史或审计价值的临时状态。

不形成长期记忆不代表必须立即删除原始来源。原始来源是否保留，仍应遵循用户选择、来源规则和保留策略。

6.3 六项沉淀质量标准

质量维度核心问题最低要求
来源真实性信息从哪里来？保留来源引用、采集方式和处理记录
时间准确性何时发生、何时观察、何时记录？区分四种时间，未知不得伪造
语义清晰性属于什么类型、涉及什么对象？使用明确类型、实体和关系
确认与可信度是观察、事实主张、推断还是争议？保留断言状态、置信度和确认主体
持续价值未来是否帮助理解、决策或行动？明确用途、复用价值或证据价值
权属与治理谁控制、谁能使用、何时到期？明确主体、分类、目的、授权、保留和撤回规则

来源、时间、语义、状态和治理是沉淀的基本门槛。不能因内容看起来有用而跳过授权或来源核验。

6.4 建议的沉淀质量等级

以下等级是本规范提出的治理和评测分级，不表示现有 PDKS 发布版已经冻结该等级。

等级名称定义可支持用途
Q0原始来源原始音频、文件、消息、图片和系统记录原始材料与证据
Q1观察 / 事件候选已识别出可能的事件、实体或关系查看、补充、确认
Q2已确认事件用户或权威系统确认关键语义时间线、记忆生成
Q3稳定记忆 / 知识资产有来源、有价值、有有效期和纠错机制检索、理解、任务上下文
Q4可复用能力资产经抽象、重复实践、独立验证、版本化和适用范围审查授权范围内跨人员或跨项目复用

Q0 至 Q4 不是每条数据必须逐级晋升的流水线。证据片段可以停留在 Q0，个人生活事件不需要成为企业能力资产。

6.5 记忆类型

建议统一以下记忆类型：

  • episodic：情景记忆，某次会议、经历、活动和事件；
  • semantic：语义记忆，稳定事实、人物、项目和概念；
  • procedural：程序记忆，如何完成某类工作的方法；
  • preference：用户明确表达的偏好；
  • goal：个人目标；
  • commitment：对未来行动或结果的承诺；
  • relationship：人与人、人与项目或对象之间的关系；
  • routine：反复发生的活动和习惯；
  • project_context：项目背景、关键决策、当前问题和变化。

一次偶然行为不能自动成为稳定习惯；一次会议中的提议不能自动成为正式承诺；模型推断不能自动成为已确认事实。

6.6 记忆生成流程

记忆生成应包含七个步骤：

  1. 接收：来源进入受控来源库或事件接入层；
  2. 解析：转写、OCR、结构化抽取或人工录入；
  3. 候选化：形成事件候选和记忆候选，标注来源、时间和置信度；
  4. 关联：连接人物、项目、任务、目标和历史事件；
  5. 确认：按影响程度决定自动接受、用户确认或人工审核；
  6. 整合：形成或更新记忆视图，不覆盖历史来源；
  7. 复核：发现冲突、过期或用户纠错时更新状态并保留依据。

6.7 记忆生命周期

推荐状态流转：

candidate → active → stale / disputed → superseded / withdrawn / expired → archived

  • candidate：候选，等待确认；
  • active：有效，可在授权范围内检索；
  • stale：可能过期，需要复核；
  • disputed：存在冲突或用户提出异议；
  • superseded：被新版本替代，保留历史关系；
  • withdrawn：用户撤回，不再参与普通检索；
  • expired：超过有效期；
  • archived：归档，不再默认参与实时判断。

冲突不能简单采用“最新一条覆盖”或“模型置信度最高者胜出”。应保留冲突来源和有效时间；权威系统状态按业务权威规则处理；个人偏好以用户确认为准；无法判断时并列保留并标记 disputed。

6.8 记忆维护要求

每条长期记忆应具备稳定 ID、类型、内容、来源事件、证据引用、断言状态、置信度、创建和更新时间、有效时间、复核或到期时间、派生过程、算法版本、用户控制入口、共享策略和替代关系。

记忆衰减只能影响检索优先级或触发复核，不得无依据地修改原始事件。用户纠正后，应保留更正关系和必要审计记录。

STANDARD SECTION 35

7. 个人意图与运行对象标准

7.1 五类 Intent Object

类型定义核心属性
Goal用户希望达到的状态目标、衡量方式、期限、进展
Commitment主体对未来行动或结果作出的承诺承诺主体、对象、期限、确认依据
Task具有预期结果、责任主体和完成条件的行动单元标题、负责人、状态、截止时间、完成条件
Routine按周期或条件重复发生的活动周期、触发条件、例外、暂停状态
Project为实现目标而持续推进的工作集合目标、范围、阶段、依赖、成果

7.2 状态与确认状态分离

Intent Object 的执行状态与确认状态必须分开。

执行状态建议包括 proposed、active、paused、blocked、completed、cancelled、expired。

确认状态建议包括 user_confirmed、synced_from_authoritative_source、inferred_candidate、unknown。

inferred_candidate 不得直接作为 user_confirmed；从会议中推断出的任务，只有在责任、期限和完成条件得到确认后，才可升级为正式任务或承诺。

7.3 行动闭环

目标、承诺和任务是人的运行对象，不是 Agent 执行授权。正确流程为：

PDKS Action → ADS Intent Object → Context Package → Agent Action Proposal → Approval → Execution → Verified Result Event

每一步必须保留独立状态、来源、授权和结果。Agent 生成建议、创建草稿或执行成功，均不得被混为同一状态。

STANDARD SECTION 39

8. 本体、身份与关系标准

8.1 本体治理结构

本规范采用共同核心本体与领域本体协同的治理方式：

  • ADS Core：个人、企业和业务领域共享的稳定基础概念和关系；
  • Domain Ontology：具体业务领域的专业概念、规则、术语和状态；
  • Personal Namespace：个人工作、生活、学习和资源上下文的应用语义空间；
  • Enterprise Namespace：企业业务对象、企业状态和组织规则；
  • Local Extension：个人或组织本地扩展，不得静默改变共同核心定义。

个人、企业和业务领域中心是数据责任和治理边界，不是三个本体层级。共享本体定义不意味着共享任何数据实例。

8.2 五层本体的核心概念

  • L1 信号与观察：SourceRecord、Observation、CaptureSession、ExtractionRun；
  • L2 事件与活动：Event、Activity、Task、Commitment、Interaction、DecisionEvent、Outcome；
  • L3 对象与状态：Actor、Person、Organization、BusinessObject、PersonalObject、Relation、StateAssertion、IdentityMapping；
  • L4 上下文与决策：ContextPackage、Goal、Constraint、DecisionRecord、Risk、Issue、Dependency、Uncertainty；
  • L5 能力与执行：CapabilityAsset、Skill、Rule、Workflow、Agent、Tool、Action、Approval、AgentRun、Evaluation。

8.3 关系谓词目录

建议基础关系谓词包括：

谓词含义
involves_actor事件或活动涉及某主体
about_object事件或断言关于某对象
generated_from记录或证据来自某来源
derived_from当前对象由另一对象派生
supports证据支持某项断言
contradicts两项断言存在冲突
assigned_to任务分配给某主体
committed_by承诺由某主体作出
depends_on任务或对象依赖另一对象
part_of对象属于某集合或项目
participates_in主体参与某活动或项目
supersedes新记录替代旧记录
authorized_by数据处理或投影由某授权允许
projected_from企业侧投影源自个人侧记录

关系必须声明方向、来源或依据、状态和有效时间。涉及身份、责任、权属和授权的关系不能只靠文本相似度自动确认。

8.4 身份解析规则

  1. 同名不代表同一对象；
  2. 同一对象在不同系统中可以拥有多个原生 ID；
  3. 身份映射必须保留命名空间、源系统、原生 ID 和解析状态；
  4. 未唯一确认时使用 candidate 或 unresolved；
  5. 不得仅凭名称、文本相似或向量相似度自动合并人物、客户、项目和产品；
  6. 主数据权威性必须按对象类型和业务系统确定；
  7. 个人对象与企业主数据之间的映射应是受控引用，不得自动转移所有权。
STANDARD SECTION 44

9. 标识符、字段与数据格式标准

9.1 稳定标识符

每类对象必须具有稳定且不重复的 ID。ID 一经发布不得被重新分配给其他对象。推荐采用 UUIDv7、ULID 或等价的全局唯一标识实现；既有 PDKS ID 可以保留，不应为追求格式统一而破坏历史引用。

跨系统引用必须同时保留来源命名空间和原生 ID。对象名称、文件名或路径不能替代稳定 ID。

9.2 通用记录元数据

各类记录应根据对应 Schema 提供适用的通用元数据：

  • id；
  • subject_ref 或 owner_ref；
  • object_type / event_type / memory_type 等类型标识；
  • schema_version；
  • created_at、updated_at；
  • occurred_at、observed_at、recorded_at 或 valid_time（按对象适用）；
  • source_refs、evidence_refs；
  • assertion_status 和 confidence（按对象适用）；
  • classification；
  • purpose_tags；
  • ontology_version；
  • processing_provenance；
  • sharing_policy；
  • retention；
  • lifecycle_status；
  • extensions。

各对象的字段名以其正式 Schema 为准。通用元数据是语义要求，不要求不同 Schema 机械采用完全相同的字段布局。

9.3 JSON 与文本格式

  • 机器交换数据应使用 UTF-8 JSON；
  • 连续事件日志可以使用 JSONL；
  • 人工阅读和编辑的知识视图可以使用 Markdown + YAML Frontmatter；
  • 原始多媒体应以附件或受控对象存储保存，并由元数据引用；
  • 时间字段使用 ISO 8601；
  • 枚举值使用稳定、明确的英文代码，展示名称可以本地化；
  • 未知字段不得被静默解释为已知字段；
  • 扩展字段必须放在 extensions 或已定义命名空间中；
  • JSON Schema 应明确版本、必填字段、枚举、格式、边界和 additionalProperties 策略。

9.4 Schema 与本体的关系

JSON Schema 约束数据结构和字段类型；OWL/RDF 可表达语义类和属性；SHACL 可校验图结构约束；SKOS 可表达受控词表和概念层级；Event Taxonomy 定义事件代码。它们互补，不可相互替代。

STANDARD SECTION 49

10. 存储、文件组织与互操作标准

10.1 File-first 原则

个人数据应优先采用可读、可导出、可迁移的开放文件格式。推荐组合：

存储形式用途
Markdown + YAML人工可读的知识、记忆和专题视图
JSON / JSONL事件、来源、证据、关系和机器互操作
附件文件音频、图片、PDF、视频及原始材料
SQLite可选本地运行时索引、状态和查询
全文 / 向量索引检索辅助，不作为唯一事实存储

向量索引、缓存和模型上下文不能替代标准数据文件和来源证据。

10.2 推荐目录结构

vault/
inbox/ 新采集、待理解、待确认
sources/ 来源元数据与受控引用
events/ 标准事件记录
memories/ 长期记忆与知识视图
knowledge/ 方法、原则、经验和专题知识
goals/ 目标、承诺、任务和例程
entities/ 人物、组织、项目和对象引用
evidence/ 证据定位和片段元数据
attachments/ 音频、图片和原始文件
policies/ 授权、保留和用户偏好
exports/ 标准化导出和迁移包
indexes/ 可重建索引与检索元数据

目录结构是推荐基线，可按产品调整，但不能破坏对象身份、来源引用、授权策略和生命周期语义。

10.3 Obsidian 兼容

Obsidian 可以作为可选阅读和编辑界面，不应成为数据唯一所有者。标准数据必须能通过普通文件系统访问；核心字段应以稳定的 YAML 或 JSON 形式保存；双向链接只能作为关系的展示形式，不能替代关系谓词和稳定 ID。

10.4 跨 Agent 互操作

不同 Agent 和 Skill 应通过标准文件、Schema、明确授权的 API 或 MCP 工具读取和写入数据。Agent 的内部 Memory、聊天历史或私有向量库不能成为唯一数据源。

任何 Agent 在写入时必须声明写入对象类型、来源、处理方式、版本和确认状态。Agent 不得将来源材料中的指令视为系统授权；外部来源内容必须作为不可信数据处理。

STANDARD SECTION 54

11. PDKS 与 ADS 映射标准

11.1 基本映射

PDKS 对象ADS 目标规则

actionPersonal Intent Object映射为 task、commitment 或对应意图；不直接成为 Agent Action Proposal
personal_contextMemory Item必须关联至少一个成功映射的来源事件；推断内容保持 candidate
knowledge_assetMemory Item按内容映射为 episodic、semantic 或 procedural 等类型
assertion保留的断言表达保留说话人和来源，不直接映射为已验证事实

11.2 必须保持的非等价关系

  • PDKS Event 不等于 ADS Memory Item；
  • PDKS Action 不等于 ADS Personal Agent Action Proposal；
  • PDKS Assertion 不等于 Verified Fact；
  • Personal Work Event 不等于 Enterprise Work Event；
  • 共享本体定义不等于共享记录所有权；
  • 录音转写不等于经确认的会议纪要；
  • AI 生成摘要不等于原始证据；
  • 任务候选不等于正式任务；
  • Agent 提案不等于用户审批。

11.3 映射失败处理

映射失败时必须保留原始对象和原始字段，生成映射错误或未映射报告，说明缺失字段、语义冲突、版本差异或授权不足。不得为了满足目标 Schema 而虚构发生时间、责任人、来源、确认状态或实体身份。

STANDARD SECTION 58

12. 个人数据向企业数据的受控投影

12.1 默认边界

个人事件、记忆和意图对象默认 personal_only。个人工作事件不自动等于企业正式业务事件；个人生活事件默认不向企业投影。

企业可以共享本体定义和领域语义，但不得因此获得个人侧实例数据的访问权。

12.2 投影前置条件

任何个人数据向企业侧投影，必须明确：

  • 发起人和授权主体；
  • 目标企业、租户、系统和接收者；
  • 明确的业务目的；
  • 允许投影的对象和字段；
  • 必须排除的字段和附件；
  • 投影的有效期；
  • 是否允许下游再使用或转发；
  • 撤回机制和派生数据处理规则；
  • 审计记录和业务确认责任人。

授权必须可追溯、可撤回，并与具体数据范围和目的绑定。不得用一次笼统授权覆盖未来所有数据和用途。

12.3 投影规则

  1. 个人侧记录与企业侧投影使用不同 ID 和生命周期；
  2. 投影生成最小必要的新企业记录，不复制个人原始音频、完整笔记或无关生活信息；
  3. 企业侧记录应保留来源投影引用、授权引用、投影时间和字段映射版本；
  4. 企业业务状态以企业权威系统为准；
  5. 企业侧不得通过投影引用反向读取个人原始事件；
  6. 撤回授权后停止未来投影，并按规则处理企业侧派生记录；
  7. 依法或依制度必须保留的记录应说明保留依据、范围和期限；
  8. 投影结果不得被描述为个人全部上下文或个人对企业的完整授权。
STANDARD SECTION 62

13. 隐私、安全与生命周期治理

13.1 数据分类建议

分类含义默认处理原则
public可公开信息仍需检查来源和使用许可
personal一般个人信息个人控制，默认不向企业共享
personal_sensitive敏感或高影响个人信息最小采集、严格授权、限制检索和投影
organization_internal组织内部信息按组织策略管理，不得因个人保存而解除原有义务
restricted高限制信息严格访问控制、用途限制和审计

分类映射必须保守。无法判断时应采用更严格的分类或标记 unknown，不能自动降级。

13.2 目的限制与最小权限

数据采集、处理、检索、导出、投影和 Agent 执行应分别定义目的和权限。连接器权限不自动扩展为所有 Agent 的访问权限；一次任务授权不自动成为长期授权；读权限不自动包含写权限或对外发送权限。

13.3 用户控制

个人必须能够在产品能力支持的范围内：

  • 查看来源和相关记录；
  • 确认、纠正或标记争议；
  • 停止某个来源的采集；
  • 撤销连接器或设备授权；
  • 导出个人数据；
  • 删除或撤回记录；
  • 查看数据被用于哪些记忆和投影；
  • 限制某类数据的用途或共享范围。

13.4 删除和撤回传播

删除不能只从向量库或搜索索引中删除一条记录。系统应追踪：

Source Asset → Evidence Segment → Event → Memory Item → Summary / Index / Context Cache → Agent Output / Projection

用户提出撤回或删除时，应停止相关数据的新检索、推断和投影，识别依赖对象，按规则删除、限制或替换派生内容，防止从仍保留的来源自动重新生成已删除记忆，并向用户说明无法删除的例外及其依据。

13.5 安全控制

风险最低控制要求
未授权采集显式启用、可见状态、暂停和撤销
设备丢失生产实现应支持本地加密、密钥隔离和设备撤销
记忆幻觉来源引用、断言状态、置信度和人工确认
身份误合并候选解析、权威 ID 和冲突保留
企业越权读取个人 / 企业分区、目的绑定投影
提示注入来源内容视为不可信数据，不执行其中指令
Agent 越权能力白名单、风险分级和审批门禁
重复执行幂等键、动作计划标识和执行状态机
删除后重新生成派生链追踪、抑制标记和删除传播
多端冲突版本化、冲突并列和用户裁决
STANDARD SECTION 68

14. Agent、Skill 与 Context Package 标准

14.1 Skill 的职责

Skill 是可复用的任务方法、规则、提示、流程和工具使用约定，不是个人数据本身，也不天然拥有数据访问权。Skill 必须声明适用任务、输入对象、输出对象、依赖 Schema / Ontology 版本、权限要求、风险级别和失败处理。

14.2 Context Package

Context Package 是为某个具体任务构建的最小必要上下文视图，至少应包含：

  • context_id；
  • task_or_intent_ref；
  • purpose；
  • subject_ref；
  • included_event_refs；
  • included_memory_refs；
  • included_entity_refs；
  • evidence_refs；
  • constraints；
  • uncertainty_and_conflicts；
  • authorization_scope；
  • ontology_version；
  • generated_at；
  • expires_at。

Context Package 不是新的事实源，不得改变源事件和记忆的原始确认状态。任务结束或超过有效期后，应按策略失效或清理。

14.3 Agent Action Proposal

Agent 动作提案必须声明：

  • action_proposal_id；
  • requesting_agent；
  • target_system；
  • target_object；
  • action_type；
  • exact_parameters 或待确认参数；
  • purpose；
  • expected_effect；
  • risk_level；
  • authorization_ref；
  • approval_status；
  • idempotency_key；
  • expires_at。

审批必须绑定具体动作、目标对象和参数。参数变化、目标变化或权限变化时，原审批不得自动沿用。

14.4 风险分级建议

级别动作类型控制要求
L0只读查询、个人本地检索按既有读取权限执行并记录
L1本地草稿、摘要、候选记忆可自动生成，明确标记候选
L2创建或修改个人任务、日历等可逆动作用户确认或预先明确授权
L3对外发送、企业系统写入、删除、支付或其他高影响动作逐次明确审批、结果核验和审计

风险等级应结合动作影响、可逆性、对象敏感度和授权范围评估。不得因为某个 Agent 或 Skill 被安装，就默认授予 L2 或 L3 权限。

STANDARD SECTION 73

15. 数据质量、符合性与验收

15.1 数据质量维度

建议从以下维度评估：

  • 完整性：必需字段和必要引用是否存在；
  • 可追溯性：来源、证据和处理过程是否可定位；
  • 时间准确性：发生、观察、记录和有效时间是否区分；
  • 语义一致性：事件、对象、关系和状态是否符合本体；
  • 身份准确性：对象解析是否有足够依据；
  • 可信表达：断言状态和置信度是否分离；
  • 治理完整性：分类、用途、授权、保留和撤回是否明确；
  • 互操作性：是否可通过公开 Schema 导入、导出和验证；
  • 可纠正性：用户是否能够纠正、撤回和处理冲突；
  • 可恢复性：删除、备份、恢复和迁移是否有明确机制。

15.2 建议符合性等级

等级名称验收要求
C0可读可导出数据使用开放格式，可由普通工具读取
C1结构化记录记录通过对应 Schema 校验，具备稳定 ID 和版本
C2证据可追溯事件、记忆和知识可追溯至来源和证据
C3治理可控分类、目的、授权、撤回、删除和生命周期可验证
C4语义互操作本体、映射和身份引用可跨工具解释，冲突不会被静默合并
C5Agent 可安全使用Context、动作提案、审批、幂等和结果核验闭环可验证

符合性等级是本规范提出的评估框架，不等于当前 PDKS 预览版本已达到相应等级。系统应公开说明实际通过的等级和未完成项。

15.3 最小验收用例

  1. 一段录音能够关联来源资产、采集会话、转写文本和音频时间片段；
  2. 一条会议行动项在责任人未确认时保持候选，不自动成为正式承诺；
  3. 一条记忆能够追溯到来源事件和证据；
  4. 用户纠正记忆后，旧记录保留必要历史关系，不再作为当前有效事实；
  5. 同名项目在身份不确定时不被自动合并；
  6. 个人生活事件不会自动投影到企业；
  7. 一条个人工作事件投影到企业时，能查到目的、字段范围、接收者、授权和有效期；
  8. 用户撤回授权后，后续投影停止，派生数据按策略处理；
  9. Agent 创建外部任务前能够展示准确目标和参数，并满足审批要求；
  10. Agent 执行后通过目标系统或可靠回执核验结果，失败不得记录为成功；
  11. 导出和迁移后稳定 ID、来源引用、时间语义和授权状态保持一致；
  12. 不同 Agent 读取同一标准记录时，对对象类型和确认状态的解释保持一致。

15.4 试点评价指标

  • 来源接入成功率；
  • 事件抽取准确率和召回率；
  • 事件时间识别准确率；
  • 证据定位成功率；
  • 实体消歧准确率；
  • 未确认承诺误升级率；
  • 记忆来源可追溯率；
  • 用户纠错完成率；
  • 重复事件去重准确率；
  • 授权投影字段合规率；
  • 撤回与删除传播完成率；
  • Agent 动作审批合规率；
  • Agent 执行结果核验率；
  • 用户主动使用和有效节省时间情况。

跨人员、跨岗位复用属于后续验证，不应作为首期唯一成功标准。应先验证单人连续上下文、来源可追溯、用户可控和任务辅助价值。

STANDARD SECTION 78

16. 版本管理与标准治理

16.1 版本对象

以下标准资产必须独立版本化：

  • PDKS Record Schema；
  • PDKS Event Taxonomy；
  • PDKS Ontology；
  • ADS Core Ontology；
  • Domain Ontology；
  • ADS 数据契约 Schema；
  • PDKS—ADS Mapping；
  • 授权与投影策略；
  • Skill / Capability Manifest；
  • Context Package 和 Agent Action 契约。

不同资产的版本号不能相互替代。数据记录必须声明其所依据的 Schema 和 Ontology 版本。

16.2 版本变更

  • Patch：修正文档、示例或不改变语义的兼容性问题；
  • Minor：增加可选字段、概念或兼容扩展；
  • Major：删除字段、改变既有语义、修改必填约束或破坏兼容性。

任何版本变更必须说明影响对象、兼容性、迁移方式、映射损失、回滚策略和生效时间。不得静默修改已经发布的字段含义或枚举含义。

16.3 标准治理责任

建议设立以下责任角色：

  • 标准维护者：维护文档、Schema、Taxonomy 和版本；
  • 本体维护者：评审共同概念、关系和领域扩展；
  • 数据责任人：确定数据用途、权属、分类和保留；
  • 安全与隐私责任人：审查采集、授权、访问、撤回和删除；
  • 业务领域责任人：确认领域语义和权威状态；
  • 产品责任人：确保用户可理解、可查看、可纠正和可控制；
  • 试点验证人：通过真实或合成测试数据验证符合性。

16.4 标准冻结门槛

V0.1 草案进入冻结评审前，至少应完成：

  1. PDKS 九类对象与现有 Record Schema 的逐项映射核对；
  2. PDKS Event Taxonomy 与 ADS 事件命名规则核对；
  3. ADS Ontology、Event Ledger、Memory Item、Intent Object 和 Mapping Schema 的一致性检查；
  4. 个人—企业投影授权规则的安全与隐私评审；
  5. 录音、转写、证据定位和保留策略的试点验证；
  6. JSON Schema 自动校验与最小验收用例；
  7. PDKS 工程包和 GitHub 镜像文件的版本及哈希核验；
  8. 形成变更记录、已知限制和兼容性声明。

STANDARD SECTION 87

19. 最终标准结论

个人数智底座的数据标准，不是单纯的数据字段规范，也不是单独的知识分类体系，而是一套贯穿“采集—来源—证据—事件—语义—记忆—意图—上下文—行动—治理”的完整标准体系。

PDKS 负责让个人数据以开放、稳定、可迁移的方式表达；ADS 共同本体和领域本体负责让不同系统和 Agent 理解这些数据的语义；个人数智底座运行时负责把事件转化为可纠正的记忆、可推进的目标和受约束的行动；个人与企业之间通过明确授权和最小必要投影建立协同。

最终应形成以下能力：

  • 数据能够采集，但不等于无边界采集；
  • 事件能够记录，但不等于未经确认的事实；
  • 知识能够沉淀，但必须保留来源和质量；
  • 记忆能够持续，但必须允许纠错、过期和撤回；
  • 个人工作与生活能够被统一理解，但不因此混淆个人与企业边界；
  • Agent 能够使用个人上下文，但不能绕过授权和审批；
  • 数据能够在不同工具、Agent 和存储系统之间迁移，而不被单一平台锁定。

本规范的最终目标，是让个人拥有一套长期属于自己、机器能够理解、用户能够控制、不同智能体能够互操作，并能够在安全边界内连接企业数智底座的数据与语义基础设施。

V0.1.0 结论：建议作为个人数智底座数据与数智标准的统一研究草案进入评审和试点验证；在完成机器标准核对、安全隐私评审和试点验收前，不应标记为正式冻结标准。
