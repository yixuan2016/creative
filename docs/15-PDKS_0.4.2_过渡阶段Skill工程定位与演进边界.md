# PDKS 0.4.2：过渡阶段 Skill 工程定位、能力边界与演进路线

> Runtime Track 0.4.2 / Agent Skill 0.3.2 · Experimental / Preview  
> 文档性质：研发阶段定义与工程约束，不是最终标准。

## 摘要

PDKS 当前处于从个人知识管理 Skill 向个人数智底座原型演进的过渡阶段。0.4.2 的主要任务不是宣称底座已经建成，而是把 Skill 工程做扎实：明确它能做什么、依赖什么宿主能力、哪些只是本地参考原型、哪些仍未实现；同时保持既有标准和 Ontology 基线稳定，为后续多源工作感知、持续上下文和跨域语义协同留下可验证的演进接口。

本轮将 Skill 升级到 0.3.2，PDKS 标准 0.1.0、JSON Schema 0.1.x、Ontology 0.2.1、Event Taxonomy 0.1.0 均保持不变。个人、企业、中心 Ontology 的分层只作为研究提案，不引入正式类、属性或跨域数据流。

## 1. 为什么强调过渡阶段

Skill 是 Agent 的行为规范、工作流和资源包；数智底座还需要持续数据入口、可靠持久化、索引检索、权限治理、生命周期管理、跨设备能力和真实系统连接。仅具备 Skill 文件、SQLite 原型和 RDF 投影，并不能证明平台能力已经完成。

## 3. 能力状态模型

- available_in_skill：指令本身可用，可处理用户主动提供的材料。
- prototype_local：本地参考代码存在，需要操作者和本地环境。
- prototype_partial：部分流程可运行，但端到端能力不完整。
- host_dependent：依赖宿主 Agent 的工具、连接器、权限和运行环境。
- not_implemented：当前未实现。
- future_research：未来研究方向。

| 能力 | 状态 | 边界说明 |
|---|---|---|
| 分析用户提供材料、生成候选记录 | Skill 可用 | 不依赖外部连接器 |
| SQLite / RDF / 本地校验脚本 | 本地原型 | 不等于云端个人记忆服务 |
| 读取钉钉、邮件、日历等连接数据 | 宿主依赖 | 必须实际发现连接器并取得授权 |
| 后台持续采集、录音卡/设备集成 | 未实现 | 没有原生连接器、设备或后台采集实现 |
| 正式 Consent / Policy Service | 未实现 | 示例 consent_ref 不是真实授权 |
| 企业/中心 Ontology Runtime | 未来研究 | 目前只有概念提案 |

## 4. Skill、宿主 Agent 与底座的职责分离

Skill 负责指导理解、抽取、组织、语义映射和校验；宿主 Agent 负责提供模型、文件访问、应用连接器、数据库、执行环境和授权；未来个人数智底座负责多源持续感知、事件账本、个人长期上下文、知识资产、检索、纠错、撤回、删除和数据可携带。

安装 Skill 不代表宿主已经拥有相应数据连接或持久化能力。没有写入回执时，只能说“已准备”，不能说“已保存”。

## 5. 个人、企业、中心 Ontology 的研究假设

不建议设计成简单的单向继承树。初步研究模型为：

**Shared Semantic Core + Scope-specific Extensions + Mapping Contracts + Governance / Policy Plane**

- Shared Core：通用的人、事件、来源、证据、断言、行动、知识、时间和溯源语义。
- Scope Extensions：个人、企业、中心分别扩展自身业务概念与约束。
- Mapping Contracts：定义跨域映射、脱敏、聚合、目的、授权引用、来源和损失报告。
- Governance / Policy Plane：由真实授权与策略服务决定数据能否被读取、转换和共享。

共享概念不等于共享数据。同一会议可以在个人与企业视角形成不同记录；个人原始录音、私人对话和个人上下文默认不向组织共享；中心层优先使用经过授权的聚合、脱敏和标准化结果。Ontology 描述语义，不自行授予访问权限。

本轮不新增正式 Ontology namespace、OWL 类或属性，不实现跨域同步服务。

## 6. 阶段退出标准

从过渡阶段进入个人数智底座原型阶段前，应满足：
1. 至少两个宿主 Agent 环境完成安装、调用和一致性验证。
2. 典型工作场景的来源、证据、时间和不确定性可追溯。
3. 重复导入、纠错、撤回、删除和导出有可重复测试。
4. 连接器权限、持久化回执和授权撤回路径明确。
5. 有真实试点数据的隐私与质量评估。
6. 用户能理解、修正和撤销 Agent 生成的上下文。

这些是未来退出条件，不是 0.4.2 已经达成的成果。
