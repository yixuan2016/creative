Executive Summary

这次试点究竟要证明什么？

前四份专题完成了从工作感知、企业运行认知、统一数据模型到工程原型的连续研究。第五份专题把研究带入真实业务：验证 ADS 能否准确理解项目状态、解释状态依据、识别不确定性，并帮助团队以更低成本采取下一步行动。

核心主张：试点成功不等于 AI 能写出漂亮周报，而是系统能在正确权限和可核验证据下呈现项目真实状态，让团队更快发现阻塞、确认责任和推进工作。

01 · Pilot Design

试点定位：验证企业基础能力，而不是只做一个 Agent

试点要回答三个层次的问题：上下文是否可信、业务工作是否改善、能力是否能够复制。

假设可验证问题证据
H1 多源信息可形成一致上下文项目、任务、决策、风险、依赖和交付物能否正确关联？对象关联准确率、证据引用完整率
H2 权威来源与协同线索可共存会议观点与项目状态冲突时，是否保留冲突而非覆盖？冲突识别与人工确认记录
H3 上下文包减少重复提示Agent 能否在任务上下文中完成状态和下一步分析？任务评测、人工修改率
H4 辅助能力降低协作成本状态汇总、信息查找和风险跟进是否更快？基线对比、遗漏和返工记录
H5 标准可跨项目复用新项目是否主要通过配置而非重写代码接入？接入工时、组件和规则复用率
H6 治理可伴随能力运行授权、证据、撤回和审计是否有效？权限测试、撤回演练、审计日志
边界：第一阶段只读。Agent 可以摘要、分析、提示和草拟跟进，但不自动修改项目状态、任务负责人、交付日期或客户承诺。

纳入 / 不纳入

纳入 项目运行必要上下文

  • 项目、任务、里程碑和负责人
  • 正式决策、风险、问题和依赖
  • 交付物、验收证据及版本
  • 经批准的会议纪要和项目协同记录
  • Agent 输出和人工反馈

不纳入 无差别采集和自动决策

  • 全员全群全量聊天抓取
  • 默认持续录音或屏幕监控
  • 个人记忆自动转为企业资产
  • 未经批准的正式业务写回
  • 自动批准决策、合同或验收
02 · Pilot Scope

项目选择：先做一个样板，再扩展验证

1 个样板项目 · 打通端到端流程
↓
2—4 个扩展项目 · 验证配置复用和复杂场景
↓
1 个交付团队 · 项目经理、交付负责人、技术负责人和执行角色
准入维度优先条件不建议进入首批
业务代表性有明确目标、里程碑、跨角色协作和风险极特殊且无法代表其他项目
数据可用性稳定对象 ID、状态、任务和更新时间关键内容仅有口头信息且无法授权
责任清晰有项目经理和数据责任人无人对状态和字段质量负责
参与意愿团队愿意参与基线采集和结果评审团队认为试点是个人绩效监控
风险可控数据分类和客户信息边界明确敏感数据无批准的处理机制
可比较性有历史周报、评审或可采集基线无法建立可信基线
不要为了规模牺牲质量。若授权、数据质量或业务资源不足，缩小范围把一个项目做实，不以扩大覆盖率掩盖问题。
03 · First Business Scenario

首个场景：项目交付状态评审与风险跟进

当前工作方式

  1. 打开项目系统查看项目和任务状态；
  2. 搜索钉钉群、会议纪要和邮件了解变化；
  3. 查找决策记录、问题单和交付物；
  4. 向任务负责人逐一确认状态；
  5. 手工整理进展、阻塞、风险和待办；
  6. 形成周报或评审材料，会议后再分散录入行动项。

试点后的目标方式

选择项目与评审时间范围
↓
ADS 检索授权项目、任务、决策、风险、依赖与证据
↓
认知引擎重建状态，标注来源、时间、冲突和未知
↓
Agent 生成摘要、关键变化、阻塞链和跟进草稿
↓
项目经理确认 / 修正 / 驳回
↓
反馈入账；正式变更仍由授权人员在原系统完成

每次评审应交付的运行视图

01 · 项目概览

目标、阶段、正式状态、负责人和里程碑。

02 · 本期变化

状态变化、任务变化和重要决策。

03 · 交付进展

已完成、进行中、逾期、阻塞的关键任务和证据。

04 · 风险与依赖

影响对象、责任人、依赖路径和下一步动作。

05 · 决策链

已提出、待确认、已批准和已撤回的决策。

06 · 未知与冲突

缺少确认、来源不一致和过期的信息。

04 · Data Integration

数据接入：先接权威数据，再补充协同上下文

数据源首批用途权威程度建议接入首批边界
项目管理系统项目、任务、负责人、计划、状态对正式字段权威只读 API / Webhook / 增量同步仅试点项目和必要字段
OA / 审批系统正式决策和变更审批对审批结果权威只读 API / 事件订阅仅项目相关审批
文档 / 知识系统交付物、方案、验收证据按版本和审批规则确认元数据 + 受控引用优先引用，不复制整份文档
风险 / 缺陷系统风险、问题、严重度、责任人对正式风险记录权威API / 事件订阅仅项目关联记录
钉钉项目群 / 会议纪要变化线索、原因和待确认事项默认是线索批准范围内的纪要或人工提交不全量抓取个人聊天
个人工作感知补充个人记忆或遗漏线索未经确认不构成企业事实单独评估后再考虑非第一阶段依赖

权威字段矩阵示例

属性权威来源示例协同线索作用冲突处理

task.assignee项目 / 任务系统群聊提示实际执行人变化待正式分配记录确认
milestone.due_at已批准计划会议提出调整建议未批准前不改变基线
decision.statusOA 审批 / 正式决策记录会议讨论属于 proposed正式审批后才标记 approved

接入顺序

  1. 项目管理系统：建立 Project、Task 和 Milestone。
  2. OA / 审批：补齐正式 Decision 和变更审批。
  3. 文档系统：补齐 Deliverable 和 EvidenceRef。
  4. 风险 / 缺陷系统：补齐 Risk、Issue 和 Dependency。
  5. 会议纪要：范围获批后作为线索来源。
  6. 个人感知来源：不作为第一阶段前置依赖。

目标技术架构：让可信上下文成为 Agent 的工作环境

业务系统与授权协同来源

↓

↓
标准事件接入与事件账本
↓
对象注册表 + 共同本体 / 项目领域本体
↓
权威字段规则 + 状态重建引擎
↓
冲突识别 · 证据引用 · 未知项 · 新鲜度
↓
授权校验与任务级 Context Package
↓
项目交付 Agent / API
↓
人工确认、修正、驳回 · 反馈事件 · 审计与评估

分层责任边界

能力层试点责任不承担的责任
连接与接入读取授权数据、增量同步、标准化不决定业务事实
事件与对象保存变化、解析对象、关联来源不擅自合并不确定对象
语义与规则字段含义、权威来源、状态计算不由大模型自由覆盖规则
认知与上下文项目状态视图、冲突和未知不替代正式业务记录
Agent 应用解释、摘要、提示、草拟跟进不绕过审批执行正式动作
治理与评估授权、审计、质量、指标和撤回不把安全检查留给提示词

06 · Agent Workflow

让 Agent 进入工作流程，而不是另建一个聊天窗口

TASK A

项目状态评审准备

项目概览、本期变化、关键任务、里程碑、风险、决策、未知和证据索引。

TASK B

阻塞与依赖分析

阻塞原因、上游依赖、受影响任务和里程碑、责任人及待确认问题。

TASK C

会议后行动项整理

候选决策、行动项、负责人候选、截止时间候选和关联对象。

人工确认状态

accepted

接受

人工确认，形成后续正式操作建议。

corrected

修正

保留原建议和修正内容。

rejected

驳回

记录驳回原因，供规则复盘。

deferred

待补充

信息不足，等待后续证据。

优先嵌入团队已有的项目系统或工作台入口。若只能使用 Web 原型，也必须绑定真实项目对象和权限，不做脱离业务系统的聊天演示。

出现哪些情况必须暂停？
  • 数据用途或授权尚未获批；
  • 对象无法可靠识别，错误关联可能影响业务结论；
  • 权威字段责任人未明确；
  • 高影响事实频繁错误且无法解释；
  • 出现未授权数据暴露或审计缺失；

基线怎么采集？

  • 第 1—2 周至少记录两周现状；
  • 选择不少于 3 次状态评审或同类管理任务；
  • 记录准备人、参与人数、准备时间、查找时间和会后修正时间；
  • 记录状态遗漏、负责人遗漏、日期错误和重复确认次数；
  • 区分项目复杂度、阶段和团队规模，避免简单比较。

样本量是设计建议。真实业务样本不足时必须披露限制，不能用合成数据冒充真实业务准确率。合成数据只用于边界测试。

业务收益计算

时间收益

节省工时 = 基线任务总工时 − 试点后任务总工时

质量收益

遗漏改善率 = (基线遗漏率 − 试点遗漏率) / 基线遗漏率

协同收益则比较跨角色确认次数、阻塞发现到责任人确认的时间、会后行动项录入时间和重复沟通次数。折算经济价值时，工时成本口径和可归因比例需由财务或业务负责人确认。

10 · Trust, Privacy & Control

治理、安全与员工信任：先建立边界，再扩大感知

目的限定

每个数据源都说明为何需要、服务哪个任务。

最小必要

只接试点项目、必要字段和有限时间范围。

权威分层

正式记录、人工确认、线索和推断分开标识。

原始数据留源

优先保存受控引用，不默认复制全文。

可撤回可纠错

授权撤回和源数据更正影响派生上下文。

审计可追溯

记录主体、用途、对象、策略、时间和结果。

个人工作感知的特殊边界

本试点不以录音卡、手机或桌面采集作为必要条件。若未来评估此类来源，必须先明确采集目的、知情与自愿机制、敏感信息过滤、原始数据留存、访问范围、撤回删除和适用制度审查。不得通过隐蔽录音、无差别聊天抓取或个人绩效监控来获得上下文。

13 · Go / No-Go

什么时候可以扩大试点？

GO 扩大

  • 关键质量指标达到冻结阈值
  • 真实团队完成完整人工确认闭环
  • 业务指标出现可重复改善
  • 没有未解决重大治理问题
  • 撤回、过期和高风险动作测试通过
  • 多个项目可复用主要模型和规则

NO-GO 暂停或重构

  • 关键状态准确率不达标且原因不明
  • 关键结论缺少可核验证据
  • 权限和撤回机制未通过
  • 大量人工补录，无法证明更省事
  • 团队不愿使用或感知为监控工具
  • 每个项目都需要重写模型和逻辑
结果分类：Go（扩大）；Conditional Go（限定场景，先补缺口）；No-Go（停止扩展，保留研究结论并调整场景或假设）。按计划完成开发不是 Go 的充分条件。

Conclusion

用真实业务结果决定是否建设企业运行认知基础设施

以项目交付为切入口，以一个样板项目打通闭环，以多个项目验证复用，以真实指标决定是否扩大。

企业运行认知基础设施的价值不在于把所有数据集中起来，也不在于让 Agent 代替项目经理，而在于让企业在正确权限下，把分散在系统、任务、决策、风险和协同过程中的信息组织成可信的运行上下文。

最终检验标准：真实项目团队愿不愿意持续使用，业务负责人能不能看到可核验的收益，数据和安全责任人能不能放心让它进入企业工作流程。
