## 摘要：把“理解企业运行”变成可实现的数据与引擎

ADS-WORK-01 研究了多源工作感知如何形成个人工作记忆，并在授权、审核、语义映射和验证后转化为企业数智资产；ADS-WORK-02 进一步提出企业工作上下文基础设施，使企业能够关联业务对象、事件、决策、任务、依赖、风险和证据，形成对企业运行的动态理解。

本文件继续向工程架构推进，定义一套**企业工作上下文统一数据模型**，并给出**企业运行认知引擎**的逻辑架构、核心处理流程、服务接口、数据治理和试点实施方式。

本设计的核心不是要求所有企业数据进入一个新平台，而是建立一层可连接、可解释、可治理的上下文组织能力：

- 以工作事件作为变化记录的基本单元；
- 以企业业务对象作为语义关联的锚点；
- 以状态断言表达“当前是什么”，同时保留来源、有效时间和可信状态；
- 以决策、任务、风险和关系表达业务运行脉络；
- 以证据引用支撑核验和追溯；
- 以任务级上下文包为 Agent 提供最小必要信息；
- 以 ADS 共同本体、领域本体和联邦治理机制保持跨系统、跨领域语义一致。

### 本设计的关键判断

1. **统一数据模型不等于统一物理数据库。** 统一的是语义、标识、事件封装和治理规则；数据可以分布在个人、企业和领域中心责任边界内。
2. **事件、状态、证据和标准业务数据必须分开建模。** 事件记录发生了什么；状态表达在某个有效时间内对象被认为处于什么状态；证据支持核验；标准业务数据是经过责任方验证、可供业务使用的数据资产。
3. **上下文引擎不是替代 ERP/CRM/项目系统的主数据系统。** 它关联并解释权威来源，按字段登记权威系统，不静默覆盖源系统。
4. **运行认知必须允许不确定性存在。** 已确认、观察到、推断中、冲突、过期和未知是一级状态，不是日志备注。
5. **Agent 消费的是有范围、有版本、有授权的上下文包。** 不允许默认对企业全量知识图谱或所有原始工作记录开放读取。
6. **企业工作上下文基础设施属于企业数智底座内部能力。** ADS 提供共同语义、联邦目录、授权协调和跨域协同，不因此新增第四级底座。

## 1. 设计目标、范围与架构约束

### 1.1 设计目标

本设计需要使企业能够：

- 从业务系统和经批准的协同来源接入工作事件；
- 将事件映射到客户、项目、产品、订单、流程、任务等业务对象；
- 保留事件发生时间、观察时间、记录时间和状态有效时间；
- 对多源状态进行重建，识别冲突、过期、缺失和未知；
- 将决策、任务、依赖、风险和证据组织为可追溯关系；
- 按任务、角色、用途和风险级别生成 Agent 上下文包；
- 记录 Agent 使用上下文、调用工具、审批和执行结果；
- 将经验证的数据与能力资产回流到正确的责任底座；
- 在不集中复制所有原始数据的情况下，支持跨系统和跨领域协同。

### 1.2 本设计不解决什么

本设计不直接定义：

- 企业全部业务领域的完整主数据标准；
- 所有业务系统的替换或迁移方案；
- 某一家厂商、某种数据库、向量库、图数据库或消息中间件的选型；
- 未经授权的员工音频、屏幕或通信内容持续采集；
- 个人工作记忆自动转为企业资产的机制；
- 由 AI 独立完成高风险业务审批或专业验收；
- 企业全部业务流程的一次性自动化。

这些内容需要分别由业务领域架构、技术选型、安全合规和专项工程设计处理。

### 1.3 设计约束

| 编号 | 约束 | 设计要求 |
|---|---|---|
| AC-01 | 责任边界不变 | 个人、企业、业务领域中心仍各自承担数据与资产责任 |
| AC-02 | 权威源优先 | 每个关键业务属性应登记权威来源和责任方 |
| AC-03 | 来源可追溯 | 重要事件、状态和结论必须可追溯到来源或确认记录 |
| AC-04 | 时间语义明确 | 区分发生、观察、记录和有效时间 |
| AC-05 | 不确定性显式化 | 不将推断、冲突或未知压缩成单一确定值 |
| AC-06 | 最小权限 | Agent 仅获取完成任务所需的最小上下文 |
| AC-07 | 可撤回与可纠错 | 支持授权撤回、内容纠错、失效标记和审计 |
| AC-08 | 可演进 | 模型、接口、本体和策略均须版本化 |
| AC-09 | 开放互操作 | 保留源系统 ID、标准化引用和可迁移格式 |
| AC-10 | 不新增底座层级 | 本能力归属企业数智底座，并遵循 ADS 既有跨层治理机制 |

### 1.4 规范用语

本文中的“必须”表示建议作为架构强制要求；“应该”表示默认要求，特殊情况需有理由；“可以”表示可选实现。本文为研究设计稿，这些规范用语仍需经过正式架构评审后才能成为组织标准。

## 2. 总体架构：统一模型、上下文引擎与服务平面

### 2.1 三个核心组成

**A. 统一数据模型（Canonical Work Context Model）**

定义企业工作事件、业务对象引用、关系、状态断言、决策、任务、风险、证据、能力资产、授权和审计记录的公共语义与字段约束。

**B. 运行认知引擎（Enterprise Runtime Context Engine）**

负责事件接入、身份解析、语义映射、状态重建、关系维护、冲突检测、上下文组装、缺口发现和质量评价。

**C. 上下文服务平面（Context Service Plane）**

通过 API、事件订阅和受控查询向业务应用及 Agent 提供对象时间线、当前状态、上下文包、证据引用、关系查询和受控回写能力。

### 2.2 逻辑架构

### 2.3 控制平面与数据平面

- **数据平面**负责事件、对象、关系、状态、证据和上下文的处理与查询。
- **控制平面**负责身份、授权、用途、策略、本体版本、数据分类、保留期限和审计。
- 控制平面策略应在接入、查询、上下文组装、工具执行和回写等关键节点执行，而不是只在用户登录时检查一次。

## 3. 统一数据模型：核心实体与关系

### 3.1 模型总览

建议将模型分为四组：

| 模型组 | 核心实体 | 主要作用 |
|---|---|---|
| 事实与来源组 | WorkEvent、SourceRecord、EvidenceRef | 记录发生了什么、从哪里得知、如何核验 |
| 业务语义组 | BusinessObject、ObjectAlias、Relation、StateAssertion | 关联企业业务对象、身份、关系和状态 |
| 运行管理组 | DecisionRecord、TaskRecord、RiskRecord、CapabilityAsset | 表达决策、执行、风险和可复用能力 |
| 使用与治理组 | ContextPackage、AuthorizationGrant、PolicyDecision、AuditRecord | 控制谁因何种目的使用什么上下文，并记录过程 |

实体之间的关联关系示意：

~~~mermaid

  WORK_EVENT }o--o{ BUSINESS_OBJECT : references
  WORK_EVENT ||--o{ EVIDENCE_REF : supported_by
  BUSINESS_OBJECT ||--o{ STATE_ASSERTION : has
  BUSINESS_OBJECT }o--o{ RELATION : connected_by
  WORK_EVENT ||--o{ DECISION_RECORD : may_form
  WORK_EVENT ||--o{ TASK_RECORD : may_create
  BUSINESS_OBJECT ||--o{ RISK_RECORD : affected_by
  TASK_RECORD }o--o{ TASK_RECORD : depends_on
  CAPABILITY_ASSET }o--o{ TASK_RECORD : supports
  CONTEXT_PACKAGE }o--o{ BUSINESS_OBJECT : includes
  CONTEXT_PACKAGE }o--o{ EVIDENCE_REF : cites
  AUTHORIZATION_GRANT ||--o{ CONTEXT_PACKAGE : governs
  CONTEXT_PACKAGE ||--o{ AUDIT_RECORD : accessed_by
~~~

### 3.2 统一标识原则

1. 企业内部每个上下文实体使用稳定的全局或租户范围 ID。
2. 原系统对象 ID 必须保留为外部标识，不用新 ID 覆盖源系统主键。
3. 同一对象在不同系统中的别名和映射关系单独存储，不能直接把字符串相同视为同一对象。
4. 对象合并、拆分和映射纠错必须保留历史，支持追溯。
5. 跨企业或跨责任域引用使用受控标识或联邦引用，不泄露内部数据库主键和敏感字段。

建议统一 ID 采用可排序唯一 ID 或 UUID 类方案；具体生成算法由工程标准确定。业务 ID 与技术 ID 应分离。

### 3.3 WorkEvent：工作事件

工作事件是企业工作上下文的基本变化单元，采用追加式记录。事件一旦被接收，不应直接覆盖原始事件内容；纠错通过更正事件、失效标记或新版本关联完成。

| 字段 | 类型建议 | 必填 | 说明 |
|---|---|---:|---|
| event_id | string | 是 | 事件唯一标识 |
| tenant_id | string | 是 | 企业或租户范围 |
| event_type | string | 是 | 标准事件类型 |
| event_schema_version | string | 是 | 事件结构版本 |
| occurred_at | datetime | 是 | 实际发生时间 |
| observed_at | datetime | 是 | 来源或连接器观察到的时间 |
| recorded_at | datetime | 是 | 写入事件账本时间 |
| actor_ref | ObjectRef | 否 | 人员、角色、系统或 Agent 引用 |
| object_refs | ObjectRef[] | 是 | 涉及的业务对象 |
| payload | object | 是 | 事件类型对应的业务负载 |
| source_ref | SourceRef | 是 | 来源记录引用 |
| evidence_refs | EvidenceRef[] | 否 | 支持事件的证据 |
| assertion_status | enum | 是 | observed / inferred / confirmed / disputed / rejected |
| confidence | number | 否 | 0 到 1 的模型置信度，不等于业务确认 |
| classification | string | 是 | 数据分类或敏感级别 |
| purpose_tags | string[] | 是 | 允许处理的业务目的 |
| authorization_ref | string | 条件必填 | 涉及受控共享时必填 |
| ontology_version | string | 是 | 共同本体与领域本体版本 |
| correction_of | string | 否 | 更正或替代的事件 ID |
| lifecycle_status | enum | 是 | active / superseded / withdrawn / archived |

建议首批标准事件类型：

- activity.started / activity.completed；
- task.created / task.assigned / task.updated / task.completed；
- decision.proposed / decision.approved / decision.rejected / decision.revised；
- issue.detected / issue.updated / issue.resolved；
- risk.identified / risk.escalated / risk.closed；
- feedback.received；
- object.state_changed；
- evidence.attached / evidence.verified；
- context.corrected / context.withdrawn。

事件类型目录应可扩展，但必须有事件所有者、定义、版本、字段约束和兼容规则。

### 3.4 BusinessObject：企业业务对象

BusinessObject 是企业语义关联的锚点。它不一定复制源系统全部字段，而是建立统一对象身份和最小公共属性。

| 字段 | 说明 |
|---|---|
| object_id | 上下文模型中的稳定标识 |
| tenant_id | 所属企业或租户 |
| object_type | project / customer / product / order / contract / process / ticket / resource 等 |
| canonical_name | 企业规范名称 |
| domain_id | 所属业务领域 |
| authority_refs | 权威系统与原始对象 ID |
| owner_ref | 业务责任人或责任角色 |
| classification | 数据分类 |
| lifecycle_status | active / inactive / merged / split / archived |
| valid_from / valid_to | 对象身份或业务有效区间 |
| ontology_version | 适用本体版本 |

对象的详细业务属性仍应优先从权威系统读取或以受控映射方式同步。上下文模型不应变成另一个未经治理的主数据副本。

### 3.5 ObjectRef 与身份映射

统一引用结构建议包括：

~~~json
{
  "object_id": "obj_01J...",
  "object_type": "project",
  "tenant_id": "tenant_acme",
  "source_system": "project-system",
  "source_object_id": "PRJ-2026-014",
  "resolution_status": "confirmed"
}
~~~

身份映射需支持四种结果：

- exact：源系统主键精确匹配；
- alias：通过已登记别名匹配；
- candidate：模型提出候选对象，等待确认；
- unresolved：无法可靠匹配，不建立确定关系。

模糊匹配只能产生候选，不应自动合并关键业务对象。客户、合同、订单、人员和项目等高影响对象应设置更严格的确认阈值和人工复核规则。

### 3.6 Relation：业务关系

关系应表达明确语义，而不是只有一个无类型的“相关”。

| 字段 | 说明 |
|---|---|
| relation_id | 关系唯一标识 |
| subject_ref | 主体对象 |
| predicate | 关系类型，如 belongs_to / depends_on / blocks / serves / owns |
| object_ref | 客体对象 |
| direction | 关系方向 |
| valid_time | 关系在业务世界中的有效区间 |
| recorded_at | 系统记录时间 |
| source_refs | 关系来源 |
| assertion_status | 观察、推断、确认或争议 |
| confidence | 置信度 |
| owner_ref | 关系确认责任方 |

建议关系类型按领域扩展，并登记定义、反向关系、基数约束和是否允许推断。对于 depends_on、blocks、owns 等会影响任务执行的关系，必须记录来源和确认状态。

### 3.7 StateAssertion：状态断言

状态断言用于表达某对象的某个属性在某个时间范围内被认为是什么值。它与事件不同：事件记录“状态发生了变化”，状态断言表达“某个时点或区间的状态”。

| 字段 | 说明 |
|---|---|
| assertion_id | 状态断言标识 |
| subject_ref | 被描述的业务对象 |
| property | 状态属性，如 project.status / task.due_date |
| value | 断言值 |
| valid_from / valid_to | 业务有效时间 |
| observed_at / recorded_at | 观察与记录时间 |
| authority_ref | 此字段的权威来源 |
| source_refs | 其他支持来源 |
| assertion_status | confirmed / observed / inferred / conflicted / stale / unknown |
| confidence | 模型置信度 |
| supersedes | 被替代的断言 |
| dispute_refs | 争议记录 |

**状态重建规则：** 不设一个适用于所有字段的简单来源优先级。应按“对象类型 + 属性 + 业务领域”配置权威来源。例如订单金额以指定 ERP 字段为准，项目任务状态以指定项目系统为准；会议讨论可作为状态变化线索，但不能自动覆盖权威字段。

### 3.8 DecisionRecord：决策记录

核心字段包括 decision_id、subject_refs、decision_statement、decision_status、proposed_by、approved_by、decision_time、effective_time、rationale_refs、constraint_refs、alternative_refs、evidence_refs、related_task_refs、review_condition、source_refs 和 version。

决策记录应区分“讨论意见”“候选方案”“正式决策”和“决策修订”。讨论中出现的观点不能自动写成组织决定。正式决策必须关联有权限的确认主体和依据。

### 3.9 TaskRecord：任务记录

核心字段包括 task_id、title、description、status、assignee_ref、owner_ref、created_at、due_at、completed_at、related_object_refs、dependency_refs、blocked_by_refs、acceptance_criteria、source_refs、evidence_refs、authority_ref 和 lifecycle_status。

任务状态应映射企业实际采用的工作流，不强行要求所有系统使用同一套状态词。统一模型可以定义标准状态族，再保留源系统原始状态与映射版本。

### 3.10 RiskRecord：风险记录

核心字段包括 risk_id、risk_type、description、affected_object_refs、likelihood、impact、risk_level、detected_at、owner_ref、mitigation_actions、status、evidence_refs、source_refs 和 confirmation_status。

AI 可以提出风险线索，但未经责任人确认的风险应标记为 candidate 或 inferred，不能直接变为正式管理结论或个人绩效判断。

### 3.11 SourceRecord 与 EvidenceRef

二者必须区分：

- SourceRecord 描述信息来自哪个系统、文档、会议或设备记录；
- EvidenceRef 描述某条事实或判断由哪些证据支持，以及如何定位和核验。

SourceRecord 建议字段：source_id、source_type、system_id、native_record_id、uri_or_locator、captured_at、owner_tier、classification、retention_policy、content_hash、access_policy_ref。

EvidenceRef 建议字段：evidence_id、evidence_type、source_ref、locator、supports_refs、created_at、verification_status、verified_by、verified_at、integrity_hash、access_policy_ref。

证据可以是文件引用、系统记录 ID、会议时间戳、文档版本、人工确认记录或业务系统快照。默认优先存储受控引用和校验信息，不因建立证据链而无差别复制原始文件。

### 3.12 ContextPackage：任务级上下文包

上下文包是运行认知引擎向 Agent 或业务应用交付的最小使用单元。

| 字段 | 说明 |
|---|---|
| context_id | 上下文包唯一标识 |
| task_id | 触发上下文组装的任务 |
| requester_ref | 请求者或 Agent 身份 |
| purpose | 本次上下文使用目的 |
| scope | 对象范围、领域范围和时间范围 |
| included_refs | 纳入的对象、事件、状态和证据引用 |
| excluded_summary | 被排除内容的类型说明，不暴露其敏感内容 |
| unresolved_items | 冲突、缺失、过期和待确认项 |
| allowed_actions | 本次上下文允许申请的动作 |
| authorization_refs | 授权依据 |
| policy_version | 策略版本 |
| ontology_version | 本体版本 |
| source_snapshot | 来源版本或读取时间 |
| created_at / expires_at | 创建与过期时间 |
| integrity_hash | 包内容完整性校验 |
| lifecycle_status | active / expired / revoked / superseded |

上下文包应尽量不可变；如果信息更新，应生成新版本或新包，并明确替代关系。Agent 执行时必须记录实际使用的 context_id，而不是只记录查询条件。

### 3.13 CapabilityAsset：能力资产

能力资产不是未经整理的个人笔记。建议字段包括 capability_id、name、capability_type、domain_id、description、input_contract、output_contract、preconditions、steps_or_skill_ref、applicability_scope、known_limits、validation_cases、validation_results、owner_ref、version、approval_status、effective_time、dependencies 和 deprecation_status。

能力资产必须有责任人、版本、适用范围、验证案例和失败边界。跨团队复用前应在目标团队或目标流程进行适配验证。

## 4. 统一事件封装与示例

### 4.1 标准事件信封

建议将事件信封与事件 payload 分开。信封定义跨系统通用字段，payload 按 event_type 和 schema_version 定义。

~~~json
{
  "event_id": "evt_01JCTX...",
  "tenant_id": "tenant_acme",
  "event_type": "task.updated",
  "event_schema_version": "1.0",
  "occurred_at": "2026-11-18T09:30:00+08:00",
  "observed_at": "2026-11-18T09:30:04+08:00",
  "recorded_at": "2026-11-18T09:30:05+08:00",
  "actor_ref": {
    "actor_type": "system",
    "system_id": "project-system"
  },
  "object_refs": [
    {
      "object_type": "project",
      "source_system": "project-system",
      "source_object_id": "PRJ-2026-014"
    },
    {
      "object_type": "task",
      "source_system": "project-system",
      "source_object_id": "TASK-328"
    }
  ],
  "payload": {
    "changed_property": "status",
    "old_value": "in_progress",
    "new_value": "blocked",
    "reason_code": "dependency_pending"
  },
  "source_ref": {
    "source_system": "project-system",
    "native_record_id": "TASK-328",
    "record_version": "42"
  },
  "assertion_status": "observed",
  "classification": "internal",
  "purpose_tags": ["project_delivery_context"],
  "ontology_version": "ads-common-1.x/domain-project-0.x",
  "lifecycle_status": "active"
}
~~~

示例中的 tenant、系统名和业务编号均为虚构值，仅用于说明字段结构。

### 4.2 事件处理状态

建议事件处理状态与事件业务状态分开：

| 处理状态 | 含义 |
|---|---|
| received | 已接收 |
| validated | 结构和基本策略校验通过 |
| normalized | 时间、标识和字段已标准化 |
| resolved | 业务对象映射完成 |
| pending_review | 需要人工确认 |
| accepted | 进入有效上下文 |
| rejected | 不满足接收条件 |
| superseded | 被更正或新事件替代 |
| withdrawn | 按授权或治理要求撤回 |

失败重试不能产生重复业务事件。接入层应支持幂等键，推荐由 source_system + native_record_id + source_version + event_type 等字段生成或映射幂等标识。

### 4.3 重复、乱序与更正

- **重复事件：** 使用幂等键去重，同时保留接收日志。
- **乱序事件：** 以 occurred_at 和源系统版本判断业务顺序，以 recorded_at 保留处理顺序。
- **延迟事件：** 允许迟到事件触发状态重算，但必须记录重算时间和版本。
- **更正事件：** 不物理覆盖原事件，使用 correction_of 或 supersedes 建立关系。
- **撤回事件：** 记录撤回依据和影响范围，并使依赖该信息的上下文包失效或重新评估。
- **冲突事件：** 并存保存，不用“最后写入者获胜”作为通用规则。

## 5. 运行认知引擎：处理链路与核心算法职责

### 5.1 引擎组件

| 组件 | 输入 | 输出 | 核心职责 |
|---|---|---|---|
| Connector Gateway | API、Webhook、受控文件引用 | 标准接入消息 | 连接源系统、身份认证、限流、接入审计 |
| Policy Gate | 来源、主体、用途、数据分类 | allow / deny / review | 检查授权、用途和接收边界 |
| Event Normalizer | 原始消息 | 标准事件 | 字段映射、时间归一、去重和模式校验 |
| Entity Resolver | 事件对象线索 | ObjectRef 与匹配状态 | 对象识别、别名解析、候选匹配 |
| Ontology Mapper | 对象、事件和领域信息 | 规范语义映射 | ADS 共同本体与领域本体映射 |
| State Engine | 事件、权威源快照、状态断言 | 当前状态视图与历史版本 | 状态重建、有效时间计算和冲突管理 |
| Relation Engine | 对象、事件和关系候选 | 关系图与关系状态 | 维护依赖、归属、影响和决策关系 |
| Context Builder | 任务、主体、范围、策略 | ContextPackage | 最小必要裁剪、证据引用和不确定性标注 |
| Gap & Risk Detector | 状态、关系和规则 | 缺口与风险候选 | 发现缺失、过期、阻塞和异常关系 |
| Quality & Feedback | 人工反馈、业务结果 | 质量指标与修正任务 | 监测准确性、收集纠错和评估资产价值 |

### 5.2 标准处理流程

~~~mermaid
flowchart TD
  A[接收来源事件] --> B{授权与用途是否允许}
  B -- 否 --> X[拒绝 / 隔离并审计]
  B -- 需确认 --> R[进入人工审核队列]
  B -- 是 --> C[模式校验与标准化]
  C --> D[幂等去重与时间归一]
  D --> E[对象身份解析]
  E --> F{对象匹配是否可靠}
  F -- 否 --> R
  F -- 是 --> G[共同本体与领域本体映射]
  G --> H[生成事件 / 关系 / 状态候选]
  H --> I[权威源核验与冲突检测]
  I --> J{是否满足接收与确认规则}
  J -- 否 --> R
  J -- 是 --> K[写入事件账本与状态投影]
  K --> L[更新对象时间线与关系视图]
  L --> M[质量检查与缺口检测]
  M --> N[提供上下文服务]
  N --> O[Agent / 业务人员使用]
  O --> P[反馈 / 审批 / 执行结果]
  P --> Q[更正事件与质量闭环]
  Q --> K
~~~

### 5.3 状态重建职责

状态引擎不应简单地把“最近一条消息”作为当前状态。建议按字段执行：

1. 识别对象和属性；
2. 查询该对象属性的权威来源配置；
3. 获取权威系统当前值及其版本或更新时间；
4. 获取相关状态断言和事件；
5. 检查有效时间、观察时间和新鲜度；
6. 识别冲突、过期、缺失或未确认信息；
7. 生成当前状态视图和状态解释；
8. 保留重建所用来源、规则版本和计算时间。

输出示例：

~~~json
{
  "object_ref": {"object_type": "project", "object_id": "obj_project_014"},
  "property": "delivery_status",
  "value": "at_risk",
  "assertion_status": "inferred",
  "authority_source": "project-system",
  "supporting_refs": ["evt_01", "evt_02", "evidence_08"],
  "conflicts": [],
  "unknowns": ["客户验收日期尚未确认"],
  "freshness": {
    "source_updated_at": "2026-11-18T09:30:00+08:00",
    "evaluated_at": "2026-11-18T10:00:00+08:00"
  },
  "rule_version": "project-state-rules-0.1"
}
~~~

这里的 at_risk 是引擎基于规则生成的风险状态候选，不等同于业务责任人正式确认的项目状态。业务状态和认知状态应分别表达。

### 5.4 冲突检测原则

冲突至少分为：

- 值冲突：两个来源对同一属性给出不同值；
- 时间冲突：相同值对应的有效时间不一致；
- 身份冲突：不同记录可能指向同一对象，或同一标识被错误复用；
- 语义冲突：不同领域对相同术语的定义不同；
- 权限冲突：数据可见但当前用途不允许使用；
- 证据冲突：支持同一结论的证据互相矛盾。

冲突处理流程应输出冲突类型、涉及来源、各自时间、权威配置、建议处理人和当前处理状态。不得仅通过模型打分自动消除高影响业务冲突。

### 5.5 运行认知的边界

运行认知引擎输出的是“基于当前授权数据和规则形成的可解释认知视图”，不是企业全部真实状态的完美复制。数据未接入、来源未授权、事件未记录或语义未映射时，必须允许输出“未知”或“信息不足”。

## 6. Agent 上下文包标准与使用协议

### 6.1 上下文包生成输入

生成上下文包至少需要：

- requester：用户、Agent 或系统身份；
- purpose：明确业务目的；
- task：当前任务目标与风险级别；
- scope：对象、领域和时间范围；
- requested_fields：需要的字段和信息类型；
- policy_context：适用授权、角色和策略版本；
- freshness_requirement：任务可接受的数据新鲜度。

### 6.2 上下文包内容

上下文包至少包括：

1. 任务目标和任务标识；
2. 调用主体、所属组织和用途；
3. 相关业务对象及权威来源；
4. 当前状态、状态可信级别和更新时间；
5. 关键事件时间线；
6. 相关决策、约束、任务和依赖；
7. 风险、冲突、未知和过期项；
8. 支持结论的证据引用；
9. 允许的动作、审批要求和禁止动作；
10. 数据、本体、策略和上下文包版本。

### 6.3 上下文包样例

~~~json
{
  "context_id": "ctx_01J...",
  "task_id": "task_review_project_014",
  "requester_ref": "agent_project_assistant",
  "purpose": "prepare_project_status_review",
  "scope": {
    "object_refs": ["obj_project_014"],
    "time_window": {
      "from": "2026-11-11T00:00:00+08:00",
      "to": "2026-11-19T00:00:00+08:00"
    }
  },
  "current_state": {
    "delivery_status": {
      "value": "at_risk",
      "assertion_status": "inferred",
      "source_refs": ["project-system", "event-ledger"]
    }
  },
  "timeline_refs": ["evt_01", "evt_02", "evt_03"],
  "decision_refs": ["decision_05"],
  "task_refs": ["task_328", "task_331"],
  "risk_refs": ["risk_candidate_02"],
  "unknowns": ["客户验收日期待确认"],
  "allowed_actions": ["summarize", "draft_follow_up"],
  "approval_required_for": ["update_project_status", "send_customer_commitment"],
  "authorization_refs": ["grant_2026_014"],
  "policy_version": "context-policy-0.1",
  "ontology_version": "ads-common-1.x/domain-project-0.x",

}
~~~

样例中的状态是示意性推断，不代表实际项目结论。

### 6.4 Agent 使用协议

- Agent 只能读取当前 context_id 明确包含且允许使用的内容；
- Agent 不能将上下文包未包含的信息假定为事实；
- 对过期包、撤回包或策略版本失效的包，应重新申请；
- 对写操作，Agent 需提交动作意图、目标对象、预期变更和理由；
- 高风险操作必须由具备权限的人员审批；
- 工具执行结果必须区分技术成功与业务成功；
- Agent 的建议不能自动升级为正式决策或标准业务数据。

## 7. 服务接口设计（建议 API 契约）

本节定义逻辑接口和请求/响应字段建议，不代表已经部署的 API。正式接口需进一步完成 OpenAPI、错误码、认证方案、限流和兼容性评审。

### 7.1 接口分组

| 接口组 | 用途 | 典型操作 |
|---|---|---|
| Event API | 接入和查询事件 | ingest、get、timeline、correct、withdraw |
| Object API | 查询业务对象和映射 | resolve、get、aliases、relationships |
| State API | 查询状态与冲突 | current、history、conflicts、refresh |
| Context API | 生成和读取上下文包 | build、get、renew、revoke |
| Evidence API | 引用和核验来源证据 | resolve、verify、access-check |
| Action API | 提交受控业务动作 | propose、approve、execute、rollback |
| Governance API | 授权、策略与审计 | authorize、policy-check、audit-query |

### 7.2 核心接口草案

| 方法 | 路径建议 | 说明 |
|---|---|---|
| POST | /v1/events:ingest | 接收标准工作事件 |
| GET | /v1/events/{event_id} | 查询事件 |
| POST | /v1/events/{event_id}:correct | 提交更正事件 |
| POST | /v1/events/{event_id}:withdraw | 申请撤回或失效 |
| POST | /v1/objects:resolve | 解析源系统对象引用 |
| GET | /v1/objects/{object_id} | 查询对象统一视图 |
| GET | /v1/objects/{object_id}/timeline | 查询对象事件时间线 |
| GET | /v1/objects/{object_id}/relations | 查询对象关系 |
| GET | /v1/objects/{object_id}/state | 查询对象当前状态 |
| GET | /v1/objects/{object_id}/state-history | 查询状态历史 |
| POST | /v1/context-packages:build | 申请生成任务级上下文包 |
| GET | /v1/context-packages/{context_id} | 获取上下文包 |
| POST | /v1/context-packages/{context_id}:revoke | 撤销或失效上下文包 |
| POST | /v1/actions:propose | 提交 Agent 动作意图 |
| POST | /v1/actions/{action_id}:approve | 人工审批动作 |
| POST | /v1/actions/{action_id}:execute | 执行已批准动作 |

~~~json
{

  "task": {
    "task_id": "task_review_project_014",
    "risk_level": "low"
  },
  "scope": {
    "object_refs": [

      "from": "2026-11-11T00:00:00+08:00",
      "to": "2026-11-19T00:00:00+08:00"
    }
  },
  "requested_fields": [
    "current_state",
    "timeline",
    "decisions",
    "tasks",
    "dependencies",
    "risks",
    "unknowns",
    "evidence_refs"
  ],
  "freshness_requirement": "latest_available"
}
~~~

### 7.4 接口通用要求

- 所有请求应包含认证主体和租户上下文；
- 写操作应支持幂等键；
- 返回结果应携带 trace_id、schema_version 和适用策略版本；
- 分页、排序和过滤规则必须稳定；
- 错误响应应区分认证失败、授权拒绝、对象未找到、映射歧义、状态冲突、数据过期、策略拒绝和系统错误；
- 对外暴露的 URI、对象 ID 和证据定位符不得绕过原始系统权限；
- 接口应支持向后兼容和弃用通知；
- 不能通过接口返回值推断用户拥有源系统未授予的权限。

## 8. 存储与部署逻辑：统一语义，不强制统一技术

### 8.1 逻辑存储分区

| 逻辑存储 | 保存内容 | 设计重点 |
|---|---|---|
| Event Ledger | 追加式工作事件 | 不可静默覆盖、支持重放和更正链 |
| Object Registry | 统一对象 ID、源 ID 和别名 | 身份映射、合并拆分历史 |
| Relation Store | 类型化业务关系 | 有效时间、来源和确认状态 |
| State Projection | 当前状态和历史状态视图 | 可重建、带来源和规则版本 |
| Evidence Index | 证据元数据与受控引用 | 不默认复制原始内容 |
| Capability Registry | 能力资产、版本和验证记录 | 适用范围、审批和弃用管理 |
| Context Cache | 临时上下文包与检索缓存 | TTL、撤销、最小化和加密 |
| Audit Store | 访问、策略、审批和动作记录 | 防篡改、可审计、保留策略 |
| Search / Retrieval Index | 文本和语义检索索引 | 可重建，不能成为权威事实源 |

### 8.2 存储技术选择原则

本设计不预设必须采用图数据库、向量数据库或某个消息中间件。建议按访问模式选择：

- 事务型数据存储：对象注册、授权、任务和审批状态；
- 追加式日志或事件存储：事件账本和事件重放；
- 关系查询或图查询能力：对象关系、依赖和决策链；
- 搜索索引：全文检索和语义检索；
- 对象存储或源系统引用：大文件和证据原件；
- 缓存：短时上下文包和高频只读视图。

在试点规模较小时，可以采用一个可维护的关系型数据库加事件表、搜索索引和对象存储引用，避免过早引入复杂技术栈。是否需要独立图数据库，应由关系查询规模、复杂度和性能测试决定。

### 8.3 部署与数据驻留

- 个人原始工作记录优先留在个人责任边界内，除非用户和组织规则明确授权共享；
- 企业业务数据和上下文主要在企业控制的环境中处理；
- 领域中心优先登记目录元数据、语义规范、能力描述、授权和审计信息；
- 跨域查询可通过联邦查询、受控 API 或最小必要上下文包实现；
- 敏感内容是否允许云端模型处理，需由数据分类、合同、组织政策和安全评估决定；
- 所有缓存、索引和派生数据必须继承来源数据的权限与保留约束。

## 9. 数据治理、安全与生命周期

### 9.1 授权不是一个布尔值

授权记录应至少描述：

- 授权主体与代表关系；
- 数据责任方；
- 数据范围和字段范围；
- 处理目的；
- 允许的接收方或 Agent；
- 允许的处理动作；
- 生效和到期时间；
- 是否允许派生、转发或再共享；
- 撤回方式和撤回后的处理规则；
- 适用策略版本和审计引用。

### 9.2 权限决策维度

建议采用角色权限与属性权限结合的方式。每次查询至少评估：

- 谁在访问（subject）；
- 代表谁访问（on_behalf_of）；
- 访问什么对象和字段（resource）；
- 为了什么目的（purpose）；
- 执行什么操作（action）；
- 在什么组织、项目和任务上下文中（environment）；
- 数据分类、授权状态和时间条件是否允许。

### 9.3 生命周期状态

| 对象 | 建议生命周期 |
|---|---|
| 原始来源 | captured → retained → restricted / expired → deleted or archived |
| 工作事件 | received → validated → accepted → superseded / withdrawn → archived |
| 状态断言 | candidate → confirmed / disputed / stale → superseded |
| 证据 | registered → verified / disputed → expired / restricted |
| 上下文包 | requested → built → active → expired / revoked |
| 能力资产 | candidate → validated → approved → active → deprecated / retired |

撤回或删除不能只删除一个主记录。系统应识别相关缓存、搜索索引、派生状态、上下文包和能力候选，并按适用政策进行失效、重算、限制或删除。依法或依合同必须保留的审计记录应与业务内容分离，并限制访问。

### 9.4 必须有的治理控制

- 数据分类和字段级敏感标签；
- 传输与静态加密；
- 租户隔离和最小权限；
- 访问、导出、模型调用和写回审计；
- 上下文包 TTL 与撤销机制；
- 源数据权限变更后的缓存失效；
- 模型输出标注与人工纠错；
- 数据保留、删除、法律保全和备份恢复策略；
- 对第三方信息和个人信息的目的限制及必要审查。

## 10. 企业与 ADS 三级数智底座的衔接

### 10.1 责任归属

| 层级 | 可承载内容 | 不应默认承载 |
|---|---|---|
| 个人数智底座 | 个人工作事件、个人记忆、个人证据、个人任务和用户授权共享记录 | 企业所有业务上下文和其他人的私人记录 |
| 企业数智底座 | 企业工作事件、业务对象、状态、决策、任务、风险、证据、标准业务数据和能力资产 | 未经授权的个人完整记忆或与企业目的无关的个人信息 |
| 业务领域中心数智底座 | 共同本体、标准、联邦资产目录、能力目录、跨域授权与任务审计元数据 | 默认集中存储所有企业原始业务记录和个人原始数据 |

### 10.2 从个人到企业的受控晋升

个人工作信息要成为企业资产，至少经过：

1. 个人侧识别可共享候选；
2. 明确内容权属、参与方和第三方信息；
3. 明确共享目的、字段范围、接收方和期限；
4. 个人或有权主体完成授权；
5. 企业责任人审核业务必要性和数据质量；
6. 关联企业业务对象并完成领域本体映射；
7. 完成必要的脱敏、去标识或内容裁剪；
8. 验证后进入企业责任边界；
9. ADS 联邦目录仅登记适当的元数据和受控引用；
10. 授权变化、纠错和撤回沿原链路传播。

### 10.3 从企业到领域中心的协同

企业向领域中心提供的优先是：

- 本体映射和标准版本；
- 可发现的资产元数据；
- 能力资产描述和适用条件；
- 受控接口和访问策略；
- 经授权的跨域任务状态；
- 必要的审计与评价结果。

企业业务明细、原始文件和员工个人记录不因进入联邦目录而自动跨域开放。目录可发现性与内容可访问性必须分离。

### 10.4 与 ADS 执行端、管理端、考核端的关系

- **执行端：** 通过上下文服务读取任务级信息，发起受控动作，回传执行结果。
- **管理端：** 管理本体、数据责任、授权、连接器、资产目录、能力版本和策略。
- **考核端：** 评价事件质量、上下文完整度、任务效果、Agent 可靠性和治理合规情况。
- **共同治理：** ADS 提供跨层语义、身份、授权、目录和审计协同，不替代企业业务责任。

## 11. 试点参考：项目交付上下文闭环

### 11.1 试点范围

建议选取一个项目交付流程，先接入：

- 一个项目或任务权威系统；
- 一类经批准的会议或协同记录；
- 一类项目文档或决策记录。

不需要一开始接入全部员工通信、屏幕或录音数据。

### 11.2 首批业务对象

Project、Task、Decision、Risk、Evidence、ActorRole。

### 11.3 首批事件类型

task.created、task.updated、task.completed、decision.proposed、decision.approved、risk.identified、evidence.attached、project.state_changed。

### 11.4 最小运行闭环

1. 项目系统产生任务状态变化事件；
2. 经授权的会议记录提供决策和依赖线索；
3. 事件规范化并关联到 Project / Task；
4. 状态引擎读取权威项目状态，区分系统事实和会议推断；
5. 关系引擎形成任务依赖与阻塞候选；
6. Context Builder 生成项目周报或风险评审上下文包；
7. Agent 生成状态摘要、未决事项和跟进草稿；
8. 项目负责人确认或修订；
9. 确认结果写回对应系统或上下文记录；
10. 以周期、遗漏、返工、核验成本和越权情况评估效果。

### 11.5 试点验收指标

| 类别 | 指标 | 验收方式 |
|---|---|---|
| 接入 | 事件接入成功率 | 与源系统抽样记录对账 |
| 语义 | 对象关联准确率 | 业务人员抽样确认 |
| 状态 | 权威状态一致率 | 与指定权威字段比较 |
| 可信 | 证据可追溯率 | 抽样检查结论能否定位来源 |
| 时效 | 状态新鲜度 | 测量来源更新到上下文可用的延迟 |
| 质量 | 冲突识别与误报 | 构造和抽样核验冲突案例 |
| Agent | 建议有效率 / 人工修改率 | 对照业务负责人审阅结果 |
| 业务 | 周期、遗漏、返工 | 与试点前基线或对照流程比较 |
| 治理 | 未授权访问和错误写回 | 安全测试与审计记录 |
| 成本 | 单流程运行成本 | 统计连接器、模型、存储和人工核验成本 |

验收阈值应在试点开始前由业务和安全责任人共同确定，不能在结果出来后再调整标准以迎合结论。

## 12. 工程实施路线与交付物

### 阶段 A：模型冻结与数据契约

交付物：
- 首批对象与事件目录；
- JSON Schema 或等价结构定义；
- 事件类型和版本管理规范；
- 源系统权威字段清单；
- 身份映射规则；
- 数据分类与授权契约。

进入下一阶段的条件：业务责任人和数据责任人确认对象、字段和事件定义。

### 阶段 B：最小事件管道

交付物：
- 一个或两个连接器；
- 事件网关和标准化组件；
- 幂等去重、时间语义和错误队列；
- 事件账本与来源登记；
- 基础审计和人工纠错入口。

进入下一阶段的条件：事件可重放、可去重、可追溯，源数据权限检查有效。

### 阶段 C：对象、关系与状态引擎

交付物：
- 业务对象注册表；
- 源系统 ID 映射；
- 关系模型；
- 状态断言与状态投影；
- 冲突、过期和未知识别；
- 对象时间线查询。

进入下一阶段的条件：关键对象映射和权威状态一致性达到试点阈值。

### 阶段 D：上下文服务与 Agent 接入

交付物：
- Context Package API；
- 上下文最小化与权限策略；
- Agent 只读查询工具；
- 动作意图、审批和审计机制；
- 上下文包过期、撤销和版本机制。

进入下一阶段的条件：Agent 的实际使用可追溯，未授权访问和未审批写入被阻断。

### 阶段 E：跨流程复用与能力资产化

交付物：
- 能力资产目录；
- 适用范围和验证案例；
- 跨团队复用评估；
- 版本兼容和弃用机制；
- 业务价值与治理成本评估报告。

进入规模化的条件：复用效果在第二个真实场景中得到独立验证。

## 13. 关键架构决策（ADR）建议

| ADR | 决策主题 | 建议结论 | 待评审事项 |
|---|---|---|---|
| ADR-01 | 事件记录模式 | 事件追加式保存，更正通过新事件表达 | 是否需要事件溯源与重放到何种程度 |
| ADR-02 | 统一标识 | 上下文 ID 与源系统 ID 分离，保留映射历史 | ID 生成与跨企业标识规范 |
| ADR-03 | 状态表达 | 采用状态断言，显式区分有效时间和记录时间 | 各业务领域状态模型 |
| ADR-04 | 权威来源 | 按对象类型和属性配置权威来源 | 权威字段责任目录 |
| ADR-05 | 不确定性 | 确认、观察、推断、冲突、过期和未知为一等状态 | 置信度与人工确认阈值 |
| ADR-06 | Agent 上下文 | 使用不可变、可撤销、短时有效的任务级上下文包 | TTL、刷新和撤销传播 |
| ADR-07 | 存储策略 | 统一逻辑模型，不预设统一物理数据库 | 试点规模下的技术选型 |
| ADR-08 | 跨层共享 | 目录元数据优先，内容按需受控访问 | 联邦查询和跨域授权流程 |
| ADR-09 | 证据策略 | 优先受控引用，按必要性保存副本 | 证据留存与合规要求 |
| ADR-10 | 高风险动作 | 先建议、再审批、后执行；保留审计和回滚 | 风险分级和审批矩阵 |

## 14. 主要风险与验证重点

| 风险 | 后果 | 设计控制 |
|---|---|---|
| 统一模型过度抽象 | 无法适配具体业务语义 | 公共核心模型 + 领域扩展，不追求所有领域一个大 schema |
| 事件模型过度复杂 | 接入成本过高 | 从少量高价值事件开始，按版本渐进扩展 |
| 对象匹配错误 | 错误关联导致错误推断 | 匹配状态分级、高影响对象人工确认 |
| 状态引擎误判 | 错误业务结论 | 权威字段配置、冲突保留、未知状态 |
| 上下文包过宽 | 数据泄露与模型污染 | 最小范围、字段级策略、TTL 和审计 |
| 原始证据集中复制 | 权限和保留风险扩大 | 受控引用优先、按需取证 |
| Agent 错误写回 | 业务状态被错误修改 | 动作意图、审批、幂等、回滚和责任确认 |
| 过度依赖模型 | 不稳定和难以复现 | 规则、模型、人工确认分工；版本化与评测 |
| 新平台成为数据孤岛 | 重复主数据和系统耦合 | 源系统权威、开放接口、映射和可迁移性 |

### 14.1 关键验证问题

1. 统一事件模型能否覆盖首个试点的关键业务变化，而不强迫源系统改变？
2. 对象身份解析在真实数据中的准确率是否足够？
3. 状态引擎能否明确解释当前状态的来源、时间和不确定性？
4. 上下文包是否真的比直接检索多个系统更准确、更安全、更省时？
5. 业务人员是否愿意确认和纠正系统生成的事件与关系？
6. 能力资产能否在另一个团队或项目中独立复用？
7. 单流程的模型、连接器、存储、治理和人工核验成本是否可接受？

|---|---|---|

**工作感知入口 → 个人工作记忆 → 受控资产转化 → 企业工作上下文 → 运行认知引擎 → 任务级上下文服务 → 企业 Agent 协同。**

## 16. 结论与下一步

本设计建议把企业工作上下文基础设施拆解为可实施的三项工程能力：

1. **统一数据模型：** 先定义事件、对象、关系、状态、决策、任务、证据和上下文包。
2. **运行认知引擎：** 再建设事件处理、对象解析、语义映射、状态重建、冲突检测和上下文组装。
3. **上下文服务平面：** 最后通过受控 API 向 Agent 和业务应用提供任务级上下文与受控动作接口。

建设顺序应坚持“小模型、单流程、权威源、可追溯、先只读、再受控写入”。不要一开始就追求全企业知识图谱、全员持续采集或全自动 Agent。

### 建议的下一项工程工作

选择一个真实项目交付流程，完成一套最小可执行的设计包：

- Project / Task / Decision / Risk / Evidence 五类对象的 JSON Schema；
- 8—10 种事件类型的 Schema；
- 一个权威项目系统字段映射表；
- 对象身份解析和状态重建规则；
- Context Package 的请求与响应 Schema；
- 只读 API 原型和一组可重复的验收测试。

这套设计包通过业务、ADS 架构和安全评审后，再进入原型实现。

**最终目标不是再建一个知识库，而是让企业拥有一套可计算、可追溯、可治理的运行上下文基础设施，使企业 Agent 在正确的业务事实、正确的权限和正确的责任边界内开展工作。**

## 附录 B：建议的第一批验收测试

1. 同一源事件重复投递两次，只形成一条有效业务事件。
2. 迟到事件到达后，状态视图可重算并保留重算前后版本。
3. 同一业务对象在两个源系统中的 ID 可映射到一个上下文对象，并保留来源。
4. 模糊匹配不确定时，系统进入待确认，不自动合并。
5. 权威系统状态与会议推断冲突时，系统显示冲突，不覆盖权威值。
6. 超过新鲜度阈值的状态被标记为过期或待刷新。
7. 未授权 Agent 无法生成包含受限字段的上下文包。
8. 上下文包撤销后，后续读取被阻断，相关缓存失效。
9. Agent 的高风险写操作在未审批时不能执行。
10. 每次 Agent 输出都能追溯到实际使用的上下文包、来源和策略版本。
11. 证据来源失效时，系统能识别依赖该证据的结论并触发复核。
12. 个人侧授权撤回后，企业侧按规则限制、删除或重算派生内容，并保留必要的合规审计记录。

## 附录 C：术语表

| 术语 | 定义 |
|---|---|
| 工作事件（Work Event） | 对业务活动、状态变化或工作过程的结构化记录 |
| 业务对象（Business Object） | 企业业务中具有稳定身份的对象 |
| 状态断言（State Assertion） | 对对象属性在特定有效时间内取值的可追溯表达 |
| 证据引用（Evidence Ref） | 指向支持事实或判断的来源与核验位置 |
| 运行认知引擎（Runtime Context Engine） | 负责关联事件、对象、状态、关系并生成上下文的处理能力 |
| 上下文包（Context Package） | 为特定任务和调用主体生成的最小必要信息集合 |
| 权威来源（System of Record） | 对某类业务对象或属性具有正式记录责任的系统 |
| 共同本体（Common Ontology） | ADS 跨领域共享的基础概念和关系语义 |
| 领域本体（Domain Ontology） | 特定业务领域的专业概念、属性和规则 |
| 能力资产（Capability Asset） | 经验证、版本化并明确适用范围的流程、规则、模板或 Skill |
