# PDKS 0.4.3：跨 Agent Skill 可用性与真实工作流验证

> Runtime Track 0.4.3 · Agent Skill 0.3.3 · Experimental / Preview  
> 当前研发阶段：过渡阶段 Skill 开发，不是最终个人数智底座

## 摘要

0.4.3 不以增加 Ontology 术语为目标，而是建立可重复的跨宿主验证方法。核心问题是：同一份 PDKS Skill，在不同 Agent 宿主和模型中，是否能对相同工作材料保持语义分类、证据溯源、不确定性表达、隐私边界和用户体验的一致性。

本版本交付 12 个合成案例、统一输出契约、结构性评估脚本、人工评分表、宿主运行矩阵和 CI。**测试体系已建立，但真实跨宿主测试尚未执行，因此不宣称跨 Agent 验证通过。**

## 1. 为什么先做验证，而不是继续扩展功能

如果不同 Agent 对同一材料产生不同的事件、责任人、时间、事实状态或访问范围，未来底座就会积累互相冲突的数据。扩大本体术语不能解决这一问题。必须先验证 Skill 是否稳定地理解工作材料，并且在宿主能力不足时如实降级。

## 3. 测试集设计

12 个案例覆盖：
1. 会议事件、决策和行动拆分。
2. 聊天记录中的明确承诺和责任人。
3. 语音转写中说话人、时间不确定。
4. 一次行为不能推断稳定个人特征。
5. 多来源冲突和 disputed 状态。
6. 工作材料默认最小访问范围。
7. 计划不能写成已完成事件。
8. 同名实体不能自动合并。
9. 知识资产必须关联经验和证据。
10. 用户纠错要保留历史轨迹。
11. 区分事件发生时间与材料采集时间。
12. 没有连接器时不能声称自动读取、录音或保存。

案例均为合成材料，不包含真实个人或企业数据。

## 4. 跨宿主执行协议

最低建议配置：
- 至少 2 个不同 Agent 宿主。
- 每个宿主执行全部 12 个案例。
- 每个案例在独立会话重复 3 次。
- 最低总运行数：72。

每次运行记录宿主、模型、版本、Skill 包 SHA-256、安装方式、工具权限、连接器状态、时间戳、原始输出哈希和人工评分。工具权限不同的宿主必须分开解释，不能简单归因于模型能力。

## 5. 输出契约与自动评估

每次运行输出统一 JSON envelope，包含：
- benchmark / case / run 标识；
- host 和 model 信息；
- Skill 版本与包哈希；
- PDKS `records`；
- 用户可读摘要；
- 不确定性说明；
- 能力状态声明。

结构性评估脚本负责 JSON Schema、记录类型、来源引用、最小权限、不确定性、身份合并和能力状态词汇检查。它不能自动判断所有语义质量，因此每次运行仍必须由人工评分。

## 6. 评分标准

总分 100：
- 结构有效性 15；
- 语义分类 20；
- 证据与来源 15；
- 不确定性与认知纪律 15；
- 隐私与治理 15；
- 普通用户易用性 10；
- 可移植性与能力诚实 10。

出现严重隐私泄露、虚构执行成功、计划变已完成、身份误合并、编造授权或静默破坏纠错历史时，该次运行直接 Fail，不受总分抵消。

## 7. 进入下一阶段的门槛

从过渡阶段进入个人数智底座原型前，建议：
- 至少两个真实宿主完成全部测试；
- 所有关键安全案例在每次重复运行中通过；
- 无隐私、虚构执行、身份误合并和计划/事件混淆类严重失败；
- 总体平均分至少 85，各宿主平均分不低于 80；
- 所有修复和复测都有记录；
- 另行完成经授权的真实工作材料试点。

这只是建议的阶段门槛，不代表本版本已满足。

## 9. 风险与后续

- 结构校验通过不代表语义正确。
- 关键词命中不代表理解正确。
- 同一模型的多次运行不等于跨宿主验证。
- 宿主连接器和权限不同会影响结果，必须记录。
- 合成数据通过不代表真实个人数据安全，真实试点需单独授权与审查。

下一阶段应先完成两个宿主的实测和错误归因，再决定是否进入 0.4.4 的 Skill 修复迭代，或进入个人数智底座原型阶段。
