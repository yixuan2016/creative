# PDKS 0.4.2：过渡阶段 Skill 工程定位、能力边界与演进路线

> 版本：PDKS Runtime Track 0.4.2 / Agent Skill 0.3.2  
> 成熟度：Experimental / Preview  
> 文档性质：研发阶段定义与工程约束，不是最终标准

## 摘要

PDKS 当前处于从个人知识管理 Skill 向个人数智底座原型演进的过渡阶段。0.4.2 的主要任务不是宣称底座已经建成，而是把 Skill 工程做扎实：明确它能做什么、依赖什么宿主能力、哪些只是本地参考原型、哪些仍未实现；同时保持既有标准和 Ontology 基线稳定，为后续多源工作感知、持续上下文和跨域语义协同留下可验证的演进接口。

本轮将 Skill 升级到 0.3.2，PDKS 标准 0.1.0、JSON Schema 0.1.x、Ontology 0.2.1、Event Taxonomy 0.1.0 均保持不变。个人、企业、中心 Ontology 的分层只作为研究提案，不引入正式类、属性或跨域数据流。

## 1. 为什么要强调“过渡阶段”

Skill 与数智底座不是同一层级的交付物。Skill 是 Agent 的行为规范、工作流和资源包；数智底座还需要持续数据入口、可靠持久化、索引检索、权限治理、生命周期管理、跨设备能力和真实系统连接。仅仅具备 Skill 文件、SQLite 原型和 RDF 投影，并不能证明这些平台能力已经完成。

因此，0.4.2 把“阶段定位”写入 Skill 主入口、机器可读配置、测试和发布文档，防止后续研发过程中把概念设计、接口定义和局部原型误报为产品能力。

## 3. 能力状态模型

必须使用以下状态表达能力：

- `available_in_skill`：指令本身可用，可处理用户主动提供的材料。
- `prototype_local`：本地参考代码存在，需要操作者和本地环境。
- `prototype_partial`：部分流程可运行，但端到端能力不完整。
- `host_dependent`：依赖宿主 Agent 的工具、连接器、权限和运行环境。
- `not_implemented`：当前未实现。
- `future_research`：未来研究方向。

### 当前能力矩阵

| 能力 | 状态 | 说明 |
|---|---|---|
| 分析用户提供文本 | Skill 可用 | 不需要外部连接器 |
| 生成 PDKS 候选记录 | Skill 可用 | 需要区分事实、陈述和推断 |
| 读取授权文件 | 宿主依赖 | 需要宿主实际提供文件工具 |
| SQLite 持久化 | 本地原型 | 不等于云端个人记忆服务 |
| Ontology 映射 / RDF 投影 | 本地原型 | 可由本地脚本验证 |
| SHACL 校验 | 宿主/依赖环境 | 缺依赖必须报告 unavailable |
| 钉钉原生连接器 | 未实现 | 不能假定可读取钉钉 |
| 录音卡/设备集成 | 未实现 | 不含硬件、固件或原生 App |
| 后台持续采集 | 未实现 | 不允许暗示自动监听 |
| 正式 Consent / Policy Service | 未实现 | 示例 consent_ref 不是真实授权 |
| 生产级密钥管理与加密 | 未实现 | 不得存放真实敏感数据于公开仓库 |
| 跨系统迁移 | 部分原型 | 映射、权限和回执仍需完善 |
| 企业/中心 Ontology Runtime | 未来研究 | 目前只有概念提案 |

## 4. Skill、宿主 Agent 与底座的职责分离

### Skill 负责
- 指导 Agent 理解来源材料。
- 抽取事件、断言、行动、知识和上下文。
- 组织证据、时间、来源和不确定性。
- 将候选记录映射到既有标准。
- 提供校验、纠错、导出和迁移流程指引。

### 宿主 Agent 负责
- 提供模型、文件访问、应用连接器、数据库、执行环境和自动化工具。
- 提供真实的权限确认和执行回执。
- 限定可读取、可写入和可执行的范围。

### 未来个人数智底座负责
- 多源持续感知与事件账本。
- 个人长期上下文和知识资产。
- 检索、纠错、版本、撤回、删除和数据可携带。
- 个人数据主权和可审计治理。

三者不能混为一谈。Skill 安装成功不代表宿主已经拥有相应数据连接或持久化能力。

## 5. 个人、企业、中心 Ontology 的研究假设

不建议把三者设计成简单的单向继承树。初步研究模型是：

**Shared Semantic Core + Scope-specific Extensions + Mapping Contracts + Governance / Policy Plane**

- Shared Core：表达通用的人、事件、来源、证据、断言、行动、知识、时间和溯源语义。
- Scope Extensions：个人、企业、中心分别扩展自身业务概念与约束。
- Mapping Contracts：定义跨域映射、脱敏、聚合、目的、授权引用、来源和损失报告。
- Governance / Policy Plane：由真实授权与策略服务决定数据能否被读取、转换和共享。

关键结论：
1. 共享概念不等于共享数据。
2. 同一会议可以在个人与企业视角形成不同记录。
3. 个人原始录音、私人对话和个人上下文默认不向组织共享。
4. 中心层优先使用经过授权的聚合、脱敏和标准化结果。
5. 组织层级不自动构成授权链。
6. Ontology 描述语义，不自行授予访问权限。

本轮不新增正式 Ontology namespace、OWL 类或属性，不实现跨域同步服务。

## 7. 阶段退出标准

从过渡阶段进入个人数智底座原型阶段前，应满足：
- 至少两个宿主 Agent 环境完成安装、调用和一致性验证。
- 典型工作场景的来源、证据、时间和不确定性可追溯。
- 重复导入、纠错、撤回、删除和导出有可重复测试。
- 连接器权限、持久化回执和授权撤回路径明确。
- 有真实试点数据的隐私与质量评估。
- 用户能理解、修正和撤销 Agent 生成的上下文。

这些是未来退出条件，不是 0.4.2 已经达成的成果。

## 8. 验证方式

```bash
python skills/pdks-personal-knowledge/scripts/validate_skill_stage.py --json
python -m unittest discover -s tests -v
python prototype/pdks_ontology_cli.py ontology-check
python skills/pdks-personal-knowledge/scripts/build_ontology_manifest.py --check
```

SHACL 运行时需要 pySHACL。依赖缺失时应标记为 unavailable / skipped，不得视为符合。

## 9. 风险与后续研究

当前最大风险不是 Ontology 术语不够多，而是把“数据理解能力”误认为“持续感知能力”，把“本地可运行”误认为“生产可用”，把“语义映射”误认为“跨组织数据共享”。下一阶段应先通过不同宿主、不同工作场景的实测，验证 Skill 是否真的能稳定理解用户在做什么，再逐步推进个人数智底座原型。
