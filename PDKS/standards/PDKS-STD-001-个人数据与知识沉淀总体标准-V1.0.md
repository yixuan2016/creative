# PDKS-STD-001：个人数据与知识沉淀总体标准

**版本：** V1.0 评审稿  
**状态：** 标准评审稿，不代表全部工程能力已经实现或通过生产验收  
**适用对象：** PDKS 标准、运行时、连接器、Agent Skills、个人知识库与个人数智底座相关实现

## 1. 标准定位

PDKS（Personal Data & Knowledge Sedimentation System，个人数据与知识沉淀体系）是面向个人工作与生活数据的持续采集、语义理解、知识加工、可信存储、检索应用与生命周期治理基础设施。

PDKS 不等同于笔记软件、聊天记录归档器或单一 Agent 的长期记忆。它需要将分散在不同应用、设备和活动中的原始资料，转化为可追溯、可验证、可关联、可迁移、可被多个 Agent 使用的个人数据与知识资产。

本标准规定 PDKS 的数据采集、接入、记录结构、事件语义、知识分类、提炼、质量、存储、安全治理和生命周期要求，并为 Skills 与运行时提供统一契约。

### 1.1 与现有系统的关系

| 系统 | 定位 | 与 PDKS 的关系 |
|---|---|---|
| PDKS | 个人数据与知识沉淀基础设施 | 负责个人数据资产的采集、加工、保存和供给 |
| Personal AI Life OS | 个人智能操作系统 | 消费 PDKS 提供的可信个人上下文，进一步进行理解、规划、管理和受控行动 |
| ADS 个人数智底座 | 个人级数智资产与运行基础 | PDKS 是个人知识与数据资产的重要形成机制，不等同于完整个人数智底座 |
| ADS 企业数智底座 | 企业业务数据与协同数智资产 | 仅接收经过授权、映射、治理和验证的适用数据，不直接读取个人原始资料 |
| ADS 智能生态系统中心数智底座 | 跨领域共同语义、治理与协同能力 | 通过受控标准和语义映射提供跨域互操作，不汇集无授权的个人私有上下文 |

### 1.2 现有兼容基线

本文件是总体规范，不自动修改已有机器可读资产。当前 PDKS 0.5.3 预览版的兼容基线为：

- Record Schema：0.1.x
- Event Taxonomy：0.1.0
- Ontology：0.2.1
- 稳定术语命名空间：`urn:pdks:ontology#`
- Ontology Version IRI：`urn:pdks:ontology:0.2.1`

任何对已冻结术语、字段含义、枚举或约束的变更，都必须提供版本变更说明、兼容性分析、迁移映射、验证和回滚方案。不得因本文件发布而静默改变既有数据含义。

## 2. 规范性用语

- **必须 / MUST：** 强制要求；不满足不得宣称符合本标准。
- **不得 / MUST NOT：** 明确禁止。
- **应 / SHOULD：** 通常应当执行；偏离时必须说明理由和风险。
- **可以 / MAY：** 可选能力。
- **候选知识：** AI 或规则引擎从素材中提取、尚未完成必要核验或用户确认的知识。
- **证据：** 能够定位到原始来源、内容片段、时间戳或文件版本的可追溯依据。
- **个人事实：** 有明确来源和适用时间，并达到相应确认门槛的事实性断言；不得把模型推断直接标记为已确认事实。

## 3. 总体设计原则

1. **个人自主控制：** 用户拥有数据访问、授权、保留、导出、撤回和删除的最终控制权。
2. **来源优先：** 原始来源和证据优先于 AI 摘要；摘要不得替代原始证据。
3. **本地优先、可迁移：** 数据应保存在用户可访问、可备份、可导出的目录和格式中；云服务为可选能力。
4. **统一标准、多 Agent 复用：** 不同 Agent 使用同一记录结构、事件语义和存储契约，不建立彼此割裂的知识库。
5. **采集与授权分离：** 安装、初始化或加载 Skill 不代表用户同意连接数据源或开始采集。
6. **事实与推断分离：** 明确声明、观察、模型推断、假设和待核实信息必须可区分。
7. **增量、幂等、可恢复：** 重复执行不得产生重复资产；中断后应能从检查点恢复。
8. **可解释、可纠错：** 每项重要知识应能回溯来源、处理过程、版本和状态。
9. **最小化采集：** 只采集完成明确目的所需的数据，支持来源级范围控制。
10. **语义与权限分离：** 本体关系不构成授权；所有读取、共享和外部动作均由独立权限策略控制。

## 4. PDKS 总体架构

PDKS 采用分层、模块化结构：

1. **数据源层：** 钉钉、邮件、日历、会议音频、文档、本地文件、浏览器、AI 对话、任务系统及经授权的个人生活数据。
2. **连接器层：** 负责身份验证、授权范围、增量读取、分页、检查点、错误恢复、撤销和来源元数据。
3. **采集与证据层：** 保存原始文件或原始记录引用、来源标识、内容哈希、采集时间和采集批次。
4. **标准化层：** 将不同来源映射为统一记录信封，不丢失来源特有字段和原始定位信息。
5. **语义理解层：** 提取主体、事件、对象、关系、事实断言、决策、任务、承诺和时间状态。
6. **知识加工层：** 分类、摘要、关联、去重、冲突检测、质量评估和候选知识管理。
7. **存储与索引层：** 保存原始资料、结构化记录、知识资产、证据索引和检索索引。
8. **应用与 Agent 层：** 通过统一 API、MCP 工具和 Skills 提供采集、检索、复盘、上下文构建和知识发布能力。
9. **治理层：** 横向执行身份、授权、敏感级别、用途限制、审计、保留和删除策略。

以上是逻辑架构，不要求每一层独立部署。早期版本可以采用本地模块化单体。

## 5. 十项标准要求

### 5.1 数据采集标准

采集对象包括但不限于：

| 来源类别 | 典型数据 | 采集注意事项 |
|---|---|---|
| 协同消息 | 钉钉私聊、群聊、@、回复 | 区分本人负责、本人参与、相关知晓；保留会话与消息 ID |
| 邮件 | 收发邮件、附件、线程 | 保留发件人、收件人、时间、线程和附件引用 |
| 日历 | 会议、日程、提醒 | 区分计划时间与实际发生时间 |
| 会议与语音 | 录音、转写、发言人、时间戳 | 原音频与转写分开管理；标注识别不确定性 |
| 文件与文档 | PDF、Word、Excel、Markdown、图片、代码 | 保留文件哈希、路径、版本和页码/段落定位 |
| 浏览器与网页 | 网页、文章、资料、引用 | 保留 URL、标题、作者/站点和采集时间 |
| AI 对话 | 用户输入、模型输出、工具结果 | 区分用户表达、模型生成和工具返回 |
| 任务与项目 | 任务、状态、负责人、交付物 | 保留任务系统 ID 和状态变更历史 |
| 个人生活 | 经授权的生活事件、计划和观察 | 敏感类别单独授权，默认不采集高敏感内容 |

每个连接器必须声明：来源类型、身份方式、授权范围、可读取对象、增量游标、分页能力、历史回补能力、速率限制、错误码、撤销方式、保留策略和已知限制。

采集必须支持增量、幂等、断点续采、重试、重复识别和可审计运行记录。不能实现的能力必须明确标注，不得伪装为已支持。

### 5.2 数据接入标准

所有连接器必须通过统一接入契约向 PDKS 提交记录。连接器不得直接写入彼此独立的知识库，也不得绕过授权与治理层。

每个来源应有唯一的 `source_id`；来源中的原生记录应保留 `source_record_id`。同一来源记录的重抓必须能够识别为同一记录或新版本，不得简单按正文相似度覆盖。

连接器运行状态至少包括：未配置、待授权、已授权、运行中、部分失败、失败、已暂停、已撤销。

### 5.3 数据结构标准

每条标准记录至少应包含以下逻辑字段。具体字段名、类型和必填性以当前 Record Schema JSON Schema 为准：

| 字段组 | 逻辑字段 | 要求 |
|---|---|---|
| 身份 | record_id、record_type、schema_version | 全局唯一、类型明确、版本明确 |
| 来源 | source_id、source_record_id、source_uri | 可追溯到原始来源 |
| 时间 | occurred_at、captured_at、recorded_at、timezone | 区分发生时间、采集时间和入库时间 |
| 内容 | content_ref、content_hash、summary | 原文与摘要分离，避免重复复制大文件 |
| 主体 | actor、participants、entity_refs | 能识别个人、参与者和相关实体 |
| 语义 | event_type、relations、domain | 采用受控词汇或明确标注未映射 |
| 证据 | evidence_refs、evidence_locator | 重要事实和决策必须能定位依据 |
| 认知状态 | epistemic_status、confidence | 区分明确、观察、推断、假设和核验状态 |
| 治理 | sensitivity、consent_scope、retention | 可执行访问、用途和保留控制 |
| 生命周期 | lifecycle_status、supersedes、deleted_at | 支持更新、替代、过期和删除 |
| 处理 | processor、processed_at、processing_version | 记录加工工具与规则版本 |

时间字段不得混用：`occurred_at` 表示事件实际发生时间；`captured_at` 表示采集时间；`recorded_at` 表示系统登记时间；`valid_from/valid_to` 表示事实或状态的有效区间。未知时间应明确为空或未知，不得伪造精确时间。

### 5.4 事件本体标准

事件是连接原始资料与个人世界模型的重要语义单元。事件描述“在某个时间和情境中，哪些主体参与了什么活动，作用于什么对象，产生了什么结果”。

事件提取至少考虑：

- 事件身份与类型；
- 发生时间、持续时间和时间精度；
- 参与主体、角色和组织；
- 相关项目、目标、任务和对象；
- 活动、原因、上下文和触发因素；
- 决策、承诺、行动、结果和后续影响；
- 证据引用、提取方式和置信信息；
- 事件状态、有效性和关联事件。

工作事件与个人生活事件可以有不同领域扩展，但必须复用共同的事件身份、时间、主体、证据和关系语义。不得把一条聊天消息直接等同于一个完整事件；同一事件可以由多条消息、会议、文件和任务状态共同证明。

事件类型以 Event Taxonomy 0.1.0 为兼容基线。新增类型应提供定义、正反例、父类、适用范围、映射关系和版本说明。

### 5.5 知识分类标准

建议采用多轴分类，不以单一文件夹或单一标签承载全部语义：

**按知识内容分类：**

- 事实知识：可核验的客观信息。
- 事件知识：工作和生活中实际发生的活动与状态变化。
- 决策知识：决策内容、理由、约束和结果。
- 任务与承诺知识：责任、期限、依赖和履行状态。
- 项目知识：项目背景、过程、成果和风险。
- 经验知识：从实际执行中总结的经验与教训。
- 方法知识：可重复执行的流程、步骤和技巧。
- 关系知识：人员、组织、项目、目标和资源之间的关系。
- 偏好与习惯候选：从表达或行为中观察到、尚待确认的稳定模式。
- 创新知识：创意、假设、问题定义和待验证方向。

**按个人领域分类：** 工作、学习、健康与生活、家庭与关系、财务、兴趣、成长及其他个人领域。领域目录可配置，不能限制新领域扩展。

**按认知状态分类：** 用户明确声明、来源观察、规则推导、模型推断、待核实假设、已验证、存在争议、已被替代。

### 5.6 知识提炼标准

从素材到知识必须经过可追溯的加工链：

`原始资料 → 标准记录 → Observation / Event → 候选断言与知识 → 证据核验 → 确认或发布 → 持续更新`

提炼规则：

1. 摘要不得改变原文含义，不得补造参与者、时间、结果或因果。
2. 事实、推断、假设和建议必须分开表达。
3. 重要结论必须附证据引用；音视频应附时间戳，文档应附页码/段落，消息应附消息 ID 或会话定位。
4. 多来源信息应分别记录来源，不得把模型综合结论伪装成单一来源原话。
5. 决策应尽量保留决策背景、备选方案、约束、理由、责任主体和后续结果。
6. 经验知识应保留适用场景、前提、失败条件和反例，不得仅凭单次成功宣称普遍有效。
7. 用户未确认的个人偏好、健康、关系、财务等敏感推断不得升级为长期确认事实。
8. AI 无法确定时应输出待确认项，而不是猜测填满字段。

### 5.7 知识质量标准

质量评估应采用多维度指标，不得只用一个模型置信度代表真实性。

| 维度 | 评价问题 |
|---|---|
| 来源可信度 | 来源是否明确、可靠、可验证？ |
| 证据完整性 | 是否保留足够的原始定位信息？ |
| 时间准确性 | 发生时间、采集时间和有效时间是否区分？ |
| 语义完整性 | 主体、动作、对象、结果和上下文是否足够？ |
| 事实确定性 | 是明确事实、观察还是推断？ |
| 一致性 | 是否与既有记录冲突或重复？ |
| 时效性 | 内容是否可能已经过期？ |
| 可复用性 | 是否有明确适用范围、步骤和边界？ |
| 治理合规性 | 是否符合授权、用途和敏感级别要求？ |

质量结果应保留各维度状态、缺失项和评估版本。低质量记录可以进入待处理区，但不得静默发布为高可信知识。

### 5.8 存储与交换标准

采用 File-first、可迁移、可读写分离的存储策略：

| 资产 | 推荐承载 | 说明 |
|---|---|---|
| 原始文档、音频、图片等 | 用户控制的文件目录 / 内容寻址文件库 | 保留原件、哈希和来源信息 |
| 人类可读知识 | Markdown + YAML Frontmatter | 兼容 Obsidian 和普通编辑器 |
| 原始记录与证据索引 | JSON / JSONL | 便于机器处理和交换 |
| 运行任务、检查点和事务状态 | SQLite（运行时启用时） | 作为对应运行时的权威操作存储 |
| 语义定义 | OWL/RDF、SHACL、JSON-LD、受控词表 | 定义概念、约束和交换语义 |
| 检索索引 | FTS / 可选向量索引 | 可重建，不作为唯一事实来源 |

必须明确不同存储资产的权威边界。不得同时维护两套可写权威事实库。Obsidian 是知识文件的查看和编辑入口，不是 PDKS 唯一的数据模型。当前 File Store Adapter 0.1.0 为单向投影，不得宣传为双向同步。

导出应支持 Markdown、JSON/JSONL、原始附件和语义资产；应包含版本、来源映射和必要的证据引用。

### 5.9 安全与授权标准

敏感等级建议统一为：

| 等级 | 含义 | 示例与要求 |
|---|---|---|
| P0 | 公开 | 可公开分享的资料 |
| P1 | 普通个人数据 | 一般工作笔记、普通个人记录 |
| P2 | 敏感个人数据 | 私人沟通、个人关系、财务或健康相关信息 |
| P3 | 高敏感数据 | 认证凭据、密钥、极高敏感内容；默认禁止进入普通知识采集链 |

等级最终应与现有 Ontology/Record Schema 枚举兼容，不得自行引入不兼容枚举。

每个数据源必须单独授权，授权至少明确：数据范围、用途、采集频率、历史回补、保留期限、可访问 Agent 和撤销方式。安装 PDKS、初始化 Vault 或启用某个 Skill 不代表授权任何数据源。

Agent 只能访问当前任务所需且被授权的上下文。跨 Agent、跨设备、跨组织共享必须显式授权并记录审计。语义关系、数据存在或用户曾经提供信息，均不构成向外部系统传输的许可。

**当前预览版安全限制：** GitHub 当前记录的 PDKS 0.5.3 预览版 Vault 文件尚未实现静态加密。未完成加密、密钥管理和安全审查前，只能使用合成或非敏感数据，不得把 P2/P3 数据导入该预览版。不得在聊天、Skill 参数或普通日志中收集密码、OAuth Token、API Key、私钥或支付凭据。

### 5.10 知识生命周期标准

标准生命周期：

`Captured → Normalized → Candidate → Reviewed → Confirmed / Published → Updated / Superseded / Expired → Archived / Deleted`

- 原始证据原则上不可被摘要覆盖；需要修正时创建新版本或关联修正记录。
- 冲突信息必须并存并标记冲突，不得静默覆盖历史断言。
- 事实和偏好应支持有效时间、过期和替代关系。
- 删除请求应覆盖索引、派生内容、缓存和受控备份策略；无法立即物理删除时必须标记删除状态并说明残留边界。
- 来源授权撤销后，应停止后续采集，并按授权与保留政策处理已有副本。
- 重要加工和发布过程必须保留版本、操作者/Agent、时间和结果记录。

## 6. 个人知识向 ADS 的受控流转

PDKS 形成的个人知识不自动成为企业标准数据。进入企业数智底座之前，至少必须完成：

1. 用户明确授权具体数据、用途、接收方和有效期限；
2. 识别个人数据、第三方数据、企业数据及其权利边界；
3. 根据 ADS 共同本体和目标领域本体进行语义映射；
4. 完成去标识化、最小化和必要的敏感信息处理；
5. 由相应领域责任方验证语义、质量和业务适用性；
6. 完成企业侧治理审批、血缘登记和撤回机制；
7. 记录映射版本、证据和接收结果。

任何个人私有记忆、私人关系或生活数据不得因为与工作相关就自动上传企业或中心底座。

## 7. 质量指标与运行度量

PDKS 至少应度量：

- 来源接入覆盖率与授权有效率；
- 采集成功率、增量延迟、失败恢复率；
- 重复记录率与幂等执行成功率；
- 原始来源可追溯率；
- 重要断言证据覆盖率；
- 事件抽取准确率、漏提率和误提率；
- 候选知识确认率、纠错率和过期率；
- 检索命中率、引用准确率和用户采纳率；
- 数据导出完整性、删除执行率和权限违规数。

指标必须注明样本范围、评估集和统计口径，不得只报告模型自评。

## 8. 符合性与验收

实现只有在同时满足以下条件时，才可以声明符合本标准的相应范围：

- 记录结构通过对应 JSON Schema 校验；
- 事件和关系符合当前兼容本体及受控词汇；
- 重要知识具有可定位证据；
- 候选、确认、冲突、过期和删除状态可区分；
- 采集具备授权、增量、幂等和可恢复能力；
- 文件、数据库和语义资产的权威边界明确；
- Agent 访问遵守用途和最小权限；
- 通过 Skills 技术规范及验收矩阵中的适用测试；
- 未完成的安全、跨平台或真实来源验证项被明确披露。

本文件发布本身不等于 PDKS 0.5.3 已经符合全部条款。

## 9. 版本与变更治理

标准分为总体规范、记录 Schema、事件分类、Ontology、Skills 契约和运行时 API 等独立版本。各自升级，但必须维护兼容矩阵。

任何破坏性变更必须包含：变更原因、受影响字段/术语、旧新版本映射、样例、迁移脚本、dry-run 报告、完整性验证、回滚方案和消费者兼容说明。新增领域词汇不得未经治理直接修改 Core Ontology。

## 10. 实施路线建议

1. **规范对齐：** 冻结现有 Schema 0.1.x、Taxonomy 0.1.0、Ontology 0.2.1 的兼容关系，补齐字段字典和示例。
2. **首个垂直闭环：** 以本地文件和钉钉 DWS 为首批来源，完成授权、采集、证据、事件提取、知识候选、归档和检索。
3. **质量与治理：** 完成冲突、纠错、生命周期、权限、撤销、备份和恢复。
4. **多源扩展：** 按优先级增加邮件、日历、会议、浏览器和 AI 对话连接器。
5. **跨 Agent 互操作：** 在 Codex、WorkBuddy、Claude 等宿主上验证相同 Skill 契约和同一 Vault。
6. **与 PALOS / ADS 集成：** 通过稳定 API 和语义映射提供个人上下文与经治理的标准数据。
