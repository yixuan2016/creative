# 个人—企业—中心 Ontology 分层扩展研究提案

> 状态：研究提案（Experimental Proposal），不是正式标准
> 对应版本：PDKS 0.4.2 / Skill 0.3.2
> 稳定基线：PDKS Ontology 0.2.1（本轮不修改）

## 1. 研究问题

个人数智底座、企业数智底座和中心数智底座需要共享部分语义，但三者的数据所有权、业务目的、管理责任、访问权限和数据粒度不同。若简单采用“个人 Ontology 继承企业 Ontology、企业 Ontology 再继承中心 Ontology”，容易造成数据权属混淆和未经授权的跨域传播。

本提案暂定采用：

**共享语义核心 + 作用域扩展模块 + 独立治理/策略边界 + 显式映射与转换契约。**

## 2. 四个逻辑部分

| 部分 | 职责 | 当前状态 |
|---|---|---|
| Shared Core | Person、Event、Source、Evidence、Assertion、Action、Knowledge、Time、Provenance 等通用语义 | 现有 PDKS Ontology 0.2.1 的研究基线 |
| Scope Extension | Personal / Enterprise / Center 各自扩展概念、关系和业务约束 | 研究提案 |
| Mapping Contract | 说明跨作用域如何映射、转换、脱敏、聚合、保留来源及报告损失 | 研究提案 |
| Governance & Policy | 规定数据主体、控制者、目的、授权、保留期限、访问与撤回 | 需要真实策略服务，当前未实现 |

## 3. 三种作用域的边界假设

### Personal Scope
- 以个人为数据主体和个人数据空间的主要控制者。
- 包含个人工作事件、学习、思考、生活、关系、目标、能力和个人知识。
- 原始录音、私人对话和个人上下文默认不向组织共享。
- 对外提供的应是经过选择、最小化和授权的工作相关派生结果。

### Enterprise Scope
- 以组织业务活动、项目、流程、角色、任务、决策、交付物和组织知识为核心。
- 组织获得的是其业务目的所需且经授权的工作信息，不因此拥有员工全部个人数据。
- 同一事件可能在个人视角和企业视角分别形成记录，二者通过来源与映射关系关联，不直接合并为同一所有权记录。

### Center Scope
- 以跨组织、跨业务单元的标准、能力、指标、治理、协同和汇总认知为核心。
- 优先消费经过授权的聚合、脱敏或标准化数据。
- 不因处于更高管理层级就自动获得个人原始记录或企业全量明细。

## 4. 关键原则

1. **共享概念不等于共享数据。** 共享 `Event` 语义，不代表所有作用域共享同一条 Event 记录。
2. **映射不等于身份合并。** 不因名称相同就使用 `owl:sameAs`；跨域实体需要显式身份解析和证据。
3. **转换必须可追溯。** 每次派生、脱敏、聚合、过滤都记录来源、目的、执行者、规则版本和损失说明。
4. **策略不由 Ontology 自动授予。** Ontology 描述语义，授权系统决定是否允许读取、转换或共享。
5. **默认不外流。** 个人到企业、企业到中心的数据流必须逐级经过目的限制、最小化、授权和审计。
6. **保留多视角。** 一个工作事件可以有个人叙述、项目管理视角和中心指标视角，不应把不同叙述压成唯一事实。
7. **可撤回与可删除。** 未来实现必须明确派生数据、缓存、索引和备份的撤回/删除传播路径。

## 5. 建议的映射契约字段（研究草案）

- `mapping_id`：映射规则标识
- `source_scope` / `target_scope`：源与目标作用域
- `source_concept` / `target_concept`：概念映射
- `transformation`：字段选择、脱敏、聚合、重分类等转换
- `purpose`：处理目的
- `authorization_ref`：由可信策略服务解析的授权引用
- `provenance`：来源记录、来源主体、转换主体、时间与规则版本
- `loss_report`：字段丢失、粒度变化、语义不确定性
- `reversibility`：是否可逆及恢复限制
- `retention_policy_ref`：保留策略引用
- `review_status`：草拟、待审、批准、拒绝、撤回

## 6. 研究验证问题

- 同一会议在个人与企业作用域是否需要两个记录，如何保持可追溯而不混淆所有权？
- 员工个人知识如何在不暴露私人上下文的情况下形成组织可复用的工作方法？
- 项目事件如何聚合为中心层指标，聚合后如何保留统计口径与证据链？
- 授权撤回后，派生记录、向量索引、报表和缓存如何定位并处理？
- 不同企业的术语相似但制度不同，如何区分精确映射、近似映射和不可映射？

## 7. 本轮不做的事

- 不新增正式 Ontology namespace、OWL 类或属性。
- 不创建真实的跨域数据同步服务。
- 不实现企业/中心权限系统。
- 不把组织层级当成自动授权链。
- 不宣称该模型已在 ADS 或真实业务环境验证。

下一步应先用 2—3 个具体工作场景进行概念验证，再决定是否进入独立的 Ontology 扩展版本。
